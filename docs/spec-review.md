## 🔴 C-01: 送信周期2.5秒とDS18B20の変換時間が両立しない

### 問題

仕様書 §10 は送信周期「約2.5秒」、§3.2 は「1センサー = 1 GPIO」で5本。
DS18B20の温度変換時間は分解能に依存します。

| 分解能 | 変換時間 | 温度分解能 |
|---:|---:|---:|
| 9bit | 93.75 ms | 0.5 °C |
| 10bit | 187.5 ms | 0.25 °C |
| 11bit | 375 ms | 0.125 °C |
| 12bit（既定） | **750 ms** | 0.0625 °C |

`DallasTemperature` の既定は `setWaitForConversion(true)`（＝ブロッキング）です。
このまま12bitで5本を順に読むと **750ms × 5 = 3.75秒** となり、送信周期2.5秒を守れません。
さらにAM2320の読み取りも加わります。

### 対策

**5本が独立GPIOである利点を活かし、変換を同時に開始します。**

```cpp
// setup()
for (int i = 0; i < 5; i++) {
    ds[i].setResolution(11);              // 0.125°C。空気温度には十分
    ds[i].setWaitForConversion(false);    // ノンブロッキング化
}

// loop()
for (int i = 0; i < 5; i++) ds[i].requestTemperatures();  // 5本同時に変換開始
delay(400);                                               // 11bit = 375ms + マージン
for (int i = 0; i < 5; i++) t[i] = ds[i].getTempCByIndex(0);
```

これで温度取得は約400msに収まり、周期に十分な余裕ができます。

### 分解能の選定理由

空気温度の測定にDS18B20の絶対確度は **±0.5°C**（-10〜85°C）です。
12bit（0.0625°C）はセンサー確度に対して過剰であり、時間コストに見合いません。
**11bit（0.125°C）を推奨**します。

## 🔴 C-02: DS18B20の `85.00°C` が異常値として定義されていない

仕様書 §13 は `-127.00` のみを異常として扱っています。
しかし DS18B20 のスクラッチパッドの**パワーオンリセット値は `85.00°C`** です。

つまり「変換完了前に読んだ」「電源が瞬断した」場合、
`-127.00`（=センサー無応答）ではなく **もっともらしい `85.00`** が返ります。

これは監視システムとしてはより危険です。「85°C」は排気温度としてありえない値ではないため、
そのままダッシュボードに表示されると誤警報を招きます。

### 対策

ホスト側・ファーム側の両方で判定する:

| 読み値 | 判定 |
|---|---|
| `-127.00` ちょうど | センサー未認識 → `null` + `err` に理由 |
| `85.00` ちょうど（かつ前サンプルとの差が大きい） | 変換未完了/リセット疑い → `null` + `err` |
| `0.00` が連続 | 配線疑い |

## 🟡 W-01: GPIO割り当ての検証（D6→D8変更の背景と、GPIO3の注意）

### D6→D8の変更は正解です

XIAO ESP32-S3 の **D6 = GPIO43 は UART0 の TXD** です。
USB CDC を使っていてもボードによってはブート時のログ出力やレベル遷移の影響を受けるため、
1-Wire データ線としては不適です。D8 = GPIO7 への変更は妥当です。

**この理由を仕様書に明記しておくことを推奨します**（後日「なぜD6を避けたか」を忘れるため）。

### ✅ 検証済み（2026-08-23）: D2 = GPIO3 — 問題なし

> **実機検証の結果、起動・再起動・書き込みのいずれも正常でした。**
> 現行配線を維持します。退避先 D9/D10 への変更は不要です。
> 以下は経緯の記録として残します。

#### 当初の懸念

ESP32-S3 の **GPIO3 はストラッピングピン**（JTAG signal source select）です。
DROKアダプタボードの 4.7kΩ プルアップにより、ブート時に GPIO3 が High に固定されます。

実際に問題が出るかはボード実装とeFuse設定に依存するため断定はしませんが、
**動作確認項目として明示的にテストしてください**:

- [ ] DS18B20 #3（D2/GPIO3）を接続した状態で、電源投入 → 正常起動するか
- [ ] リセットボタンからの再起動が正常か
- [ ] Arduino IDE からの書き込みが接続状態のままできるか

問題が出た場合の代替ピン: **D9 = GPIO8 / D10 = GPIO9**（どちらも空いています）。

### 現在の割り当て（確認済み・変更なし）

| 用途 | XIAO | GPIO | 備考 |
|---|---|---:|---|
| DS18B20 #1 Front Intake | D0 | 1 | |
| DS18B20 #2 GPU Intake | D1 | 2 | |
| DS18B20 #3 GPU Exhaust | D2 | 3 | ✅ 検証済み・問題なし（2026-08-23） |
| DS18B20 #4 Top Exhaust | D3 | 4 | |
| AM2320 SDA | D4 | 5 | XIAOの既定SDA。適切 |
| AM2320 SCL | D5 | 6 | XIAOの既定SCL。適切 |
| DS18B20 #5 Rear Exhaust | D8 | 7 | D6(GPIO43=U0TXD)から変更済 |
| 予備 | D9 / D10 | 8 / 9 | GPIO3で問題が出た場合の退避先 |

## 🟡 W-02: 較正手順が無い（ΔT判定の前提が崩れる）

仕様書 §12 は `Front Intake - Room` などの温度差を表示し、
§17 は「Front Intake - Room が大きい → 排気再循環の可能性」で判定するとしています。

しかし DS18B20 は ±0.5°C、AM2320 は ±0.5°C の確度です。
**最悪ケースでΔTには ±1.0°C の系統誤差が乗ります。**
再循環の判定に使う量が数°Cのオーダーである以上、これは無視できません。

### 対策: ベースライン較正手順を仕様に追加

1. 全センサー（DS18B20×5 + AM2320）を**同じ場所の静止空気中**に置く
2. サーバー・エアコンの影響がない状態で **30分以上** 放置し熱平衡させる
3. 10分間データを取得し、各センサーの平均値を算出
4. 全センサーの平均を基準として、各センサーのオフセットを算出
5. `calibration.json` に保存し、取り込み時に適用

```json
{
  "calibrated_at": "2026-08-25T10:00:00+09:00",
  "reference": "mean_of_all",
  "offsets_c": {
    "air.room": 0.00,
    "air.front_intake": -0.19,
    "air.gpu_intake": 0.06,
    "air.gpu_exhaust": 0.31,
    "air.top_exhaust": -0.12,
    "air.rear_exhaust": -0.06
  }
}
```

これにより **センサー間の相対精度** は概ね ±0.1°C まで改善します。
絶対精度は改善しませんが、本システムが必要としているのは相対値なので問題ありません。

## 🟡 W-03: DS18B20 の ROM ID を記録していない

各DS18B20は工場出荷時に固有の64bit ROM ID を持ちます。
現状の仕様では「D0につながっているものが Front Intake」と**配線位置でのみ**同定しています。

ケース内作業でプローブを差し替えてしまうと、
**較正オフセットもラベルも静かに間違ったまま運用が続きます。**

### 対策

起動バナー（`type:"hello"`）で各チャネルのROM IDを送出し、ホスト側で前回値と比較。
不一致なら `PROBE_CHANGED` を通知する（`docs/requirements.md` FR-403）。

```cpp
DeviceAddress addr;
ds[i].getAddress(addr, 0);   // → 16桁hexで送出
```

## 🟡 W-04: JSON出力にメタ情報が無い

仕様書 §10 のJSONは値のみで、以下が判別できません。

| 不足 | 起きる問題 |
|---|---|
| スキーマバージョン | ファーム更新時にホストが黙って誤解釈する |
| シーケンス番号 | 取りこぼしに気づけない |
| 稼働時間 | ESP32が勝手に再起動しても分からない |
| エラー理由 | `null` の原因が配線かセンサー故障か切り分けられない |
| メッセージ種別 | 起動バナーやログを同じストリームに流せない |

改訂スキーマは `docs/requirements.md` §5.2 を参照。

### 併せて: 非JSON行の混入

ESP32はブート時にROMログを出力することがあります。ホスト側のパーサは
**行頭が `{` でない行、およびJSONパースに失敗した行を黙って破棄**してください。
例外を投げて停止する実装にしてはいけません。

## 🟡 W-05: ウォッチドッグが無い

センサー読み取りが1-Wireのタイミング不良でハングした場合、
現状の設計ではESP32が無言のまま停止します。

### 対策

- ESP32側: Task Watchdog Timer を有効化（`esp_task_wdt`）。ループが10秒回らなければ自動リセット
- ホスト側: 30秒以上サンプルが来なければ `SENSOR_FAULT`（FR-401）

両側で持つことが重要です。ESP32側だけでは「USBケーブルが抜けた」を検出できません。

## 🟡 W-06: AM2320 の I²C 設定

仕様書 §6.1 のプルアップ（10kΩで動作確認済、延長時4.7kΩ）は妥当です。追加で:

- **I²Cクロックを 100kHz 以下に設定**すること。AM2320 は高速モードで不安定になります。
  `Wire.setClock(100000);`
- AM2320 は省電力のためスリープしており、**最初のI²Cトランザクションは意図的に失敗**します
  （ウェイクアップ用）。Adafruitライブラリは内部で処理していますが、
  自前実装する場合は「1回目のNACKは正常」と理解しておくこと
- 30〜50cm延長時は **ツイストペア または SDA/SCL に対してGNDを隣接**させる。
  ケース内はファンPWMとGPU電源のノイズ源が多い環境です

## 🔴 C-04: AM2320 の異常検出をソフトウェア側でも行う

元仕様 §14 に、コネクタの挿し間違いにより AM2320 が発熱した事象が記録されています。
**物理的な対策は本リポジトリの管理対象外です**が、
ソフトウェア側でも異常を早期に検出できるようにします。

### ファームウェア側

- [ ] AM2320 の読み取りに失敗した場合、`err` フィールドに理由を含める
- [ ] I²C の応答が連続で得られない場合、**センサーへの給電を止める**か、
      ポーリング間隔を大きく延ばす（異常状態で叩き続けない）
- [ ] 起動時のセルフチェックで、AM2320 が期待するアドレスに応答するか確認する

### ホスト側

- [ ] `SENSOR_MISSING` を即座に通知する（`requirements.md` FR-402）
- [ ] 室温が物理的にありえない値（0℃未満 / 60℃超）を `suspect` として扱う
- [ ] 湿度が 0% または 100% に張り付いた場合も `suspect` とする

**「値が来ない」だけでなく「明らかにおかしい値が来る」ケースを拾うことが重要です。**
配線異常時は、無応答ではなく異常値が返ることがあります。

### 🟢 参考: センサー選定について

AM2320 は継続使用が決定していますが、
将来の交換時に備えて代替候補を記録しておきます。

| 候補 | 確度 | 特徴 |
|---|---|---|
| AM2320（現行） | ±0.5°C / ±3%RH | 安価 |
| SHT31-D | ±0.3°C / ±2%RH | ブレイクアウト基板が豊富。ヒーター内蔵で結露復帰可 |
| SHT45 | ±0.1°C / ±1%RH | 高精度 |

**室温は全ΔT判定の基準点**になるため、精度向上は再循環検出の精度に直結します。

## 🟢 I-01: センサー配置の具体化

仕様書 §15 の配置図は概念図としては良いですが、実装時に迷います。追記推奨:

| センサー | 具体的な位置 | 固定方法 |
|---|---|---|
| #1 Front Intake | フロントファン**吸気側**（ケース外側寄り）から 2〜3cm | 結束バンド + 樹脂スペーサー |
| #2 GPU Intake | GPUのファン直前、基板から 1〜2cm離した空間 | 隣接スロットのブラケットに固定 |
| #3 GPU Exhaust | GPU背面/上面の排気直後 1〜2cm | 同上 |
| #4 Top Exhaust | トップラジエーター/ファンの排気側 1〜2cm | ファンネジに共締め |
| #5 Rear Exhaust | リアファン排気側 1〜2cm | 同上 |
| AM2320 | サーバーから 30〜50cm、机上または壁面。高さは吸気口と同程度 | 樹脂ケース、通気孔あり |

**共通原則**（仕様書に記載済、再掲）:
- 金属部に密着させない（空気温度を測るため）
- ファンブレードから 3cm 以上離す
- ケーブルにストレインリリーフ

**追加**: プローブ本体に **ラベル（#1〜#5）を巻いてください**。W-03 と併せて二重の同定手段になります。

## 🔴 C-05: GPUの排気方向がセンサー配置の前提を変える ★v0.2で追加

Workspace構想メモで GPU が **RTX PRO 6000 Blackwell Workstation Edition（600W）** と確定しました。
これは仕様書 §15 の配置図の前提を覆します。

### 事実

同じ RTX PRO 6000 でも冷却方式が3種あります。Max-Q版（300W）は密閉ブロワー式で
リアI/Oから排気しますが、**発注された Workstation Edition（600W）は
カード下方から吸気し、上方へ排出する flow-through 方式**です。
複数のレビューが、この方式は高負荷時のGPU温度を下げる一方
**ケース内部温度を上げ、全体の熱管理を複雑にする**と指摘しています。

### 配置への影響

| センサー | 元仕様の想定 | 改訂 |
|---|---|---|
| DS#3 GPU Exhaust | GPU背面付近 | **カード上面側 1〜2cm**。背面ではない |
| DS#4 Top Exhaust | 上面/ラジエーター排気 | **最重要になる**。GPU排気とCPUラジエーター排気が混ざる位置 |
| DS#5 Rear Exhaust | 背面排気 | GPU排気ではなく**リアケースファンの排気**を測ることになる |

### 検証すべき仮説（新規）

**「GPUの600W排気がCPU AIOラジエーターの吸気になっていないか」**

360mm AIO がトップマウントの場合、GPUが真下から熱風を吹き上げる形になります。
成立していれば、CPU温度がGPU負荷に強く連動する挙動を示します。

検証方法:
- 派生メトリクス `d.top_rise` = `air.top_exhaust - air.gpu_exhaust` を追加
- `gpu.0.power` と `cpu.package` の相関を測定
- GPU負荷を上げてCPU温度が連動するなら、この経路が存在する

**まず測定します。** 対策（ラジエーターのフロント移設等）はデータを見てから判断してください。
測定できる仕組みを持つこと自体が本プロジェクトの価値です。

### センサー配置に影響する構成要素

以下はケース構成によって変わるため、実機で確認したうえでセンサー位置を確定します。

- 360mm AIO ラジエーターのマウント位置（トップ / フロント）
- ボトムファンの有無（GPUが下方から吸気するため、吸気温に直結します）
- フロントファンの向き（吸気であること）

      GPUが下から吸うカードなので、**ボトムファンの有無は吸気温に直結します**
- [ ] フロント Noctua NF-A12x25 G2 ×3 の向き（吸気であること）

## 🔴 C-06: 電源回路の確認（到着前・安全事項） ★v0.2で追加

GPU 600W + Ryzen 9 9950X 170W + その他で、システム全体の連続消費は **900〜1000W** 程度が見込まれます。
PSU は 1200W Platinum / ATX 3.1 なので**容量は適正**です。

**問題は壁側です。**

日本の一般的な 100V / 15A 回路の上限は 1500W。上記の消費は回路容量の 60〜67% を占めます。
仕様書 §7 が「エアコン直風を避ける」と記載している以上、同室にエアコンがあります。
**同一回路であれば、フルロード時にブレーカーが落ちる可能性があります。**

Kaggleの学習が10時間走った後にブレーカーが落ちると、
学習結果を失うだけでなくファイルシステムを破損する可能性があります。

### ソフトウェア側で担保すべきこと

電源環境の整備自体は本リポジトリの管理対象外ですが、
**電断が起こりうる前提でソフトウェアを設計します。**

- SQLite は WAL モード（`PRAGMA journal_mode=WAL`）を有効にする。
  突然の電断でもデータベースが破損しにくくなります
- 取り込みデーモンは中途半端な状態を永続化しない（1サンプル単位でコミット）
- 再起動後に自動復帰する（systemd の `Restart=always`）

将来的に `power.wall` メトリクス（スマートプラグ経由）を追加すれば、
フルロード時の消費電力を熱データと並べて分析できます。

## 🟢 I-02: 電源とグラウンド

- DS18B20 × 5 の待機電流は各 1μA 程度、変換時 1.5mA 程度。
  5本同時変換（C-01の対策）でも 7.5mA 程度なので XIAO の 3V3 出力で問題ありません
- ただし **5本同時変換はピーク電流が集中する**ため、
  3V3 と GND の間に **100μF 程度の電解 + 0.1μF セラミック** を入れておくと安定します
- 将来マザーボード内部USBヘッダーへ移す場合、
  内部ヘッダーは 5V/500mA 供給ですが、**ケース内はノイズが多い**ため
  USBケーブルはシールド付きを使うこと
