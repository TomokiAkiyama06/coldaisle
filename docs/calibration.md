# センサー較正の手順（#13 / FR-107）

DS18B20 も AM2320 も確度は **±0.5℃**。最悪ケースで ΔT に **±1.0℃ の系統誤差**が
乗ります（`spec-review.md` W-02）。再循環の判定（`d.intake_rise > 5.0`）は
数℃の話なので、これは無視できません。

**改善するのはセンサー間の相対精度**です。絶対精度は変わりません。
本システムが判断に使うのは温度**差**なので、それで足ります。

---

## 0. プローブにラベルを貼る（**最初に1回**）

較正は「どのプローブがどのチャネルか」が分かっている前提の作業です。
**先にラベルを貼ってください。**

1. DS18B20 の**ケーブル根元**（プローブ本体側）に、剥がれにくいラベルを巻く
2. 番号ではなく**役割**を書く（`front_intake` / `gpu_intake` /
   `gpu_exhaust` / `top_exhaust` / `rear_exhaust`）
3. ダッシュボードの「センサー構成」を開き、**ROM とラベルの対応を控える**

```text
チャネル        メトリクス          種別      GPIO   記録された ROM      いまの ROM
front_intake    air.front_intake    ds18b20   1     28FF............
gpu_intake      air.gpu_intake      ds18b20   2     28FF............
```

**ラベルと ROM の二重の同定手段**になります（spec-review W-03）。
ラベルは剥がれ、ROM は読めますが、ROM だけだと現物のどれか分かりません。

### 差し替えてしまったとき

起動バナーの ROM が記録と違うと、`PROBE_CHANGED` が**発生中のアラートとして
出続けます**（人が較正をやり直すまで消えません。FR-403）。
ダッシュボードのセンサー構成では、その行に印が付きます。

**元に戻せるなら戻してください。** ダッシュボードの「いまの ROM」列に、
差し替わった先の ROM が出ます。

戻せないなら、こうします。

1. ラベルを貼り直す（現物と役割を合わせる）
2. この手順の 1 → 4 を実行する（**較正をやり直す**）
3. `--apply` が**差し替えを記録として受け入れます**（出力に出ます）
4. `coldaisle-fand` を再起動してから取り込みを再起動すると（順番は §4）、次の起動バナーで `PROBE_CHANGED` が解けます

**ROM だけを受け入れる手段はありません。** 記録された ROM が意味するのは
「いまのオフセットが対応している個体」です。較正し直さずに受け入れると、
**古いオフセットが新しいプローブに対応していることになり、アラートが黙る
だけで実害は残ります。**

---

## 1. 物理的な準備

ここが手順の本体です。**ソフトウェアは平均を取るだけ**なので、
置き方を間違えると「本物の温度勾配をオフセットとして焼き付ける」ことになります。

1. **全センサー（DS18B20 ×5 と AM2320）を1か所に集める**
   - プローブの先端どうしを 5cm 以内に寄せる
   - 束ねてもよいが、**互いに密着させない**（熱容量で追従が変わる）
2. **静止した空気の中に置く**
   - エアコンの吹き出し口、窓際、PC の排気の近くを避ける
   - サーバーは**止めておく**（動かすなら十分離す）
   - 人の出入りが少ない場所にする
3. **30分以上そのままにする**
   - プローブ自身の熱容量が周囲と釣り合うまで待ちます
   - **これを省くと、待ち時間の差がそのままオフセットになります**

## 2. 記録する

取り込みデーモンを動かしたまま、**10分以上**放置します。

```bash
uv run coldaisle-daemon --source serial
```

較正コマンドは**シリアルポートを開きません**（開いてよいのは取り込みデーモンだけ。
AGENTS.md ルール6）。保存済みのデータから計算します。

## 3. 計算する

```bash
uv run coldaisle-calibrate --minutes 10
```

```text
基準 24.001 C（mean_of_all）
ばらつき 0.501 C（上限 2.00）

  front_intake   平均   23.810 C  オフセット +0.000 → +0.191 C  (239 件)
  gpu_exhaust    平均   24.311 C  オフセット +0.000 → -0.310 C  (239 件)
  ...

書き込んでいません。内容を確認して `--apply` を付けてください。
```

**ここで止まります。** 較正値は以降のすべての測定の解釈を変えるので、
既定では書き込みません。

### 受け付けられない場合

方針（上限・最低件数・窓の長さ）は `config/calibration.yaml` にあります。

| 表示 | 意味 | どうするか |
|---|---|---|
| ばらつきが上限（2.00℃）を超えている | **同じ空気に置かれていない** | 1 からやり直す。熱平衡の待ち時間を延ばす |
| 測定が少ないチャネルがある | 記録した時間が足りない | `--minutes` を延ばすか、もう少し待つ |
| 測定が無いチャネルがある | センサーが1本届いていない | 配線と `err` を確認する |

`--force` で押し切れますが**勧めません**。上限を超えたまま較正すると、
**本物の温度勾配が以降ずっと見えなくなります。**

## 4. 書き込んで再起動する

```bash
uv run coldaisle-calibrate --minutes 10 --apply
```

`config/calibration.json` が更新されます。**取り込みより先に `coldaisle-fand` を再起動し、
そのあと取り込みデーモンを再起動してください**（どちらも較正値は起動時に読みます）。

順番に意味があります（決定記録 0096 §2.7 / §5 #9）。

- `coldaisle-fand` は起動時に較正を読み、Learned Thermal Model の artifact をその値で照合します（L9）。
  較正の掛かる metric の offset が変わっていれば、その artifact は使われず Fallback になります
  （fand が artifact を読む配線は決定記録 0079 段 4（#86）で入ります。それより前から、この順番で運用してください）
- **取り込みだけを再起動すると、fand は古い較正で照合済みの artifact のまま、新しい較正の値を読み続けます。**
  L9 による拒否は起きません
- fand を先に再起動すれば、新しい較正の値で照合し直してから、新しい較正の値が store に入ります

**較正の変更は、取り込みを再起動した時点で記録されます**（決定記録 0099）。`--apply` は記録を書きません。
store の値の意味が変わるのは、ファイルを書いた時刻ではなく、取り込みが新しい較正で起動した時刻だからです。

- 取り込み（`--source serial` / `mock`）は起動時、ソースを読む前に、較正ファイルから作った実効の offset の
  写像（較正を当てる全温度 metric。湿度と、対応表に無いキーは含みません）を、同じ DB の
  `calibration_activations` の最後の行と比べます。**変わったときだけ**1行を追記します。
  `note` / `calibrated_at` / `reference` / `samples` だけの変更や、`0.0` と `-0.0` の違いでは増えません
- **手で `config/calibration.json` を書き換えた場合も同じ**です（取り込みの再起動で記録されます）
- `--source replay` は較正を当てないので、記録を読みも書きもしません
- 表は追記のみです（更新・削除は DB が拒否します）。過去の履歴は埋めません。migration（0011）より前に
  取り込んだデータは Dataset v2 の学習に使えません（決定記録 0099 §2.8）

取り込みは次のとき**起動しません**（構造化ログに理由を出して終了します。再起動は systemd に任せます）。

| 状態 | 対処 |
|---|---|
| 同じ DB の取り込みが既に動いている（`<db>.ingest.lock` が取れない） | 古い取り込みを止めてから起動する（古い取り込みが動いたまま記録すると、古い較正の値が新しい較正として扱われる） |
| DB に hard link の別名がある（lock は DB の実体の path の隣に作るため、別名からは共有できない） | 別名を消す。symlink は実体の path に揃えるので構わない |
| 時計が記録の最後の行の時刻以下（較正が変わらない起動でも） | 時刻が追いつくのを待つ（壁時計が戻った。mock の圧縮再生で時刻を先へ進めた DB なら作り直す） |
| 較正が変わったのに、時計が保存済みの readings の最大の時刻以下 | 同上 |
| 記録の表が壊れている・書けない | 理由を確かめる（記録を残さずに新しい較正の値を保存すると、後から見分けられない） |

運転中に壁時計が記録の最後の行の時刻より前へ戻ったときは、取り込みは止まらず、その間の sample を
**保存せずに捨てて数えます**（終了時の `before_calibration_record`）。時計が追いつくと保存を再開します。

```bash
# 何が変わったかを残す（#40）
uv run coldaisle-memory --apply --commit
```

## 5. 確かめる

較正後、**同じ状態のまま**もう一度測って、ばらつきが **±0.15℃ 以内**に
収まっていることを確認します（#13 の受入基準）。

```bash
uv run coldaisle-calibrate --minutes 10   # 書かずに見るだけ
```

`ばらつき` が 0.15 以下になっていれば完了です。

---

## やり直すときの注意

**2回目以降の較正は、前回のオフセットに足されます。**

保存されている値には前回の補正が既に入っているので、計算で出るのは**残差**です。
出力は `前回 → 今回` の形で両方を表示します。

```text
  front_intake   平均   24.001 C  オフセット +0.191 → +0.191 C  (239 件)
```

残差がほぼ 0 なら、**前回の較正がまだ有効**ということです。

## やり直す時期

`config/calibration.yaml` の `revalidate_after_days`（既定 183 日 ≒ 6ヶ月）を
過ぎると、**取り込みデーモンが起動時に警告します。**

```json
{"level": "warning", "msg": "較正をやり直す時期（または未較正）", "age_days": 190.2}
```

次のときもやり直してください。

- **プローブを差し替えた**（`PROBE_CHANGED` が出たとき。FR-403 / 手順0）
- センサーを増やした・交換した
- 測定値が説明のつかないずれ方をしている

## 出荷時の状態

`config/calibration.json` は**全チャネル 0.0 / 未較正**で配布されています。
`calibrated_at` が `null` なので、デーモンは起動のたびに警告を出します。
**較正済みのつもりで生値を見ることにならない**ようにするためです。
