# 決定記録 0067: 騒音は概算で測る（測定を制御から切り離す・音声を残さない・曲線は approximate のまま）

## 1. Context

#94 の Acoustic Cost Model は、Zone 別の単調な区分線形曲線から**無単位の** `acoustic_cost` を返す。
いまの曲線は `source.kind: approximate` で、根拠は仮置きである。

#95 は騒音の測定方式を設計する Issue で、要件の未決 Q-26（音響センサーのハードウェア）も持つ。
所有者の方針（2026-09-24）は **「音量は正確に測らず、概算でよい」**。騒音は Fan 制御の
目的関数の1項にすぎず、安全にも関わらない。校正済みの測定機材や規格準拠の手順に費用と手間を
かけるほどの精度は要らない。

一方で、概算でも次を決めておかないと、測った値が制御や安全の経路に紛れ込んだり、
概算を精密な値と取り違えたりする。

## 2. Decision

### 2.1 精度の水準: 概算

- 機材は **手持ちのもの**（スマートフォンの騒音計アプリ、または安価な騒音計）でよい。
  校正器・測定用マイク・規格準拠（IEC 61672 など）は求めない
- 目的は **Zone 間・Demand 間の相対的な大小と、曲線の形（どこから急にうるさくなるか）** を
  つかむこと。絶対値（dBA）の正しさは目的にしない
- Q-26 の答えは「専用の音響センサーは導入しない」とする

### 2.2 曲線は `source.kind: approximate` のまま

- 概算の測定から作った曲線も `approximate` とし、`measured` を名乗らない
- `source.basis` に「概算 study（機材の種類・日付）」を書き、仮置きの曲線と区別する
- `measured` は、将来 精密な測定をするときのために残す。その条件は、そのとき別の記録で決める
- `acoustic_cost` は引き続き無単位。dBA の読みをそのまま曲線の値にしない
- 曲線は `demand=0.0` と `demand=1.0` の点を必須とする（`ZoneAcousticCurve` の既存の契約）。
  Critical Safety の floor がある Zone では floor 未満を測れない（§2.4）ので、**測った最小の点の
  `acoustic_cost` を 0.0 まで平らに延ばす**。floor 未満は運転中に届かないため、その区間の値は
  最適化に効かない。延ばしたことは `source.basis` に書く

### 2.3 測定は制御ループの外で行う

- 騒音計 / アプリの値を ingest daemon・control daemon・API・AI 層から読まない
- 騒音を Fan 制御の入力（Supervisor / MPC / Reactive Guard / Critical Safety）にしない。
  #94 へ渡すのは `acoustic.yaml` の曲線だけで、起動時に検証して読む既存の経路を通る
- 理由: 測定の誤差や欠測が Fan Demand を下げる経路を作らない（AGENTS.md ルール 3）

### 2.4 Fan を動かすのは `coldaisle-fand` の `CALIBRATION` モードだけ

- PWM / hwmon へ直接書く測定スクリプトは作らない（AGENTS.md ルール 2）
- `CALIBRATION` でも Reactive Guard の floor と Critical Safety は外れない。
  介入で持ち上がった点は、その Demand の値として使わない
- 読みと対応づけるのは decision trace の **effective の Demand**（requested ではない）

### 2.5 音声を残さない

- 録音はしない。記録するのは読んだ数値（dBA）と聞いた印象のメモだけ
- アプリが録音を保存する場合も、リポジトリに置かず、LLM にも渡さない（AGENTS.md ルール 8）。
  念のため `*.wav` / `*.flac` を `.gitignore` に入れる

### 2.6 周波数情報は耳で補う

- スペクトル解析はしない。代わりに、各点で **「純音（キーン）」「うなり（ワンワン）」「低いこもり」が
  気になるか** を聞いて印を付ける
- dBA が同じくらいでも印の付いた設定は、曲線の点を上げる（うるさい側に倒す）判断材料にする
- これで #95 の「SPL だけの案と周波数情報を使う案の比較」を、**dBA の順位と耳の評価の順位が
  食い違う設定を列挙する**という簡単な形で置き換える

### 2.7 繰り返しの確認

- 同じ設定を別の日（または時間帯）に 2 回以上読み、差を記録する
- 差が大きい（目安は 3 dB 以上）ときは、背景の音か位置が変わったとみなし、その点を測り直す

### 2.8 もう1つの選択肢: 普段の運転中に「うるさいか」を答えて不快の下限を探す

騒音計を使わず、**普段の運転中にユーザーが「うるさい / 気にならない」を答え**、その時点の
Fan の状態と突き合わせて、不快に感じ始める下限を探す方法も認める（所有者の提案、2026-09-24）。
dBA ではなく本人の感じ方を直接測れるので、#94 の目的（不快度のコスト）には騒音計より近い。

- **見るのは UI、答えるのは書き込み専用の入口。** UI（0046 のエアフロー画面など）は表示専用のまま、
  いまの effective Demand と RPM を見せるだけにする。回答は 0045 のローカル Unix ソケット
  （`coldaisle-eventd`）へ新しい種類 `noise_feedback`（値は `loud` / `ok`）として送る
  （例: `coldaisle-event noise-feedback loud`）。読み取り API（0009 GET-only）に書き込みを足さない
- **ブラウザの UI にボタンを置く案は本記録では決めない。** ブラウザからソケットへは届かず、
  API に書き込みの入口を作ることになるため、置くなら別の記録で入口と認可を決める
- **回答は Fan Demand を変えない。** 回答は `events` 表への追記だけで、制御ループは読まない
  （0045 §2.6 と同じ）。「うるさい」と答えても Fan は下がらない
- **下限の求め方**: 回答時刻の decision trace から各 Zone の effective Demand と RPM を取り、
  Zone ごとに「`loud` が繰り返し付き始める Demand」を下限の目安とする。CPU / GPU の負荷や
  GPU 本体の Fan が高いときの回答は、coldaisle が変えられない音の可能性があるので分けて扱う
- **下限は曲線の点としてだけ使う。** 下限より上で `acoustic_cost` が急に上がる形にするのは、
  人が確認する `acoustic.yaml` の PR で行う。下限を Fan Demand の ceiling にはしない
  （温度が上がれば Fan はうるさくても回す。騒音は目的関数の1項で、安全より下）
- 回答した人の識別は残さない。0045 §2.3 の peer credential による認可はそのまま使う
- 実装（`noise_feedback` を 0045 の許可リストへ足す・集計スクリプト）は別 Issue とする

## 3. Consequences

- 良くなること
  - 追加の機材なしで、今ある手順だけで曲線の根拠が仮置きから一歩進む
  - 概算を `approximate` のまま扱うので、精密な値と取り違えない
  - 測定の値が制御と安全の経路に入らない
- 悪くなること
  - 絶対値は機材ごとに数 dB ずれうる。緩和: 同じ機材・同じ位置で相対比較だけに使う
  - 純音・うなりは耳の主観に頼る。緩和: 印は「気になる / 気にならない」の二値にとどめ、
    曲線の値そのものを耳で決めない
  - 評価者は 1 人。個人の好みの範囲として扱う

## 4. 却下した代替案

| 案 | 却下した理由 |
|---|---|
| 校正済み測定用マイク + 音響校正器で規格に沿って測る | 所有者の方針（概算でよい）。騒音は目的関数の1項で、この精度は制御の結果をほとんど変えない |
| 1/3 オクターブ帯・FFT による純音・変調の解析 | 録音と解析の手間が要り、会話を含む音声を扱うことになる。耳による印で足りる |
| マイクを ingest daemon のセンサーとして常時取り込む | 会話を常時扱うことになり、騒音が監視・制御の入力に混ざる |
| 実測 dBA で Fan を絞る | 測定誤差で Fan Demand が下がる経路になる（ルール 3） |
| 概算の曲線を `measured` と名乗る | 精密な値と取り違える。`measured` の意味を将来のために空けておく |
| 「うるさい」の回答で Fan Demand をその場で下げる | 騒音の感じ方が冷却を弱める経路になる（ルール 3）。回答は記録だけにする |
| 回答を読み取り API の POST で受ける | 0009 の GET-only を破る。書き込みは 0045 の入口に寄せる |
| 測定スクリプトから PWM を直接書く | Guard / Safety を迂回する経路を作る（ルール 2） |

## 5. 未決事項

1. 曲線の点を読みからどう `acoustic_cost` へ写すか（例: 最小の読みを 0、最大を 1 に線形で並べる）。
   最初の測定結果を見てから `acoustic.yaml` の PR で決める
2. §2.8 の回答を UI のボタンから送れるようにするか（入口と認可を別の記録で決める）。
   また、§2.1 の騒音計による概算と §2.8 の回答のどちらを主にするか（両方でもよい）
3. 将来 精密な測定をするか（`measured` の条件）。概算の曲線で不足が見えたときに新しい記録で決める
