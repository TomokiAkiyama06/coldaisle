## 1. Context

#94 の Acoustic Cost Model は、Zone 別の単調な区分線形曲線から**無単位の** `acoustic_cost` を返す。
いまの曲線は `source.kind: approximate` で、実測の根拠を持たない。`docs/acoustic-model.md` は
実測がそろえば同じ契約のまま `source.kind: measured` にできると書いているが、
**「何をどう測れば measured と名乗ってよいか」が決まっていない**。

#95 はその測定方式を設計する Issue で、要件の未決 Q-26（音響センサーのハードウェア）も持つ。
測定そのものには GPU サーバーが要るが、次の点は実機の前に決めておかないと、
測った後で「この値は何を意味するか」が曖昧になる。

- 測定の経路が制御系（Fan の書き込み）と音声データ（室内の会話）にどう触れるか
- 単一の dBA だけで不快度を決めないために、何を併せて取るか
- 同じ Fan 設定の繰り返しのばらつきと、SPL のみの案と周波数情報を使う案の比較を、どう判定するか

## 2. Decision

測定プロトコルの手順・既定の候補値は `docs/acoustic-measurement.md` に置く。
この記録では、そのうち**後から変えると既存の測定を無効にする**ものだけを決める。

### 2.1 測定は制御ループの外で行う

- マイク / 騒音計は **ingest daemon・control daemon・API・AI 層のどれからも読まない**。
  音響の測定は `coldaisle` の常駐プロセスに組み込まず、所有者が開始する study として扱う
- 音響の値を Fan 制御の入力（Supervisor / MPC / Reactive Guard / Critical Safety）にしない。
  #94 へ渡すのは、study から作った**曲線と interaction の設定**だけで、起動時に検証して読む
  既存の経路（`acoustic.yaml`）を通る
- 理由: 騒音計の欠測や誤差が Fan Demand を下げる経路を作らない（AGENTS.md ルール 3）。
  騒音は安全の入力ではない

### 2.2 Fan を動かすのは `coldaisle-fand` の `CALIBRATION` モードだけ

- 測定計画の Demand は、0028 §2.5 (a) の `CALIBRATION` として `coldaisle-fand` に渡す。
  PWM / hwmon へ直接書く測定スクリプトは作らない（AGENTS.md ルール 2）
- `CALIBRATION` でも Reactive Guard の floor と Critical Safety は外れない。
  測定中に Guard / Safety が介入した区間は、**介入の記録（decision trace）から印を付けて
  study の集計から除外する**。介入した値を「その Demand の騒音」として残さない
- 測定計画の値は `requested`、音に対応づけるのは decision trace の **`effective` と実測 RPM**。
  requested だけを鍵にすると、floor で持ち上がった区間を取り違えるため

### 2.3 生の音声を残さない・コミットしない・LLM へ渡さない

- マイクは室内の会話も拾う。**既定では生の音声を保存しない**。保存するのは 2.4 の派生量だけ
- 周波数解析の検証のために生の音声を一時的に残す場合は、`data/acoustic/` 配下
  （`.gitignore` 済み）に置き、run の終了時に削除する運用を手順書に書く。
  音声ファイル（`*.wav` / `*.flac`）は `.gitignore` でも除外する
- 生の音声・スペクトルの時系列を LLM のプロンプトに入れない（AGENTS.md ルール 8）。
  LLM が扱ってよいのは segment ごとに集計した値だけ
- 機材の個体識別子（シリアル番号・校正証明書の番号）はコミットしない（AGENTS.md ルール 10）。
  manifest には 0031 と同じく**不透明な alias（32 桁の hex）**を書く

### 2.4 1 つの定常区間（segment）から取る量

単一の dBA だけで不快度を決めない（#95 の原則）。1 segment につき、少なくとも次を残す。

| 区分 | 量 | 目的 |
|---|---|---|
| レベル | `LAeq` / `LZeq`（等価騒音レベル） | 従来の比較軸。「SPL のみの案」の入力 |
| 帯域 | 1/3 オクターブ帯のレベル（Z 特性） | 低周波のこもりと高域の風切りを分ける |
| 純音性 | 突出した純音のピーク（周波数・突出量） | 羽根通過周波数（RPM/60 × 羽根枚数）の鳴き |
| 変動 | 包絡線の変調（うなり）の周波数と深さ | 近い回転数の Fan 同士のうなり |
| 背景 | 背景騒音との差 | 差が小さい segment を集計に使わない |

計算の具体的な設定（サンプリング周波数・FFT 長・窓・平均化）は候補値として
`docs/acoustic-measurement.md` に置き、run の manifest に**実際に使った値とその hash を残す**。
解析の設定が違う run 同士は比較しない。

### 2.5 `measured` を名乗る条件

`acoustic.yaml` の `source.kind: measured` は、次がそろった曲線にだけ付ける。

1. 曲線の点が、2.2 の除外を経た segment から作られている
2. 各点が **同じ Fan 設定の繰り返し測定** を持ち、ばらつき（2.6）が記録されている
3. `source.basis` が、根拠とした study の manifest hash を指す

`measured` は「曲線の根拠が実測である」ことだけを示し、`acoustic_cost` が dBA になるわけではない
（`docs/acoustic-model.md` の既存の定義をそのまま使う）。

### 2.6 繰り返しのばらつきの評価

- 同じ Fan 設定を、**別の時間帯に**少なくとも 3 回測る。同じ設定の連続測定だけでは
  室内の背景や温度のドリフトを拾えないため
- 測定順は設定ごとに無作為化し、基準の設定へ定期的に戻る点を混ぜる（ドリフトの検出用）
- 設定ごとに `LAeq` と各帯域レベルの標準偏差・範囲を記録する。許容幅は実測前の候補値として
  手順書に置き、確定値はこの study の結果を見て所有者が決める

### 2.7 SPL のみの案と周波数情報を使う案の比較

- 所有者が聴取位置で付けた `annoyance_score` を**判定の基準**にする
- 案 A: `LAeq` だけで `annoyance_score` を説明する。
  案 B: `LAeq` に純音性・変調（2.4）を加える
- 比較は**セッション単位で分けた交差検証**の順位相関（Spearman）で行う。同じセッションの
  segment を学習と評価の両方に入れると、その日の背景や気分を拾って案 B が有利に見えるため
- 加えて、`LAeq` がほぼ同じで `annoyance_score` が違う設定の組を列挙し、案 A が区別できない
  事例として残す。数値の差が小さいときに「案 B が良い」と結論しない
- 評価者は 1 人（所有者）であることを限界として記録する。個人の好みを一般の不快度として扱わない

## 3. Consequences

- 良くなること
  - 実測値が制御と安全の経路に入らない。騒音計が壊れても Fan 制御は変わらない
  - 測った値に「どの Demand が実際に効いていたか」が付き、Guard / Safety が持ち上げた区間を
    取り違えない
  - `source.kind: measured` の意味が、根拠の manifest まで辿れる形で固定される
- 悪くなること
  - 音響の study は常駐しないため、季節や構成の変化は手で再測定するしかない。
    緩和: 再測定の契機（Fan 交換・ケース構成の変更）を手順書に書き、決定記録 [0056](0056-model-drift-detection-and-retraining-triggers.md) §2.5 の
    宣言された変更（`DeclaredChange`）と同じ契機にする
  - 生の音声を残さないため、後から別の解析をやり直せない。緩和: 検証期間だけ一時保存を認め、
    その間に解析設定を固める
  - 評価者が 1 人で、不快度のばらつきを推定できない。緩和: 同じ刺激を繰り返し評価させて
    本人の一貫性だけは測る

## 4. 却下した代替案

| 案 | 却下した理由 |
|---|---|
| マイクを ingest daemon のセンサーとして常時取り込む | 室内の会話を常時扱うことになる。騒音が監視・制御の入力に混ざり、欠測時の扱いを Safety 側に作る必要が出る |
| 騒音を MPC の実時間入力にし、実測 dBA で Fan を絞る | 騒音の測定誤差や欠測で Fan Demand が下がる経路になる（ルール 3）。騒音は最適化のコストに留める |
| 測定スクリプトから PWM を直接書く | Guard / Safety を迂回する経路を作る（ルール 2、0028 の却下案と同じ） |
| `LAeq`（dBA）だけを取る | #95 の原則に反する。純音やうなりは dBA にほとんど現れない |
| 生の音声をすべて保存して後から解析する | 会話を含む音声を溜めることになる。public リポジトリの衛生（0021）とも相性が悪い |
| 同じ設定を連続で繰り返してばらつきを測る | 時間帯による背景とドリフトを拾えず、ばらつきを過小に見積もる |
| 案 A / B を全 segment のランダム分割で比較する | 同じセッションの背景・評価者の状態が学習と評価に漏れ、案 B が過大に良く見える |

## 5. 未決事項

1. **測定機材（Q-26）。** 候補は `docs/acoustic-measurement.md` §3 に並べた。
   どれを買うかは所有者が決める（費用と、校正器を持つかどうか）
2. 繰り返しのばらつきの許容幅、背景騒音との差の下限、定常とみなす待ち時間の確定値。
   実測後にこの study の結果から決め、新しい記録に残す
3. 心理音響指標（ラウドネス・シャープネス）を加えるか。案 B で説明しきれないときに検討する
4. study の解析を行うツールをリポジトリに置くか（置くなら `coldaisle` の常駐プロセスとは
   別の入口にし、音声の入力を持たせない形で別 Issue にする）
