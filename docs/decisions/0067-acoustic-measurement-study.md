## 1. Context

#94 の Acoustic Cost Model は、Zone 別の単調な区分線形曲線から**無単位の** `acoustic_cost` を返す。
いまの曲線は `source.kind: approximate` で、根拠は仮置きである。

#95 は騒音の測定方式を設計する Issue で、要件の未決 Q-26（音響センサーのハードウェア）も持つ。
所有者の方針（2026-09-24）は次のとおり。

- 音量は正確に測らなくてよい
- **騒音計は無く、dBA は測れない**
- 代わりに、**いまの状態を UI で見ながら「うるさいか」を答え、不快に感じ始める下限を探す**

#94 が表したいのは騒音の物理量ではなく**不快さのコスト**なので、本人の回答は騒音計より
目的に近い。一方で、回答が Fan の制御や安全の経路に入らないこと、UI を表示専用のまま保つこと、
回答をいつの Fan の状態と結びつけるかを決めておく必要がある。

## 2. Decision

### 2.1 測定の主な方法: 「うるさいか」の回答

- 騒音計・マイク・スマートフォンの騒音計アプリは使わない。dBA は記録しない
- ユーザーが**普段の運転中に**「うるさい（`loud`）」/「気にならない（`ok`）」を答え、
  回答した時刻の Fan の状態と突き合わせる
- 回答には2種類ある。**区別して記録する**（`noise_feedback` の必須フィールド `sampling` に
  `prompted` / `spontaneous` を持たせる。§2.2）
  - **定時の回答（`prompted`）**: 前もって決めた時刻（例: 作業の区切りの決まった時刻）に、
    うるさいかどうかに関わらず必ず `loud` か `ok` を答える
  - **気づいたときの回答（`spontaneous`）**: うるさいと感じたときなどに自由に答える
- **割合で下限を出す集計（§2.7）には、定時の回答と §2.5 の段階確認の回答だけを使う。**
  気づいたときの回答は、うるさいときほど出やすい（答えるかどうかが答えの中身に左右される）ので、
  `loud` の割合を過大に見せる。気づいたときの回答は「確かめるべき状態の候補」を探すのにだけ使う
- Q-26 の答えは「**音響センサーは導入しない**」とする

### 2.2 見るのは UI、答えるのは書き込み専用の入口

- UI（0046 のエアフロー画面など）は**表示専用のまま**、いまの各 Zone の effective Demand と
  RPM を見せるだけにする
- 回答は 0045 のローカル Unix ソケット（`coldaisle-eventd`）へ、新しい種類
  `noise_feedback` として送る。メッセージの本体は次の2つのフィールドを**どちらも必須**で持つ
  - `value`: `loud` / `ok`
  - `sampling`: `prompted`（定時の回答） / `spontaneous`（気づいたときの回答）。§2.1 の区別を
    保存の境界で失わないため。0045 は未知・欠けたフィールドを受け取らないので、ここで決めておく
  - 例: `coldaisle-event noise-feedback loud --sampling prompted`
- 読み取り API（0009 GET-only）に書き込みを足さない
- **ブラウザの UI にボタンを置く案は本記録では決めない。** ブラウザからソケットへは届かず、
  API に書き込みの入口を作ることになるため、置くなら別の記録で入口と認可を決める
- 認可は 0045 §2.3 の peer credential をそのまま使う。**0045 どおり `events` の行には書き手の
  `peer_uid`（OS のユーザー ID）が残る。** これを例外にはしない。本記録が持たないのは、
  それ以上のアプリ側の識別（名前・端末・回答者ごとの ID など）だけである
- AI 層はこの入口に届かない（0045 §2.7。AGENTS.md ルール 1）

### 2.3 回答は Fan Demand を変えない

- 回答は `events` 表への追記だけで、制御ループは読まない（0045 §2.6 と同じ）。
  「うるさい」と答えても Fan は下がらない
- 回答から作った下限を Fan Demand の ceiling にしない。温度が上がればうるさくても Fan は回す。
  騒音は目的関数の1項で、安全より下（AGENTS.md ルール 3）

### 2.4 回答と Fan の状態の結びつけ

- 回答の時刻**以前で最も新しい** decision trace の tick から、各 Zone の **effective の Demand** と
  RPM を取る。回答より後の tick は使わない（その状態はまだ鳴っていなかった）。
  requested ではない（Guard / Safety が持ち上げた値が実際に鳴っている音である）
- 回答の直前の一定の区間（lookback。目安は回転数が落ち着くのに要する時間。値は集計の設定に置く）で、
  各 Zone の effective の Demand が変わっていないことを求める。区間の途中で Demand が変わった回答は、
  どの状態を聞いて答えたか分からないので集計に使わない
- lookback 区間の**全体にわたって** tick が途切れていないことを求める。tick があるかどうかだけでは
  足りない（区間の最初に tick が1つあり、その後ループが止まって watchdog と引き継ぎで Max になった
  場合、最後の tick は古い低い状態のままで、Max の音への回答を低い状態に結びつけてしまう。0028 §2.6 / §2.7）
  - lookback の始点から最初の tick までの間隔、隣り合う tick の間隔、最後の tick から回答までの間隔の
    **すべて**が、trace に記録された周期
    （`ControlTickRuntime.tick_period_ms`）の許容倍数以内であること。許容倍数は集計の設定に置く
  - どこか1か所でも満たさない回答は、状態が分からないので集計に使わない
- **結びつけは decision trace が消える前に行い、結果を残す。** decision trace の保持は 30 日
  （`config/retention.yaml` の `control_trace_days`。決定記録 0030）で、`events` は無期限である。
  集計の時点でまとめて突き合わせると、30 日より前の回答は tick も lookback も失って全部捨てることになる。
  そこで、回答と tick の突き合わせを
  **定期的に（ロールアップと同じ日次で、保持期間の削除より前に）実行し、結果を無期限の記録として残す**。
  下限の集計は、この残した結果だけを読む。保持期間そのものは変えない
- 残す結果には、**後から分類に要る値をすべて含める**（元の trace と readings は 30 日で消えるため）
  - 元の回答の `events.id`。**残す結果の中で一意**とし、日次の突き合わせは何度実行しても同じ回答を
    二度数えない（冪等）。時刻（ミリ秒）は一意ではないので、どの回答を処理済みかの判定には使わない
  - 回答の `value` / `sampling` と時刻
  - 結びついた tick の各 Zone の effective の Demand と RPM、lookback の判定
  - その tick の運転モード（`AUTO` / `CALIBRATION` など。§2.5 の段階確認を普段の回答と分けるため）
  - 分けて集計する条件の元の値: CPU / GPU の Power と `gpu.0.fan_speed`（lookback 区間の値。
    高負荷かどうかの判定の閾値は集計の設定に置き、判定そのものではなく元の値を残す）
- 突き合わせる前に trace が消えた回答は「状態不明」として数を残し、集計には使わない
- CPU / GPU が高負荷のとき、GPU 本体の Fan（`gpu.0.fan_speed`）が回っているときの回答は、
  coldaisle が変えられない音の可能性があるので**分けて集計する**
- 1つの回答は 3 Zone すべての状態を指すので、どの Zone がうるさいかは1つの回答からは分からない。
  AUTO では共通の負荷と協調制御のために 3 Zone の Demand が一緒に動くので、普段の回答を各 Zone の
  Demand で数えると、うるさくない Zone にも見かけの下限ができてしまう（例: Front と Rear がいつも一緒に
  上がり、実際に聞こえるのは Front だけでも、Rear にも下限が出る）
- そこで **Zone ごとの曲線は、Zone が独立に動いた証拠があるときだけ作る。**
  - 当てはめに使える標本は、§2.5 の段階確認（1 Zone だけを動かす）の回答と普段の回答。
    **出どころによらず、以下の条件をすべて同じように満たす必要がある**（段階確認の回答だからといって
    どの条件も免除しない。段階確認中も Guard / Safety が固定したはずの Zone を持ち上げうるし、
    1回の掃引では各帯の回答が1つずつしかなく、割合が 0% / 100% になるだけで §2.7 の揺れを表せない）
    - **その Zone だけが動いた**: 他の 2 Zone の effective の Demand が、比べる回答どうしで設定の許容幅以内
    - **繰り返し**: 標本が、集計の設定で決めた数以上の**異なる暦日**にまたがる。暦日は残した回答の時刻と
      設定のタイムゾーンから決める（残す結果だけから判定でき、元の trace が消えても数えられる）
  - 普段の回答だけで作るときは、**曲線を当てはめる標本そのものを、その Zone だけが動いた回答に限る**。
    他の 2 Zone の effective の Demand が、比べる回答どうしで設定の許容幅以内に揃っている回答だけを
    その Zone の Demand の帯に数え、3 Zone が一緒に動いた回答は Zone ごとの帯に数えない
    （条件を満たす標本が少し在ることを確かめるだけで、相関した回答全体から当てはめない）
  - 限った標本が、その Zone の Demand の**離れた少なくとも 2 つの帯**に、それぞれ集計の設定で決めた数
    以上あることを求める。1 つの帯に集まった標本からは `loud` の割合がどこで変わるか分からないため。
    下限は、標本がそろった帯の間でだけ推し、標本の無い範囲へ延ばさない
  - さらに、標本のそろった帯を Demand の順に並べたとき、`loud` の割合が閾値（§2.7）を**ちょうど1回だけ、
    下から上へ**またぐことを求める。つまり、閾値未満の帯が1つ以上、閾値以上の帯が1つ以上あり、
    **閾値以上になった帯より高い Demand の帯はすべて閾値以上**であること。
    - どの帯も閾値の同じ側 → 観測した範囲で下限をまたいでいない（どこで不快になり始めるか分からない）
    - 一度閾値以上になった後に閾値未満の帯がある（未満→以上→未満など）→ 単調でなく、証拠が食い違う
    - 下限は、またいだ位置の直前の帯と直後の帯の間に置く
  - これを満たさない Zone は曲線を作らない
  - どちらも無い Zone の曲線は、いまの `approximate` のまま変えない。普段の回答からは、
    3 Zone をまとめた「この状態はうるさい」の記録だけを残す

### 2.5 意図的に確かめる補助の方法

**この方法は、いまは実施できない。** `coldaisle-fand` は運転モードを固定で持ち
（`StaticOperatingMode`）、`CALIBRATION` へ切り替えて Zone ごとの requested を渡す入口がまだ無い。
入口は 0028 §2.2 の「モード変更はローカル Unix ソケットだけ」に沿って別の Issue / 決定記録で作る。
それまでは §2.1 の回答（定時・気づいたとき）だけで進める。

普段の回答だけでは、高い Demand の状態がなかなか現れない。補助として、入口ができた後に、所有者が
`coldaisle-fand` の `CALIBRATION` モードで1つの Zone ずつ Demand を段階的に上げ、
各段で `noise_feedback` を答えてよい。各段では必ず答えるので `sampling: prompted` とする。

- Fan を動かすのは `CALIBRATION` だけ。PWM / hwmon へ直接書くスクリプトは作らない（ルール 2）
- `CALIBRATION` でも Reactive Guard の floor と Critical Safety は外れない。
  結びつけは §2.4 と同じく effective の Demand で行う
- 1つの Zone だけを動かすので、この方法なら Zone ごとの下限が直接分かる

### 2.6 曲線への写し方

- Zone ごとに「`loud` が繰り返し付き始める effective Demand」を**不快の下限**の目安とする
- 曲線は下限までは緩やかに、下限より上で `acoustic_cost` が急に上がる形にする。
  具体の値は、人が確認する `acoustic.yaml` の PR で決める。自動では書き換えない
- 曲線は `source.kind: approximate` のままにし、`measured` を名乗らない。
  `source.basis` に「noise_feedback の集計（期間・回答数）」を書く
- 曲線は `demand=0.0` と `demand=1.0` の点を必須とする（`ZoneAcousticCurve` の既存の契約）。
  Critical Safety の floor がある Zone では floor 未満の状態が現れないので、**観測した最小の点の
  `acoustic_cost` を 0.0 まで平らに延ばす**。floor 未満は運転中に届かないため最適化に効かない。
  延ばしたことは `source.basis` に書く
- `acoustic_cost` は引き続き無単位

### 2.7 繰り返しと測り直し

- 同じ状態への回答が `loud` / `ok` で割れるのは普通のことで、下限は割合で見る
  （例: `loud` が半分を超え始める Demand）。割合の閾値は集計の設定に置く
- 割合に数えるのは §2.1 の定時の回答と §2.5 の段階確認の回答だけ（気づいたときの回答は数えない）
- Fan の交換・ケースの向きや設置場所の変更の後は、それ以前の回答を下限の集計に混ぜない。
  0056 §2.5 の宣言された変更（`DeclaredChange`）と同じ契機で区切る

### 2.8 実装は別 Issue

- `noise_feedback`（`value` / `sampling`）を 0045 の許可リストへ足すこと、回答と trace の日次の
  突き合わせと結果の保存（§2.4）、下限の集計、その設定ファイルは、本記録の承認後に別 Issue で実装する
- §2.5 の段階確認に要る `coldaisle-fand` のモード・requested の入口（0028 §2.2）も、別 Issue で作る。
  入口ができるまで §2.5 は実施しない

## 3. Consequences

- 良くなること
  - 追加の機材が要らない
  - 測る量が「本人が不快か」そのもので、#94 の目的に直接つながる
  - 普段の運転の中で少しずつ回答がたまる
  - 回答が制御と安全の経路に入らず、UI も表示専用のまま
- 悪くなること
  - 回答は主観で、その日の体調や作業内容で揺れる。緩和: 1回の回答ではなく割合で見る
  - 普段の回答では、どの Zone がうるさいかを分けにくい。緩和: §2.5 の補助の方法で Zone を1つずつ確かめる
  - 評価者は 1 人。個人の好みの範囲として扱う
  - UI から直接は答えられない（CLI から答える）。緩和: ボタンが要るなら別の記録で入口を決める

## 4. 却下した代替案

| 案 | 却下した理由 |
|---|---|
| 騒音計 / 測定用マイクで dBA やスペクトルを測る | 機材が無い（所有者の方針）。#94 が表したいのは不快さで、dBA はその代わりにすぎない |
| スマートフォンのアプリで dBA を読む | 同上。精度の分からない数値を根拠に加える利点が小さい |
| 「うるさい」の回答で Fan Demand をその場で下げる | 騒音の感じ方が冷却を弱める経路になる（ルール 3）。回答は記録だけにする |
| 回答を読み取り API の POST で受ける | 0009 の GET-only を破る。書き込みは 0045 の入口に寄せる |
| 回答を requested の Demand と結びつける | Guard / Safety が持ち上げた区間で、鳴っている音と取り違える |
| 回答から曲線を自動で書き換える | 主観の揺れがそのまま制御の目的関数に入る。人が確認する PR を通す |
| 概算の曲線を `measured` と名乗る | 精密な値と取り違える |
| 測定スクリプトから PWM を直接書く | Guard / Safety を迂回する経路を作る（ルール 2） |
