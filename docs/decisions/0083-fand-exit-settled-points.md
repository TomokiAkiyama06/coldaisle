## 1. Context

PR #203 は 0080 §2.10 の段階 2 を実装する（終了コード 4 / 5 / 6 / 7、`safety.yaml` v4 の
`hardware_write_fail_exit_ms`、`faulthandler`、起動時の DB の書き込み確認）。実装の途中で、0080 が
決めていなかった点と、0080 の記述と実装が食い違う点が出た。2026-10-01 に所有者へ示し、次のとおり承認された。

## 2. Decision

### 2.1 終了コード 7 で止めるとき、受け渡し口に残った authority の降格は lock を待たずに1回書く

- 終了コード 7 の後片付けは、例外の経路と同じく**管理ソケットのスレッドを待たない**
  （root の `ExecStopPost` が Max を書くまでを遅らせない。0080 §2.6）
- ただし、どの tick にも取り出されずに枠に残った降格は、`AuthorityRuntime` へ入れたうえで、
  journal へ**lock を待たずに1回だけ**書き残しを試す。lock を取れなければ、主体と理由つきで error に残す
- 例外の経路（`drain=False`）は変えない（journal へは書かない）。0081 の「受理した降格を失わない」に、
  終了を遅らせない範囲で寄せるための扱いである

### 2.2 運転中の `WATCHDOG=1` の送信の失敗は、捕まえて運転を続ける（0080 §2.4 の読み替え）

- 実装（`ControlLoop._beat`）は送信の失敗を捕まえてログに残し、運転を続ける（0060 §2.7 の
  「watchdog の失敗で冷却を止めない」）。0080 §2.4 の「未捕捉の例外として終了コード 1」は実装の事実と違う
- 実装に合わせる。送れない状態が続けば systemd の deadman が時間切れで fand を止め（SIGABRT）、
  `ExecStopPost` が Max を書く。一度の送信の失敗で制御を手放さない
- 0080 未決 7（終了コード 1 の分離）は、この読み替えのもとで引き続き #74 で扱う

### 2.3 そのほか実装で決めた点

- **`CONTROL_CONFIG_VERSION` を 11 から 12 に上げる。** `safety.yaml` を v4 にしたため。v2 → v3 のときに
  束ねた版も上げた前例に合わせる。`ControlTick` の版は上げない
- **書き込みの失敗の期間の数え方**: zone ごとに、`write_ok` と `readback_ok` がそろって成功していない期間を
  単調時計で数える。起点は最初に失敗した tick の開始で、判定は `>=`。backend の例外は全 zone の失敗として
  数え、1回成功すればその zone だけ数え直す。判定は tick の後にしか行わないので、実際の終了は最大で
  約1周期遅れうる
- **起動時の DB の書き込み確認**は、DB・`-wal` / `-shm` に加えて `-journal` も対象にする（0080 §2.1 の
  移行手順が `-journal` も揃えるため）。SQLite のエラーは CANTOPEN / PERM / AUTH / READONLY を権限の失敗
  （`db_not_writable`）、BUSY / LOCKED を lock の失敗として分ける。DB のディレクトリが無いときは
  `db_not_writable` ではなく通常の起動失敗（終了コード 5）として報告する
- **引き継ぎ記録を消さないことの試験**は、記録の書き手（0080 段階 4 / #77）ができた段階で足す。
  段階 2 では「終了コード 7 の経路が返却・削除の処理を通らない」ことを構造で確かめる
- **`pwmN_enable` が外から戻されたことの検出**は、実機の backend が `readback_ok=false` を返す前提とする
  （simulated backend にはこの fault が無い。実機の backend の段階で試験する）
- **`hardware_write_fail_exit_ms` の値は暫定**（0080 §2.6）。リポジトリには試験用の fixture の値だけを置き、
  導入先で v4 へ移すときに `watchdog_timeout_ms` と同じ値・`status: provisional` で置く。#50 / #75 の後に
  実測から導いて所有者が承認し、`confirmed` にする

## 3. Consequences

- 良くなること: 終了コード 7 でも受理済みの降格が journal に残りやすくなり、再起動で高い stage に戻る場面が減る。
  0080 の記述と実装の食い違いが解消する
- 悪くなること: 終了コード 7 の後片付けで journal の lock を1回試す分だけ（待たない）処理が増える。
  lock を取れなければ降格は失われる。緩和策: error に主体と理由を残す

## 4. 却下した代替案

- **終了コード 7 で降格を書かない（例外の経路と同じ）**: 0081 の方針と食い違い、受理済みの降格が再起動で失われる
- **終了コード 7 で lock の待ち上限（`tick_deadline_ms`）まで待つ**: root の Max の書き込みが遅れる
- **`WATCHDOG=1` の送信の失敗で終了コード 1 にする（0080 §2.4 に合わせてコードを変える）**: 一度の失敗で
  制御を手放す。送れない状態が続けば deadman が止めるので、止める判断は deadman に任せる
