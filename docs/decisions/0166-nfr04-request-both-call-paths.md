## 1. Context

0163 §2.4 は、NFR-04（初回トークン 2 s）を測るときの要求を「coldaisle の最も長い実際のプロンプト（`explain_context` を足したアラートの説明）と同じ長さ」とした。
PR #370 の Codex の指摘で、この前提が成り立たないことが分かった。

- アラートの説明の材料（`ExplainContext.metrics`）は 16 件までに限られる
- 日次レポートの所見の要求は、`DailyReport.facts_markdown()` の全文を user に入れる。値のあるメトリクスごとに 1 行と、アラートの詳細を含む。
  catalog にないメトリクスも入る
- そのため、ふつうの日の日次レポートのほうがアラートの説明より長くなりうる。アラートの説明だけを測ると、prefill がいちばん長い要求を測らずに NFR-04 を合格にしうる

初回トークンの時間は、prefill の長さで決まる。どちらが長いかは日とアラートで変わるので、一方を「最も長い」と決めることはできない。

## 2. Decision

### 2.1 測る要求

0163 §2.4 の「要求」の行を次で置き換える。

| 項目 | 決め |
|---|---|
| 要求 | coldaisle が PAW の vLLM へ送る **2 つの経路のそれぞれで、実際に作られた要求の本文**。経路は (a) 日次レポートの所見（`coldaisle-report`）と (b) アラートの説明（`Explainer.explain`）。**両方を測る**。`probe()` は短いので測らない |
| 本文の拾い方 | ループバックの記録用の窓口（§2.2）に `OPENAI_BASE_URL` を向けて、本番と同じ部品で要求を作らせ、その本文（`messages` と送る欄）をそのまま保存する。手で同じ長さの文を作らない |
| (a) の選び方 | 導入先の DB の写しで、直近 7 日の各日の日次レポートの要求を作り、本文の bytes が最も長い日のものを使う |
| (b) の選び方 | 同じ写しで、直近 7 日に発火したアラートのそれぞれの説明の要求を作り、本文の bytes が最も長いものを使う。7 日に発火が無ければ、最後に発火したアラートを使う |
| 送る形 | 保存した本文の `stream` を `true` にし、`max_tokens` を 1024 にして送る。`chat_template_kwargs.enable_thinking=false` と `model`・`temperature` は保存したまま（どちらの経路も非思考で送っている）。prefix cache を避けるため、system の本文の最初に時刻の 1 行を毎回変えて足す（0163 §2.4 の回数の行と同じ目的） |
| 合格 | 0163 §2.4 の合格の基準（§5 の 6 の (a)）を**経路ごとに**当てる。(a) と (b) のどちらも、PAW の他の要求が無いときに 20 回すべて 2 s 以内 |

- 測定はコードと CI に足さない（0163 §2.4 のまま）。記録用の窓口と要求を作る手順は `docs/llm-setup.md` に一回限りの手順として書く
- 送るのは今の呼び出しと同じ集計値だけである（ルール 8 / FR-504）。記録用の窓口はループバックだけで待ち受け、外へ送らない
- 保存した本文は導入先の作業用のフォルダにだけ置き、リポジトリに入れない（ルール 10。DB の値が入る）

### 2.2 記録用の窓口と要求の作り方

- 記録用の窓口は標準ライブラリだけの一回限りのスクリプトで、`127.0.0.1` の空いたポート（例 `18099`）で待ち受ける。
  `POST` の本文をそのままファイルに保存し、`content` が空の `chat.completion` を返す。空の応答なので、所見と説明は「作れない」として捨てられる
- (a) は `coldaisle-report --db <写し> --date <日> --no-send --print` を、Provider を明示して（0163 §2.2「試すときの Provider の指定」）`OPENAI_BASE_URL` を記録用の窓口に向けて走らせる。
  `--no-send` でもレポートは作業ディレクトリの `var/reports/` に書かれるので、`/opt/coldaisle` ではなく作業用のフォルダで走らせる
- (b) は `Explainer` を本番の説明スレッドと同じ部品（`AiSettings.explain_context`・`ToolRegistry` と `LlmExclusions`）で組み、写しの発火済みのアラートについて `explain()` を呼ぶ一回限りのスクリプトで作る
- DB の写しは root で SQLite の backup を取り、操作者の uid に渡す（導入先の DB は操作者から読めない）

## 3. Consequences

### 良くなること

- prefill が最も長い要求を、経路を問わず測る。日次レポートのほうが長い日に NFR-04 を誤って合格にしない
- 実際の要求の本文を使うので、「同じ長さ」の作り方の揺れが無くなる（token の数は文の中身で変わる）

### 悪くなること・その緩和

| 悪くなること | 緩和 |
|---|---|
| 測定が 20 回から 40 回に増える | 一回限りの手順で、1 回は数秒。PAW の要求と重ならない時間を選ぶ |
| 直近 7 日にない長い日（アラートの多い日など）は測らない | 2 s を超える兆しがあれば、所有者が PAW 側の設定を含めて扱いを決める（0163 §2.4 のまま）。長い日に限った遅れは参考として記録する |
| 記録用の窓口と要求を作るスクリプトは CI で確かめない | 手順は内部の関数の名前に依存する。測定の前に手元の DB で 1 回通す（PR #370 で `var/` の開発用の DB で確かめた） |

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| アラートの説明だけを測る（0163 §2.4 のまま） | 指摘のとおり、最も長い要求を測らないことがある |
| 日次レポートだけを測る | アラートの説明が長い日もありうる。どちらが長いかは日で変わる |
| 2 つの経路のうち長いほうだけを測る | 長さを比べる手間は変わらず、短いほうの経路の遅れ（system の文の違いなど）を見ない。40 回でも負担は小さい |
| `max_tokens` や上限を付けて要求を短くする・プロンプトの上限をコードに足す | 測定のために本番の要求の形を変えることになる。本記録はコードを変えない |
| 測定をコードと CI に足す | 0163 §2.4 で退けた。共用の窓口で、CI からは PAW の vLLM に届かない |

## 5. 未決事項

なし。測った結果が 2 s を超えたときの扱いは 0163 §2.4 のまま所有者が決める。
