# 決定記録 0004: ストレージ層の読み出し契約

- **種別**: Decision Record
- **Status**: FINAL（2026-08-24 承認）
- **Date**: 2026-08-24
- **Supersedes**: なし
- **関連**: [`0002-metric-naming.md`](0002-metric-naming.md) §2.8 / §2.11 /
  `docs/requirements.md` §5.3 / FR-201〜203 / FR-301〜303 / `docs/api-contract.md` §3
- **対象 Issue**: #5

決定記録 0002 は**何をどう保存するか**を確定した。本記録はその上で
**保存したものをどう返すか**を確定する。#9（読み出し API）と #10（ロールアップ）は
本記録を参照先とする。

---

## 1. Context

#5 で `SqliteStore.latest()` / `series()` / `stats()` を実装するにあたり、
要件にも 0002 にも書かれていない意味づけが必要になった。

いずれも**内部実装ではなく API のレスポンスにそのまま現れる**。
`GET /api/v1/stats` が返す p95 が補間値なのか実測値なのか、
`from` / `to` の端が含まれるのかは、Workspace 側が数値を解釈するために必要な情報であり、
コードのコメントに置くと契約の外に落ちる。

---

## 2. Decision

### 2.1 期間は半開区間 `[from, to)`

`series()` / `rollup()` / `stats()` のすべてで、`from` を含み `to` を含まない。

連続する窓を並べたときに端の1点が二重に数えられないため。閉区間にすると、
1分バケットを24個並べた合計が実際の行数と合わなくなり、
欠測率（0002 §2.8）の分母が壊れる。

### 2.2 `stale` は保存時ではなく読み出し時に付ける

`quality` の4値のうち `ok` / `missing` / `suspect` は取り込み時に確定し、
`readings.quality` にそのまま入る。**`stale` だけは行に書かない。**

`stale` は「前回受信からの経過」であり、行に書き込んだ時点では確定しない。
書き込み後に時間が経てば同じ行が `stale` になるため、行の属性ではなく
**参照時点の属性**である。`latest()` が `at_ms` と `stale_after_ms` から判定する。

`stale` と判定した場合も**値は返す**。値を伏せると、
ダッシュボードと LLM から「直前まで何度だったか」という判断材料が消える。
古いことは `quality` と `age_ms` で伝える。

### 2.3 p95 は nearest-rank。補間しない

順位 `ceil(0.95 × n)` の実測値をそのまま返す。線形補間しない。

補間すると、**センサーが一度も出していない値**が p95 として API に出る。
0.01℃ の差が判断を変える場面は無い一方、「この値は実際に観測されたか」を
後から確かめられることには意味がある（#19 のベースライン測定、#38 の根拠付きアラート）。

n が 0 のときは `null`。

### 2.4 傾きの単位は「メトリクスの単位 / 分」

最小二乗法。x は窓の先頭を原点とした経過分。点が2つ未満なら `null`。

FR-407（`RAPID_RISE`: 5℃/分超）が分を単位に閾値を持つため、
ルールエンジンが単位を変換せずに比較できる形で返す。
原点を窓の先頭に取るのは、`ts_ms` のまま扱うと x が 1e12 台になり
`Σx²` で有効桁が落ちるため。

### 2.5 生データ窓の欠測率は「行数を母数にした下限値」

`stats().missing_ratio = 1 - ok_value_count / row_count`。

生データには「来なかったサンプル」の行が無い。したがってこの値は
**通信断を含まない下限値**である。期待サンプル数を母数にした本来の欠測率は
ロールアップの `expected_count`（0002 §2.8）が持つ。

2つの欠測率が併存することになるが、統合しない。統合すると、
生データ側で `devices.interval_ms` を参照することになり、
「センサーの異常」と「サンプルの不着」を分けた 0002 §2.8 の区別が崩れる。

### 2.6 `series(limit=...)` は古い側を落とす

返す並びは常に時刻の昇順、打ち切りは古い側から行う。

監視で欠けてはならないのは直近である。先頭から `LIMIT` すると、
点が多い期間を指定したときに**最新の異常だけがグラフから消える**。

### 2.7 同一 `(metric, ts_ms)` の再投入は拒否する

`INSERT OR REPLACE` にしない。主キー違反をそのまま送出する。

上書きすると、同じ時刻に2つの値が観測された事実が消える。これは較正の
二重適用やリプレイの取り違えを示す兆候であり、握りつぶすと原因が追えない。
取り込みループはこれを1サンプルのパース失敗と同様に**記録して継続**する
（AGENTS.md のコード規約）。

### 2.8 接続はインスタンスごとに1本、スレッド間で共有しない

- `journal_mode = WAL`（読み手と書き手が互いをブロックしない）
- `synchronous = NORMAL`（WAL と組み合わせ、電源断で失うのは直近のチェックポイント以降のみ）
- 書き込みは `BEGIN IMMEDIATE`（DEFERRED はロック昇格の失敗が `busy_timeout` を待たずに落ちる）
- `busy_timeout` の既定は 5 秒

取り込みデーモンと API はそれぞれ自分の接続を持つ。WAL では
これで排他を書かずに済み、片方の長い読み出しが取り込みを止めない。

### 2.9 `agg=5m` はテーブルを作らず、1分バケットから合成する

FR-302 は `raw / 1m / 5m / 1h` を挙げるが、0002 §2.8 が確定した3段は
生 / 1分 / 1時間である。**5分のテーブルは作らない。**
**API は `5m` を受け付ける**（FR-302 の受理値は変えない）。実装だけを合成にする。
合成する場所と丸め方は #10 で決める。

行数の内訳は 1分と1時間で足り、5分を保存すると
「どの粒度が真か」が3つから4つに増えるだけになる。

#### 合成の可否

| 統計量 | 1分値から合成できるか | 式 |
|---|---|---|
| `min_value` / `max_value` | できる | `MIN()` / `MAX()` |
| `mean_value` | **`ok_value_count` で加重すれば**できる | `SUM(mean_value * ok_value_count) / SUM(ok_value_count)` |
| `ok_value_count` / `row_count` | できる | 総和 |
| `expected_count` | できる | 総和。いずれかが NULL なら NULL |
| **`p95_value` / 中央値** | **できない** | 生データから計算する（`stats()`） |

**`mean` を「1分値の単純平均」で計算してはならない。** 欠測があると誤る。

```text
12:00  ok_value_count=24  mean=27.0
12:01  ok_value_count=24  mean=27.0
12:02  ok_value_count=3   mean=35.0   ← センサー異常で3サンプルしか取れなかった

単純平均:        (27.0 + 27.0 + 35.0) / 3        = 29.67   ← 誤り
ok_value_count 加重: (27*24 + 27*24 + 35*3) / 51 = 27.47   ← 正しい
```

`readings_1m` が `ok_value_count` を持っているのはこのためである
（0002 §2.8 の 1分→1時間の再集計と同じ式を、5分でも使う）。

**分位数は合成できない。** 各バケットの p95 の平均は全体の p95 ではなく、
元の分布を復元する情報がロールアップに残っていない。
したがって `stats()` は `agg` を取らず、常に生データから計算する。
生データの保持期間（30日、0002 §2.8）を超えた窓では p95 を返せない。

### 2.10 マイグレーションは追記のみ、1ファイル1トランザクション

- ファイル名は `NNNN_<slug>.sql`。番号は0埋め4桁で、ファイル名順＝適用順
- **適用済みのファイルは書き換えない。** 書き換えると、既存の DB と
  新規に作った DB でスキーマが分岐し、どちらが正しいか判定できなくなる
- 番号の飛びと重複は**読み込み時点で**落とす。後から欠番を埋められると、
  DB ごとに適用済みの集合が変わる
- 1ファイルは丸ごと成功するか丸ごと巻き戻る。中途半端なスキーマが残ると、
  次回の起動が「テーブルが既にある」で失敗し、手作業でしか復旧できない
- DB のバージョンがコードより新しい場合は**開かずに中止する**

## 3. Consequences

### 良くなること

- `stale` を行に書かないため、保持期間内の行を後から書き換える処理が存在しない。
  `readings` は追記のみのテーブルになる
- p95 と傾きが「実測に基づく」ことを説明できる。#38 の Evidence 形式で
  そのまま根拠として提示できる
- 欠測率が2つあることが明示される。どちらの障害（センサー / 通信）かが
  値の出どころで分かる

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| `latest()` の結果が呼び出し時刻に依存し、キャッシュしにくい | 判定に使った `age_ms` を返し、上位が再判定できるようにする |
| 欠測率が2つある（2.5） | 返すモデルを分ける。`Stats.missing_ratio` と `RollupPoint.missing_ratio` を同じ名前の1つのフィールドにまとめない |
| nearest-rank の p95 は n が小さいと粗い | 窓の行数（`ok_value_count`）を併せて返す。母数を見れば粗さが分かる |
| `5m` に対応するテーブルが無い（2.9） | API は `5m` を受け付け、#10 で 1分からの合成を実装する |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| p95 を線形補間で出す | 観測していない値が API に出る（2.3） |
| `stale` を行に書き、定期ジョブで更新する | 追記のみのテーブルでなくなる。更新の遅れがそのまま誤表示になる |
| `stale` のとき値を `null` にする | 「直前まで何度だったか」が消える。古いことは `quality` で伝わる（2.2） |
| `INSERT OR REPLACE` で再投入を許す | 観測が黙って消える（2.7） |
| 期間を閉区間 `[from, to]` にする | 連続する窓で端が二重に数えられる（2.1） |
| 欠測率を1つに統合する | センサー異常と通信断の区別が消える（2.5、0002 §2.8） |
| `readings_5m` テーブルを足す | 真の粒度が4つに増える。1分から合成できる（2.9） |
| `stats()` にも `agg` を持たせ、ロールアップから統計量を出す | p95 が合成できない。粒度によって p95 の意味が変わる（2.9） |
| ストア層でスレッドセーフにする（ロック / 接続プール） | WAL で足りる。排他を自前で持つと、止まったときの原因が層をまたぐ（2.8） |

### 未決1 を #9 へ送る理由

0002 §5 は置き場所を #5 で決めるとしていたが、**ストア層は単位を持たずに動く。**
単位と表示名が必要になるのは `api-contract.md` §3 の `unit` フィールドと
ダッシュボードの表示であり、どちらも #9 の担当である。

使う側が確定する前に YAML の形だけ決めると、後から
「API が必要とする形と合わない」ことが分かり、決め直しになる。
ストア層は `metric` 文字列だけを扱い、単位を知らないまま完成させる。
