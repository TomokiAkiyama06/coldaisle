## 1. Context

#106 は「ケース内の風の流れと Fan 制御の判断を流れとして見る UI」で、置き場所が要判断だった。
所有者は 2026-09-18 に **両方** と決めた。いま coldaisle の Web UI に実装し、あとで
Workspace（#60）からリンクする。デザインは所有者がレビュー済み（現在の状態 = Airflow /
Airflow-Override、グラフ = 案B）。

一方で、画面が表示する値の半分（運転モード、安全状態、制御方式、Workload Regime、
系統ごとの Demand、決め手、推定風量、Air Balance）は制御の判断記録（#74 / #82）と
Air Balance（#81）から来るが、どれもまだ動いておらず、読む API も無い。
空気の温度センサー（`air.*`）も現在は未接続である。

仕様に書かれていない判断が複数あるため、ここに記録して承認を求める。

## 2. Decision

2026-09-18、リポジトリ所有者がセッション内で本記録を承認した（スロットリング表示は案1を選択）。

### 2.1 置き場所: 既存ダッシュボードとは別の静的ページ `/airflow.html`

- `src/coldaisle/web/airflow.html` / `airflow.css` / `airflow.js` を足し、ダッシュボードの見出しからリンクする
- 既存の `app.js` / `styles.css` には手を入れない（並行している #48 / PR #134 と衝突させない）
- ビルド工程を増やさない。依存の無い SVG で描き、外部参照を持たない（0011 §2.1 と同じ。
  デザインの IBM Plex は Google Fonts から読むため使わず、システムフォントにする）
- 「現在の状態」と「グラフ」は同じページのタブ（`#now` / `#graph`）
- Workspace（#60）からは将来このページへリンクする。本 PR の範囲外

### 2.2 表示専用

フォーム・送信ボタン・POST を持たない。叩くのは GET だけ（`/latest` `/health` `/series`
`/airflow/config`）。系統の切り替えや期間・系列の切り替えは**見る対象を変えるだけ**で、
制御には何も送らない。モード変更の入り口は `coldaisle-fand` の Unix ソケットだけ（0028 §2.2）。

### 2.3 制御の状態は「未接続」と出す。模擬データは明示的に分ける

- 実データの表示では、制御由来の項目をすべて「未接続」（点線の枠）と出す。**正常（緑）に見せない**
- 模擬データは `?mock=normal`（通常）/ `?mock=override`（背面ファン停止・予備制御）のときだけ、
  別ファイル `airflow-mock.js` を読み込んで表示する。このとき実データを1件も取りに行かない
- 模擬データの表示中は、画面上端の縞の帯と見出しの「模擬データ」で言う
- 判断記録を読む API（#82 / 0030）ができたら、模擬データと同じ形で `page.control` を埋める

### 2.4 空気の温度の色分けは設定から読む

区切りを `config/airflow-ui.yaml` に置き、読み取り専用の `GET /api/v1/airflow/config` で返す
（AGENTS.md ルール9）。4つの境目で5段階（青→琥珀→赤）。段数は配色と対なのでコードに持つ。
区切りはデザインの初期値（27 / 28 / 29 / 30 ℃）で、**仮**（凡例に「区切りは仮」と出す）。
制御・アラートの閾値ではない。

色は `quality = ok` の値にだけ付ける。古い・未取得は灰色の点線（今の空気の温度ではないため）。

### 2.5 デザインからの差分（最も単純な選択をした）

| 項目 | デザイン | 実装 | 理由 |
|---|---|---|---|
| ファンの札 | FRONT 1〜3 / TOP 1〜3 と1基ずつ | 系統ごとに1枚（前面・トップ・背面） | タコメータは系統（ヘッダ）ごとに1本。3枚に同じ値を出すと1基ずつ測っているように見える |
| ファンの札の名前 | FRONT / TOP / REAR | 前面 / トップ / 背面 | 表示はすべて日本語 |
| PWM | `122/255` | `PWM（実測） 48%` | 保存値は 0〜100%（`fan.*.pwm`）。Demand ではなく実測の PWM |
| 層の英語名（Supervisor など） | 小さく併記 | 出さない | 内部名を出さない |
| CPU 使用率 | 29% | 「未計測」 | 取得している入力が無い（メトリクスが存在しない） |
| AI による補足 | 右下に表示 | 出さない | 決定論的なデータだけで描く。AI の文面の出どころが無い |
| AIO ポンプ・VRM ファン | 無し | 「参照のみ（制御対象外）」パネル | 回転数は実測できている。制御対象ではないことを明示 |
| VRM 温度・Chipset 温度 | 無し | 出さない | 所有者の指示（マザーボードの温度は出さない） |
| 風の矢印 | 3px の破線 | 2px の破線。回さない | 所有者の指示（細い矢印・ファンを回さない） |

### 2.6 GPU のスロットリング表示（所有者がデザインの案1を採用）

熱源の定義の `status` と `sourceStatus()` を経由して表示する。判定は DOM に触らない
`airflow-status.js`（`gpuThrottleStatus()`）に置き、node で直接試験する。

`/api/v1/latest` の `gpu.0.throttle.{hw_thermal, sw_thermal, hw_power_brake, sw_power_cap, hw_slowdown}`
（0 / 1。#65 / 決定記録 0043）を読む。

| 条件 | 色 | 小さな札 | 理由の行（GPU の名前の下） |
|---|---|---|---|
| `hw_thermal` または `sw_thermal` が 1 | 赤 | 熱による制限 | 理由：熱による制限（ハードウェア / ソフトウェア / ハードウェア・ソフトウェア） |
| （熱が無く）`hw_power_brake` または `sw_power_cap` が 1 | 琥珀 | 電力による制限 | 理由：電力による制限（ハードウェア / ソフトウェア） |
| （上のどちらも無く）`hw_slowdown` だけが 1 | 琥珀 | ハードウェアによる減速 | 理由：ハードウェアによる減速 |

- 制限がかかっている間は、側面図の GPU のブロックと札の枠がその色になり、札の右に小さな札、
  見出しの下に理由の行が出る。「熱源」パネルにも同じ札と理由を出す
- 熱と電力が同時に立っているときは熱（赤）を優先する
- **`quality` が `ok` 以外（値が無い・古い・疑わしい）のフラグは「分からない」として読まない。**
  立っているフラグが1つも無ければ何も出さない。「スロットリングなし」とは言わない
  （値が届いていない場合と区別できないため）
- T.Limit までの余裕（`gpu.0.tlimit_margin`）は出さない（案3。採用されていない）
- 模擬データ `?mock=throttle` で、熱による制限（ハードウェア）の表示を確認できる

### 2.7 データの出どころの表示

見出しの出どころの表示は `/api/v1/health` の `source`（取り込みの種類）から決める。
**URL に `?mock=` が無いことを「実機」とみなさない。**

| `source` | 表示 |
|---|---|
| `serial` | 実機データ |
| `mock` | 模擬データ（MockSource） |
| `replay` | 再生データ（過去の記録） |
| それ以外・不明 | 出どころ不明（実機のライブ値とは限りません） |

`?mock=` の模擬データ（画面側の模擬）は従来どおり「模擬データ（…）」と帯で言う。

## 3. Consequences

### 良くなること

- 空気の温度センサーや制御デーモンが無くても、実測できている回転数・PWM・GPU/CPU 温度・使用率・電力を
  流れの図の上で見られる。未接続の部分は未接続と分かる
- 模擬データで、通常時と Override 時の見え方を実機なしで確認できる（受入基準「Mock で表示を確認できる」）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 0011 の「作り込まない」より大きい画面が coldaisle 側に増える | 所有者の決定（置き場所は両方）。既存ダッシュボードとはファイルを分けた |
| 模擬データの形が、将来の判断記録 API の形と一致する保証が無い | 画面側は `page.control` 1か所で受ける。API ができた時点で変換を1つ書く |
| 表示名（場所の名前）が `config/metrics.yaml` の表示名と別に JS にある | 図の上の場所の名前であり、メトリクスの表示名とは役割が違う。参照するメトリクス名が metrics.yaml にあることはテストで確かめる |
| 見た目は自動で検証していない | 0011 と同じく「壊れていたら気づける」線（外部参照・書き込み無し・innerHTML 無し・叩く先・模擬の分離）をテストで引いた |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 既存の `app.js` にタブを足す | 並行する PR #134 と同じファイルを大きく変えることになる |
| 制御の状態を空欄や「—」にする | 値が無いのか、正常で何も無いのかが区別できない |
| 模擬データを実データの画面に常に重ねる | 実機の値と取り違える。受入基準に反する |
| 色の区切りを JS に書く | AGENTS.md ルール9 |
| 区切りを静的な JSON として web/ に置く | 設定は `config/` に置く約束。環境変数で差し替えられない |
| MockSource のシナリオで制御状態を作る | 制御状態はまだどこにも保存されない。取り込み側に表示専用の偽データの経路を作ることになる |
