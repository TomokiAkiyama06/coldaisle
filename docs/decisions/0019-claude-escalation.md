## 1. Context

**ローカルモデルに高価な機材の故障判断をさせない**（構想メモ §10）。

定型のアラート説明（#38）と日次レポート（#25）はローカルで足りる。
足りないのは、**初見の異常**である。「hotspot と core の差が3日前から
10℃ 広がった」は、サーマルパッドの劣化かもしれないし、センサーの異常かもしれない。
**間違えると数十万円の機材を失うか、無駄に RMA へ出す。**

---

## 2. Decision

### 2.1 **coldaisle は送信しない**

案件資料をファイルに書き、「できた」と知らせるだけ。読んで、必要と判断したら
**人が** Claude へ渡す。

Issue は「送信前に必ずユーザー確認を挟む（自動送信しない）」と書いているが、
**確認を挟む実装ではなく、送信経路を持たない実装**にした。

- 送る手段が無ければ、**誤って送ることもできない**（0018 §2.2 と同じ考え方）
- 監視ホストから外部へ出る経路と API 鍵が増えない
- この資料には室温・機材構成・障害の経過が入る。**外に出す判断は人のもの**

### 2.2 判定に**LLM を使わない**

受入基準そのものだが、理由を書いておく。**判定をモデルに任せたら本末転倒である。**
「ローカルモデルに故障判断をさせない」ための仕組みの入口を、そのモデルに
決めさせることになる。

引き金は3つ。どれも `config/escalation.yaml` にあり、**すべて継続を条件にする。**

| 引き金 | 条件 | 1回で騒がない理由 |
|---|---|---|
| `step_change` | 隣り合う日の平均が `delta` 以上動き、`hold_days` ぶん戻らない | 1日の跳ねは負荷の山かもしれない |
| `sustained_deviation` | 基準 ± `tolerance` を `hold_hours` 続けて外れる | 一時的な逸脱は既存のアラートが見る |
| `repeated_critical` | 同じ critical が `window_days` で `min_count` 回 | 1〜2回は対処済みかもしれない |

**継続は「見た日」で数える。** 値のある日だけを並べると、間に取り込みが止まった日が
あっても「3日続いた」と書ける。**続いたことを見ていないのに続いたと書くのが、
この資料でいちばんやってはいけないこと**なので、間に欠けた日があれば引き上げない。

条件を満たすルールは**すべて**返す。1件目で打ち切ると、残りは翌日以降も出てこない
（1件目が条件を満たし続けるかぎり毎日そちらが選ばれ、資料は重複として捨てられる）。

`sustained_deviation` は **`enabled: false`** で出荷する。基準値を実測していない
（#19）ため、いま有効にすると正常な運転を毎日引き上げる。

### 2.3 案件資料は**圧縮する**

構想メモ §10 の5節（問題 / 測定値 / 経過 / 試行済み / 争点）。

- **経過は日ごとの平均だけ。** 生の時系列を入れない（FR-504 / 受入基準）
- 測定値は直近24時間の統計。関係するメトリクスだけ
- 上限を超えたら切り、**切ったことを書く**
- 派生値は保存されない（0002 §2.2）ので **1日平均どうしの差**から出し、
  **そう書く**。生の差の平均とは厳密には一致しない

### 2.4 「試行済み」に書くのは**測って分かることだけ**

`config/rules.yaml` の閾値と 24時間の p95 を比べ、収まっているかを書く。
**別の基準を持たない。** 品質フラグと取りこぼしも同様。

Issue の例には「ファン回転数に変化なし」「負荷パターンに変化なし」があるが、
**どちらも測っていない。** 書けば、読む側は確認済みだと思う。
測っていないことは**争点**の側に「人が確認すること」として書く。

### 2.5 同じ案件を**毎日作らない**

資料の名前を `{起点の日}-{引き金}-{対象}.md` にし、あれば作らない。
毎朝同じ資料が増えると読まれなくなる。作り直しは `--force`。

**起点を窓の端で決めない。** 再発の判定は動く窓（`window_days`）で行うが、
起点にそれを使うと、古い発火が窓から出るたびに日付が動き、**同じ状況の資料が
毎朝できる。** 新しい発火から遡り、間隔が窓を超えたところで切った先頭を起点にする。

### 2.6 区切りより**後の値を見ない**

朝の cron は前日を対象にするが、DB には当日の値が既に入っている。
「試行済み」に当日の品質を混ぜると、**当日の故障を前日の案件に付ける**か、
逆に区切り時点の故障を隠す。

`SqliteStore.latest(at_ms=...)` は `at_ms` を鮮度の判定にしか使わず、行そのものは
常に最新を返していた。**`at_ms` は「その時点での最新値」という意味に変えた**
（引数を渡さないときの挙動は変えていない）。

### 2.7 知らせに載せるのは**問題の1文と場所だけ**

測定値・経過・争点は資料に残す。1文を載せるのは、これが無いと「読みに行くかどうか」
を判断できないためで、アラートの通知が値を載せるのと同じ理由である（0013）。

**知らせ自体が送信物である。** `config/escalation.yaml` の `to` に slack / line を
書けば、その1文はそこへ届く。既定は `stdout`（ローカルのログ）だけにし、
設定ファイルにもその旨を書いた。

文面も「送信していません」では足りない。**何を送っていないのか**を書く
（「Claude へは送っていません」）。書かないと、Slack で読む人には
「どこへも出ていない」と読める。

## 3. Consequences

### 良くなること

- 高価な機材の故障判断が**人の手に残る**（2.1）
- 引き上げの条件が設定ファイルに書いてあり、**あとから検証できる**（2.2）
- 資料に生ログが入らない（2.3）
- 「確認済み」と書かれていることは、本当に測ってある（2.4）
- 続いたと書いてあるものは、続いたところを見ている（2.2）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 人が渡すまで Claude の回答は得られない | 引き上げは1日1回の判断。分単位の話ではない |
| 閾値が実測前なので、引き金の当たりが分からない | `sustained_deviation` は #19 まで無効。残る2つは相対値と回数で、基準値に依存しない |
| 資料が正しく圧縮されているかは実データ待ち | 上限で切り、切ったことを書く（2.3） |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| coldaisle から Claude API へ送る（確認プロンプト付き） | 送る手段があれば誤って送れる。鍵と外向きの経路が増える（2.1） |
| 引き上げるかどうかをローカルモデルに判断させる | 「ローカルに故障判断をさせない」仕組みの入口をローカルに決めさせることになる（2.2） |
| 案件資料の文面をモデルに書かせる | 数値を幻覚できる（0016 §2.1 と同じ） |
| 1回の critical で引き上げる | 対処済みかもしれない。読まれない資料が増える（2.2） |
| 生の時系列を添付する | 受入基準に反する。読む側も追えない（2.3） |
| 欠けた日を詰めて継続を数える | 見ていない継続を「続いた」と書くことになる（2.2） |
| 条件を満たした1件目だけ返す | 残りが翌日以降も出てこない（2.2） |
| 知らせに資料の全文を載せる | 外部の宛先を設定していると、読む前に全部出ていく（2.7） |
| 知らせを場所だけにする | 何の件か分からず、読みに行く判断ができない（2.7） |
| Issue の例文どおり「負荷パターンに変化なし」と書く | **測っていない。** 確認済みだと誤読される（2.4） |
