## 1. Context

所有者は、重大（critical）・警告（warning）の**発生**の通知に、対象の値と関係する値の
直近 60 分のグラフを Slack で添えることを選んだ（2026-10-15）。文章だけでは
「急に跳ねたのか、ゆっくり上がってきたのか」「室温も一緒に上がっているのか」が分からず、
ダッシュボードを開ける端末に移るまで判断できない。

今の Slack の宛先は Incoming Webhook（`COLDAISLE_SLACK_WEBHOOK`。0013 §2.1）で、
**Webhook はファイルを添付できず、送った投稿の `ts` も返さない**（同じスレッドへ続けられない）。
画像を上げるには Slack アプリの Bot トークン（`chat:write`・`files:write`）が要る。

通知は監視の外側にある（0013 §1）。グラフはさらにその外側で、**グラフのせいで文章の通知が
遅れる・止まる・ルールの評価が遅れることがあってはならない。**

## 2. Decision

### 2.1 送り方: Bot トークンがあれば本文も `chat.postMessage`、無ければ今の Webhook のまま

| 環境変数 | 本文 | グラフ |
|---|---|---|
| `COLDAISLE_SLACK_BOT_TOKEN` と `COLDAISLE_SLACK_CHANNEL` の**両方**あり | `chat.postMessage`（返る `ts` を控える） | その `ts` のスレッドへ上げる |
| どちらかが無い | `COLDAISLE_SLACK_WEBHOOK`（今のまま） | 添えない |

- `COLDAISLE_SLACK_CHANNEL` はチャンネル**ID**（`C` で始まる）。名前（`#…`）は使わない
  （改名で届かなくなるのを避け、`files.completeUploadExternal` が ID を要るため）
- 片方だけ設定されているときは Bot の宛先を作らず、**起動時に 1 度だけ警告する**
  （LINE と同じ。0013 §2.1 / §2.7）。Webhook があれば Webhook で本文を送る
- **Bot の送信が失敗し、Webhook も設定されていれば、その 1 通は Webhook で送り直す**
  （トークンの失効・Bot のチャンネルからの退出で critical が届かなくなるのを避ける）。
  応答を失っただけで Bot の投稿が実は届いていた場合は 2 通になるが、届かないより良い。
  送り直したときはグラフを添えない（スレッドの `ts` が無い）
- Slack の Web API は HTTP 200 で `{"ok": false, "error": "…"}` を返すことがある。
  `ok` が true でなければ失敗とする
- 日次レポート・故障疑いの案件（`coldaisle-report` / `coldaisle-escalate`）も同じ
  `notifiers_from_env()` を通るので、Bot があれば `chat.postMessage` で届く（グラフは添えない）

### 2.2 グラフは本文の**後から**、別のスレッドで作って同じスレッドへ上げる

1. 送信スレッド（`Router`。0013 §2.4）が本文を `chat.postMessage` で送り、`ts` を得る
2. 添える条件（2.4）に合えば、グラフの依頼（ルール・メトリクス・`ts`・時刻）を
   **グラフ専用のスレッド**の待ち行列へ `put_nowait` で積む。**待たない**
3. グラフのスレッドが**自分の接続**で DB を読み（接続はスレッド間で共有しない。0004 §2.8）、
   PNG を描き、`files.getUploadURLExternal` → 返った URL へ本体を POST →
   `files.completeUploadExternal`（`channel_id`・`thread_ts`）で同じスレッドへ上げる

- 待ち行列は有界（8 件）。溢れたら数えて記録し、その依頼は捨てる（文章は届いている）
- 描けない（DB を開けない・値が 1 点も無い・例外）・上げられない（HTTP / `ok: false`）ときは
  **記録して捨てる。再送しない。** 文章の通知は既に届いている
- 停止時はグラフの待ち行列を**待たない**（最長 5 s だけ待ち、残りは捨てる）。
  停止時に送り切るのは文章の通知だけ（0013 §2.4）
- ルールエンジン・取り込みのスレッドはグラフに一切関わらない（遷移を `Router` に渡すまでは今のまま）

### 2.3 描くもの

**サーバーで決定論的に描く。LLM は使わない**（AGENTS.md ルール 1・8 に触れない）。
同じ DB の内容と同じ設定からは同じ PNG ができる。

- 期間: 発火の通知を送った時刻から遡って `window_s`（既定 3600 s = 60 分）。
  `readings` の生の値（`series()`。品質 `ok` の点だけ）
- 描くメトリクスは**本文の「現在値:」と同じもの**。0142 §2.2a の選び方（`DisplayNames.context_metrics`）を
  そのまま使い、選び方を 2 か所に持たない（重複は先に出たほうだけ）:
  1. アラートのメトリクス（`Notification.metric`）
  2. ルールの定義が参照する残りのメトリクス（`metric` / `core_metric` / `fan_metric`）
  3. 1・2 が派生値なら材料（`config/metrics.yaml` の `minuend`・`subtrahend`）
  4. `config/notify.yaml` の `context_always`（既定 `[air.room]`。0142 §2.2a）

  ルールの文を持たない ID（`config/rules.yaml` に無いルール）は、1・その材料・4 だけ。
  本文の「現在値:」と違い、取り込みのサンプルに無い値（`GPU_FAN_*` の GPU の値など）も DB から読んで描く
- **派生値は保存しないので**（0002 §2.2）、材料の 2 本を同じ `ts_ms` で突き合わせて引き算する
  （両方 `ok` の時刻だけ。`compute_derived` と同じ規則）
- **単位ごとに別の面（パネル）にする。** 1 つの面に 2 つの縦軸を持たない。
  例: `GPU_FAN_BELOW_CURVE` は °C の面（GPU コア・室温）と % の面（GPU Fan）
- **閾値の線**（赤の破線）を、ルールの種類ごとに対応する面に引く:

  | ルールの種類 | 引く線 |
  |---|---|
  | しきい値（`ThresholdRule`） | `threshold` |
  | 範囲（`RangeRule`） | `low` と `high` |
  | 温度が高いのに回転が低い（`HotAndSlowRule`） | `core_metric` に `core_threshold`、`fan_metric` に `fan_below` |
  | 変化率（`SlopeRule`）・flag・連続欠け・その他 | 引かない（値の軸の閾値ではないため） |

- 30 s（`gap_s`）より離れた 2 点は線で結ばない（欠けを欠けとして見せる）
- 色は系列ごとに固定の順（青・橙・緑・黄）。閾値は赤の破線。1 つの面に最大 4 系列
- 画像の中の文字は ASCII だけ（メトリクス名・数値・`-60m` などの時刻）。**日本語の凡例は
  ファイルのコメント**（`initial_comment`）に書く: `直近60分: GPU吸気(air.gpu_intake)=青、…／閾値 40.0 = 赤の破線`
- 大きさは `width`×`height`（既定 960×300 を 1 面ぶん）。点数は面ごとに最大 `max_points`（既定 4000）で、
  超えたら同じ間隔で間引く（直近を必ず残す）

### 2.4 添える・添えないの条件

| 場合 | 添えるか | 理由 |
|---|---|---|
| critical / warning の**発火**が実際に Slack へ送られた | 添える | 所有者の判断 |
| 解除・発火の説明（`🔎`）・日次レポート・案件資料 | 添えない | 発火の時点のグラフで足りる。解除のたびに上げると連投になる |
| info | 添えない | Slack へ送らない（`routing`） |
| メトリクスを持たないアラート（`SENSOR_FAULT`・`PROBE_CHANGED`） | 添えない | 何を描くか決まらない。無音のときは描く値も無い |
| `repeat_after_s` / 夜間の方針で**本文を送らなかった** | 添えない | 送っていない通知に続けない（`Router` が送ったものだけに続く） |
| 同じ `(ルール, メトリクス)` に `repeat_after_s` 以内にグラフを**実際に上げた**（または上げている途中） | 添えない | 発火と解除を往復するアラートで画像が連投されるのを抑える。描けなかった・上げられなかった・停止で捨てたグラフは数えない（次の発火には添える） |
| 夜間に届いた critical | 添える | スレッドへの返信はチャンネルの通知にならない（Bot が始めたスレッドを人はフォローしていない） |
| Webhook で送った・Webhook へ送り直した | 添えない | スレッドの `ts` が無い（2.1） |

### 2.5 依存を足さない（標準ライブラリで PNG を書く）

PNG は `zlib` と `struct` で書き、線は整数の座標で引く。文字は 5×7 の点の字形（ASCII の英数字と
いくつかの記号）をコードに持つ。**新しい依存を足さない。**

| 案 | 重さ | 評価 |
|---|---|---|
| **標準ライブラリだけ（採用）** | 0（コード約 400 行と字形の表） | 取り込みのプロセスにネイティブの画像ライブラリを載せない。出力が版で変わらない。日本語は描けない → 凡例はコメントへ（2.3） |
| Pillow | wheel 約 4.5 MB（C 拡張・FreeType を同梱） | 文字がきれい。画像の解析系の CVE が定期的に出る（使うのは書き出しだけだが、取り込みのプロセスに読み込まれる）。日本語には別にフォントが要る |
| matplotlib | numpy・Pillow・fonttools ほか合わせて約 60〜80 MB | いちばん見やすいが、通知のためだけには重い。導入先の venv と CI が太る。日本語にはフォントが要る |
| SVG を上げる | 0 | Slack は SVG を画像としてプレビューしない（ファイルとして置かれるだけ） |

見た目が足りないと分かれば、後の記録で Pillow へ移す（描画の入口は 1 関数にしてある）。

### 2.6 トークンと URL を残さない

- トークンは環境変数（`/etc/coldaisle/coldaisle.env`）だけから読む。設定ファイル・コードに書かない（0013 §2.1）
- トークンは `Authorization` ヘッダにだけ載せる。クライアントの `repr` に出さない
- 失敗は `DeliveryError`（#305）にし、文は**宛先の名前・Slack の API の名前・HTTP の状態コード・
  Slack の `error` の符号（`not_in_channel` など）だけ**にする。元の例外の連鎖は切る
- `files.getUploadURLExternal` が返す上げ先の URL（署名入り）もログ・例外に出さない
- httpx のログは既に WARNING 以上だけ（#305。`coldaisle.logs`）

### 2.7 設定は別のファイル（`config/notify-graph.yaml`）にし、壊れていてもグラフだけを止める

```yaml
enabled: true
window_s: 3600
gap_s: 30
width: 960
panel_height: 300
max_points: 4000
```

- **読めない・形が不正なら、起動時に error を 1 度記録してグラフだけを無効にする。**
  文章の通知・取り込みは止めない（監視 > 通知 > グラフの順に大事）
- `config/notify.yaml` の `NotifyConfig`（`extra="forbid"`）には足さない。壊れたグラフの設定で通知ごと
  起動しなくなるのを避けるため。どのアラートにも足すメトリクス（室温）だけは、本文と揃えるため
  `config/notify.yaml` の `context_always`（0142）を使い、このファイルには持たない

## 3. Consequences

### 良くなること

- 通知を開いた端末で、値の動き（急な跳ね・ゆっくりの上昇）と室温との関係がすぐ分かる
- Bot トークンを用意するまでは今と同じ動き（Webhook のまま。コードの切り替えは要らない）
- 新しい依存が無い

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 秘匿情報が 1 つ増える（Bot トークンはチャンネルへの投稿とファイルの読み書きができる） | scope を `chat:write`・`files:write` だけにする。置き場所は Webhook と同じ `/etc/coldaisle/coldaisle.env`（`0640`・`root:coldaisle`）。ログ・例外に出さない（2.6） |
| 図の文字が粗い・日本語が描けない | 凡例は日本語でコメントに書く（2.3）。足りなければ Pillow へ（2.5） |
| Bot の送信の失敗で Webhook へ送り直すと、まれに 2 通になる | 届かないより良い（2.1）。送り直したことは記録する |
| 取り込みのプロセスにスレッドと DB の接続が 1 つずつ増える | 最初のグラフのときに開く。待ち行列は有界（2.2） |
| 実際の Slack への到達はテストで確かめられない | Slack の API は偽物（`httpx.MockTransport`）で確かめる。到達は所有者が `docs/notifications.md` の手順で確かめる |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 本文は Webhook のまま、グラフだけ Bot で同じチャンネルへ（スレッドにしない） | Webhook は `ts` を返さず、どの通知のグラフか分からない。連続すると取り違える |
| 本文とグラフを 1 回の `files.completeUploadExternal`（`initial_comment` に本文）で送る | グラフを描き終わるまで本文が届かない。描けない・上げられないときに本文の送り方が変わる |
| グラフを `Router` の送信スレッドで描いて上げる | 上げるのに数秒かかると、次の文章の通知（別の critical）が待たされる（2.2） |
| 解除にもグラフを添える | 解除のたびに画像が届き連投になる。発火の時点のグラフで足りる（2.4） |
| 1 つの面に 2 つの縦軸（°C と %） | 軸の取り違えを招く。単位ごとに面を分ける（2.3） |
| matplotlib / Pillow を足す | 2.5 |
| グラフの設定を `config/notify.yaml` に足す | 壊れたグラフの設定で通知ごと起動しなくなる（2.7） |
