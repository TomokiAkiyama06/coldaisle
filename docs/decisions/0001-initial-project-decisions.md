### D-02 補足: 3段の粒度

| 粒度 | 保持 | 用途 |
|---|---|---|
| 生データ（2.5秒） | **30日**（約2GB） | 直近の詳細調査 |
| 1分ロールアップ | 無期限 | 日〜週の推移 |
| **1時間ロールアップ**（追加） | 無期限 | 月単位の閲覧・年次比較 |

1分粒度のまま1年分（約52万行/メトリクス）をグラフ化すると重くなるため、
月表示用に1時間粒度を追加します。ダッシュボードは期間に応じて粒度を自動選択します。

### D-04 補足: 段階的な有効化が必要

夜間も通知する以上、**誤警報が睡眠を削ります。**
「通知が信用されなくなる」より深刻な実害です。

したがって、ベースライン測定（#19）が完了するまでは夜間通知を critical のみに絞り、
閾値確定後に warning を有効化します。切り替えはフラグで行えるようにします。

これに伴い、以下の優先度を上げます。

- **#36（GPU Mode 別の閾値）** — 学習中の高温を異常と誤認しないため
- **#19（ベースライン測定）** — 実測に基づく閾値でないと誤警報が出る

### D-06 補足: coldaisle 専用チャットUIは作らない

```text
変更前: coldaisle にチャットUIを実装する
変更後: coldaisle は AI が呼ぶための読み取り専用ツールを提供するだけ
        チャットUI は Workspace 側が担当する
```

coldaisle 側の作業は #22（ツール定義）に集約されます。
**v0 ダッシュボード（#17）は引き続き実装します。**
グラフと現在値の目視確認と、自然言語での問い合わせは別の機能です。

### D-09 補足: Prometheus 不採用の理由（記録）

- ミドルウェアが2つ増える割に、SQLite + 自作ダッシュボードで要件を満たせる
- AI へ数値を渡す経路（`get_stats`）を自前で持つほうが素直
- Workspace へ内蔵表示する方針（D-13）と噛み合わない

将来、監視対象が複数ノードに増えた場合は再検討の余地があります。

### D-12 補足: 「別リポジトリだが内蔵させる」の意味

```text
リポジトリ:  coldaisle（独立）  と  personal-ai-workspace（独立）
              │
              │ REST API / WebSocket
              ▼
実行:        Workspace の UI に Server Health パネルとして内蔵表示される
              利用者から見れば1つのアプリ。実体は2つのサービス
```

- **コードは分ける**（Workspace の作り直しで監視が止まらないように）
- **見た目は統合する**（利用者は2つのアプリを行き来しない）
- 接続は #35 の Server Health API 経由

git submodule での取り込みは推奨しません。バージョン管理が煩雑になる割に、
API 経由と比べた利点がありません。
