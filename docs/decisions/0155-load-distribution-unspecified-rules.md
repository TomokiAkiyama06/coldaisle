## 1. Context

PR #348 で 0151（FINAL）の `coldaisle-load-distribution` を実装した。その途中で、0151 に書かれていないのに
実装では決めなければならない点が 14 あった。実装はどれも、0151 の範囲で最も保守的な形
（定常に入れない・`fand` / `bios` に入れない・黙って捨てない）にしてある。ただし仕様に無い判断なので、
AGENTS.md「決定記録」のとおりここに残し、所有者の承認を取る。**本記録の承認が PR #348 のマージの前提**である。

14 点のうち 13 点は PR #348 の最初の commit で決めた。残る 1 点（§2.5）は Codex のレビュー（P1）への対応で
足した。同じレビューの P2（品質で除いた行が segment を切らない）は、0151 §2.3 の「品質で除いた時刻など」を
実装が守っていなかった誤りで、0151 のとおりに直した。判断を含まないので本記録には入れない。

並びは、**集計の結果（どの観測がどの分布に入るか）に効く度合いの高い順**とした。§2.1〜§2.8 は分布の件数や
値を変えうる。§2.9 以降は出力の表し方か入力の受け方で、分布の値は変えない。

## 2. Decision

### 2.1 `--group-by trace-regime` では、落ち着きの計時と segment を Regime のラベルで決める

- **決めたこと**: trace-regime の切り口では、`transition` の計時のやり直しと segment の境目に、電力の帯の状態ではなく
  評価時刻の as-of の trace の `workload_regime` を使う。電力の帯はこの切り口では使わない。`unknown_no_trace` /
  `unknown_ambiguous` / `unknown_unreadable` の時刻は、電力の `unknown` と同じく計時を止める
- **理由**: 0151 §2.3 は segment のまとめのキーを「状態（または `trace-regime`）」と書く。落ち着きは「まとめのキーの
  状態が変わってから」と読むのが、segment と計時を同じ鍵にそろえる素直な読み方である。電力の帯も合わせて使うと、
  Regime が同じなのに帯の境目の揺れで `transition` が増え、Regime の切り口の分布が帯の設定に左右される
- **代替案**: (a) 電力の帯と Regime の**どちらか**が変われば計時をやり直す（いちばん保守的。`transition` が増え、Regime の
  切り口が帯の `provisional` の値に依存する）／(b) trace-regime では計時をせず、すべてを定常に入れる（0151 §2.3 に反する）

### 2.2 除く区間（`exclude`）を挟むと、落ち着きの計時をやり直す。名前つきの区間の外ではやり直さない

- **決めたこと**: `exclude` の区間の中の評価時刻は状態を決めない（0151 §2.6b の 1）。その後の最初の時刻から計時を始め
  直す。名前つきの区間の外（`outside_periods`）の時刻は状態を決め、計時を続ける
- **理由**: 除く区間は人が「この間は信用できない」と渡したもの（時計の調整・試験の操作）で、その間に負荷や Fan が
  どう動いたか分からない。前後を同じ定常として繋ぐと、除いた区間の直後を誤って定常に入れうる。名前つきの区間の外は
  分布に使わないだけで、物理の変化ではない（`period` の切り替わりと同じ。0151 §2.3）
- **代替案**: (a) 除く区間でも計時を続ける（除いた区間の中の変化を見落とす）／(b) 名前つきの区間の外でもやり直す
  （`ac_on` の区間の始まりから毎回 `settle_ms` が `transition` になり、区間の境目で分布が削れる）

### 2.3 区間の不一致の割合の数え方（§2.6a の分母と分子）

- **決めたこと**: trace の区間ごとの割合の分母と分子を次のとおり数える
  - 壁時計の重なりに触れる Fan のサンプルは、**分母に入れ、不一致（分子）に数える**
  - 一致した tick どうしでモードが食い違うサンプル（`mode_mixed`）は、分母に入れ、分子に入れない（PWM は合っている）
  - 3 zone の `ts_ms` が揃わないサンプルは、0151 のとおり分母と分子に入れる。ただし覆いの数（3 zone が揃った
    サンプル。0151 §2.6a「Fan のサンプルの覆い」）には入れない
  - 別の区間の trace が候補の窓に入ったサンプル（`cross_segment`）は、0151 のとおりどの区間にも入れない
- **理由**: 重なりに触れるサンプルは as-of の trace の選び方そのものが信用できない。一致に数えれば甘くなり、除けば
  分母が減って割合の検査が緩くなる。不一致に数えるのがいちばん保守的である。`mode_mixed` は書き込みの確かめと
  PWM の一致を満たしており、不一致に数える根拠が無い（その時刻は `undetermined` にする）
- **代替案**: (a) 重なりのサンプルを `cross_segment` と同じく除く（割合の分母が減る）／(b) `mode_mixed` を不一致に数える
  （試験の操作の切り替わりのたびに区間が `undetermined` に倒れやすくなる）

### 2.4 `bios_confirmed` の中の食い違いを、直前の Fan のサンプルの側にも広げる

- **決めたこと**: `bios_confirmed` の中の評価時刻 `t` は、`t` の as-of の trace が無く、**かつ** `t` 以前で最も新しい
  `fan_max_age_ms` 以内の Fan のサンプルにも as-of の trace が無いときだけ `bios` にする。どちらかに trace があれば
  `undetermined`（理由 `bios_confirmed_conflict`）
- **理由**: 0151 §2.6a は「as-of の trace がある時刻」を食い違いとする。`cooling` の根拠は直前の Fan のサンプルなので、
  `t` の as-of が無くても（fand が 2 s 前に止まった）サンプルの側に trace があれば、Fan はまだ fand の指令のままでありうる。
  BIOS の期間に fand の指令の名残を混ぜない
- **代替案**: (a) 0151 の文言どおり `t` の as-of だけを見る（fand が止まった直後の数秒が `bios` に入りうる）

### 2.5 `--allow-partial` では、集計そのものを実際に覆った期間に絞り、その始めから計時をやり直す

- **決めたこと**: 生データが消えたバケットがあるとき、`--allow-partial` の集計は、来歴の `covered_period` の始め
  （消えた最後のバケットの次の 1 分の始め。`--start` より前なら `--start`）から `--end` までだけを分布と件数に入れる。
  その始めの直前の行が残っていても `start_lookback_incomplete` とし、始めから `settle_ms` を `transition` にする
- **理由**: 来歴だけを狭めると、消えかけのバケット（行数が `row_count` より少ない）に残った行が分布に混ざり、
  「求めた期間をそのまま名乗らない」（0151 §2.7）に反する（Codex のレビュー P1）。消えたバケットの直後は、さかのぼりの
  行が残っていても状態が続いていたとは言えない
- **代替案**: (a) 期間の全体を集計し来歴に覆った期間を書くだけ（PR #348 の最初の実装。残った行が混ざる）／(b) 消えた
  バケットだけを除いて飛び飛びに集計し、覆いを区間の列で書く（来歴が複雑になり、消えた前後を繋ぐかの判断が増える）

### 2.6 `start_lookback_incomplete` は metric ごとに、その metric の評価時刻で判定する

- **決めたこと**: metric ごとに、`--start - lookback_ms` から `max_gap_ms` 以内に ok の行が無い、または `--start` の後の
  最初の ok の行までに `max_gap_ms` を超える間隔があれば、その metric のさかのぼりは不完全とし、区間の中の最初の
  評価時刻から計時を始める。どれか 1 つでも不完全なら来歴の `start_lookback_incomplete` を立て、該当の metric を
  `start_lookback_incomplete_metrics` に並べる。電力・trace・`fan.*` の欠けは、状態が `unknown` / `undetermined` に
  なって計時が止まることで扱う（別の判定を持たない）
- **理由**: 各 metric は自分の ok の行の時刻で評価する（0151 §2.4）ので、欠けも同じ時刻の列で見るのが一貫する。
  電力などの欠けは状態の判定の側ですでに保守的に倒れる
- **代替案**: (a) すべての metric をまとめて 1 つの判定にする（1 本のプローブの欠けで全 metric の始めが `transition` になる）

### 2.7 `d.*` の `unpaired` は、落ち着きの計時をやり直さない（segment は切る）

- **決めたこと**: 減数と対にできない評価時刻は分布に入れず `unpaired` に数え、segment を切る。計時はやり直さない
- **理由**: 対が無いのはデータの欠けで、負荷や Fan の変化ではない。計時は状態の変化を表す（0151 §2.3）
- **代替案**: (a) `unpaired` でも計時をやり直す（減数のプローブの短い欠けのたびに `settle_ms` が削れる）

### 2.8 負の電力の値は、どの帯にも入れず `unknown` にする

- **決めたこと**: 窓の平均が負になった軸は `unknown`
- **理由**: 帯の最初の下限は 0（0151 §2.2）で、負の値の入る帯が無い。計測の誤りを `idle` に入れない
- **代替案**: (a) 最初の帯（`idle`）に入れる

### 2.9 標準偏差は母標準偏差（ddof = 0）にする

- **決めたこと**: `std` は母標準偏差
- **理由**: 分位点を NumPy の既定（type 7）に合わせた（0151 §2.5）ので、標準偏差も NumPy の既定（`np.std` の ddof = 0）に
  そろえる。`min_samples`（120）以上でしか出さないので、標本標準偏差との差は 0.5 % 未満
- **代替案**: (a) 標本標準偏差（ddof = 1）

### 2.10 `undetermined` の理由は、区間ごと受け入れなかった理由を先に出す

- **決めたこと**: Fan のサンプルが属する trace の区間が受け入れられない（`segment_open` / `pwm_mismatch_ratio` など）とき、
  その区間のどのサンプルの時刻も、サンプルごとの理由（`pwm_mismatch` / `write_unverified` など）ではなく区間の理由で数える
- **理由**: 人が見て直すべきなのは区間の性質（simulated の backend・書き込みの失敗が続く運転）である。サンプルごとの
  理由に散らばると、区間ごと落ちたことが表から読めない。`cooling` の値はどちらでも `undetermined` で変わらない
- **代替案**: (a) サンプルごとの理由を先に出す

### 2.11 品質の件数は、その行の時刻のグループに数える

- **決めたこと**: `missing` / `suspect` / `stale` / 値の無い ok（`null`）の行は、その行の時刻の `cooling` × ラベル × `period` の
  鍵に数える。`transition` かどうかは分けない。除く区間・名前つきの区間の外の行は、`(excluded)` / `(outside)` の鍵に
  まとめる。`d.*` は被減数の行と `unpaired` を数える
- **理由**: 0151 §2.7 は「metric ごと・グループごとに品質別の件数」と書くが、落ち着きの計時は ok の行の時刻の列で
  行う（§2.6）ので、非 ok の行に `transition` を当てる根拠が無い
- **代替案**: (a) metric ごとの合計だけを出す（グループごとの欠けの偏りが見えない）

### 2.12 較正の変更の一覧は `[--start, --end)` の行だけ。記録の検証に外れたら集計を拒否する

- **決めたこと**: `calibration_activations` の全行を 0099 §2.5 の規則で検証し、`ts_ms` が `[--start, --end)` の行を一覧にする。
  検証に外れたら何も出力せずに終了する
- **理由**: 期間より前の変更は期間の全体に同じく当たっており、期間の中で値の意味を変えない。記録が壊れているのを
  「変更なし」と読み替えない（0099 §2.7）
- **代替案**: (a) さかのぼりの区間（`lookback_ms`）の変更も一覧に入れる／(b) 検証に外れても続け、警告だけを出す

### 2.13 `--periods` の時刻は、引用符で囲んだ文字列だけを受ける

- **決めたこと**: `start` / `end` は文字列だけを受け、タイムゾーンが無ければ設定の `timezone` で解釈する。引用符の無い
  時刻は拒否する
- **理由**: PyYAML は引用符の無い時刻を `datetime` にし、タイムゾーンの扱いが版と書き方で変わる。解釈を 1 つにする
- **代替案**: (a) `datetime` も受けて変換する

### 2.14 `--end` は必須。終了コードは入力の誤りが 2、集計の拒否が 1

- **決めたこと**: `--end` を省けない。設定・時刻・DB を読めない入力の誤りは 2、生データの欠け・較正の記録の不整合など
  集計の拒否は 1 で終える。どちらも何も出力しない
- **理由**: 0151 §2.10 の設定に期間の長さの鍵が無く、既定の長さを持てない（ルール 9）。2 つの失敗を呼び出し側が
  見分けられるようにする
- **代替案**: (a) 設定に `duration_hours` を足し、`--end` を省けるようにする（`coldaisle-soak-report` と同じ。0151 の設定の鍵を変える）

## 3. Consequences

### 良くなること

- 0151 に無い判断がすべて文書になり、出力を読む人が「なぜこの観測が除かれたか」を記録でたどれる
- どの判断も、定常・`fand`・`bios` に入れない側か、黙って捨てない側に倒してある

### 悪くなること・その緩和

| 悪くなること | 緩和 |
|---|---|
| 保守的に倒したぶん、`transition` と `undetermined` が増え、分布の件数が減る | 除いた件数を理由ごとに出す（0151 §2.8）。件数が足りなければ期間を延ばすか、本記録の該当の節を見直す |
| `--allow-partial` の分布が求めた期間より短い | 来歴に実際に覆った期間を書く。保持期間のうちに走らせれば起こらない |

## 4. 却下した代替案

各節の「代替案」のとおり。共通の理由は、0151 が定める保守的な側（定常に入れない・`fand` / `bios` に入れない・
黙って捨てない）から外れること。
