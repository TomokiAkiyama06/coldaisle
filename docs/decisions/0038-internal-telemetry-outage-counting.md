# 決定記録 0038: Internal Telemetry の欠測の数え方

- **種別**: Decision Record
- **Status**: Proposed
- **Date**: 2026-09-18
- **Supersedes**: なし（決定記録 0008 §2.1.1 を Internal Telemetry の周期メトリクスへ拡張する。`air.*` の扱いは変えない）
- **関連**: [`0008-rollup-and-retention.md`](0008-rollup-and-retention.md) §2.1.1・§2.1.2 /
  [`0032-internal-telemetry-metric-names.md`](0032-internal-telemetry-metric-names.md) /
  [`0029-telemetry-loss-classes.md`](0029-telemetry-loss-classes.md)
- **対象 Issue**: #65

## 1. Context

決定記録 0008 §2.1.1 は、1件も届かなかった分を0行のバケットとして作り、埋めるのは
「観測し始めてから最新の分まで。設置前や停止後にまで期待値を作らない」としている。
上限は生データの最新時刻である。

Internal Telemetry collector（`coldaisle-telemetry`）は外付けデバイスと別プロセスで動き、
単独でも ingest と同時にも止まりうる。0008 のままでは次の欠測が記録に残らない。

- collector と ingest が同時に止まると、生データの最新時刻が進まず停止区間が埋まらない
- 停止した metric の最後の生データが保持期間で消えると、以降の日が埋まらない

一方で、設定で無効にしていた期間（未設置の T_SENSOR、保守で外した sensor など）を
欠測として数えると、欠測率が実際の障害と関係のない値になる。ロールアップは readings
だけでは「無効だった」と「止まっていた」を区別できない。すべての source が静かな期間には
痕跡がまったく残らないためである。

## 2. Decision

Internal Telemetry の周期メトリクス（`config/internal-telemetry.yaml` で有効な入力）について、
欠測を次のように数える。

1. **有効な間の停止は欠測とする。** ロールアップは有効な metric とその `interval_ms` を
   登録として受け取り、1分あたりの期待サンプル数 `60000 / interval_ms` を持たせる
   （`interval_ms` は 60000 を割り切る値に限る）
2. **無効だった期間は欠測にしない。** 登録状態をロールアップの実行ごとに Store の
   `periodic_metric_registrations` へ保存する。登録が外れた metric が再び登録されたら、
   無効を記録した時刻より後の**最初の観測**から数え直す。まだ観測が無ければ埋めない
3. **埋める上限はジョブの時計で最後に完了した分**とする（`floor(now, 1分) - 1分`）。
   進行中の分は欠測に数えない。生データの最新時刻が後ろなら、そちらまで集計する
4. 初めて登録された metric は、最初の観測から数える（設置前は欠測ではない。0008 と同じ）

`air.*`（外付けデバイスのチャネル）は変えない。0008 §2.1.1 のとおり生データの最新の
分までを上限とし、停止後に期待値を作らない。ロールアップはデバイスの撤去と通信断を
区別できず、登録に相当する有効・無効の情報を持たないため。

## 3. Consequences

- collector の障害・停止が、ingest の状態や生データの保持期間に関係なく欠測率に残る
- 保守や未設置で無効にした期間が欠測率を汚さない
- 登録はロールアップの実行時にしか見えない。2回の実行の間に無効化と再有効化の両方が
  起きた場合、その無効期間は欠測として残る（緩和: 有効状態の変更は起動時の構造化ログに
  残るので、欠測率を読む側が照合できる）
- 登録が外れた状態でロールアップが最終バケットを数え直すと、そのバケットの
  `expected_count` は `NULL` になる（登録が外れた後は周期を知らないため）
- Store に周期メトリクスの登録状態を持つテーブルが1つ増える（マイグレーション 0003）

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 0008 のまま生データの最新時刻を上限にする | collector と ingest の同時停止、保持期間後の停止が記録から消える |
| 登録状態を readings_1m の最終バケットから推測する | 全 source が静かな期間には痕跡が残らず、無効期間を停止と誤認する |
| N 分より長い空白の手前では埋めない | collector の長い障害も欠測から外れる |
| `air.*` にも同じ上限を適用する | デバイスの撤去と通信断を区別できず、0008 §2.1.1 と矛盾する |

## 5. 未決事項

- `air.*` にも有効・無効の登録を持たせ、同じ規則にそろえるか（デバイス構成の管理が要る）
- 登録の変化をロールアップの実行時ではなく collector の起動・設定変更時に記録するか
