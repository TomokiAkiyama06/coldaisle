## 1. Context

2026-10-14 に 0121 の T6 を行った。検出（`stall_min_rpm` を上げた設定で `tach_stall` が上がるまで）は 3 zone とも合格した。
立ち上がりは次のとおりで、0121 の「3 回の最長が 2500 ms（窓の半分）未満」を Top と Rear が満たさなかった。

| zone | 測ったもの（PWM を書いた時刻から） | 3 回 |
|---|---|---|
| Top | `stall_min_rpm` 450 RPM 以上 | 2246 / 2136 / 2688 ms |
| Front | `stall_min_rpm` 300 RPM 以上 | 1121 / 1457 / 1008 ms |
| Rear | 0.35 の回転数の 90% 以上（0.0 の間の最低は 439〜442 RPM） | 3696 / 2915 / 2685 ms |

記録を確かめて分かったこと:

- この基板（nct6799）の driver（nct6775）は、最後の更新から 1.5 s（`HZ + HZ/2`）経った後の最初の読み取りで
  `fanN_input` を更新する。上の表は試験の側が 0.1 s ごとに読んだ値で、値は約 1576 ms ごとに変わった（中央値）。
  読む頻度が測る値を変えるので、この表は fand から見た時間ではない。Top の 3 回目は、書き込みから 1119 ms で 370 RPM、
  次の更新の 2688 ms で 684 RPM だった。450 RPM を実際に超えたのはこの間のどこかである
- 実運用で `fanN_input` を読むのは fand（1 s ごと）と収集のサービス（2.5 s ごと）だけで、更新の間隔は最大で約 2.5 s になる
  （PR #284 のレビュー）。ただし、どの読み手が読んでも、読んだ値の古さは更新の閾値の 1.5 s 未満である
- Rear は PWM 0 でも 439 RPM 以上で回り、`stall_min_rpm`（350）を下回らない。Rear の立ち上がりの時間は stall の計時に
  関わらない

そこで、試験の側から基板を読まずに、fand の trace の回転数で測り直した（2026-10-14 07:46〜07:50。収集のサービスは
動かしたまま。Top と Front を各 5 回）。0.35 を書いた tick から、trace の回転数が `stall_min_rpm` 以上になった tick までは、
10 回すべて 2 tick（1999〜2000 ms）だった。trace の回転数が変わる間隔は、ほとんどが 2 tick（ときどき 1 tick）だった。

## 2. Decision

### 2.1 `stall_window_ms` は 5000 のまま

窓は延ばさない。延ばすと、本物の stall（Fan の故障）を見つけて Max にするまでが同じだけ遅れる。

### 2.2 立ち上がりの合格の条件を「fand の周期で測った最長 + 更新の閾値 < 窓」にする

0121 §2.8 の「止まった状態から `stall_min_rpm` まで」の合格の条件を、次に置き換える。

- 時間は、試験の側から基板を読まずに、fand の trace で測る（0.35 を書いた tick から、trace の回転数が `stall_min_rpm` 以上に
  なった最初の tick まで）。回数は zone ごとに 5 回
- 5 回の最長に、driver の更新の閾値（nct6775 では 1500 ms）を足した値が、`stall_window_ms` 未満

閾値を足すのは、fand が読む値は最大でほぼ閾値の分だけ古く、ほかの読み手（収集のサービス）との位相によっては、
試験で見たより遅く見えうるため。trace で 2 tick（2000 ms）に届いたなら、回転数が実際に超えたのは 2000 ms より前で、
どの位相でも fand が見るのは 2000 + 1500 = 3500 ms より前になる。

2026-10-14 の結果は、Top・Front とも 2000 + 1500 = 3500 ms で、5000 ms 未満なので合格とする。参考に、0.1 s ごとの読み取りの
最長（Top 2688 ms）に閾値を足しても 4188 ms で、5000 ms 未満である。

基板や driver を変えたとき、または `fanN_input` を読むプロセスを増やしたときは測り直す。

### 2.3 Rear の 90% までの時間は記録だけにする

Rear の「0.0 の間の最低の回転数が 350 RPM より高い」は合否の条件として残す（2026-10-14 は 439 RPM で合格）。
「0.35 の 90% までの時間が 2500 ms 未満」は、Rear が `stall_min_rpm` を下回らず stall の計時に関わらないので、
値として記録し、合否にしない。

## 3. Consequences

### 良くなること

- 立ち上がりの時間を、fand が実際に見るもので測る。試験の側の読み取りが driver の更新を変えない
- 本物の stall を見つける速さは変わらない

### 悪くなること・その緩和

- 余裕の条件が緩む（窓の半分 2500 ms → 窓から閾値を引いた 3500 ms）。fand から見た最悪の時間（最長 + 閾値）が
  窓の内側に収まることは保つので、止まった Fan を立ち上げるときに stall と誤って判定しない
- 測り方が変わる（試験の側の 0.1 s の読み取り → fand の trace）。trace の時刻は tick の刻みなので、1 s より細かくは見えない
- Rear の応答の速さは合否から外れる。値は結果に残す

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| `stall_window_ms` を 7500 に延ばす | 今の条件のままで合格するが、本物の stall の検出が 2.5 s 遅れる |
| 0.1 s の読み取りの値に、観測した更新の間隔（1576 ms）を足す | 試験の側の読み取りが更新の間隔を変えるので、実運用の間隔（最大約 2.5 s）と違う |
| 0121 を書き直す | 決定記録は書き換えない（追記のみ）。一部を置き換える新しい記録にする |
