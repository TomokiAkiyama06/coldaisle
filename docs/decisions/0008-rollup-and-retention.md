## 1. Context

決定記録 0002 §2.8 が3段（生 / 1分 / 1時間）と列の意味を確定し、
0004 §2.9 が `5m` の合成方針を決めた。本記録はそれを**いつ・どこで・どう動かすか**を
確定する。運用の順序を間違えると復元できないデータ損失になるため、
実装のコメントではなく記録に残す。

---

## 2. Decision

### 2.1 ロールアップは未集計の範囲だけを見る。ただし最終バケットは数え直す

毎回すべてを数え直すと、保持期間ぶんの行を走査することになる。
一方で前回の最終バケットは**実行時点で途中だった可能性がある**ため、
そのバケットだけは必ず再計算する（`INSERT OR REPLACE`）。

**再計算の窓は最終バケット1つだけ。** それより古いバケットの
`expected_count` は当時の値のまま残る（決定記録 0002 §2.8 が求める性質）。

### 2.1.1 1件も届かなかった分は「0行のバケット」として作る

1分まるごと届かなかった場合、集計だけでは `readings_1m` に行が生まれない。
行が無い分は上位の集約でも数えられず、`SUM(expected_count)` が
**届いた分だけの合計**になる。その結果、1分落ちた1時間が
「欠測ゼロ」として残り、生データを消したあとは復元できない。

そこで、観測済みの範囲に空いた分を `ok_value_count = 0` / `row_count = 0` /
`expected_count = N` の行として作る。**決定記録 0002 §2.8 が分けようとした
「センサー異常」と「サンプル不着」の区別は、これが無いと成立しない。**

埋めるのは**そのメトリクスを観測し始めてから最新の分まで**。
設置前や停止後にまで期待値を作らない。

### 2.1.2 期待サンプル数は周期的なメトリクスにだけ持たせる

`sys.dropped_samples` / `sys.device_restarts` は起きたときしか書かない
（決定記録 0007 §2.4）。期待値を持たせると欠測率が無意味な値になるため、
`expected_count` は `NULL` とし、穴埋めもしない。

判定は「デバイスのチャネルに対応するメトリクスかどうか」（`coldaisle/channels.py`）。

### 2.2 1時間は1分から合成する。生データからやり直さない

`ok_value_count` で加重した平均を使う（0002 §2.8 / 0004 §2.9）。
生から数え直すと、保持期間を過ぎて消えた区間の1時間バケットが作れなくなる。

### 2.3 `5m` は表を持たず、読み出しのたびに合成する

0004 §2.9 の決定に従う。**1時間の書き込みと同じ SQL 組み立てを使う。**
別々に書くと、平均の重み付けを片方だけ直す事故が起きる。

### 2.4 削除は「1分ロールアップ済みの範囲」までしか進めない

`apply_retention()` は保持期間の境界と**1分バケットの最終位置**の
小さいほうを基準にする。

- ロールアップが一度も走っていない DB では**何も削除しない**
- 最終バケットの行も削除しない。そのバケットはまだ埋まりきっていない可能性があり、
  集計し直す前に生を消すと二度と正しくならない

ジョブは「ロールアップ → 削除」の順に実行する（`run()`）。この安全弁は、
順序を間違えた呼び出しに対する保険である。

### 2.4.1 ロールアップもメトリクスごとにループする

`WHERE ts_ms >= ?` の1本にすると主キー `(metric, ts_ms)` を使えず、
`EXPLAIN QUERY PLAN` は `SCAN readings` を返す。**毎日の差分集計が
保持期間ぶん（30日で約730万行）を毎回舐めることになる。**

しかも集計は書き込みトランザクションの中で走るため、その間ずっと
取り込み側が待たされ、`busy_timeout` を超えて落ちうる。
メトリクスごとに範囲を区切り、トランザクションも分けて短く握る。

### 2.5 削除はメトリクスごとにループする

`DELETE FROM readings WHERE metric = ? AND ts_ms < ?` を既知のメトリクスで回す。
主キー `(metric, ts_ms)` を使うため（決定記録 0002 §2.4）。
`WHERE ts_ms < ?` の1本は全走査になる。

メトリクスの列挙も全走査を避ける（0004 §2.11 と同じ再帰 CTE）。

### 2.6 `VACUUM` は定期実行しない

削除で空いたページは以降の挿入が再利用するため、**定常状態でファイルは
増え続けない。** `VACUUM` が要るのは「縮めたい」ときだけで、実行中は
書き込みを止め、一時的に元と同じだけの空き容量を要求する。

CLI の `--vacuum` として手動で用意し、自動実行はしない。

### 2.7 ロールアップは取り込みデーモンの中で動かさない

`coldaisle-rollup` を別プロセスとして cron / systemd タイマーから呼ぶ
（配線は #26）。取り込みループに集計と `VACUUM` を同居させると、
**取り込みが遅れる理由を増やす。** 取り込みは止めない、が最優先。

WAL なので、取り込みと並行して読み書きしても互いをブロックしない。

### 2.8 日次CSVは従来の実ファイルに合わせる

`~/server_sensor_logs/` に残っていた実際の出力（2026-08-23 / 24）に合わせた。
**推測ではなく実物から確定した。**

```text
timestamp,room_temp,room_humidity,front_intake,gpu_intake,gpu_exhaust,top_exhaust,rear_exhaust
2026-08-23T20:16:40,24.5,60.0,24.31,23.94,24.0,24.06,24.19
2026-08-23T20:35:31,,,24.75,24.31,25.25,24.5,24.62
```

| 項目 | 決定 |
|---|---|
| 列名 | **デバイスのチャネル名**（`air.` を付けない）。列順も従来どおり |
| 時刻 | ローカル時刻の ISO8601。**秒まで・オフセット無し** |
| 取得できなかった値 | **空欄**。実ファイルにも `-127.00` / `85.00` は1件も無い |
| `sys.*` メトリクス | **書かない。** 従来の列だけを保つ |
| 日境界 | ローカル時刻。タイムゾーンは設定から受け取る |

`ok` でない値を数値として書かないのは、表計算のグラフと平均に
センサーの人工物がそのまま乗るため。値が要るときは SQLite を見る
（品質フラグごと残っている）。

チャネル名とメトリクス名の対応は `coldaisle/channels.py`（レイヤ横断）に1つだけ置く。
取り込みが保存の向きに、CSV が復元の向きに使う。逆写像は導出する。

### 2.8.1 `5m` の合成は入力をバケット境界へ広げ、出力を要求範囲で絞る

要求の開始が5分境界に揃っていない場合（12:02 など）、先に1分行を絞ると
12:02〜12:04 だけの平均が「12:00 のバケット」として返る。**途中までの値が
完全なバケットに見える。**

入力はバケット境界まで広げ、出来上がったバケットを要求範囲で絞る。
返すバケットは常にその5分ぶん全体から作られる。範囲に入らない端のバケットは返さない。

（SQLite の `HAVING` は別名ではなく元の列を先に解決するため、
絞り込みでは式を書き直す必要がある。）

### 2.9 `expected_count` は直近の起動バナーの `interval_ms` から出す

複数デバイスは v1 の想定外（要件 N-04）。起動バナーを受け取れていなければ
`NULL` とし、そのバケットの欠測率は行数を母数にした下限値になる（0002 §2.8）。

## 3. Consequences

### 良くなること

- 1日ぶんの読み出しで **raw 34.5ms → 1m 1.8ms（実測19倍）**。
  ダッシュボードが期間に応じて粒度を選べる
- 集計前の生データが消えない。ジョブの順序を間違えても壊れない
- CSV が従来の資産（既存ファイル・既存の読み取りスクリプト）と互換

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 最終バケットの生データが1周期ぶん残る（2.4） | 実運用では次の実行で消える。保持期間に対して無視できる |
| ロールアップの実行が別プロセスに依存する（2.7） | #26 で systemd タイマーとして配線する。未実行なら削除も進まないので、データが消えるより安全側に倒れる |
| `VACUUM` しないとファイルは縮まない（2.6） | 定常状態では増えもしない。縮めたいときに手で実行する |
| CSV に `suspect` の値が出ない（2.8） | 正本は SQLite。品質フラグごと残っている |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 毎回すべてのバケットを数え直す | 保持期間ぶんの行を毎回走査する（2.1） |
| 1時間を生データから直接集計する | 消えた区間の1時間バケットが作れない（2.2） |
| `readings_5m` を作る | 真の粒度が4つに増える。決定記録 0004 §2.9 で却下済み |
| 削除を1本の `DELETE ... WHERE ts_ms < ?` で行う | 主キーを使えず全走査になる（2.5、0002 §2.4） |
| 削除のたびに `VACUUM` する | 書き込みを止め、同容量の空きを要求する。定常状態では不要（2.6） |
| ロールアップを取り込みデーモンに同居させる | 取り込みが遅れる理由を増やす（2.7） |
| CSV の列名をメトリクス名（`air.room`）にする | 従来の出力と互換でなくなる。既存ファイルは `room_temp`（2.8） |
| CSV に `-127.00` などをそのまま書く | 表計算のグラフと平均に人工物が乗る。実ファイルにも1件も無い（2.8） |
| 欠落した分をバケットとして作らない | 通信断が上位の集約から消え、生を消したあとは復元できない（2.1.1） |
| すべてのメトリクスに同じ期待値を持たせる | 事象メトリクスの欠測率が無意味になる（2.1.2） |
| ロールアップを1本の `SELECT ... GROUP BY metric` で行う | 主キーを使えず全走査。書き込みロックを握ったまま数百万行を舐める（2.4.1） |
