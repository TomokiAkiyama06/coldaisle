## 1. Context

2026-11-08 の負荷の段の試験（fand の auto のまま）と 0182 で、Fan が動いた区間を Dataset に残せるようになった。ところが、学習した
model は Fan の効果をまだ学べていない。test の `action_changed` の 152 件で、記録の action 列の予測と hold の予測の MAE がほぼ同じだった。

原因は 0182 §2.5 に書いたとおり、**fand の auto は 3 zone をそろえて動かす**ことにある。試験の区間では Front と Rear の `effective` は
全段で同じ値で、Top もほぼ同じだった。zone ごとの列が強く相関するので、普段の運転を何日採っても zone ごとの効果を分けられない。
Learned MPC（#86）は zone ごとに Demand を選ぶので、zone ごとの効果が分からない model では、どの zone を動かすべきかを決められない。

0174 は、風量の特性（回転数の掃引・応答の行列・EFU）を「測らない」と決めた。理由は、風量を直接測る機器が無く、熱の応答から
推すにも長い掃引と条件の管理が要ることだった。本記録で要るのは**風量ではなく温度への効き**で、0153 §2.5 の応答の行列の一部で足りる。
0153 の手順と安全の決まりは 0174 の後も有効なので、それを使う。

## 2. Decision

### 2.1 何をするか

- 0153 §2.5 の応答の行列の手順で、**負荷 (i)（GPU 300 W だけ）について 1 回**、次の段を行う
  `R, F+, R, Rr+, R, T+, R`（R = 3 zone とも 0.60、F+ / Rr+ / T+ = その zone だけ 0.90）。`−`（0.35）の段と `All+` は行わない（§5 の 1）
- 各段の長さは 0153 §2.5 の落ち着きの判定（最長 20 分）ではなく、**固定の 10 分**とする（§5 の 2）。目的は Dataset の
  ための変化で、応答の値を確定することではない
- 結果は Thermal Dataset v2（0087 / 0181 / 0182）の元のデータとしてだけ使う。`air-balance.yaml` には写さない。EFU は求めない。
  `coldaisle-airflow-characterization` の解析は、行うなら参考に残すだけで、承認の対象にしない

### 2.2 測定中の安全（0153 §2.2 をそのまま使う）

- Demand は `coldaisle-control manual --front --rear --top --lease`（人の uid）で決め、Reactive Guard と Critical Safety を通す。
  sysfs・hwmon へ試験の側から書かない。本番の設定のまま行い、試験専用の設定・floor を外す設定を使わない
- lease は段ごとに「段の長さ + 5 分」で送り直す。所有者が離れて送り直しが止まれば `AUTO` に戻る
- floor・`forced_max` が掛かった tick は、そのまま Dataset に残してよい（Dataset は `effective` を記録するので、掛かった値が action に
  なる）。0153 の「その段を捨てる」は応答の値の決まりで、本記録では使わない
- **中止の基準**は 0121 §2.1（0130 の後）: `cpu.package` 88 °C・`gpu.0.core` 85 °C・`board.connector_12v2x6` 70 °C。どれかに届いたら
  負荷を止めて `coldaisle-control max`。Critical Safety が `DEGRADED` / `EMERGENCY` になった・fault が出たら、負荷を止めて原因を見る。
  fand の挙動がおかしければ `systemctl stop coldaisle-fand`（BIOS へ返す）
- 負荷: GPU の電力の上限を 300 W にし、行列計算で上限に張りつかせる。終わったら 600 W に戻す（上限の変更は root。所有者が行う）。
  負荷のスクリプトは SIGTERM で同期してから終わる（0121 T4）。CPU の負荷はかけない
- GPU の Fan は 0130 の曲線のまま（固定の duty にしない）
- **所有者が在宅で**、開始・各段の切り替え・終了を行う。操作のスクリプトは事前に内容を示し、所有者が承認してから走らせる。
  スクリプトがするのは `coldaisle-control manual` / `auto` / `max` と負荷の開始・停止と、段の時刻の記録だけ
- 試験の期間中は較正を変えない。LLM は関わらない（ルール 1 / 8）

### 2.3 時間

R・F+・R・Rr+・R・T+・R の 7 段 × 10 分 = 70 分。前後に、負荷を掛けて auto で落ち着かせる 10 分と、負荷を止めて auto で冷やす 15 分を
足して約 1 時間 40 分。

### 2.4 試験の後

- 試験の日を含む期間で Dataset v2 を作り、学習・offline 評価（0172）を回す。zone ごとの係数と、評価の `action_effect`
  （記録の action 列と hold の予測の差）を見る
- 結果は #84 に残す。効果が見えなければ、`−` の段や別の負荷（§5 の 1）を足すかを、新しい記録で決める

## 3. Consequences

良くなること:

- zone ごとに独立した変化を持つデータが初めて採れる。Thermal Model が zone ごとの効果を学べるか、を実データで確かめられる
- 0153 の手順と安全の決まりをそのまま使うので、新しい制御の経路も設定も増えない

悪くなること（と緩和策）:

| 悪くなること | 緩和策 |
|---|---|
| manual の間は fand の auto の判断で Fan が動かない | Guard と Critical Safety は通る。lease が切れれば `AUTO` に戻る。中止の基準で `max` |
| 1 回・1 つの負荷・`+` の段だけでは、zone の効果の一部しか見えない | 目的は「分けて学べるか」の確かめ。足りなければ §2.4 の後で足す |
| 固定の 10 分では温度が落ち着ききらない段がある | Dataset は過渡の区間も example にできる（window と horizon で過渡を学ぶ）。応答の値は確定しない |
| GPU の電力の上限の変更に root が要る | 所有者が行う（0121 T4 と同じ）。戻し忘れを防ぐため、手順の最後に 600 W へ戻す行を置く |

## 4. 却下した代替案

| 案 | 却下した理由 |
|---|---|
| 0153 §2.5 の全段（`−` と `All+`・3 つの負荷・2 回）を行う | 1 回で約 5 時間 × 負荷 3 つ × 2 回。0174 が退けた負担に近い。まず「分けて学べるか」を小さく確かめる |
| 試験をせず、3 zone を 1 つの Demand として扱う設計に変える | Learned MPC の zone ごとの最適化（#86）を捨てることになる。試験が安く済むなら先に確かめる |
| fand の auto の曲線に zone ごとのずれを入れて普段から分ける | 制御の側の変更（Baseline の曲線・0119）で、学習データのために運転を変えない |
| CALIBRATION モードを使う | 0153 §2.2 のとおり MANUAL で足りる。新しい入口を足さない |
