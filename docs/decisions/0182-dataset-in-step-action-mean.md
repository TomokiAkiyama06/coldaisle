# 決定記録 0182: Thermal Dataset v2 の step の値を区間の時間平均にし、区間の中の変化は幅の上限で除く（ramp で動く Fan の区間を捨てない）

## 1. Context

2026-11-08 13:57〜15:21 に、fand の auto のまま負荷だけを段階的に変える試験を行った（GPU 連続・GPU 5 s / 5 s の断続・CPU 全スレッド・
GPU 60 s / 60 s の断続と、それぞれの冷却。中止なし）。Fan の Demand は 0.40〜1.00 の範囲で動き、学習に要る変化は採れた。
ところが、本番の DB の写しの 11-02〜11-08 で Dataset v2 を作ると、その変化がほとんど残らない。

| spec（窓 30 s・5 s・anchor 30 s・特徴量 6） | example（7 日） | 試験の 90 分の anchor 候補 180 のうち残ったもの | `in_step_change` の除外 |
|---|---|---|---|
| step 10 s × 12 | 10,138 | **26** | 8,826 |
| step 2 s × 60 | 10,547 | 37 | 8,417 |
| step 1 s × 60（horizon 30 / 60 s） | 14,841 | 73 | 4,164 |

原因は 0087 §2.3 の規則と fand の運転の組み合わせにある。

1. **fand の auto は ramp で毎 tick（1 s）Demand を少しずつ動かす。** 試験の区間の 10 s の窓 540 のうち 161（30 %）で `effective` が動き、
   幅は p90 で 0.09、p99 で 0.25（Top は最大 0.55）。丸めの揺らぎではなく、本物の ramp である
2. **0087 §2.3 は区間の中で 1 tick でも値が違えば example を作らない。** 0087 の緩和策は「tick の周期を `step_ms` と同じに選べば起きない」だが、
   step 1 s でも tick の時刻の揺れで区間に 2 つ目の tick が入り、半分以上が除かれる。step 1 s で horizon 120 s にすると列が 531 になり、
   0048 の構造上限 512 列を超える

つまり、**Fan が動いた区間ほど Dataset に残らない。** 普段の運転を何日採っても、Fan の効果を学べない。

試行の評価（`coldaisle-thermal-evaluate`）も、試験を含む test の日で `action_changed` の example が 2 件しかなかった。

## 2. Decision

### 2.1 step `k` の値は、区間 `[t_a + k × step_ms, t_a + (k + 1) × step_ms)` の `effective` の時間平均

- 区間の中の時刻 `t` の値は、`t` 以前で直近の ControlTick の `effective`（0087 §2.1 の as-of と同じ規則）とする。tick と tick の間は
  直前の値が掛かっていた（区分的に一定）とみなす
- step の値は、その区分的に一定な値を区間の長さで重み付けして平均したもの（zone ごと）。区間の開始の as-of の tick は 0087 §2.2 の
  鮮度の検査を通っていること（変えない）
- 区間の中の tick がすべて同じ値なら、平均は開始の as-of の値と**同じ値**になる（0087 で作れた example の action の値は変わらない）
- 記録する `source_ts_ms` / `source_tick_id` は、今のとおり開始の as-of の tick とする

理由: 学習する model（0048 の ridge・0150 の反実仮想 Thermal Model）は action に線形である。熱の応答の時定数（数十秒〜数分）より
短い step の中では、出力への効き方は「step の中で掛かった Demand の積分」でほぼ決まる。step の中の時間平均は、その積分を
step の長さで割ったもので、MPC が「step の間は保つ」とした値（`ActionPlan.held`、0052 §2.3）と同じ尺度になる。
0087 が平均を退けた理由「実際には一度も掛からなかった値を作る」は、平均が**掛かった値の積分**を表すこと、
§2.2 の上限で区間の中の幅を抑えることで、誤差の上限が spec に見える形にした。

### 2.2 区間の中の幅の上限 `action_max_in_step_range`（spec の必須の欄。既定値なし）

- zone ごとに、区間の中の tick の `effective` の最大と最小の差（開始の as-of の値を含む）を取る。どれか 1 つの zone・どれか 1 つの
  step で上限を**超えた**ら、その example を作らない。除外の理由は今の「区間内の変化」（`in_step_change`）に数える
- 値は `0 ≤ action_max_in_step_range ≤ 1`。**0 を渡すと 0087 §2.3 と同じ example の集合になる**（幅 0 = 区間の中で値が変わらない）
- spec の欄なので manifest に残り、学習・評価の入口は今のとおり spec を照合する

理由: 平均で表せるのは、区間の中の変化が熱の応答に比べて小さい間だけである。上限を明示の値にすれば、どこまでを「保った」と
みなしたかが Dataset ごとに残る。0181 の `anchor_stride_ms` と同じく、既定値を置かずに渡させる。

### 2.3 example に区間の中の幅を残す

- 各 example に、zone ごとの「全 step を通した区間の中の幅の最大」を記録する（欄の名前と置き場所は実装の PR で決める）
- 0172 の評価の層（`action_changed` / `action_held` と並べて）で、幅の帯ごとの誤差を見られるようにする。gate に入れるかは §5

### 2.4 変えないこと

- 格子・horizon・step の番号（0087 §2.4 / §2.5）、`prior_action`（§2.7）、鮮度・連続・再起動・欠番の検査（§2.2）
- Learned MPC が出す plan（step の間は保つ）と、model artifact の形（0079）
- 0181 の anchor の間隔・学習の入口の上限

### 2.5 本記録では解けないこと（記録だけ）

試験の区間では、Front と Rear の `effective` は全段で同じ値で、Top もほぼ同じだった（fand の auto は温度に応じて 3 zone をそろえて
上げる）。この運転のデータだけでは、**zone ごとの効果を分けて学べない**（列が強く相関する）。本記録は「動いた区間を捨てない」
ことだけを決める。zone を分けた変化は、回転数の掃引・応答の行列（0153）のような、zone ごとに Demand を変える測定で採る。

### 2.6 試験（すべて `-m "not hardware"`）

- 区間の中の値がすべて同じ example は、平均が開始の as-of の値と一致する
- 区間の途中で値が変わる example は、時間で重み付けした平均になる（tick の間隔が不揃いな場合を含む）
- 幅が上限ちょうどの example は作り、超えた example は `in_step_change` に数える
- `action_max_in_step_range = 0` の Dataset の example の集合と値が、0087 の規則で作ったものと同じ
- 区間の中の幅の記録が、zone ごとの最大と一致する

## 3. Consequences

良くなること:

- Fan が ramp で動いた区間を Dataset に残せる。普段の運転と負荷の試験から、Fan の効果を学ぶ材料が増える
- どこまでを「保った」とみなしたかが、spec の値として Dataset ごとに残る

悪くなること（と緩和策）:

| 悪くなること | 緩和策 |
|---|---|
| step の中で値が動いた example の label は、厳密には「保った」場合の結果ではない | §2.2 の上限で幅を抑え、§2.3 の記録で幅の帯ごとの誤差を評価で見る。上限 0 で 0087 と同じ集合に戻せる |
| spec の欄が増え、manifest と digest が変わる（既存の Dataset v2 とは別物になる） | 学習・評価の入口は spec を照合するので、混ざらない。既存の Dataset は作り直す（実データの Dataset はまだ試行だけ） |
| zone ごとの効果は、この変更だけでは分けられない | §2.5 のとおり、zone ごとの測定（0153）で補う。それまでの model の zone ごとの係数は、評価で確かめるまで信用しない |

## 4. 却下した代替案

| 案 | 却下した理由 |
|---|---|
| 0087 のまま、step を 1 s にする | 試験の区間で 73 / 180 しか残らない（tick の時刻の揺れ）。horizon 120 s では列が 531 で、0048 の上限 512 列を超える |
| 開始の as-of の値を step の値にし、区間の中の変化に許容幅を置く | p90 で 0.09 動く区間では、開始の 1 点が区間を代表しない。幅を許すなら、値も区間を表すもの（平均）にしたほうが label と合う |
| tick の数で単純に平均する | tick の間隔が揃わないと、短い間隔の値に重みが偏る。時間で重み付けするほうが「掛かった量」を正しく表す |
| fand の ramp を変える・試験の間だけ Fan を段で動かす | 制御の側の変更で、Dataset の規則の問題を解くために制御を変えない。zone ごとの段の測定は §2.5 のとおり別に行う |
| 区間の中の軌道（tick ごとの値）をそのまま action 列に入れる | 列が tick の数だけ増え（1 s で 120 step × 3 zone）、0048 の上限を超える。MPC の plan の形（step の間は保つ）とも合わない |
