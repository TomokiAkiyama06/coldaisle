## 1. Context

#23 は当初「ダッシュボード内のチャットパネル」だったが、決定 D-4 で
**coldaisle 専用のチャットUIは作らない**ことになった。チャットは Workspace 側が持つ。

残るのは3つ。

1. Workspace のチャットから**呼べる形**でツールを公開する
2. **どのツールを呼んだか**を可視化できるようにする
3. **「提案であり制御は行わない」**という位置づけを明記する

ツールの実体は #22 で作った（`ai/tools.py`）。**プロセスの中にしか無い。**
Workspace は別のシステムなので、このままでは呼べない。

---

## 2. Decision

### 2.1 窓口は L2 に置き、実体は**合成の起点が渡す**

`api/`（L2）が `ai/`（L3）を import すると、レイヤ間の依存が逆流する
（AGENTS.md「下位レイヤが上位レイヤを import しない」）。

L2 は `Tools` プロトコル（`guidance` / `definitions` / `call`）だけを知り、
実体を渡すのは `coldaisle/server.py`。`daemon.py` / `report.py` と同じ、
合成のためだけの入口である。

```text
uvicorn coldaisle.server:app   # 読み取りAPI + ツールの窓口
uvicorn coldaisle.api:app      # 読み取りAPI のみ（そのまま使える）
```

入口を2つ残すのは、**L2 だけで動くことを保てる**ようにするためである。
テストも `create_app()` をそのまま使える。

### 2.2 **GET だけ**で公開する

ツールは読み取り専用なので、**読み取り専用であることが HTTP メソッドに出る**
（api-contract §1「v1 に POST / PUT / DELETE は存在しない」）。

引数はクエリ文字列で受け、型の変換は各ツールの引数モデル（Pydantic）に任せる。
JSON 本体を受け取る口を作ると、そこだけ POST になり、契約の
「書き込み系は存在しない」が「存在するが書き込まない」に変わる。
**方式で保証できるものを、約束に落とさない。**

### 2.3 呼び出しの記録を `meta` に返す

```json
{"meta": {"tool": "get_stats", "arguments": {...}, "ok": true, "ts_ms": 0,
          "elapsed_ms": 3, "read_only": true, "advisory": true},
 "result": {...}}
```

#23 の「どのツールを呼んだかを可視化（回答の根拠が追えること）」がこれである。
Workspace 側でそのまま表示できる形にし、**組み立て直させない**。

### 2.4 **存在しないツール名や壊れた引数でも 200**

`meta.ok` を `false` にし、`result.error` に理由を入れる。

**モデルが寄こす名前と引数は入力データであって、呼び出し側の誤りではない。**
4xx にすると、Workspace 側は会話を続けるために例外を毎回ツール結果へ
翻訳することになる。`ToolRegistry.call()` が例外を投げない設計（0015）と同じ理由で、
HTTP の層でも落とさない。

### 2.5 位置づけは**注意書きと説明文の両方**に書く

| 置き場所 | 誰が読むか |
|---|---|
| `GET /api/v1/tools` の `guidance` | 呼び出し側が system prompt に入れる |
| 各 description の `（読み取り専用。制御は行わない）` | モデルが必ず見る |

説明文への追記は**組み立て時に一括で付ける**。1つずつ書くと、
ツールを足したときに書き忘れる。

この層には実行する手段が無い。**「実行しておきました」と書かれた時点で嘘になる。**

## 3. Consequences

### 良くなること

- Workspace のチャットが coldaisle のデータを読める（#23 の残り）
- 回答の根拠が追える（2.3）
- 窓口が増えても**書き込み系は生えない**（2.2。テストが OpenAPI 全体を見張る）
- L2 が L3 を知らないままである（2.1。テストが import を見張る）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 起動の入口が2つになる | 既定は `coldaisle.server:app`。`api:app` は L2 単体の確認用と位置づける |
| 引数がクエリ文字列に限られる | いまのツールの引数はすべてスカラー。配列が要るなら契約の変更として扱う |
| 認証が無いままツールを公開する | `127.0.0.1` 限定は変わらない（api-contract §5）。外部公開は認証の設計とセット |

---

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| `api/` から `ai/` を import する | 依存が逆流する（2.1） |
| POST でツール呼び出しを受ける | 契約の「書き込み系は存在しない」が方式で保証できなくなる（2.2） |
| 存在しないツールに 404 を返す | Workspace 側が例外を結果へ翻訳し続けることになる（2.4） |
| coldaisle 側でチャットの会話ループを持つ | 決定 D-4 でチャットは Workspace 側と決めた。会話の状態を2か所に持たない |
| 注意書きを system prompt にだけ書く | 呼び出し側が入れ忘れると、モデルには何も伝わらない（2.5） |
| 既存の `/api/v1/*` を関数定義に自動変換する | 集計の上限や `<data>` タグ付けは L3 の判断（0015）。API の形とは別物 |
