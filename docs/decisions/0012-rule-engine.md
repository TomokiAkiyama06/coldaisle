## 1. Context

要件 §6.4 が状態機械（`OK → PENDING → FIRING → RESOLVED`）とヒステリシスを、
決定記録 0007 §5 未決3 が「ルールエンジンをどのプロセスに置くか」を残していた。

**AI は一切関与しない決定論的レイヤ**であり（Issue #18）、同じ入力からは
必ず同じ判定が出ることが前提になる。

## 2. Decision

### 2.1 取り込みと**同じプロセス・同じ時計**で動かす（0007 §5 未決3 の決定）

`coldaisle-daemon` の中で、サンプルを保存した直後に評価する。

**組み立てる場所は `coldaisle/daemon.py`（パッケージ直下）。** `ingest/`（L0）の
中に置くと、取り込み層がルールエンジン（L2）を import することになり、
レイヤの依存が逆向きになる（AGENTS.md「レイヤ間の依存は一方向」）。
合成の起点は層の部品ではないので、`clock` / `channels` / `metrics` と同じく
層の外に置く。

継続時間ベースのルール（FR-401〜409）は、**ホスト受信時刻の進み方に依存する。**
別プロセスの実時計で判定すると、圧縮再生でルールを検証できない
（決定記録 0007 §2.11）。同じ時計を共有できるのは同じプロセスの中だけである（#42）。

### 2.2 状態機械を駆動する時刻の定義

**時間軸は1本（ホスト受信時刻。決定 D-05）。** その1本を、状況によって
2つの出どころから読む。

| 状況 | 読む先 | 理由 |
|---|---|---|
| サンプルがある | そのサンプルの `ts_ms` | 処理が追いつくまでに時計は進む。`clock.now_ms()` で評価すると、**一括再生では継続時間の条件が一瞬で満たされる** |
| サンプルが無い（ティック） | `clock.now_ms()` | 「来ていないこと」は現在時刻でしか測れない |

**評価時刻は巻き戻さない。** 処理が滞ると前者が後者より古くなるため、
`max(これまで, 今回)` で単調にする。単調でないと経過時間が負になり、
継続時間の判定が動かなくなる。

`clock.now_ms()` だけで駆動する案は採らなかった。一括投入（`--bulk`）では
読み取りが先に走り切って時計が終端まで飛ぶため、**全ルールが即座に発火する。**
サンプルの時刻で評価すれば、再生でも実運用と同じ判定になる。

### 2.3 ソースは別スレッドで読み、空振りのたびに時刻ベースを評価する

`SENSOR_FAULT`（FR-401）は「30秒サンプルが無い」ことで判定する。
**同じスレッドでソースを読むと、待機中は何もできず、サンプルが来ないこと自体を
検出できない。** 気づけるのは再開した後になり、critical の意味がなくなる。

- 読み取りスレッドはソースを回して詰めるだけ。**DB には触らない**
  （接続はスレッド間で共有しない。決定記録 0004 §2.8）
- 受信時刻は**受け取った瞬間に確定して**メッセージと一緒に運ぶ（決定 D-05）
- 待ち受けに時間切れ（既定1秒）を設け、空振りのたびに時刻ベースを評価する

**ティック間隔は無音の閾値より十分短くする。** 圧縮再生では閾値を超えてから
復帰するまでの猶予も圧縮される（速度30なら 30秒の無音は実時間1秒）。

### 2.4 条件が成立した時点で行を作る。発火に至らなければ消す

`pending` の行を先に作り、継続時間を満たしたら `firing` にする。
「条件はいつ成立し、継続時間の要件をいつ満たしたか」を後から検証できる
ようにするため（決定記録 0002 §2.9）。閾値を実測で見直す #19 で
この差分が判断材料になる。

**継続時間に届かなかった揺らぎは消す。** 残すと、本物の発火が埋もれる。

### 2.5 ヒステリシス。発火と解除で別の閾値を使う

成立中は解除の閾値を越えるまで成立し続ける。1つの閾値で判定すると、
境界付近を往復するデータで発火と解除を繰り返す（要件 §6.4）。

設定の読み込み時に**解除が発火の内側にあること**を検査する。
外側にあると、発火した瞬間に解除条件も満たしてしまう。

### 2.6 `PROBE_CHANGED` は**続く状態**。不一致が解けるまで発火したまま

`PROBE_CHANGED` が意味するのは「ROM ID が変わった瞬間」ではない。
**「較正のオフセットが、いま間違ったプローブに対応している」という、
人が直すまで続く状態**である。

差し替えたまま較正し直さなければ、以降のすべての測定値に誤ったオフセットが
乗り続ける。ΔT の判定（`d.intake_rise` など）は数℃の話なので、これは実害になる。

したがって条件を**不一致の継続**として定義する。

```text
条件: 起動バナーの ROM セット ≠ `device_sensors` に記録された ROM セット
```

- 差し替え直後から `firing`
- 人が較正をやり直して**記録側を更新する**と、次の起動バナーで一致して `resolved`
- 承認（ack）の仕組みを別に作らなくても、状態機械の枠組みにそのまま乗る

**不一致のあいだ、記録側を上書きしない。** 上書きすると次の瞬間に一致してしまい、
アラートが自分で消える。記録された ROM は「較正が対応している構成」であり、
人が直すまでの基準として残す（`record_hello(replace_sensors=False)`）。

記録に無いチャネル（増設）は不一致としない。

#### イベントと状態を取り違えない

**気づいてほしいものほど早く消える**のが、この取り違えの怖いところ。

| 種類 | 例 | 扱い |
|---|---|---|
| 状態 | `PROBE_CHANGED` / `SENSOR_MISSING` / `RECIRCULATION` | 条件が続く限り `firing` |
| 真のイベント | デバイス再起動の検出（FR-106） | 記録は残すが**アラートにしない** |

デバイス再起動は本当に点の出来事である（再起動したこと自体は元に戻らない）。
`sys.device_restarts` として記録するに留め、アラートの対象にしない
（決定記録 0007 §2.4）。

### 2.5.1 無音の基準は「いつから見ているか」

`SENSOR_FAULT` は最初のサンプルを待たない。**起動時からデバイスが無い場合が
いちばん重要**であり、最初のサンプルを基準にする実装だと、その場合に永久に鳴らない。

監視を始めた時刻（`Engine.begin()`）を基準にする。

### 2.6.1 未解決のアラートは引き継ぐ

デーモンを再起動したとき、同じ事象で行を作り直さない。
作り直すと、**1つの故障が再起動の回数だけ履歴に並ぶ。**
`pending` / `firing` の行があればそれを引き継ぐ。

**起動時に DB から状態を取り込む**（条件の成立を待たない）。取り込まないと、
条件が解けていても解除できず、**`firing` のまま永久に残る。**
逆にまだ異常なら、同じ事象の行がもう1つ増える。

### 2.7 `SENSOR_FAULT` は1件届いただけで解除しない

再開してから `clear_s`（既定10秒）だけ届き続けたら解除する。
断続的な接続で発火と解除を繰り返すと、通知が意味を失う。

### 2.8 派生値が計算できない間、そのルールは黙る

`d.intake_rise` は両方の測定値が `ok` のときだけ計算される（決定記録 0009 §2.2）。
計算できない間、そのルールは何も言わない。

**疑わしい値から作った派生値で判定しない。** `-127.00` から室温を引いた値は
「再循環が無い」ように見え、故障を隠す。センサーが壊れていることは
`SENSOR_MISSING`（FR-402）が別に伝える。

### 2.9 未知のメトリクスは組み立て時に落とす

ルールが参照するメトリクス名が `config/metrics.yaml` に無ければ、
エンジンの構築時に失敗させる。綴り違いは**「一度も成立しないルール」として
静かに通る**のがいちばん危ない。

### 2.10 閾値はすべて `config/rules.yaml`。値は暫定

コードに埋めない（AGENTS.md ルール6）。**実測で確定するのは #19。**
その旨をファイル冒頭に書き、テストで存在を確かめている（受入基準）。

### 2.3.1 待ち行列は**有界**。溢れたら古い側を捨てて数える

読み取りスレッドとの待ち行列は 256 件で上限を切る。無界だと、保存が詰まった
ときにメモリが際限なく伸びる（NFR-05: 常駐100MB未満）。

満杯のときは**古い側を捨てて新しい方を入れる**（決定記録 0004 §2.6 と同じ理由。
監視で欠けてはならないのは直近）。ブロックする案は採らない。シリアルでは
読み取りが止まると OS のバッファが溢れ、**どのみち失われるうえに気づけない。**

**黙って捨てない。** 捨てた数は `sys.queue_drops` として残し、
`/api/v1/health` の `queue_drops_1h` に出す。捨てるのは読み取りスレッドだが、
DB を触るのは取り込みスレッドだけなので（0004 §2.8）、次のサンプルに乗せて書く。

### 2.4 同じ `(metric, ts_ms)` は**無視する**（0004 §2.7 を改める）

決定記録 0004 §2.7 は「拒否する（主キー違反を送出）」としていた。
**`INSERT OR IGNORE` へ改める。**

- **再生は冪等であるべき。** 同じ CSV を2回流しただけで取り込みが止まるのは困る
- 上書き（`INSERT OR REPLACE`）はしない。0004 §2.7 の「観測が黙って消える」
  という懸念はそのまま有効である。**先に入った値を残す**
- **黙って捨てない。** 書けた行数と渡した行数の差を数え、ログと
  終了時のまとめに出す（`duplicates`）

### 2.3.2 ソースが落ちたことを正常終了と区別する

`Source.stream()` が例外を投げたら、**読み取りスレッドから主スレッドへ渡して
送出し直す。** 正常終了（尽きた）と同じ扱いにすると、`main()` が 0 を返し、
**途中で死んだ監視をサービス管理（systemd）が再起動できない。**

これは「1サンプルのパース失敗でプロセスを落とさない」（AGENTS.md）とは別の話。
1件の失敗は続ける。**入力そのものが失われたら止まって知らせる。**

### 2.3.3 起動バナーも受信時刻で記録する

待ち行列に積まれている間に時計は進む。処理時刻で記録すると、起動バナーの
記録と `PROBE_CHANGED` の時刻が、**その後に処理したサンプルより後になる**ことがある。

## 3. Consequences

### 良くなること

- **圧縮再生でルールを検証できる**（#42 の受入基準）。`recirculation` を
  速度60で流すと `RECIRCULATION` が5分の継続を満たして発火し、
  `dropout` では `SENSOR_FAULT` が鳴る。実時計で判定していたら一度も鳴らない
- 正常なデータ（`idle`）では1件も鳴らないことをテストで固定した。
  **鳴りっぱなしのアラートは、鳴らないアラートと同じくらい役に立たない**
- 閾値と継続時間が設定に集まり、#19 の実測結果を反映する場所が1つになった

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 取り込みプロセスにスレッドが1つ増える（2.3） | 読み取りスレッドは DB に触らない。落ちても取り込みループが記録して続く |
| ルールの評価が取り込みを遅らせうる | 評価は同期だが軽い（`RAPID_RISE` の傾きだけ DB を引く）。失敗しても取り込みは止めない |
| API プロセスからはルールを評価しない | アラートは DB 経由で読む（FR-304）。二重評価による食い違いを避ける |
| 圧縮再生ではティック間隔の調整が要る（2.3） | 実運用は速度1・ティック1秒で、比率は問題にならない |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| ルールエンジンを別プロセス（API 側）に置く | 継続時間の判定が実時計になり、圧縮再生で検証できない（2.1、0007 §2.11） |
| 同じスレッドでソースを読む | 待機中に評価できず、サンプルが来ないこと自体を検出できない（2.3） |
| 発火してからアラート行を作る | 「いつ成立したか」が残らない。#19 の判断材料が失われる（2.4、0002 §2.9） |
| 揺らぎの `pending` も履歴に残す | 本物の発火が埋もれる（2.4） |
| 発火と解除に同じ閾値を使う | 境界付近を往復するデータでフラッピングする（2.5） |
| `PROBE_CHANGED` を点の出来事として即座に解決する | 発生中のアラートから即座に消える。**静かに間違ったまま運用が続くのを防ぐ仕組みが、まさに静かに消える**（2.6） |
| 不一致のあいだも記録側の ROM を上書きする | 次の瞬間に一致し、アラートが自分で消える（2.6） |
| 待ち行列を無界にする | 保存が詰まるとメモリが際限なく伸びる（2.3.1、NFR-05） |
| 満杯のときブロックする | シリアルでは OS のバッファが溢れ、どのみち失われるうえに気づけない（2.3.1） |
| 重複を主キー違反として拒否する | 同じ CSV を2回流しただけで取り込みが止まる。再生は冪等であるべき（2.4） |
| 重複を上書きする | 同じ時刻に2つの値が観測された事実が消える（2.4、0004 §2.7） |
| 評価を `clock.now_ms()` だけで駆動する | 一括投入で時計が終端まで飛び、全ルールが即座に発火する（2.2） |
| 最初のサンプルを待って無音の基準を立てる | 起動時からデバイスが無い場合に永久に鳴らない（2.5.1） |
| 起動時に DB の未解決アラートを読まない | 条件が解けていても `firing` のまま残り、同じ事象の行が増える（2.6.1） |
| ソースの失敗を正常終了として扱う | 途中で死んだ監視を再起動できない（2.3.2） |
| 疑わしい値でも派生値を計算して判定する | もっともらしい数値が故障を隠す（2.8、0009 §2.2） |
