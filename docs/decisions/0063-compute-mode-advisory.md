## 1. Context

`issues/37-compute-mode-advisory.md` は、室温が 32 °C ある真夏の昼に 600 W の連続負荷を
始めるのは危険だが、**AI が Compute Mode を拒否する設計にしてはいけない**とした。
利用者の実行を止める権限を AI に与えることになる。出すのは判断材料だけで、決めるのは人間である。

#66（決定記録 0040 §2.2）は `compute_mode_advisory` を
`{"safe": bool, "warnings": [...], "blocking": false}` として先に入れ、
実測フルロード履歴との比較は #50 の測定後に #68 で扱うとして未決に残した（0040 §5 未決4）。
いま欠けているのは次の3つである。

- 切替前に見せる**現在の環境条件**（室温・GPU 吸気・湿度）が payload に無い
- **過去のフルロード実績との比較**が無く、「その時より何度高いのか」を出せない
- 比較できないとき（履歴が無い・室温の記録が無い）に、**それを言う場所が無い**

3つ目は本 Issue の実装で最も壊れやすい点である。判断材料が欠けていることを黙って
落とすと、受け手には「警告が無い＝問題なし」に見える。**欠測を正常として扱う実装が
この一連の PR で繰り返し指摘されてきた。**

## 2. Decision

### 2.1 助言だけを作り、どんな条件でもブロックしない

- `compute_mode_advisory.blocking` は型で常に false のまま（0040 §2.2 / 決定 D-08）
- advisory は `coldaisle.control` / `coldaisle.event_entry` を import しない。
  Fan Demand・PWM・設定の書き込みへ至る経路を作らない（AGENTS.md ルール1 / 2）
- Workspace もこの payload を根拠に切替を拒否しない（`docs/api-contract.md` §3 に明記）
- 判定は決定論的で、AI は**文面生成にも使わない**。`summary` の言い換えだけが AI の
  持ち場であり（0040 §2.7）、advisory の文言は AI を通らない

実装は `src/coldaisle/api/compute_mode_advisory.py` に不変条件 I-1〜I-7 として書き、
`tests/test_compute_mode_advisory.py` が1つずつ破ろうとする。

### 2.2 現在の環境条件を宣言し、使えない条件を黙って落とさない

`config/compute-mode-advisory.yaml` の `current.conditions` に並べた metric を、
並べた順に `conditions[]` として返す。**値が無くても件数は変わらない。**

| 判定 | 規則 |
|---|---|
| `usable` | `quality=ok` かつ `0 <= age <= current.max_age_s`（未来の時刻の値も使わない）。それ以外（`suspect` / `stale` / `missing` / 未保存）は false |
| `exceeded` | `usable` かつ `advisory_max` を超えている。使えない値では常に false |

一度も保存されていない metric は保存済みの `missing` と同じに扱う（0042 §2.3 と同じ理由）。
`usable` でない条件は `warnings` に1件ずつ出す。

**`quality=suspect` を現在の条件に使わない。** signal の source 判定では suspect を
「値は届いている」に数えるが（0042 §2.4）、切替前に人へ見せる数値としては
疑わしい値を根拠にしない。ここでの安全側は「表示しない」である。

### 2.3 フルロード実績は**観測値**から導く。申告は根拠にしない

比較対象（`reference`）は、記録された電力（`history.load.metric`、既定 `power.gpu.0`）
だけから切り出す。

- バケットの平均が `history.load.min_value` 以上
- そのバケットの `quality=ok` の値が `history.load.min_ok_samples` 以上
  （数サンプルしか届かなかったバケットを5分ぶんの根拠に数えない）
- 連続したバケット（`max_gap_s` までの欠落は同じ期間に繋ぐ）の**観測できた合計**が
  `min_duration_s` 以上
  - 繋ぐのは**バケットが無い（または `quality=ok` の値が `min_ok_samples` に満たない）欠落**だけ。
    閾値未満を十分に観測したバケットは欠落ではないため、そこで期間を必ず切る
  - 読むのは**完了したバケットだけ**。進行中のバケットは観測が5分に満たない
  - さかのぼり範囲（`lookback_days`）に**丸ごと入るバケットだけ**を読む。境界をまたぐバケットは数えない
- 該当する期間のうち**最も新しいもの**を比較に使い、件数を `reference_count` に出す

**GPU Mode の申告（`events` / `sys.gpu_mode`）は使わない。** 決定記録 0045 §2.6 が、
申告は説明と注釈のための記録であり閾値の選択にも制御にも使わないと定めている。
申告は「Compute Mode にしたと通知があった」ことしか意味せず、実際に負荷が掛かったかは
別である。同じ通知を連投されても実績は増えない。

期間の開始・終了・継続時間は**根拠バケットの時刻**から決める。現在時刻からも、
書き手が申告した時刻からも作らない（0045 §2.5 と同じ理由）。`covered_s` は
観測できたバケットの合計であり、繋いだ欠落の時間を含まない。

### 2.4 比較できなかったことを `limitations` に残す

- 期間が見つからない → `reference: null` と、さかのぼり条件を含む1件
- 期間はあるが、その間の室温・湿度・GPU 温度の記録が無い → その metric ごとに1件

`reference` が `null` のときに「比較の結果、問題なし」と表示してはならない
（`docs/api-contract.md` §3 に明記）。`warnings` は切替の判断に効く事実、
`limitations` は**評価できなかったこと**であり、混ぜない。

### 2.5 `safe` の意味を狭める（0040 §2.2 の定義を置き換える）

```text
safe = signal が green  かつ  すべての conditions が usable  かつ  exceeded が1つも無い
```

0040 §2.2 は `safe` を「signal が green か」だけとしていた。それだけだと、助言用に
選んだ条件が監視必須 metric に含まれない場合（設定は自由に変えられる）に、
**条件が読めないまま `safe: true` を返せてしまう。** 室温が助言上限を超えているのに
`safe: true` になるのも同じく避ける。

**履歴が無いことは `safe` を false にしない。** これは §4 で述べるとおり意図的な選択で、
運用開始直後や、フルロードを一度も回していない期間に `safe` が恒常的に false になり、
本当の問題と区別できなくなるのを避ける。代わりに `reference: null` と `limitations` で
「比較していない」ことを構造として見せる。**この点は所有者の判断を仰ぐ**（§5 未決1）。

`safe` は**将来の高負荷時の安全を保証しない**（0040 §2.2 のまま）。

### 2.6 履歴は `refresh_s` の窓ごとに1回評価し、評価時刻を payload に出す

`server-health` は WebSocket で毎秒組み立て直す（0040 §2.3）。30 日ぶんの集計を
毎回走らせない。同じ `refresh_s` の窓の中では同じ結果を返す。
呼び出しは現在時刻とスナップショットを読む**前に**順序を取り（窓はその順に単調に進む）、履歴は窓が変わったときだけ、その呼び出しの時点で評価する。時計が戻った呼び出し（同じ窓の中で戻った場合を含む）は、自分より後の時刻で評価した結果を使わずに自分の時点で評価し、キャッシュを置き換えない。

窓の鍵は時刻そのものなので、**同じ時刻・同じ DB なら常に同じ結果**になる。
評価が現在より古いことを隠さないため、`evaluated_at_ms` / `evaluated_at` を payload に
出す（`generated_at_ms` より古いことはあっても、新しいことはない）。現在の条件（`conditions`）は
キャッシュせず、毎回のスナップショットから作る。

集計はバケット（既定 5 分）から読む。生の時系列を1件ずつ走査しない
（0004 §2.9 の合成を使う）。advisory は他のフィールドと**同じ読み取りスナップショット**で
作り、現在値と食い違う時点を混ぜない（0042 §2.6）。

### 2.7 `schema_version` は 1 のまま、フィールドを**追記**する

`compute_mode_advisory` にキーを足すだけで、既存のキー（`safe` / `warnings` /
`blocking`）の意味も型も変えない（`safe` の判定は §2.5 で狭まるが、型と「true が
より安全側」という向きは変わらない）。0042 §2.5 が総件数フィールドの追加を却下したのは
「warnings で足りる」ためで、**文字列に押し込めない構造化データはこれに当たらない**。
数値の比較を Workspace が自分で描くには、文字列ではなくフィールドが要る。

### 2.8 しきい値はすべて設定に置き、現時点では**暫定値**とする

`config/compute-mode-advisory.yaml` が唯一の情報源（AGENTS.md ルール9）。
`COLDAISLE_COMPUTE_MODE_ADVISORY` で差し替えられる（0009 §2.9）。
`metrics.yaml` に無い metric 名と、同じ条件の重複は起動時に拒否する。

**初期値はすべて暫定で、実測（#50 / #19）の前に決めた目安である。**
特に次の3つは実測後に所有者が見直す。

| 値 | 暫定値 | 根拠 |
|---|---|---|
| `air.room` の `advisory_max` | 30.0 °C | #19 のベースライン未測定 |
| `air.room_humidity` の `advisory_max` | 65 %RH | 結露リスクの閾値は未測定 |
| `history.load.min_value` | 400.0 W | RTX PRO 6000 の TGP 600 W に対する概ね 2/3 |

## 3. Consequences

### 良くなること

- 切替ダイアログが「いまの条件」と「前回フルロード時との差」を1リクエストで描ける
- 比較できないことが `reference: null` + `limitations` として構造に現れ、
  「警告が無い＝問題なし」に見えなくなる
- 実績の判定が観測値だけに依存するため、Workspace の通知が漏れても、
  逆に連投されても、実績の件数・継続時間は変わらない
- AI が停止していてもアドバイザリは変わらない（#68 の受入基準）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 履歴部分が最大 `refresh_s`（既定5分）古い | `evaluated_at` を payload に出す。現在の条件はキャッシュしない |
| フルロードの定義が電力1本に依存する。電力が読めない期間は実績にならない | 読めなかったことは `limitations` に出る。使う metric は設定で変えられる |
| 実機は NVML が hotspot を公開しないため、`peaks` は `gpu.0.core` になる | `peak_metrics` は設定。公開される機種では hotspot を足せる |
| `safe` の意味が 0040 から狭まり、Workspace の表示が変わりうる | `blocking` は false のままで、切替の可否には影響しない |
| 助言上限が暫定値のまま warning を出す | 値はすべて設定にあり、コメントで暫定と明示。実測後に所有者が変える |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 条件が危険なら切替を拒否する（`blocking: true`） | 利用者の実行を止める権限を与えることになる（決定 D-08 / `issues/37`） |
| AI に文面を書かせる | 数値の捏造と「安全です」の断言を防げない（0040 §2.7 と同じ理由） |
| GPU Mode の申告（`events` / `sys.gpu_mode`）をフルロード期間の根拠にする | 申告は実際の負荷を意味しない。通知の連投で実績が増える（0045 §2.6） |
| 履歴が無いときに `safe: false` にする | 運用開始直後やフルロード未実施の期間に恒常的に false になり、本当の問題と区別できない。代わりに `reference: null` と `limitations` で見せる（§5 未決1 として所有者に残す） |
| 条件が欠けても `safe` は signal だけで決める（0040 のまま） | 条件が読めないまま「安全」と表示できてしまう（§2.5） |
| 生の時系列を毎回走査して実績を探す | WS が毎秒組み立てるため現実的でない。バケットで足りる（0004 §2.9） |
| 履歴を DB の新しい表に materialize する | 追加の書き手とマイグレーションが要る。読み出しで足りるうちは持たない |
| 「通常時の室温」を長期の平均から出す | 「通常時」の定義（idle だけか全体か）が決まっていない。§5 未決2 に送る |
| `schema_version` を 2 に上げる | 既存キーの意味も型も変えない追記であり、Workspace の既存表示は壊れない（§2.7） |
