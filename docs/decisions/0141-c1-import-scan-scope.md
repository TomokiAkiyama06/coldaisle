## 1. Context

0134 §2.4 の 1 は、承認者が `raise` の検証を行うコードを書き換えられないことを、隔離した interpreter
（`/opt/coldaisle/.venv/bin/python -I`）が報告する場所を実際に開いて確かめる手順として決めた。走査の起点は
`sys.path` の各項・`sys.prefix`・`sys.base_prefix` で、それぞれの下をすべて辿り、出会った symlink の実体も
起点に足す。そのうえで、`roots.txt` に `/opt/coldaisle` と interpreter の置き場所以外が出たら C1 は失敗とした。

#217 の文書の PR（#316）で手順書へ写したところ、レビューで次が見つかった。

1. **2 節の既定の導入で C1 が通らない。** 2 節は venv を `/usr/bin/python3.12`（システムの Python）で作る。
   このとき `sys.base_prefix` は `/usr` で、`/usr` の下をすべて辿ると、import に使わない標準の symlink
   （`/usr/lib/ssl/certs -> /etc/ssl/certs` など）の先が `roots.txt` に入る。これらは「`/opt/coldaisle` と
   interpreter の置き場所以外」なので、0134 の文面どおりだと C1 は必ず失敗する
2. **import に使う場所そのものも外を指す。** Ubuntu のシステムの Python では、標準ライブラリの
   `sitecustomize.py` が `/etc/python3.x/sitecustomize.py` への symlink である。`site` は `-I` でも
   `sitecustomize` を import するので、これは実際に読まれるコードである。走査の範囲をどう絞っても、
   「外の場所が出たら失敗」の決まりのままでは C1 は通らない
3. `/usr` の下をすべて辿ると、切れた symlink に出会う機会も増える。0134 の「解決できない symlink は理由を
   問わず失敗」と合わさると、承認者の権限と関係のない distro のファイルで C1 が通らなくなりうる

開発機で確かめた（システムの Python 3.14 で作った venv。`sys.base_prefix=/usr`）。§2.1 の範囲では
`roots.txt` は 13 項（`/usr/lib/python3.14` とその `lib-dynload`・`python314.zip`・`_sysconfigdata`・
`libpython3.14.so`・`/usr/bin/python3.14`・`/etc/python3.14/sitecustomize.py` と venv）で、走査は 0.5 秒、
解決できない symlink は 0 だった。

0134 は FINAL で、§5 の 7 は「段階 C の実施で見つかった問題は、別の記録・手順の修正で扱う」としている。
本記録はその別の記録である。

## 2. Decision

### 2.1 走査の起点は、Python が実際に読む場所に限る

起点（`roots.txt` の最初の項）は、隔離した interpreter が報告する次のものとする。

| 起点 | 下をすべて辿るか | 理由 |
|---|---|---|
| `sys.path` の各項（site の処理の後。`.pth` が足した項を含む） | 辿る | import の探索の場所そのもの。site-packages の `.pth` と、editable の導入で `.pth` が足す `src` もここに入る |
| `sys.prefix`（venv） | 辿る | `pyvenv.cfg`・`bin/python`・site-packages。小さい |
| `sys.executable`（venv の `bin/python`） | 辿る（symlink の実体の interpreter とその祖先は、0134 の symlink の解決で起点に足される） | 起動される実行ファイル |
| `sys.base_prefix` | **辿らない。そのものと祖先だけを見る** | システムの Python では `/usr` になる。`/usr` の下で import と起動に使う場所（標準ライブラリ・`lib-dynload`・`python3xx.zip`・`_sysconfigdata`・interpreter の実体・`libpython`）は、`sys.path` の項か実行ファイルの symlink の実体として、上の行で下まで見られる |

- symlink の解決（項そのもの・項の下のすべての symlink・path の途中の要素の symlink を、増えなくなるまで起点に足す）は 0134 のまま
- `.pth` は `sys.path` の項（site-packages）の下のファイルとして「書けない」の検査に掛かる。`.pth` が足す場所は、
  site の処理の後の `sys.path` に出るので起点に入る
- `--registry-limits` の置き場所（`/opt/coldaisle/config` と `model-registry.yaml`）は、0134 §2.4 の表の 1 のとおり
  別に見る

### 2.2 外へ解決した先は、出たこと自体では失敗にせず、書けない検査で受け入れる

- `roots.txt` に `/opt/coldaisle` と interpreter の置き場所（2 節）以外の場所が出ても、**それだけでは C1 を失敗に
  しない。** その場所も起点なので、下のすべてのディレクトリと、起点の祖先が `touch` の検査に掛かる。ファイルは
  `: >>` の検査に掛かる（0134 §2.4 の判定の決まりのまま）。所有者・mode・ACL・補助グループをまとめて、カーネルの
  判定そのもので「承認者が書き換えられない」ことを見る
- 1つでも「書ける」が出たら失敗とする（0134 のまま）。外の場所が承認者の書ける場所なら、ここで失敗する
- 外の場所は一覧にして結果（#217）に残し、`stat -c '%A %U:%G %n'` で root の所有であることも記録する。
  受け入れの根拠を後から辿れるようにするためで、判定は上の検査で行う

### 2.3 0134 の趣旨は弱めない

守る性質は「承認者が書ける場所のコードを、手順に従った `raise` の検証が読まない」で、0134 と同じである。

- `sys.base_prefix` の下のうち本記録で辿らなくなるのは、import にも起動にも使われない場所（`/usr/share`・
  `/usr/lib/ssl` など）だけである。Python が読む場所は §2.1 の起点として残る
- 外の場所を受け入れるのは、0134 が求める「書けない」の検査がその場所にも同じように掛かった後だけである
- 「解決できない symlink は理由を問わず失敗」（0134 §2.4）は**残す**（§5 の 1 で判断を求める。推奨は残す）。
  走査の範囲が import の場所に絞られたので、distro の切れた symlink に出会う機会は 0134 の範囲より少ない

### 2.4 手順書

`docs/ubuntu-deploy.md` 6.7 の手順 9 の 6 のスクリプトと箇条書きを §2.1 / §2.2 の形にし、本記録を参照する。
**本記録が FINAL になるまで、手順 9 の 6 で C1 を通したとはしない**（0134 の文面のままでは通らず、本記録の
形はまだ承認されていないため）。

### 2.5 ディレクトリの目印は推測できない名前で排他的に作る

ディレクトリに書けるかは、`mktemp -p <ディレクトリ> .probe-XXXXXXXX` で見る。成功（＝書ける）したら出力された
目印をすぐ消す。失敗なら書けない。0134 §2.4 の `touch -- <dir>/.probe-<任意の名前>` と、6.4 / 6.6 の
`.probe-fand`（#311）の固定の名前の形は使わない。

- 固定の名前だと、書けるディレクトリに、同じ名前で書けない（他人の所有・mode `0444` の）ファイルやディレクトリを
  先に置いておけば `touch` が失敗し、「書けない」と誤って判定される。特に §2.2 で受け入れる外の場所が誰かの
  書ける場所だったとき、Python のコードを差し込める場所を C1 が受け入れてしまう（危険な向き）
- `mktemp` は乱数の名前を `O_CREAT | O_EXCL` で作り、既にある名前なら別の名前で作り直す。先に置かれた名前に
  左右されず、ディレクトリへの書き込みと探索の権限そのものを見る
- 書けることを確かめる側（6.4 の手順 4・6.6）も同じ形にする。固定の名前のファイルが先にあると、書けるのに
  「書けない」と出て fand を起動できない（安全側だが、手順として揃える）

## 3. Consequences

### 良くなること

- 2 節の既定の導入（システムの Python）で C1 を通せる
- 走査が Python の読む場所に絞られ、短く終わる（開発機で 13 項・0.5 秒）。結果の一覧も読める長さになる
- 外の場所（`sitecustomize` の実体など）が、「出たら失敗」ではなく「書けないことを確かめた」として記録に残る
- ディレクトリの書き込みの判定が、先に置かれた固定の名前のファイルで誤って「書けない」にならない（§2.5）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| `sys.base_prefix` の下のうち、§2.1 の起点の外は見なくなる | そこは Python の import と起動に使われない。使われる場所が新しく出たら（`sys.path` に出る・実行ファイルの symlink の先になる）、起点に入る |
| 外の場所を自動では拒まなくなる | 書けない検査は同じに掛かる。一覧と `stat` を結果に残し、人が見る |
| 動的リンカが読む共有ライブラリ（`libc` など）は見ない | 0134 §2.2 のとおり `LD_PRELOAD` などは `-I` の範囲の外で、0134 でも対象にしていない（本記録で狭めたものではない） |

## 4. 却下した代替案

1. **0134 の文面どおり（`sys.base_prefix` の下をすべて辿り、外の場所は失敗）**: 2 節の既定の導入で必ず失敗し、
   `raise` を使えるようにならない（§1 の 1・2）
2. **`sys.base_prefix` の下は辿るが、外の場所は書けない検査で受け入れる**: 判定としては成り立つ。ただし
   `/usr` の全体を走査して時間が掛かり、import と関係のない切れた symlink で C1 が止まりうる（§1 の 3）。
   結果の一覧も読めない長さになる
3. **外の場所を許す一覧（`/etc/python3.x` など）を手順に書く**: 導入先の distro と Python の版ごとに一覧が
   変わり、一覧の外を見落とす。カーネルの判定で書けないことを見るほうが漏れが無い
4. **インタプリタを `/opt/coldaisle-python` の uv の管理する Python に固定する**（`/usr` を使わない）: 2 節は
   システムの Python を既定にしており、導入の形を変えることになる。また `sitecustomize` のような外の場所が
   無くなる保証にはならない
5. **目印を固定の名前のまま、先に同じ名前のものがあれば失敗とする**: 先にあるものが前回の確認の残りか、
   差し込まれたものかを手順で区別できない。名前を推測できなくするほうが単純で漏れが無い（§2.5）
6. **`-S`（site を処理しない）で起動して `.pth` と `sitecustomize` を読ませない**: editable の導入では
   `.pth` が `src` を `sys.path` に足すので、`-S` では `coldaisle` を import できない。0134 §2.2 の起動の形を変える
   ことにもなる
