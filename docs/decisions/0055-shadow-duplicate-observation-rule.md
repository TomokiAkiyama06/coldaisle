## 1. Context

`coldaisle.control.shadow.outcome.ObservationIndex` は、同じ metric・同じ時刻に観測が2つ
あると**値の小さいほうを採って**いた。根拠として置かれていたのは「どちらでも誤差の扱いは
同じだが、入力の順序で結果が変わらないように順序を固定しておく」である。

**「どちらでも誤差の扱いは同じ」は成り立たない。** 予測誤差は `error = 実測 - 予測` で、
正の側が underprediction（実測のほうが高い＝**冷却が足りない向きの外し方**）である。
小さいほうを採ると正の誤差が小さくなり、

- underprediction を実際より小さく見せる
- その誤差を読む #91 の cost gate（`maximum_underprediction_c`）が本来より通りやすくなる

つまり偏りは**安全でない向き**に出る。順序を固定する目的（同じ入力から同じ結果を返す）は
正しいが、**選ぶ値がその目的と独立ではなかった**。

いまこの経路に食い違う重複は届かない。`readings` は `PRIMARY KEY (metric, ts_ms)` なので、
`SqliteStore.series()` から作った `OutcomeObservation` は時刻ごとに1つである。届くのは
**`OutcomeObservation` を直接組み立てて渡す経路**（再生・試験・将来の取り込み）だけで、
`ObservationIndex` と `ShadowOutcomeMatcher.match()` は公開 API としてその列を受け取る。

#91（決定記録 0054 §2.6）は評価の入口で**食い違う重複を拒む**ことを既に決めており、
そちらの経路は塞がっている。残っているのは記録側の照合器で、0054 §5 はこれを
**#154 で決める未決事項**として送った。0053 は FINAL なので書き換えず、本記録で閉じる。

## 2. Decision

### 2.1 食い違う重複は受け取らない。同じ値の重複は1つに畳む

`ObservationIndex` を作るとき、**品質が `OK` で値を持つ観測**（`OutcomeObservation.usable`）
を metric と時刻で束ね、次のように扱う。

- 同じ metric・同じ時刻に**違う値**があれば `ShadowObservationConflictError` を上げて
  **受け取らない**（fail closed）。索引を作らず、照合も始めない
- **まったく同じ値の重複は許し、1つに畳む。** 冪等な取り込みで同じ行が2度届くのは
  入力の誤りではない。畳んでから索引に入れるので、`matched` の数も export の内容も
  「何回渡したか」に依存しない
- 品質が `OK` でない観測は**証拠に使わない**ので、食い違いの判定でも見ない。
  証拠にならない値の不一致で照合そのものを落とすと、採点できたはずの予測まで巻き込む
- `ShadowOutcomeMatcher.match()` に `Sequence[OutcomeObservation]` を直接渡す経路も
  **同じ契約**である。索引を外で作るかどうかで結果が変わってはならない

**どちらを選んでも片方の事実が消える。** 小さいほうを採れば「高いほうの実測があった」という
事実が消え、大きいほうを採れば「予測が当たっていた」という事実が消える。時刻ごとに1つの値
しか持てない以上、食い違いは入力の誤りであって、照合器が選んでよいものではない。
**#91 と同じ規則に揃える**（0054 §2.6）。二重に見える規則を置かないほうが、あとで読む人が
「どちらの経路を通ったか」で結果を疑わずに済む。

「安全側に寄せて大きいほうを採る」も採らない。§4 に理由を書く。

### 2.2 0053 §2.3 の他の規則は変えない

本記録が置き換えるのは §2.1 の1点だけである。

- 期待時刻は `expected_ts_ms = action 時刻 + offset` で記録時に確定する
- `±shadow.outcome_match_tolerance_ms` の中の**最も近い**観測。**同距離なら過去側**
- 観測は action より後に限る。**品質が `OK` の値だけ**を証拠にする
- 照合器は**時計も I/O も持たない**。処理した時刻を一切使わない
- 採点してよいのは、予測した候補 action が実際に掛かっていた区間だけ（`unidentifiable`）

**「同距離なら過去側」と「食い違う重複を拒む」は別の規則である。** 前者は*違う時刻*の観測の
どちらを採るかで、時刻は観測そのものの事実だから選べる。後者は*同じ時刻*に2つの値があると
いう入力の矛盾で、選べば片方の事実が消える。

### 2.3 新しい例外を型で分ける

- `ShadowObservationConflictError(ValueError)` を `coldaisle.control.shadow` から公開する
- 既存の `ShadowOutcomeUnusableError`（予測と照合設定が噛み合わない）とは**別の型**にする。
  設定の誤りと入力データの矛盾は、呼ぶ側の直し方が違う

## 3. Consequences

- **underprediction が実際より小さく見える経路が無くなる。** #91 の cost gate は、偏りを
  受け取らない入力の上で判定する
- 記録側（#90）と評価側（#91）の重複の扱いが**1つの規則**になる。経路によって結果が違う、
  という疑いを持たなくて済む
- 同じ証拠から同じ `matched` / export が出る。重複の回数が結果に漏れない
- **壊れた入力では照合が止まる。** いまの `SqliteStore` 経由では起きないが、将来の取り込みが
  食い違う重複を作れば、黙って偏った数字を出す代わりに例外で止まる。**これは意図である**
- 合成データを作る試験は、同じ時刻に違う値を混ぜられなくなる（混ぜたいときは時刻をずらすか、
  品質を `OK` 以外にする）

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| いまのまま「小さいほうを採る」 | underprediction を小さく見せる。偏りが**安全でない向き**に出る |
| 「安全側に寄せて大きいほうを採る」 | 偏りの向きは安全側になるが、**予測の当たりが消える**。外れていない予測を外れたことにする道具は、昇格の判断（#92）を別の向きに誤らせる。事実を1つ消すことに変わりはない |
| 「先に来たほうを採る」 | 入力の順序で結果が変わる。再現できる比較にならない |
| 平均を採る | どちらの観測とも違う値を作る。**記録に無い値を証拠にしない** |
| 両方を索引に残し、両方と突き合わせる | 1つの予測に2つの誤差が出る。`matched` と coverage の数え方が壊れる |
| 黙って落として数だけ数える | 「観測があったのに証拠にしなかった」区間が未照合と区別できなくなる |
| 品質が `OK` でない観測も食い違いの判定に含める | 証拠に使わない値の不一致で、採点できたはずの予測まで落とす |
