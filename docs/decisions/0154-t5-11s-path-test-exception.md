## 1. Context

### 1.1 約 11 s の経路とは何か

fand が hang したときに Max になるまでの順序は、0080 §2.5 のとおり
「watchdog の時間切れ → `WatchdogSignal`（SIGABRT）→ `TimeoutAbortSec` で SIGKILL → cgroup の停止 →
`ExecStopPost`（`safety_handoff.py` が root で3 zone に Max を書く）」である。最悪時間は
**`WatchdogSec` 5 s + `TimeoutAbortSec` 5 s + 引き継ぎ実行部の時間（1 s 未満）≒ 約 11 s**（0080 §2.3・0119 §2.12）。
この間、Fan は止まる直前に書いた低い Demand のまま回る。

2026-10-14 の T5（`docs/fan-header-mapping.md`）では、`SIGSTOP` したプロセスにも systemd が watchdog の signal の後に
`SIGCONT` を送るため、fand は SIGABRT（faulthandler）で終わり、`TimeoutAbortSec` を待たずに引き継ぎが走った。
Max までは 12 試行すべてで 5143〜5324 ms（**約 5.2 s の経路**）で合格した。

SIGABRT で終わらないが SIGKILL では終わる hang（**kill できる hang**。ユーザー空間の固まりで SIGABRT の処理まで届かないもの）では
`TimeoutAbortSec` の 5 s も待ち、その後の SIGKILL から Max までは実測 44〜51 ms（予備確認の `kill -KILL`）である。つまりこの故障の最悪は
**5000 + 5000 + 約 50 ms ≒ 10.05 s**（systemd の処理の遅れを除く）で、これが「約 11 s の経路」である。
5.2 s の試行は Max を確かめた直後に負荷を止めたので、その後の約 5 s の上がりは測っていない（0127 §2.5）。
0119 §2.13 は `watchdog_timeout_ms` を `confirmed` にする条件として、この最悪時間の間の温度の上昇が上限までの余裕に
収まることを求める。

### 1.1a 故障のモデル: 本記録が扱うのは kill できる hang だけ

- **kill できる hang**（ユーザー空間で固まり、SIGABRT で終わるか、終わらなくても SIGKILL で終わる）: Max までの時間に
  上限がある（約 5.2 s か約 10.05 s）。本記録の試験が確かめるのはこの経路の**時間の長さと、その間の温度**である
- **D 状態の hang**（hwmon の書き込み・読み戻しが driver の中で戻らない。中断できないカーネルの I/O。0080 §2.5 の最後・
  0127 §2.5）: `TimeoutAbortSec` が約束するのは期限で SIGKILL を**送る**ことだけで、D 状態のプロセスは SIGKILL では
  終わらない。プロセスが実際に終わって `ExecStopPost` が動くまでの時間に**上限が無く**、systemd の deadman ではこの
  故障を守れない。測った 44〜51 ms も kill できるプロセスにだけ当てはまる。さらに `ExecStopPost` が動いても、同じ driver への
  書き込みで止まりうる（0028 未決 6）。**本記録の試験はこの故障を確かめず、確かめられない**（`SIGSTOP` は D 状態を作らない）

### 1.2 本番の設定では再現できない

- SIGABRT で終わらない hang を外から作る手段が無い。`SIGSTOP` は systemd の `SIGCONT` で解け、SIGABRT で終わる
- `WatchdogSignal` を無視される signal に変えると、`SIGCONT` で fand が動き出し、Demand を書き続ける。
  「低い Demand のまま固まる」状態にならない
- `TimeoutAbortSec` の経路そのもの（SIGKILL → 引き継ぎ）は予備確認で 44〜51 ms と測ってある（**kill できる fand に限る**。D 状態では §1.1a）。足りないのは
  **固まった時間が約 10 s 続くときの温度**だけである

### 1.3 これまでの判断

- 所有者は 0127 §5 の 2 で (a)「試験専用の設定で再現する」を選んだ（`safety.yaml` の `watchdog_timeout_ms` と unit の
  `WatchdogSec` を試験の間だけどちらも 11 s にし、(i) CPU 全スレッド・(iii) CPU・(iii) GPU を少なくとも行う）
- 0121 §2.1 は試験専用の設定を §2.8 の T6 にしか認めないので、実施の前にこの記録で例外と中身を決める
  （`docs/fan-header-mapping.md` の T5「残り」）
- 2026-10-16、所有者は「`enable` の前にこの試験を行う」を選んだ。あわせて、unit のタイムアウト
  （`TimeoutAbortSec`・`TimeoutStopSec`・`TimeoutStartSec`・`RestartSec`）は `provisional` のまま進む、アイドルの
  Guard の発火（T1 で 431 回）はこのまま `enable` してよく静音化は別の Issue、`/opt` は d3c5404 のまま `enable` する、
  と決めた。これらは本記録の範囲外である

## 2. Decision

### 2.1 試験の目的

`WatchdogSec` 5 s・`TimeoutAbortSec` 5 s の本番の deadman で起こりうる最悪の時間（約 10.05 s）以上、Fan を止める直前の
低い Demand に固めたまま負荷をかけ続け、その間と Max の後 30 s の温度の上昇が、0121 §2.7 の余裕に収まることを確かめる。
対象は §1.1a の kill できる hang だけで、D 状態の hang の時間と温度は本記録の試験では確かめない（§5 の 8・9）。
**本番の値（`watchdog_timeout_ms` 5000・`WatchdogSec` 5s・`TimeoutAbortSec` 5s）は変えない。** 11 s は固まる時間を
作るための試験の中だけの値で、本番へは持ち込まない。

### 2.2 合格の条件

| 測るもの | 合格の条件 | 根拠 |
|---|---|---|
| `SIGSTOP` から Max（3 zone の `pwmN_enable=0`、20 ms ごとに読む。CLOCK_MONOTONIC）まで | **10100 ms 以上・12000 ms 以下** | 下限: kill できる hang（§1.1a）の本番の最悪 5000 + 5000 + SIGKILL から Max の実測の最長 51 ms を 100 ms に切り上げた値。これより短い試行は本番の最悪を覆わないので判定に使わない。上限: 11000 + SIGABRT から Max の実測の最長（T5 の 324 ms、apport が core を受けた予備確認の 0.86 s）に余裕を足した値。超えたら SIGABRT の経路が想定どおりでない |
| 止めている間と Max の後 30 s の温度 | 0121 §2.7 のまま: 開始 + 上昇が上限（`absolute_temp_ceiling_c` 90 °C、T_SENSOR 80 °C）より 5 °C 以上低い（`cpu.package`・`gpu.0.core` は 85 °C 未満、`board.connector_12v2x6` は 75 °C 未満）。**判定は §2.5a の速い読み取りの最大値に、読み取りの間の見落としの分（§2.5a の式の `r × L`）を足した値で行う**。DB の 2500 ms ごとの値は参考にだけ使う | 0119 §2.13・0121 §2.7。本記録で緩めない。2500 ms ごとの値では、CPU が約 5 s で 31〜32 °C 上がる間の最大を見落とし、誤って合格にしうる |
| 止める直前の `effective` | (i) は記録したアイドルの値のまま、(iii) はアイドルの値 + 0.05 以内（0121 §2.7。外れた試行は使わない） | 「低い Demand のまま固まる」最悪の条件にするため |
| 位相（`SIGSTOP` の時刻 − systemd が最後の `WATCHDOG=1` を受けた時刻） | 100 ms 以内の試行を各条件で少なくとも 1 つ（0121 §2.7） | 固まる時間を最も長くするため |

試験の値で固まる時間は約 11.1〜11.9 s になり、本番の最悪（約 10.05 s）より約 1 s 長い。温度の面で保守的な側である。

参考として、Max から3 zone の `fanN_input` が全開の 90% に届くまでの時間も記録する（判定には使わない）。

### 2.3 試験専用の設定（例外の中身）

本番の設定を書き換えず、0121 §2.1 の T6 と同じく**別の場所の設定と unit の drop-in**で差し替える。

1. **設定**: `/etc/coldaisle/control-config-test-t5-11s/` に、本番の `/etc/coldaisle/control-config/` の4ファイルを
   所有者・権限ごと写し、`safety.yaml` の `watchdog_timeout_ms.value` だけを `5000` → `11000` にする（`status` は
   `provisional` のまま。`basis` は足さない）。ほかの値はすべて本番と同じ。**`hardware_write_fail_exit_ms` は 5000 のまま**
   （0080 §2.6 の `hardware_write_fail_exit_ms <= watchdog_timeout_ms` を満たし、T2 で測った書き込みの失敗の経路は変えない）。
   置いた後に `diff -r` で、違いがこの1行だけであることを確かめる
2. **drop-in**: `/etc/systemd/system/coldaisle-fand.service.d/t5-11s.conf`（root 所有・`0644`）の全文は次のとおり。
   systemd は節の見出しの外の代入を無視するので `[Service]` を省かない。`ExecStart=` は追記される指令なので、
   置き換えるには先に空の `ExecStart=` で本番の値を消す（0080 段階 5 の上書きと同じ形）

   ```ini
   # 0154 の T5 の約 11 s の経路の試験の間だけ置く。試験のスクリプトの後片付け（§2.3 の 3）が消す
   [Service]
   ExecStart=
   ExecStart=<本番の ExecStart の値をそのまま。導入先で足した引数も含め、--config-dir の値だけを /etc/coldaisle/control-config-test-t5-11s に替える>
   WatchdogSec=11s
   ```

   `<…>` の行は、試験のスクリプトが `systemctl show -p ExecStart` ではなく置いてある unit（`systemctl cat` の本体）の
   `ExecStart=` の行から作り、`--config-dir /etc/coldaisle/control-config ` がちょうど1か所あることを確かめてから替える
   （無い・2か所以上なら置かずに止める）。
   **置いて `daemon-reload` した後に、次がすべて成り立たなければ試験を始めない**（drop-in と設定を消して `daemon-reload` し、
   0 以外で終わる。fand はまだ起動していない）:
   - `systemctl show -p WatchdogUSec --value coldaisle-fand` が `11s`
   - `systemctl show -p ExecStart --value coldaisle-fand` の `argv[]` がちょうど1つで、`--config-dir /etc/coldaisle/control-config-test-t5-11s` を含む
   - `systemctl show -p DropInPaths --value coldaisle-fand` が `t5-11s.conf` だけ
   - `TimeoutAbortSec`・`TimeoutStopSec`・`RestartSec`・`WatchdogSignal`・`ExecStopPost` の `systemctl show` の値が、置く前に
     控えた値と同じ

   もし効かないまま fand を起動しても、`WatchdogSec` 5 s と `watchdog_timeout_ms` 11000 の食い違いは「短い向き」なので
   起動はする（0080 §2.3 の warning）が、固まる時間が約 5 s になり §2.2 の時間の下限で無効になる。上の確認はこれを試験の前に防ぐ

   `TimeoutAbortSec`・`TimeoutStopSec`・`TimeoutStartSec`・`RestartSec`・`WatchdogSignal`・`ExecStopPost`・
   `KillMode`・hardening は**変えない**。0080 §2.3 の `WATCHDOG_USEC <= watchdog_timeout_ms` は 11000 どうしで等しく、
   食い違えば fand は終了コード 4 で制御を取らない（安全側）
3. **期間**: 置くのは試験のスクリプトの実行の間だけ。**後片付けの `trap` は、スクリプトの最初の操作（§2.6 の 1 の負荷・
   設定のディレクトリと drop-in を置くこと・fand の起動のどれよりも前）として登録する**。登録の前に何かを置いたり起動したり
   すると、その間の検証の失敗・読み取りの失敗・Ctrl-C で後片付けが走らず、11 s の設定や drop-in が残りうるためである。
   その後で置いて `systemctl daemon-reload` する。後片付けは、まだ置いていないもの・起動していないもの・かけていない負荷を
   飛ばし、途中のどの時点で走っても下の順序で進む（置く前に走ったときも、下の 3 と 4 の確認は行う）。
   終了時（正常・中止・エラー・Ctrl-C のどれでも）の後片付けは、`EXIT` の `trap` の1か所だけで走らせる。`INT`・`TERM`・`HUP` の
   `trap` は後片付けを直接呼ばず、**0 以外で `exit` するだけ**にする（`INT` は 130、`TERM` は 143、`HUP` は 129）。bash の `trap` は
   signal の処理の後にスクリプトの続きを実行するので、signal の `trap` で後片付けだけをすると、片付けた後に次の試行へ進み、
   最後に成功として終わりうるためである。`exit` で `EXIT` の `trap` が後片付けを1回だけ行う（走ったことを印にし、二回目は
   何もしない）。後片付けの間は `INT`・`TERM`・`HUP` を無視して二重に走らせない。後片付けの後の終了コードは、signal・中止・
   エラーで終わったときは元の 0 以外の値を保ち、後片付けが 3・4 を確かめられなかったときも 0 以外にする（0 は、すべての条件を
   最後まで行い、後片付けが 3・4 を確かめたときだけ）。後片付けは、**次の順序を必ず守る**。設定を先に消すと、すでに動いている fand が
   読み込み済みの 11 s の deadman のまま Fan を持ち続け、しかも reload 後の unit の定義は本番に戻ったように見えるためである
   1. **負荷を止める**: CPU / GPU の負荷のプロセスを止めて終わるのを待ち、GPU の電力の上限を既定に戻す。ただし fand が
      `SIGSTOP` で止まっている（`/proc/<main PID>/stat` の状態が `T`）なら、§2.5 の中止と同じく**先に 2 の `SIGKILL` を送って Max に
      してから**負荷を止める
   2. **fand を止める**: fand が `SIGSTOP` で止まっているなら、**先に `SIGKILL` を送る**
      （`SIGCONT` で動かさない。動き出した fand は止める前の古い状態で数 tick 書きうるので、止まったまま殺して
      `ExecStopPost` に Max を書かせる。実測 44〜51 ms は**kill できる fand に限る**。D 状態なら下の「3 を確かめられないとき」へ）。そのあと `systemctl stop coldaisle-fand`（`Restart=always` の再起動を
      止める。再起動していれば正常停止で BIOS へ返す）。`systemctl stop` が `TimeoutStopSec`（10 s）+ 5 s で終わらなければ
      `systemctl kill -s SIGKILL coldaisle-fand` を送ってから、もう一度 `systemctl stop` する
   3. **止まったことを確かめる**: `systemctl is-active coldaisle-fand` が `inactive`（`failed` なら `reset-failed` の後に
      `inactive`）、main PID が 0、3 zone の `pwmN_enable` がすべて `5`（正常停止で BIOS へ返した）か、すべて `0`
      （`SIGKILL` の後の `ExecStopPost` の Max。引き継ぎ記録が残る）であること
   4. 3 が確かめられたときだけ、**drop-in と試験の設定のディレクトリを消して `daemon-reload`** する
   5. **本番の設定に戻ったことを確かめる**（下の 4）

   後片付けの中の `pwmN_enable` などの sysfs の読み取りは、D 状態の driver で戻らないことがあるので、すべて時間の上限
   （`timeout 2`）をつけ、戻らなければ「読めない」として扱う（下の「3 を確かめられないとき」）。負荷をかけている間と `SIGSTOP` の
   間の読み取り（§2.5a の温度と、Max を待つ `pwmN_enable`）は、これより短い上限で読み、失敗・時間切れは**ただちに中止**にする（§2.5）。
   後片付けの「読めない」は、その中止の後の扱いであって、負荷を続けてよいという意味ではない。

   3 を確かめられないとき（`active` / `deactivating` のまま、`pwmN_enable` に `1` が残る、読めない、fand のプロセスの状態が
   `D` のまま。SIGKILL が効かない D 状態を含む）は、**drop-in と試験の設定を
   消さずに残し**、端末に大きく警告を出して（「fand が 11 s の試験の設定のまま動いている可能性。drop-in を残した」）、
   0 以外で終わる。所有者はその場で次を行う: `systemctl status coldaisle-fand` と `ps` で fand のプロセスが残っていないか、
   3 zone の `pwmN_enable` と `pwmN` を見る → 残っていれば `systemctl kill -s SIGKILL coldaisle-fand` と `systemctl stop` →
   それでも `pwmN_enable` が `1` なら 0121 §2.1 のとおり `5` を書く → `inactive` を確かめてから、手で drop-in と設定を消して
   `daemon-reload` し、下の 4 を確かめる

   **SIGKILL が効かない（fand の状態が `D` のまま終わらない、`pwmN_enable` の読み書きも戻らない）とき**は、`ExecStopPost` の Max も、
   人の `pwmN_enable=5` の書き込みも同じ driver で止まりうる（§1.1a）。Fan は最後の値のままと見なし、熱を減らす側で対処する。
   所有者が取れる手は、順に:
   1. CPU / GPU の負荷のプロセスが残っていないかを確かめて止める（`pgrep` / `pkill`。`nvidia-smi` で GPU の使用率と電力を見る）。
      GPU の負荷が止まらなければ、そのプロセスを `kill -KILL` し、GPU の電力の上限を最小にする（`nvidia-smi -pl`）。
      GPU の Fan は `coldaisle-gpu-fan`（別のプロセス・NVML。0128）が動かし続ける
   2. ほかの負荷（Docker のコンテナ・ビルドなど）も止め、マシンをアイドルに保つ。CPU は自身の温度の上限でクロックを下げる
   3. 温度を、試験のスクリプトの速い読み取り（読めれば）か `nvidia-smi` と BIOS の表示で見続ける。D 状態の調べのために
      `cat /proc/<main PID>/stack` と `dmesg` の `hung_task` を記録に残す（§5 の 9）
   4. 温度が下がらない、または読めないときの**最後の手段は電源を切る**。D 状態のプロセスがあると `systemctl poweroff` も
      止まりうるので、電源ボタンの長押しか電源ユニットのスイッチで切る。次の起動では fand は `disabled` なので起動せず、
      BIOS の制御で始まる。drop-in と試験の設定は残っているので、起動後に上の手順で消して下の 4 を確かめる

   `pwmN_enable` が `0`（Max）で終わったときは、試験の設定を消した後に、本番の設定で fand を `systemctl start` →
   STARTUP の後に `systemctl stop` で BIOS へ返す（0080 §2.8 の正常停止）か、Max のまま置くかを所有者が決める（どちらも安全側）
4. **元に戻ったことの確認**（スクリプトの最後と、所有者が目で）:
   - `systemctl show -p WatchdogUSec --value coldaisle-fand` が `5s`
   - `systemctl show -p ExecStart --value coldaisle-fand` に `--config-dir /etc/coldaisle/control-config ` がある
   - `/etc/systemd/system/coldaisle-fand.service.d/` に `t5-11s.conf` が無く、`/etc/coldaisle/control-config-test-t5-11s/` も無い
   - `systemctl is-enabled coldaisle-fand` が試験の前と同じ（`disabled`）。**drop-in がある間に `enable` しない**
   - 3 zone の `pwmN_enable` が `5`（`systemctl stop` で BIOS へ返した）か `0`（上の 3 の Max）で、`1` が無い

一時的な unit（`systemd-run` など）は使わない。本番の unit と違う形で動かすと、`ExecStopPost`・`KillMode`・権限が
本番と同じであることを別に確かめる必要が出るためである。

### 2.5 安全の扱い

- **制御の経路を迂回しない**（0121 §2.1）。Demand は fand の auto で決まり、Guard と Critical Safety を通る。
  Max を書くのは引き継ぎ実行部（Critical Safety の一部）だけで、人も試験のスクリプトも PWM を書かない。LLM は関わらない
- **中止の基準**は 0121 §2.1（`gpu.0.core` は 0130 §2.2 の 85 °C）と同じ: `cpu.package` 88 °C・`gpu.0.core` 85 °C・
  `board.connector_12v2x6` 70 °C。ただし見張りは T5 のスクリプトの DB（API の最新値。2500 ms ごと）ではなく、
  §2.5a の速い読み取りで行い、閾値は §2.5a の式で基準より下げる。**`SIGSTOP` の間は fand 自身の Critical Safety も
  止まっている**ので、この見張りと systemd の deadman だけが頼りになる
- **止めている間に見張りに届いたら**、**先に Max にし、その後で負荷を止める**。すなわち、まず fand の main PID へ `SIGKILL` を
  送り（管理ソケットは止まった fand に届かない）、本番の `TimeoutAbortSec` の経路と同じく `ExecStopPost` に Max を書かせる
  （**kill できる fand に限る**）。`SIGKILL` を送った直後に、負荷のプロセスへ `SIGKILL` を送る（`SIGTERM` で同期を待たない。
  GPU は続けて電力の上限を最小にする）。Max を待ってから負荷を止めるのではなく、両方を送ってから Max を確かめる。
  1 s で Max が見えなければ §2.3 の 3 の「SIGKILL が効かないとき」へ進む。その試行は合格にしない
- **温度が読めないときも中止する**。§2.5a の4つ（`Tctl`・`cpu.package`・`gpu.0.core`・`board.connector_12v2x6`）のどれか1つでも、
  読み取りが失敗した（エラー・値として解釈できない）か、時間の上限（250 ms）までに返らなかったら、負荷をかけている間と
  `SIGSTOP` の間は**ただちに上と同じ中止**（先に Max → 負荷を止める）を行う。1 回の失敗でも再試行を待たない。
  閾値の頼りの観測なしに、fand の Critical Safety が止まった状態で負荷をかけ続けない
  - 1 つの読み取りが driver の中で戻らなくても見張りが止まらないように、各センサーの読み取りは見張りと別のスレッド（または
    プロセス）で行い、見張りは 250 ms の期限までに結果が届かないことを失敗として扱う
  - `SIGSTOP` の間に Max を待つ `pwmN_enable` の読み取り（20 ms ごと）が失敗・時間切れ（250 ms）になったときも、Max を
    確かめられないので同じ中止を行う
  - **読み取りが成功して同じ値が続くことは、失敗として扱わない**。整数の値（NVML の GPU の温度）や EC の値はアイドルで
    長く変わらないのが正常で、値が変わらないことからは鮮度を判断できない（hwmon の `tempN_input` にも NVML の温度にも
    更新の時刻やカウンタが無い）
  - **成功するが古い値を返し続ける故障（EC や driver の値が固まる）は検知できず、これを試験の間に限り受け入れる**（§5 の 10。
    所有者、2026-10-16）。理由: 所有者が現地にいる・CPU は `Tctl`（k10temp）と `cpu.package`（EC）の別の経路の2つで見張る・
    固まる時間は最長でも約 12 s（§2.5 の 12000 ms の SIGKILL）・GPU は自身の Fan と温度の保護を持つ。2つの経路の食い違いを
    中止の条件にすること（新しい閾値が要る）は足さない。本番の運転の受け入れではない
  - §2.5a の求め方で `U` が決まらないセンサーがあれば、そのセンサーを頼る条件の試行は行わず、扱いは所有者が決める（§5 の 10）
  - Max の後（負荷を止めた後）の 30 s の読み取りの失敗は中止の操作を要しないが、§2.2 の判定に使う読み取りに欠けが
    あれば、その試行は合格にしない（判定の最大値に欠けの間の上がりが入らないため）
- **`SIGSTOP` から 12000 ms で Max が見えなければ**、上の中止と**同じ順序を丸ごと**行う: fand の main PID へ `SIGKILL` を送り、
  その直後に負荷のプロセスへ `SIGKILL` を送り、GPU の電力の上限を最小にしてから、Max を確かめる（1 s で見えなければ §2.3 の 3 の
  「SIGKILL が効かないとき」）。`ExecStopPost` が失敗していても負荷が残らないようにするためである。試行は無効とし、原因（journal の
  `Watchdog timeout` と `safety_handoff_completed`）を確かめるまで次の条件へ進まない。固まる時間は最長でも約 12 s に限る
- それでも Max にならなければ 0121 §2.1 のとおり `systemctl stop coldaisle-fand`、それも効かなければ
  `pwmN_enable` に `5` を書く。fand が SIGKILL で終わらない（D 状態）ときは、§2.3 の 3 の「SIGKILL が効かないとき」の手順を行う
- 所有者が現地にいて、開始と終了を行う（0121 §2.1）

### 2.5a 試験の見張りと判定に使う速い温度の読み取り

試験のスクリプトが、telemetry とは独立に、次を **250 ms ごとに直接読む**（読むだけで書かない。fand・telemetry・DB を通さない）。

| 対象 | 読む場所 | 使い方 |
|---|---|---|
| `cpu.package` | telemetry と同じ hwmon の属性（`config/internal-telemetry.yaml` の driver・label で特定した `tempN_input`） | 判定と見張り |
| CPU の内蔵センサー（k10temp の `Tctl`。`cpu.tctl`） | hwmon の `tempN_input` | 見張りだけ（`cpu.package` と高いほうで見張る。判定には使わない） |
| `gpu.0.core` | NVML の GPU コアの温度（`nvidia-smi` の起動は遅いので、試験のスクリプトから NVML を直接読む） | 判定と見張り |
| `board.connector_12v2x6` | telemetry と同じ hwmon の属性（T_Sensor） | 判定と見張り |

**見落としの分の式**:

- 読み取りから Max までの遅れ `L` = センサー自身の更新の間隔 `U` + 読み取りの間隔 0.25 s + 反応 `R`
- `R` = 閾値を超えた値を読んだ時刻から、スクリプトが `SIGKILL` を送り、`ExecStopPost` が Max を書き、それを読んで確かめるまで。
  SIGKILL から Max の実測 44〜51 ms だけでなく、スクリプトの判定・順番待ち・コマンドの起動の遅れを含む。**試験の前に、試験と同じ
  スクリプトの中止の経路で、その条件と同じ負荷をかけた状態で実測する**（§2.6 の 2。fand を `SIGSTOP` し、アイドル・CPU 全スレッド・
  GPU 600 W のそれぞれの負荷をかけた状態で中止を強制して、読み → SIGKILL → Max を負荷ごとに 3 回測る）。負荷で CPU が埋まると
  見張りの順番待ちとコマンドの起動が遅れうるので、アイドルの実測を負荷の条件に使わない。各条件の `R` は、その条件の負荷の
  実測の最長とアイドルの実測の最長の大きいほうにする（(i)・(iii) CPU は CPU 全スレッド、(iii) GPU は GPU 600 W、(ii) はアイドル）。
  実測までは保守的に **0.3 s** と置き、実測の最長が 0.3 s を超えたらその値で計算し直す。各試行で中止の経路が実際に動いたときは、
  その読み → Max の時間も記録し、`R` を超えていたらその値で閾値を下げてから次の条件へ進む。
  **kill できる fand に限る**。D 状態では反応に上限が無く、負荷を止めることだけが効く（§2.3 の 3）
- Max の後に負荷が止まるまでの時間 `S`（中止の経路の負荷の `SIGKILL` から、負荷のプロセスが終わり CPU / GPU の電力が下がるまで）。
  見込みは CPU（`stress-ng`）0.5 s・GPU 1.0 s で、`R` と同じ実測で確かめる。この間も熱は出続ける

最大の上昇の速さを `r` とすると:

- **中止の閾値** = 中止の基準 − `r` × (`L` + `S`) − 余裕 1 °C（切り捨て）
- **合格の判定** = 速い読み取りの最大値 + `r` × (`U` + 0.25 s) が、§2.2 の上限（85 °C / 75 °C）未満（判定は読み取りを Max の
  後 30 s まで続けるので、`R` と `S` の間の上がりは読み取りに入る。見落としうるのは読み取りの間と更新の間隔の分だけ）

`r` は、**閾値の近く（中止の基準の 15 °C 下から上）での**最大の上昇の速さを置く。見落としが問題になるのは閾値の近くだけで、
負荷の始まりの段（2500 ms ごとの記録で (i) CPU の 5.2 s に 40 → 72 °C、平均約 6 °C/s）は閾値から遠い温度で起きるためである。
閾値の近くの速さは記録から分からないので、保守的に CPU 8・GPU 3・T_SENSOR 1 °C/s と置き（0119 §2.12 の 16 s の平均は
GPU 約 1.4・T_SENSOR 約 0.2 °C/s）、§2.6 の 1 と各試行の速い読み取りで確かめる。

**`U`（センサー自身の更新の間隔）の求め方**。値が変わらないことから鮮度は推定しない（§2.5）。`U` には**上限として成り立つ
根拠**が要り、観測した最大は上限にしない（有限の時間の観測は、後で起こる長い更新の遅れを押さえない）:

1. **文書の上限だけを `U` の根拠にする**: 動いているカーネルの driver のソースに書かれた、値をためておく間隔の上限と、
   ハードウェア自身（CPU の温度センサー・EC・GPU）の更新の間隔のベンダーの文書の上限の和。版と該当の箇所を記録に残す。
   driver が読むたびにハードウェアを読む場合は driver の分は 0 とする。どちらかの文書の上限が無ければ、そのセンサーの `U` は
   **決まらない**
2. **観測は文書の上限を確かめるだけに使う**: 50 ms ごとの読み取りで、温度が上がっている区間（負荷の始まりから、250 ms の
   差分がセンサーの実際の刻み（`tempN_input` の単位の 1 m°C ではなく値が実際に動く幅。NVML は 1 °C）以上の間）に限り、値が変わった
   時刻の間隔の最大に読み取りの間隔 50 ms を足した値を求める。この値が文書の上限を超えたら、文書の上限がこの機械で
   成り立っていない疑いがあるので（温度が刻みより遅く上がっただけの場合もあるが、安全側に扱う）、`U` は**決まらない**。アイドルの区間の変化の間隔は使わない（値が変わらないのは温度が
   変わらないためでもありうる）
3. **試行の中の観測も 2 と同じに使う**: 各試行の上がりの区間で、変化の間隔の最大が `U` を超えたら、そのセンサーの `U` は
   決まらないものとして扱い、次の試行へ進まない（§5 の 11）。値が変わらない間に更新が遅れているのか温度が変わらないのかは
   その場では区別できないので、試行の中でこれを中止の条件にはしない。この見落としの分は 1 の文書の上限に頼る

`U` が決まらないセンサーがあれば、§5 の 10 の決定のとおり、そのセンサーを見張りと判定に使う条件の試行は行わず、扱いは所有者が
決める（§5 の 11）。`gpu.0.core` は §2.6 の 1 の CPU の負荷では上がらないので、2 の確かめは §2.6 の 2 の短い GPU の負荷の
上がりの区間で行う。下の表の `U` は文書を確かめるまでの見込みで（k10temp と NVML が 0.25 s、`asusec`（EC）が 1 s）、
試験の前に上の 1 で置き換える。

| 対象 | `r`（°C/s） | `U`（見込み） | `L` = `U` + 0.25 + `R` 0.3 | `S` | `r` × (`L` + `S`) | 中止の基準 | 中止の閾値 | 合格の判定（速い読み取りの最大値） |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| CPU（`Tctl` と `cpu.package` の高いほう） | 8 | 1 s（2つの `U` の大きいほう。`cpu.package` の見込み） | 1.55 s | 0.5 s | 16.4 °C | 88 | **70 °C** | `cpu.package` の最大 + 8 × (`U` + 0.25) < 85（`U` = 1 s なら 75 °C 未満、`U` = 0.25 s なら 81 °C 未満） |
| `gpu.0.core` | 3 | 0.25 s | 0.8 s | 1.0 s | 5.4 °C | 85 | **78 °C** | 最大 + 1.5 < 85（83.5 °C 未満） |
| `board.connector_12v2x6` | 1 | 1 s | 1.55 s | 1.0 s | 2.55 °C | 70 | **66 °C** | 最大 + 1.25 < 75（73.75 °C 未満） |

- `U`・`R`・`S` を求めたら、その値で上の表を計算し直し、試験の前に所有者に示す
- **試行の中で上昇の速さが `r` を超えたら、ただちに中止する**。その試行の中止の閾値は小さすぎる `r` × (`L` + `S`) で
  決めてあり、同じ試行の中で中止の基準を超えうるためである。負荷をかけている間と `SIGSTOP` の間に、速い読み取りの
  上昇の速さが `r` を超えたら、その時点で §2.5 の中止（先に Max → 負荷を止める）を行い、その試行は無効にする。観測した速さを
  新しい `r` として閾値と判定を計算し直し、所有者に示してから同じ条件をやり直す（§2.4 のやり直しの回数に数える）。
  **Max の後（負荷を止めた後）の 30 s の判定の窓の間も、上昇の速さが `r` を超えないことを確かめ続ける**。熱の遅れで負荷を
  止めた後も温度が上がり、§2.2 の判定の補正 `r` × (`U` + 0.25 s) はこの窓の中でも同じ `r` を前提にしているためである。
  この窓で `r` を超えたら、Max と負荷の停止はすでに済んでいるので中止の操作は要らないが、その試行は無効にし、観測した速さで
  閾値と判定を計算し直してから同じ条件をやり直す（上と同じ扱い）
  上昇の速さは、刻みの粗いセンサーで 1 つの刻みが速さを大きく見せないように、長さ max(0.25 s, センサーの刻み ÷ `r`) を
  0.25 s の倍数に切り上げた窓の差分で求める（例: NVML の 1 °C と `r` 3 °C/s で 0.5 s、T_SENSOR の刻みが 1 °C なら 1 s）
- CPU の中止の閾値は `Tctl` と `cpu.package` の高いほうに当てるので、`L` には**2つの `U` の大きいほう**を使う。閾値の近くで
  `cpu.package` のほうが高ければ、その値は `cpu.package` の更新の間隔だけ遅れて見えるためである（`Tctl` の速さで中止が
  早まるとは見なさない）。`cpu.package` の EC の更新が遅い（`U` が大きい）と、中止の閾値も合格の判定の幅も狭くなる。
  判定は `cpu.package` の値で行う（0121 §2.7 の上限が `cpu.package` に対するものであるため）。
  `cpu.package` の `U` が 1 s を超えたら §5 の 5

### 2.5b 止めている間の温度の見積もり

固まる時間は約 11.1〜11.9 s（§2.2）に、Max の後に負荷が止まるまでの `S`（0.5〜1.0 s。Fan は Max）を足した間の上がりを見積もる。
5.2 s の経路の記録は、Max を確かめた後に負荷を止めているので、同じくらいの `S` を含んでいる。記録から見積もる最高は次のとおり。

| 条件 | 根拠 | 見積もりの最高 |
|---|---|---|
| (i) CPU 全スレッド | 5.2 s の経路で 40 → 72 °C（Max の後 30 s まで）。0119 §2.12 では 16 s の窓で +31 °C、60 s で +33 °C と、最初の数秒の段の後は遅い（チップと冷却水の差が先に開き、冷却水は分の単位で上がる） | 40 + 33 + 余裕 3 ≒ **76 °C**（中止の閾値 70 °C を超えうる） |
| (iii) CPU | 5.2 s の経路で 43 → 74 °C。冷却水が温かいぶん開始が高い | 43 + 33 + 余裕 3 ≒ **79 °C**（中止の閾値 70 °C を超えうる） |
| (iii) GPU 600 W | 5.2 s の経路で 49 → 68 °C。0119 §2.12 の 16 s で +23 °C。GPU は自身の Fan（0130 の曲線）で冷え、筐体の Fan を固めても 600 W の定常は 78 °C（0130 §2.4 の 2） | 49 + 23 ≒ **72 °C**（定常の 78 °C を超えない） |
| T_SENSOR | 5.2 s の経路の最高 46 °C、16 s で +3 °C | **約 50 °C** |

T_SENSOR は余裕がある。GPU は見積もり 72 °C で、中止の閾値 78 °C と合格の判定 83.5 °C 未満の内側にある。CPU は、(i) の
76 °C も (iii) の 79 °C も中止の閾値 70 °C（`cpu.package` の `U` を 1 s と見込んだ値）を超える見積もりで、全スレッドのままでは
中止に届く見込みが高い。§2.6 の 1・2 の実測（`U`・`r`・
`R`・`S`）で閾値を計算し直してもなお届く見込みなら、CPU の条件は試験の前に §5 の 6 で負荷を決める。中止すれば、その試行は合格にしない（§2.5）。
CPU の条件が中止や判定の上限に届いたら、その条件は負荷を下げる（CPU の半分のスレッド）か外すかを所有者が決める（§5 の 6）。
届くと分かっている負荷で繰り返さない。

### 2.6 手順の骨子

所有者の作業用のディレクトリ（リポジトリの外）に、T5 のスクリプトを元にした試験のスクリプトを用意し、内容を事前に
示してから所有者が自分の端末のシェルで実行する。コマンドは次のとおりで、前に何も付けない（bash の `!` は終了コードを反転し、
後片付けが fand の停止を確かめられなかったときの 0 以外の終了を 0 に見せてしまう）。終わったら終了コードが 0 であることを確かめる
（0 以外なら §2.3 の 3 の「3 を確かめられないとき」の手順を行う）。

```bash
sudo bash <作業用のディレクトリ>/deploy/t5-11s.sh ii-idle i-cpu iii-cpu iii-gpu600; echo "exit=$?"
```

スクリプトの中身はリポジトリに置かない（実機の識別子を含むため。AGENTS.md ルール 10）。

0. **最初に**、終了時の後片付け（§2.3 の 3・4）を `trap` で登録する（§2.3 の 3。1 の負荷・2 の設定と drop-in と fand の起動より前）
1. 前提の確認: fand が止まっていて `disabled`、本番の unit に drop-in が無い、`coldaisle-gpu-fan` が 0130 の曲線で
   動いている、ほかの CPU 負荷（Docker のコンテナなど）が無い、CPU 電力が 40 W 未満。あわせて、§2.5a の各センサーを
   50 ms ごとに 60 s 読み（アイドルで 30 s、CPU 全スレッドで 30 s。fand は BIOS のまま）、§2.5a の求め方で、文書の上限から
   置いた `U` が上がっている区間の変化の間隔と矛盾しないことを確かめ（アイドルの区間の値が変わらないことは使わない。文書の版と
   箇所を控える。`U` が決まらないセンサーがあれば §5 の 11 で所有者が決めるまで先へ進まない）、§2.5a の窓の差分から上昇の速さ（閾値の近くの温度での速さを含む）を実測する。読み取りが失敗・時間切れになったセンサーがあれば、
   原因が分かるまで先へ進まない
2. §2.3 の 1・2 を置き、`daemon-reload`。§2.3 の 2 の確認（`WatchdogUSec` が `11s` など）が1つでも成り立たなければ試験を始めない。
   続けて、アイドルで fand を起動して `SIGSTOP` し、試験と同じスクリプトの中止の経路を強制して、読み → `SIGKILL` → Max の `R` を、
   アイドル・短い CPU 全スレッド・短い GPU 600 W の負荷をかけた状態でそれぞれ 3 回ずつ測り（§2.5a。負荷は冷えた状態から始めて
   すぐに中止を強制するので、温度は閾値から遠い）、同じ中止で負荷の `SIGKILL` から電力が下がるまでの `S` も測る（中止の経路の練習を兼ねる）。
   この間も §2.5 の見張りと読み取りの失敗での中止は効かせる。
   1 と 2 の実測で §2.5a の表を計算し直し、所有者に示してから条件の試行へ進む
3. 条件ごとに: `systemctl start`（`enable` しない）→ STARTUP の 20 s → 条件の準備（落ち着きの判定・(iii) の 10 分と
   アイドル + 0.05 への戻り）→ `WatchdogTimestampMonotonic` が変わった直後に `SIGSTOP` → (i)・(iii) はその直後に負荷を始める
   → 20 ms ごとに `pwmN_enable` を読み Max を待つ（§2.5 の 12000 ms と、§2.5a の 250 ms ごとの見張り）→ Max の後に負荷を止め 30 s 見る →
   `systemctl stop` で BIOS へ返す → 60 s 置く
4. 後片付け: §2.3 の 3 の順序（負荷 → fand の停止 → 停止の確認 → 設定を消す → 本番の確認）で行い、結果を表示する。
   DB・journal（`__MONOTONIC_TIMESTAMP` つき）を書き出す

### 2.8 合格した後の確定

- 4 条件すべてで §2.2 を満たしたら、0121 §2.10 のとおり、`watchdog_timeout_ms` 5000 の `status` を `confirmed`・`basis` を
  0121 §2.7・本記録・`docs/fan-header-mapping.md` の T5 にする変更を、所有者の承認（0028 §2.9 の**承認点 2**）を得て
  `/etc/coldaisle/control-config/safety.yaml` に当てる。確定するのは 5000 で、試験の 11000 ではない
- この確定は **kill できる hang の経路（§1.1a）に対する条件つき**であり、`basis` にもそう書く。D 状態の hang で Max までの
  時間に上限が無いことは確定の範囲の外で、その残るリスクを受け入れるかは §5 の 8 で所有者が決める。受け入れないなら
  `confirmed` にしても承認点 3 と `enable` には進まない
- この確定は「`TimeoutAbortSec` が 5 s 以下」を前提にする。unit のタイムアウトは `provisional` のまま進む（§1.3）が、

- 0121 のほかの試験の値の確定とそろってから**承認点 3** を完了とし、`enable` は所有者が判断する（0121 §2.10）
- 満たさない条件があれば、値も設定も本記録では変えない。§5 の 3 のとおり別の決定記録で案を出す。それまで `enable` しない

## 3. Consequences

### 良くなること

- 0119 §2.13 が `watchdog_timeout_ms` に求める「最悪時間の間の温度」を、本番の最悪より約 1 s 長い時間で実測できる
- 本番の値・unit・`safety.yaml` を書き換えずに済む。違いは `diff -r` で1行・drop-in で2つの指令だけ
- 引き継ぎ（Max を書く経路）・`KillMode`・権限は本番のまま試すので、5.2 s の経路の結果と同じ部品で比べられる

### 悪くなること・その緩和

- 試験の間は deadman が 11 s に延び、hang から Max までが本番より遅い。緩和: 所有者が現地・`enable` しない・スクリプトの
  実行の間だけ・止めている間の見張りと 12000 ms での SIGKILL（kill できる fand に限る）・`trap` での後片付けと確認。
  試験の中で fand が D 状態になれば SIGKILL も効かず、§2.3 の 3 の手順（負荷を止める・最後の手段で電源を切る）に頼る
- SIGKILL で終わる本番の最悪の経路の「時間」は、この試験では通らない（SIGABRT で終わる）。緩和: SIGKILL から Max は
  予備確認の 44〜51 ms で足りており（kill できる fand に限る。D 状態では上限が無い。§1.1a）、本記録で要るのは固まる時間の長さだけである。時間の下限 10100 ms で本番の最悪を覆う
- **D 状態の hang は守れないまま残る**（§1.1a）。試験に合格しても、hwmon の driver の中で書き込みが戻らなければ、Fan は最後の
  低い Demand のまま上限の無い時間残りうる。緩和は本記録の中には無く、§5 の 8・9 で所有者が受け入れか手当てを決める
- **成功するが古い値を返し続ける温度の読み取りは検知できないまま試験する**（§2.5・§5 の 10）。見張りの閾値はその値が新しいことを
  前提にしているので、固まった値が続けば中止が遅れうる。緩和: 所有者が現地にいる・CPU は `Tctl` と `cpu.package` の2つの経路で
  見張る・固まる時間は最長でも約 12 s・GPU は自身の Fan と温度の保護を持つ。所有者が試験の間に限り受け入れた（2026-10-16）
- drop-in を消し忘れると deadman が 11 s のまま残る。緩和: `trap`・§2.3 の 4 の確認・`enable` の前に
  `systemctl cat coldaisle-fand` で drop-in が無いことを所有者が確かめる

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| `WatchdogSignal` を無視される signal にして `TimeoutAbortSec` の経路を本物で通す | systemd の `SIGCONT` で fand が動き出し、Demand を書き続ける。「低い Demand のまま固まる」状態にならない |
| `SIGCONT` の後にもう一度 `SIGSTOP` する | 動き出した瞬間に fand が書くかどうかが競合で決まり、固めた Demand が保証できない |
| `WatchdogSec` / `watchdog_timeout_ms` を 10 s にする | 固まる時間が約 10.1〜10.9 s で、本番の最悪（約 10.05 s）との余裕が小さい。0127 §5 の 2 (a) の 11 s のままにする |
| 一時的な unit（`systemd-run`）で動かす | `ExecStopPost`・`KillMode`・権限・hardening が本番と同じであることを別に確かめる必要がある（§2.3） |
| 本番の `/etc/coldaisle/control-config/safety.yaml` と unit を一時的に書き換える | 戻し忘れが本番の値に残る。0121 §2.1 の T6 と同じく別の場所と drop-in にする |
| 5.2 s の結果から 10 s の上がりを見積もる（0127 §5 の 2 (c)） | 5 s の負荷で `cpu.package` が +31〜32 °C 上がり、その後の上がり方の根拠が無い（0127 §2.5）。所有者は (a) を選んだ |
| 最悪時間そのものを短くする（`TimeoutAbortSec` を短く、または `WatchdogSignal=SIGKILL`。0127 §5 の 2 (b)） | 0080 §5 の 1・3 の決定に当たり、所有者はタイムアウトを `provisional` のまま進むと決めた（§1.3）。試験が不合格なら §5 の 3 で改めて出す |
