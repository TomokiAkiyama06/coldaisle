## 1. Context

### 1.1 今の振る舞い

しきい値・範囲のルール（`recirculation`・`intake_high`・`airflow_degraded`・`room_high`・`humidity_out_of_range`）は、
取り込みの `Engine.on_sample()` がサンプルごとに評価する（`main` の `src/coldaisle/rules/engine.py`）。

- 入力の値は、そのサンプルの読み値の品質が ok のときだけ使い、ok でなければ `None` にする（`on_sample()`）。
  派生値（`d.intake_rise = air.front_intake − air.room`・`d.gpu_delta = air.gpu_exhaust − air.gpu_intake`）は、
  2 つの入力の両方が ok のときだけ計算し、どちらかが欠ければ `None`（`metrics.compute_derived()`）
- `_evaluate_threshold()` / `_evaluate_range()` は `value is None` で**何もせず返る**。`RuleState.since_ms`（条件が成立した時刻）と
  DB の pending の行はそのまま残る
- サンプルそのものが届かない間（無音）は、`on_tick()` が `SENSOR_FAULT` だけを評価し、しきい値・範囲のルールは評価しない。
  ここでも `since_ms` は残る
- 次に値が来て条件が成立していると、`_continue()` が `now − since_ms` を `fire_after_s` と比べる。
  **欠けの空白をまたいで「条件が続いた」とみなして発火しうる**（0131 §2.3 で GPU の Fan のルールについて指摘した問題と同じ）
- 再起動では、`_hydrate()` が DB の pending の行の `started_ms` を `since_ms` に戻す。停止していた時間もまたぐ
- 解除は閾値（`clear`・`low_clear` / `high_clear`）を下回った周期で即時なので、解除の側の問題は無い。
  `rapid_rise` は `fire_after_s: 0`、`sensor_fault`・`sensor_missing`・`probe_changed` は継続時間の pending を持たないので該当しない

### 1.2 空白をまたいだ発火が困る理由

- **観測していない継続を、継続として通知する。** 例: `room_high`（`fire_after_s: 600`）が 30 °C を 1 回超えて pending → 取り込みが
  2 時間止まる → 再開の最初のサンプルが 30 °C を超えている、だけで発火する。説明（0016 / #38 の `_rule_evidence()`）は
  `fired_ms − started_ms` から「条件が 7200 秒継続して発火」と書く。人も LLM の説明も、2 回の観測を 2 時間の継続と読む
- `fire_after_s` は「揺らぎで鳴らさない」ための待ち（0012 §2.4）なので、観測の無い時間で満たすと、その目的が崩れる

### 1.3 基板のセンサーの欠け方

- 送信周期は 2.5 s（ファームウェアの `INTERVAL_MS = 2500`）。1 サンプルに 7 チャネル（`air.*`）が載る
- DS18B20（`front_intake`・`gpu_intake`・`gpu_exhaust`・`top_exhaust`・`rear_exhaust`）は 1 本ずつ欠ける。読み取りの失敗・`-127`・
  ちょうど `85.00` は、そのチャネルだけが `null`（0022 §2.3、0003 §2.3）で、ホストでは `missing` / `suspect`
- AM2320 は `air.room` と `air.room_humidity` を**同時に**欠く（1 回の読み取りで両方）。読み取りの失敗が 5 回続くと、
  12 周期（約 30 s）読まない（0022 §2.11。`AM2320_FAIL_LIMIT = 5`・`AM2320_BACKOFF_CYCLES = 12`）。
  この 1 回の欠けは **5 + 12 = 17 サンプル ≈ 42.5 s** になる。起動の直後の 1 回目の読み取りは必ず失敗する（0022 §2.11）
- したがって 5 つのルールの入力の欠けは次のように依存する

| ルール | 入力 | `fire_after_s` | `fire_after_s` に要るサンプル数 | 欠ける原因 |
|---|---|---|---|---|
| `intake_high` | `air.gpu_intake` | 120 | 48 | DS18B20 1 本 |
| `recirculation` | `d.intake_rise`（`air.front_intake` − `air.room`） | 300 | 120 | DS18B20 1 本 **または AM2320** |
| `airflow_degraded` | `d.gpu_delta`（`air.gpu_exhaust` − `air.gpu_intake`） | 300 | 120 | DS18B20 2 本のどちらか |
| `room_high` | `air.room` | 600 | 240 | AM2320 |
| `humidity_out_of_range` | `air.room_humidity` | 600 | 240 | AM2320 |

- 既存の欠けの検知: `sensor_missing`（warning）は 1 つのメトリクスが **連続 5 サンプル**（`consecutive: 5` = 12.5 s）ok でないと
  即時に発火し、3 サンプル ok で解除する。`sensor_fault`（critical）はサンプルが **30 s**（`silence_s`）来ないと発火する。
  `config/quality.yaml` の `stale_after_ms` は 10 s（Store が読み出し時に stale とする閾値。0004 §2.12。取り込みのルールは
  サンプルの値で評価するので、今は使っていない）

## 2. Decision

### 2.1 選択肢と推奨

| 案 | 取り消す条件 | 発火が遅れる場面 |
|---|---|---|
| A | 入力が 1 回でも欠けたら（0131 §2.3 と同じ） | 1 サンプルの欠けでも数え直し。散発的な欠けで**発火しないまま続き、ほかの通知も出ない**（2.2） |
| B | 取り消さない（今のまま） | 遅れない。代わりに空白をまたいで発火する（1.2） |
| C | 入力の最後の ok から `stale_after_ms`（10 s）を超えた空白があったら | 4 サンプル以上の連続の欠け（12.5 s）で数え直し。4 サンプルちょうどの欠けでは `sensor_missing`（5 サンプル）が鳴らない |
| **D（推奨）** | 入力の欠けで `SENSOR_MISSING`（連続 `consecutive` = 5 サンプル）が発火したら、またはサンプルの無音で `SENSOR_FAULT`（`silence_s` = 30 s）が発火したら | 欠けの検知が成立したときだけ数え直す。**数え直しのたびに `SENSOR_MISSING` / `SENSOR_FAULT` が人に届く**（2.2） |

**D を採る。** 取り消す条件を、既存の「欠けている」の判定（`sensor_missing` / `sensor_fault`）に揃える。

- 1〜4 サンプルの短い欠け（DS18B20 の 1 回の読み損じ、AM2320 の 1〜4 回の失敗）では pending を保つ。遅れはほぼ 0（2.2）
- 欠けで `SENSOR_MISSING` / `SENSOR_FAULT` が発火したら、pending を取り消し、回復の後に条件が成立した時刻から数え直す。
  取り消しは**そのアラートがエンジンの状態として発火しているときに限り**、独立の数え方を持たない（2.3）。
  **発火が遅れるときは、必ずその原因（センサーの欠け・無音）のアラートが出ている**。黙って遅れることが無い
- アラートが出ない欠け（`sensor_missing` / `sensor_fault` の無効化・欄の省略・再起動の空白）では取り消さない（今と同じ）
- 新しい閾値を足さない。数え直しの境界は `SENSOR_MISSING` / `SENSOR_FAULT` の判定そのもの（`config/rules.yaml` の
  `sensor_missing.consecutive` と `sensor_fault.silence_s`）に従う（AGENTS.md ルール 9。値を 2 か所に持たない）

### 2.2 発火が遅れる場面の評価（2.5 s 周期・`config/rules.yaml` の今の値）

条件は時刻 0 から成立し続けるとする。欠けが無ければ、発火は `fire_after_s` の時刻（`intake_high` 120 s、`recirculation`・
`airflow_degraded` 300 s、`room_high`・`humidity_out_of_range` 600 s）。

**(1) 1 回だけの短い欠け（1 サンプル）が、発火の直前に来たとき**

| 案 | `intake_high` | `room_high` / `humidity_out_of_range` |
|---|---|---|
| A | 117.5 s で取り消し → 120 s から数え直し → **240 s**（+120 s） | 597.5 s で取り消し → **1200 s**（+600 s） |
| B・C・D | 120 s（遅れない） | 600 s（遅れない） |

**(2) 散発的な 1 サンプルの欠けが独立に起きるとき（A だけの問題）**

欠ける確率を 1 サンプルあたり p とすると、A では `fire_after_s / 2.5 + 1` サンプル連続で ok が要る。発火までの時間の期待値
（連続の成功を待つ回数の期待値 (1 − q^L) / (p·q^L)、q = 1 − p、L = 必要な連続数、× 2.5 s）:

| p | `intake_high`（欠け無しで 120 s） | `recirculation` / `airflow_degraded`（300 s） | `room_high` / `humidity_out_of_range`（600 s） |
|---|---|---|---|
| 0.1 % | 約 126 s | 約 322 s | 約 682 s（11 分） |
| 1 % | 約 159 s | 約 593 s（10 分） | 約 2567 s（43 分） |
| 2 % | 約 211 s | 約 1316 s（22 分） | 約 16146 s（4.5 時間） |
| 5 % | 約 567 s | 約 24748 s（6.9 時間） | 事実上発火しない（約 135 日） |

派生値のルールは 2 つの入力のどちらの欠けでも数え直すので、p は 2 つの和に近くなる（`recirculation` は DS18B20 1 本 + AM2320）。
**A では、AM2320 が 2 % 程度の散発的な読み損じを持つだけで、`room_high` と湿度の発火が数時間遅れ、そのあいだ `SENSOR_MISSING` も
鳴らない（5 回連続にならない）。** C と D では、独立な欠けが 4〜5 回続く確率は p^4〜p^5（p = 5 % で 1 サンプルあたり 6×10⁻⁶ 以下）で、
遅れは無視できる。

**(3) 発火が遅れる最悪の例（D）: AM2320 の 1 回の失敗の連続（17 サンプル ≈ 42.5 s）**

`room_high` が時刻 0 から成立 → 597.5 s まで ok → 600 s から AM2320 が 5 回失敗し約 30 s 読まない（600〜640 s の 17 サンプルが欠け）。

| 案 | 動き | 発火 |
|---|---|---|
| B | 642.5 s の最初の値で `642.5 − 0 ≥ 600` | 642.5 s（「642 秒継続」と記録。うち 42.5 s は観測していない） |
| C | 642.5 s で空白 42.5 s > 10 s → 取り消して 642.5 s から数え直し | **1242.5 s**（+642.5 s） |
| D | 610 s（5 回目の欠け）で `SENSOR_MISSING`（`air.room` と `air.room_humidity`）が発火、同時に取り消し → 642.5 s から数え直し | **1242.5 s（約 20.7 分。+642.5 s）**。610 s に `SENSOR_MISSING` が届き、647.5 s（3 サンプル ok）で解除される |

同じ形で `recirculation`（300 s）は 300 + 42.5 + 300 ≈ **642.5 s**、`intake_high`（120 s）は DS18B20 の 5 回の欠け（12.5 s）で
117.5 + 15 + 120 ≈ **252.5 s** になる。

**(4) 発火しないまま続く最悪の例（D）: 欠けが `fire_after_s` より短い間隔で繰り返す**

AM2320 が 10 分より短い間隔で「5 回失敗 → 30 s 休む」を繰り返すと、`room_high`・`humidity_out_of_range`（600 s）と
`recirculation`（300 s）は**一度も発火しない**。このとき `SENSOR_MISSING`（warning）が欠けのたびに発火・解除を繰り返すので、
人は「室内のセンサーが壊れかけている」ことを知る。部屋の温湿度の判定ができないことは、その通知で代わりに伝わる。
A では同じことが **1 サンプルの欠け**で起き、`SENSOR_MISSING` も鳴らない（(2)）。C では 4 サンプルちょうどの欠けの繰り返しで
起き、`SENSOR_MISSING` は鳴らない。

**(5) サンプルの無音**

| 無音の長さ | D | B |
|---|---|---|
| 30 s 未満 | pending を保つ（`sensor_fault` は鳴らない。遅れなし） | 保つ |
| 30 s 以上 | `SENSOR_FAULT`（critical）が鳴った時点で取り消し、再開の後に数え直す（一括再生では空白の後の最初のサンプルで。2.3.3） | 保つ。再開の最初のサンプルで発火しうる（1.2 の 2 時間の例） |

### 2.3 振る舞いの定め（D）

5 つのルール（`recirculation`・`intake_high`・`airflow_degraded`・`room_high`・`humidity_out_of_range`）に当てる。
`rapid_rise`・`sensor_fault`・`sensor_missing`・`probe_changed` と、0131 の GPU の Fan の 2 つのルール（0131 §2.3 のまま）の
判定は変えない（`sensor_fault` の無音の測り方だけ、一括再生のために 2.3.3 で直す）。

**原則: pending の取り消しは、取り消しの原因になった欠けを知らせるアラート（`SENSOR_MISSING` / `SENSOR_FAULT`）が
エンジンの状態として発火しているときに限る。** 取り消しのために独立の数え方を持たない。
**いまの設定で無効（`enabled: false`）の故障ルールの発火中の行・状態は、どの経路（サンプルごと・無音・復元）でも取り消しの根拠に使わない。**
無効にした後に DB に残った行を `_hydrate()` が復元しても、それでは取り消さない（通知の経路としてもう働いていないため）。
アラートが出ない欠け（故障アラートの無効化・欄の省略・再起動の空白）では取り消さず、今までどおり pending を保つ。
黙って発火が遅れる経路を作らないためである（その場合に残る空白をまたいだ発火は §5 で扱う）。

#### 2.3.1 センサーの欠け（`SENSOR_MISSING` に結びつける）

- 評価の順は今のまま（`on_sample()` で `_evaluate_silence()` → `_evaluate_missing()` → しきい値・範囲）。
  しきい値・範囲のルールは、同じサンプルの `_evaluate_missing()` の後の `SENSOR_MISSING` の状態を読む
- ルールの値が `None` のサンプルで、次の 2 つを満たす入力のメトリクスが 1 つでもあれば、pending を取り消す
  - そのサンプルでそのメトリクスが ok でない（読み値の品質が ok でない）
  - そのメトリクスの `SENSOR_MISSING` が**発火中**（`RuleState` の `firing`。0012 の状態機械の状態そのもの）で、
    **いまの設定で `sensor_missing.enabled: true`**（無効にした後に復元した行は根拠にしない）
- 入力のメトリクスは、ルールの `metric` が派生値なら `config/metrics.yaml` の `minuend` / `subtrahend` の 2 つ、そうでなければ `metric` 自身
- 取り消しは、pending の行を消し `since_ms` を戻す（0012 §2.4 の「継続時間に届かなかった揺らぎは消す」と同じ。遷移は配らない）。
  0131 §2.3 の実装で作る共通の部品（`RuleState` を pending から戻す関数）を使う
- 結果として次のときは取り消さない（pending を保つ）:
  - `sensor_missing.enabled: false`（`SENSOR_MISSING` の状態が作られない）
  - 欄が省かれたサンプル。0003 §2.3 は測定値の欄を必須にせず、`Normalizer` は `raw.channels` にある鍵にしか読み値を作らないので、
    `_evaluate_missing()` は省かれた欄を数えず `SENSOR_MISSING` も出ない。今のファームウェアは欠けた値も `null` で送る（0022 §2.3）ので、
    省略は起きない前提だが、起きても黙って遅らせない
  - 派生値の 2 つの入力が交互に欠け、どちらも 5 回連続にならないとき
  - 1〜4 サンプルの欠け（`SENSOR_MISSING` が発火しない）
- `SENSOR_MISSING` が前から発火したまま（例: 3 サンプルの ok を待つ間）に再び欠けた場合は、その 1 サンプルで取り消す。
  欠けを知らせるアラートは既に人に届いており、黙った遅れではない

#### 2.3.2 再起動

- 欠けの連続の数（`SENSOR_MISSING` の `streak`）は今もメモリにしか無く、再起動で 0 に戻る。2.3.1 は独立の数を持たないので、
  「4 回の欠け → 再起動 → 1 回の欠け」では `SENSOR_MISSING` も取り消しも起きない。**取り消しの条件とアラートの条件が食い違わない**
- `_hydrate()` が DB から読み戻した `SENSOR_MISSING` / `SENSOR_FAULT` の発火中の状態は、2.3.1・2.3.3 の「発火中」としてそのまま使う
- **復元の時の取り消し（移行を含む）**: `_hydrate()` の終わりに、読み戻した 5 つのルールの pending（未発火）のうち、
  次のどちらかに当たるものを取り消す（行を消し `since_ms` を戻す。遷移は配らない）
  - その入力のメトリクス（派生値なら `minuend` / `subtrahend`）の `SENSOR_MISSING` が発火中で読み戻され、**いまの設定で `sensor_missing.enabled: true`**
  - `SENSOR_FAULT` が発火中で読み戻され、**いまの設定で `sensor_fault.enabled: true`**

  故障ルールを無効にした後に発火中の行が DB に残っている場合（今の `_hydrate()` は `enabled` を見ずに復元する）は、その行を理由に取り消さない
  （2.3.1・2.3.3 の「故障ルールが無効なら取り消さない」と揃える）。無効にしたルールの残った行そのものの扱いは今のまま変えない
- **復元で読むアラート**: 今の `_hydrate()` は `store.alerts(limit=1_000)` で解決済みを含む新しい 1000 件だけを読むので、
  古い発火中の故障アラートや pending が窓の外に落ちうる。復元は**件数の上限なしに、有効な（`pending` / `firing` の）アラートだけを読む**
  問い合わせで行う（`SqliteStore` に足す。`state IN ('pending', 'firing')` の条件で、解決済みの行の数に影響されない）
  発火中の故障アラートは既に人に届いているので、黙った遅れにならない。発火の時刻の前後は比べない（故障アラートが先に発火していて、
  その解除を待つ間に pending が始まった場合も取り消す。安全側に、観測の切れ目をまたいだ継続を数えない）。
  **本記録の振る舞いを初めて入れる更新**では、更新の前のエンジンが取り消さずに残した「発火中の故障アラート」と「同じ空白をまたいで pending のままの
  しきい値・範囲のアラート」が DB に両方ありうる。2.3.1（今の読みが ok でないことを要する）と 2.3.3（`SENSOR_FAULT` が新しく発火したときだけ）
  はどちらもこれを取り消さず、更新の後の最初のサンプルが ok で閾値を超えていれば、空白の前の `started_ms` から数えて即時に発火しうる。
  この規則はその移行の状態も同じに閉じる（移行のための別の処理を持たない）
- 再起動の空白（停止していた時間）だけを理由には取り消さない。今の `begin()` は空白を `SENSOR_FAULT` にしないので、
  取り消すと黙った遅れになる。読み戻した pending は今までどおり引き継ぐ（空白をまたいだ発火が残る。§5 の 4）

#### 2.3.3 無音（`SENSOR_FAULT` に結びつける。一括再生を含む）

- `sensor_fault.enabled: true` のときだけ当てる。無効なら取り消さない
- **無音の条件（今の時刻、または新しいサンプルの時刻 − 直前のサンプルの時刻 ≥ `silence_s`）を満たす評価では、`SENSOR_FAULT` が
  新しく発火したか既に発火中かによらず、5 つのルールの pending をすべて取り消す。** サンプルが `clear_s` より短く戻る間に pending が始まり、
  `SENSOR_FAULT` が発火中のまま再び空白が来た場合（「戻ってすぐまた空白」）も、2 回目の空白で取り消す。発火中の `SENSOR_FAULT` は人に届いて
  おり、黙った遅れにならない
- `on_tick()` で無音が `silence_s` に届いた評価（`SENSOR_FAULT` が発火した評価と、発火中で無音が続く評価）で取り消す。無音の間は
  サンプルが来ないので pending は新しく始まらず、繰り返しの取り消しは何もしない
- **一括再生（`--bulk`）と処理の滞り**: 一括再生では受け箱が空にならず `on_tick()` が呼ばれない。また今の `on_sample()` は
  `_last_sample_ms` を新しいサンプルの時刻に**先に**更新してから `_evaluate_silence()` を呼ぶので、CSV の空白は無音として見えない。
  そこで `on_sample()` は、`_last_sample_ms` を更新する**前に**、新しいサンプルの時刻と直前のサンプルの時刻の差で無音を評価する
  - 差が `silence_s` 以上で `SENSOR_FAULT` が発火していなければ、そのサンプルの時刻（0012 §2.2 の評価時刻）で `SENSOR_FAULT` を開いて発火させ、
    同じ評価で 5 つのルールの pending を取り消す。`detail` は今と同じ形（「N 秒サンプルが届いていない」）
  - 差が `silence_s` 以上で `SENSOR_FAULT` が既に発火中なら、発火中のまま、同じ評価で 5 つのルールの pending を取り消す
  - どちらでも、そのサンプルは届いているので、`resumed_ms` をそのサンプルの時刻にし直し（前の再開からの数えは捨てる）、`clear_s` 届き続けたら今までどおり解除する
  - 実時間の運転では、`on_tick()` が先に `SENSOR_FAULT` を発火させているので、上の分岐は何もしない（発火中のまま再開の扱いへ進む）
- これにより、一括再生でも CSV の空白が `SENSOR_FAULT` として記録される。今は一括再生では空白で `SENSOR_FAULT` が出ないので、
  `sensor_fault` の振る舞いの変更である（2.5 で確かめる）

#### 2.3.4 共通

- **発火中（firing）のしきい値・範囲のルールは取り消さない・解除しない。** 欠けの間は今までどおり何もせず、回復後に解除の閾値で解除する
- 新しい閾値を足さない。`sensor_missing.consecutive`・`sensor_fault.silence_s` は今までどおりそのルールの判定にだけ使う
- 評価時刻は 0012 §2.2 のまま（サンプルの `ts_ms`）。圧縮再生・一括再生でも同じに動く

### 2.4 変わるコードの場所（実装は本記録の承認の後。0131 の実装（#292）の共通の部品の後）

### 2.5 テストで確かめること（実機なし。SimulatedClock と 2.5 s のサンプル列。AGENTS.md ルール 7）

- `intake_high`: pending の途中で `air.gpu_intake` が 4 サンプル欠けても、最初の成立から 120 s で発火すること（今と同じ）
- `intake_high`: 5 サンプル欠けると、`SENSOR_MISSING` が発火した同じサンプルで pending の行が消え、遷移が配られず、
  回復の時刻から 120 s 続いて初めて発火すること
- `recirculation`: `air.room` だけ・`air.front_intake` だけが 5 サンプル欠けたとき、どちらでも取り消すこと。
  2 つが交互に欠けてどちらも 5 回連続にならないときは取り消さないこと。`SENSOR_MISSING` が発火中の入力が ok に戻っていて、
  もう片方が 1 サンプル欠けたときは取り消さないこと
- `humidity_out_of_range`（範囲）: 低い側・高い側で同じに動くこと
- AM2320 の形（5 回失敗 + 12 周期休む = 17 サンプルの欠け）で、`room_high` の発火が 2.2 (3) の時刻（1242.5 s）になること
- 発火中のアラートが 5 サンプル以上欠けても解除されず、回復後に解除の閾値で解除されること
- **故障アラートの無効化**: `sensor_missing.enabled: false` では 5 サンプル以上欠けても取り消さず、今と同じ時刻に発火すること。
  `sensor_fault.enabled: false` では 30 s 以上の無音でも取り消さないこと
- **欄の省略**: 入力の欄をサンプルから省いた（`null` でなく鍵ごと無い）とき、`SENSOR_MISSING` が出ず、取り消しも起きないこと
- **再起動**: 4 サンプル欠けた後に再起動し 1 サンプル欠けたとき、`SENSOR_MISSING` も取り消しも起きないこと。
  発火中の `SENSOR_MISSING` を読み戻した後の欠けでは取り消すこと。停止の空白だけでは読み戻した pending を取り消さないこと
- **復元の時の取り消し（移行）**: 更新の前のエンジンが残した DB の状態として、発火中の `SENSOR_MISSING`（`air.room`）と、それより前の
  `started_ms` を持つ pending の `ROOM_HIGH`（および `RECIRCULATION`）を置いて起動し、最初のサンプルが ok で閾値を超えていても発火せず、
  そのサンプルの時刻から数え直すこと。発火中の `SENSOR_FAULT` と pending の 5 つのルールでも同じこと。入力に関係しない
  `SENSOR_MISSING`（例: `air.top_exhaust`）だけが発火中なら、`INTAKE_HIGH` の pending を引き継ぐこと。発火中（firing）のしきい値のアラートは取り消さないこと
- **無効化した後の残った行（サンプルごとの経路）**: `sensor_missing.enabled: false` にした設定で、以前の発火中の `SENSOR_MISSING`（`air.gpu_intake`）の行が
  残ったまま起動し、`INTAKE_HIGH` が pending になった後に `air.gpu_intake` が 1 サンプル欠けても取り消さないこと
- **戻ってすぐまた空白**: 30 s の無音で `SENSOR_FAULT` が発火 → サンプルが `clear_s`（10 s）より短く戻る間に `INTAKE_HIGH` が pending になる →
  再び 30 s の無音、のとき、`SENSOR_FAULT` は発火中のまま、2 回目の空白で pending が取り消され、空白の前の `started_ms` で発火しないこと。
  実時間（`on_tick()`）と一括再生（サンプルの時刻の差）の両方で確かめる。`SENSOR_FAULT` の解除は 2 回目の再開から `clear_s` の後になること
- **無効化した後の残った行**: `sensor_missing.enabled: false`（または `sensor_fault.enabled: false`）にした設定で、以前の発火中の
  `SENSOR_MISSING`（`SENSOR_FAULT`）の行と依存する pending が DB に残ったまま起動したとき、pending を取り消さず引き継ぐこと
- **復元の窓**: 発火中の `SENSOR_MISSING` と依存する pending より新しい解決済みのアラートが 1000 件を超える DB で起動しても、
  両方が復元され、復元の時の取り消しが働くこと（発火中の故障アラートの無い pending は引き継がれること）
- **無音（実時間）**: 20 s の無音では pending を保つこと。30 s の無音で `on_tick()` が `SENSOR_FAULT` を発火させた評価で取り消され、
  再開の後に数え直すこと。`SENSOR_FAULT` の解除の時刻が今と同じこと
- **無音（一括再生）**: `on_tick()` を呼ばずにサンプルを流し、サンプルの時刻に 30 s 以上の空白があるとき、空白の後の最初のサンプルの時刻で
  `SENSOR_FAULT` が発火し、同じ評価で pending が取り消され、`clear_s` の後に解除されること。空白が 30 s 未満なら何も起きないこと
- 発火の説明の「条件が N 秒継続して発火」（`explain.py` の `_rule_evidence()`）が、取り消した後は数え直した時刻からの秒数になること
- 変わらないこと: `rapid_rise`・`sensor_missing`・`probe_changed` の遷移の列が今と同じこと。実時間の `sensor_fault` の遷移の列が今と同じこと。
  0131 の GPU の Fan の 2 つのルール（1 回の欠けで取り消す）が今と同じこと

## 3. Consequences

### 良くなること

- 観測していない時間を「条件が続いた」として通知しない。`SENSOR_MISSING` / `SENSOR_FAULT` が出る長い欠け・無音（一括再生を含む）をまたいだ発火が無くなり、説明の継続秒数が観測と合う
- 短い読み損じでは今と同じ時刻に鳴る（A のように散発的な欠けで黙って遅れることが無い）
- 発火が遅れるときは必ず `SENSOR_MISSING` か `SENSOR_FAULT` が出ており、遅れの原因が人に見える
- 新しい閾値も独立の数え方も足さないので、取り消しの条件と故障アラートの条件が食い違わない（無効化・欄の省略・再起動でも）
- 一括再生でも CSV の空白が `SENSOR_FAULT` として記録される

### 悪くなること・その緩和

- **センサーが繰り返し欠けると、部屋の温湿度・再循環のルールが発火しないまま続く**（2.2 (4)）。緩和: そのとき `SENSOR_MISSING` が
  欠けのたびに届く。センサーの欠けを直すことが先で、欠けた値で部屋の判定を続けることはもともとできない
- 長い欠けの直後の発火が、最大で `fire_after_s` + 欠けの長さだけ遅れる（`room_high` で約 20.7 分。2.2 (3)）。緩和: 5 つはすべて
  warning（`rapid_rise`・`sensor_fault` の critical は変わらない）。急な上昇は `rapid_rise`（`fire_after_s: 0`）が捉える
- 夜間（0013 §2.5）は warning が届かない設定なので、夜間の `SENSOR_MISSING` も届かない。緩和: 夜間の扱いは 5 つのルール自身も同じで、
  本記録で悪くならない
- 0131 の GPU の Fan のルール（1 回の欠けで取り消す）と、取り消しの境界が違う。緩和: GPU の値は DB の最新値の stale で判定し、
  欠けは収集の停止なので 1 回で十分長い（0131 §2.3）。基板の値はサンプルごとの読み損じがあり、性質が違う。違いを本記録に残す
- **アラートの出ない欠けでは、今と同じく空白をまたいで発火しうる**（`sensor_missing` / `sensor_fault` の無効化・欄の省略・再起動の空白）。
  黙って遅れるより、観測の無い継続で早めに鳴るほうを安全側として残す。緩和: 今のファームウェアは欄を省かない。故障アラートの無効化は
  人が設定で行う。再起動の空白は §5 の 4
- 一括再生の `SENSOR_FAULT` は空白の後の最初のサンプルの時刻で記録され、空白の始まりから 30 s の時刻ではない。緩和: `detail` に空白の秒数が残る

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| A: 1 回の欠けでも取り消す（0131 §2.3 と同じ） | 散発的な欠けで発火が黙って大きく遅れる（AM2320 の 2 % の読み損じで `room_high` が約 4.5 時間）。そのあいだ `SENSOR_MISSING` も鳴らず、遅れの原因が人に見えない（2.2 (2)） |
| B: 取り消さない（今のまま） | 観測していない時間を継続として通知し、説明の継続秒数が誤る（1.2）。数時間の無音・停止の後でも、再開の 1 サンプルで鳴る |
| C: `stale_after_ms`（10 s）を超える空白で取り消す | D とほぼ同じ振る舞いだが、4 サンプルちょうどの欠けで数え直し、そのとき `SENSOR_MISSING`（5 サンプル）が鳴らない。「黙って遅れない」が成り立たない。取り込みのルールは Store の stale を使っておらず、閾値の出どころを足すことになる |
| 欠けの長さを `config/rules.yaml` にルールごとに持つ | 「欠けている」の判定が `sensor_missing` と 2 か所になり、片方だけを変えると食い違う（0131 §2.3 の stale の閾値を 2 か所に持たない理由と同じ） |
| 欠けの間は継続の時間を止め（時計を止め）、回復後に続きから数える | 観測した時間だけを足すので継続の主張は正しいが、`since_ms` が 1 つの時刻でなくなり、DB の `started_ms`・説明の秒数・再起動の引き継ぎの意味が変わる。変更が大きく、利点は D との差が小さい |
