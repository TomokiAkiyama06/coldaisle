## 1. Context

0128 §2.1 は、GPU の Fan を AIO ポンプと同じ「安全側の決まった運用」とし、fand・Learned MPC・Supervisor・LLM のどれも
GPU の Fan を読まない・書かないと定めた。0131 §2.4a はこれを安全側に読み、`gpu.*.fan_policy` と GPU の Fan の 2 つのアラートを、
LLM へ渡すものすべて（日次レポートの所見・AI ツール・アラートの自動の説明・Server Health の AI 要約・案件資料）から除く
仕組み（`config/report.yaml` の `llm_excluded_metrics` / `llm_excluded_rules`・`src/coldaisle/llm_exclusions.py`）を作った。
0138 は既存の `gpu.*.fan_speed`（0043。NVML の目標値）も一覧に足し、一覧の漏れを CI で見張った。

運用してみると、GPU の温度が高かった日の所見や、アラートの説明で「GPU の Fan は既に何 % だったか」を LLM が使えないため、
「GPU の Fan が 47 % に落ちていた（既定の制御に戻っていた）」のような見立てができない。人は本文の表とダッシュボードで
読めるが、所見と説明はそれを知らない前提で書かれ、根拠の薄い推測（「冷却が不足していた可能性」）になりやすい。

2026-10-15、リポジトリ所有者は、LLM が GPU の Fan の値を**読むだけ**許すと判断した（#333）。
書き込み・実行の手段は与えない。fand・Learned MPC・Supervisor は今どおり読まない・書かない。

0128 §2.1 の「LLM は読まない」が守ろうとしたものは、「LLM の出力が GPU の Fan の回転を変えうる経路を作らない」ことである。
これは AGENTS.md ルール 1（LLM に書き込み・実行・アクチュエーション権限を与えない）と、AI ツールが読み取り専用であること
（0015）で既に閉じている。読むことを許しても、書く経路は増えない。

## 2. Decision

### 2.1 LLM は GPU の Fan の値とアラートを読んでよい（読むだけ）

- `gpu.*.fan_speed`・`gpu.*.fan_policy` と、`GPU_FAN_NOT_MANUAL` / `GPU_FAN_BELOW_CURVE` のアラートを、ほかのメトリクス・
  アラートと同じに LLM へ渡す。経路は日次レポートの所見（`facts_markdown()`）・AI ツール（`get_latest`・`query_series`・
  `get_stats`・`list_alerts`・`describe_system`）・アラートの自動の説明（GPU の Fan の 2 つのアラートも説明を求める）・
  Server Health の AI 要約・案件資料
- **変えないこと**
  - LLM に書き込み・実行・アクチュエーションの手段を与えない（AGENTS.md ルール 1）。AI ツールは読み取り専用のまま
    （0015）。GPU の Fan・`coldaisle-gpu-fan`・unit・NVML に触れるツールを足さない
  - fand・Learned MPC・Supervisor（と Reactive Guard・Critical Safety・Fallback）は GPU の Fan を読まない・書かない（0128 §2.1 のまま）
  - `coldaisle-gpu-fan` の仕組み（決定論的な曲線・既定の制御より下げない・deadman。0128 / 0130）
  - 0043 §2.4 の区分（Advisory）・収集・保存。0131 のルールと通知と日次レポートの本文
  - 生の時系列を LLM のプロンプトに直接入れない（AGENTS.md ルール 8）。GPU の Fan の値も、ほかのメトリクスと同じ集計の経路を通る
- AGENTS.md の固定前提の文を「fand・Learned から読まない・書かない。LLM は読むだけ（決定記録 0146）」に直す
  （本記録と同じコミット。正本を先に直す）

### 2.2 除外の仕組みは残し、一覧を空にする

- `src/coldaisle/llm_exclusions.py` と、それを当てる各経路のコードは**残す**。`config/report.yaml` の
  `llm_excluded_metrics` / `llm_excluded_rules` は**空のリスト**（`[]`）にする
- 0131 §2.4a の仕組みをそのまま引き継ぐ: LLM へ渡すものは一覧を当てた後の集合だけから作る（派生の値を含む）・
  一覧は `config/report.yaml` の 1 か所・**どちらのキーも省略できず、形が不正なら LLM へ渡す経路を開かない**（安全側）・
  Server Health の AI 用の signal はアラートと品質の両方で一覧を除いて決め直す（0138 §2.3）
- 残す理由: 将来、LLM へ渡したくないメトリクス（例えば生活パターンに近い値）が出たときに、設定の 1 行で閉じられる。
  仕組みのテストは、テストの中で作った一覧（GPU の Fan の名前を使ってよい）で今までどおり確かめる
- 空の一覧は「除くものが無い」を明示した値で、キーの省略とは区別する（省略は今までどおり不正）

### 2.3 #320 の CI の見張りは逆向きにする

0138 §2.5 の見張り（`config/metrics.yaml` の `gpu.<index>.fan…` がすべて一覧に当たること）を、次に置き換える。

- 出荷の一覧（`config/report.yaml`）が、`config/metrics.yaml` の `gpu.<index>.fan…` のどれにも当たらないこと、
  その派生値にも当たらないこと（本記録の判断を、設定の書き戻しで黙って覆さない）
- 見張りの対象が空でないこと（`gpu.0.fan_speed` と `gpu.0.fan_policy` があること）
- 出荷の一覧のまま、日次レポートの所見・AI ツール・アラートの説明・Server Health の AI 要約に GPU の Fan の値と
  アラートが入ること

GPU の Fan を再び LLM から除くときは、新しい決定記録でこの見張りを変える。

## 3. Consequences

### 良くなること

- 日次レポートの所見とアラートの説明が、「GPU の Fan が既定の制御に戻っていた」「曲線どおり 70 % で回っていた」を
  根拠に書ける。GPU の温度の説明の質が上がる
- GPU の Fan のアラートにも自動の説明が付き、ほかのアラートと見え方がそろう
- 0131 / 0138 の「人の本文には出るが LLM は知らない」という二重の見え方が無くなる

### 悪くなること・その緩和

- **LLM が GPU の Fan を制御すべきだと書く余地ができる**（「Fan を上げるとよい」など）。緩和: 出力は文章だけで、
  書き込みの経路は無い（ルール 1）。GPU の Fan を変える手段は root の unit の設定だけで、人が決定記録を経て変える
- 0128 §2.1 の「AIO ポンプと同じ扱い」は、読むことについてはむしろ揃う。AIO ポンプの回転（`fan.aio_pump.rpm`。
  参照のみ）は一覧に入ったことがなく、今も LLM に渡っている。制御の扱い（fand の対象外・決定論的な曲線・deadman）は同じ
- 一覧が空でも仕組みのコードが残り、読み手が「何かを除いている」と誤解しうる。緩和: `config/report.yaml` の注記に
  空であることと本記録を書く

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| 除外の仕組み（`llm_exclusions.py`・設定の鍵・各経路の除外）を消す | 0131 / 0138 で経路を洗い、派生の値・品質の経路まで閉じた仕組みは、ほかの値を除くときにそのまま使える。消すと作り直しの費用が大きい。空の一覧で残すと動きは「除かない」と同じ |
| 一覧の鍵を省略可能にし、省略を「除くものが無い」と読む | 書き漏らしが LLM へ流れる（0131 §2.4a の安全側の読み方）。空のリストで明示させる |
| `gpu.*.fan_speed` だけを渡し、`fan_policy` と 2 つのアラートは除いたままにする | 所有者の判断は GPU の Fan の値を読ませること（#333）。「Fan が手動でない」と「回転が低い」は同じ事象の 2 面で、片方だけでは見立てが中途半端になる |
| #320 の見張りのテストを削除する | 0146 の判断（渡す）を、設定の書き戻しで黙って覆せてしまう。逆向きの見張りで残す |
| AI ツールにだけ渡し、日次レポートの所見とアラートの説明からは除いたままにする | 一覧が経路ごとに分かれる（0138 §4 と同じ理由）。所有者の目的は所見と説明の見立て |
