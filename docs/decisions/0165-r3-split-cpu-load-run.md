## 1. Context

0161 §2.4 の R3 は「正式の unit で 2 時間。普段の使い方に加えて、CPU の全スレッド 10 分と GPU 600 W 10 分を別々に 1 回ずつ」と決めている。
2026-10-22 12:31〜14:31 の本回では、GPU 600 W の 10 分（603 s・中央値 600 W）はかかったが、CPU の負荷は 5 s で終わり、かからなかった。

- 原因は試験のスクリプトにある。負荷は、root の一時 unit（中止の基準の見張り）から所有者の uid で stress-ng を起動する作りだった。
  その unit の作業ディレクトリは `/` で、stress-ng は temp-path（既定は作業ディレクトリ）に書けないと始めずに終わる
  （`temp-path '.' must be readable and writeable`）。fand とは関係が無い
- 本回は、0121 §2.3 の表の条件と trace の `schema_version` 16 をすべて満たした（`duration_ms` 最大 8 ms・tick の間隔の最大 1020 ms・fault 0・欠け 0）
- 所有者の判断で、15:02〜15:27 に同じ版・同じ unit・同じ設定で 25 分の回を動かし、CPU の全スレッドを 10 分かけた（603 s・中央値 200 W）。
  この回も同じ条件を満たした（`duration_ms` 最大 18 ms・tick の間隔の最大 1029 ms・fault 0・欠け 0）
- 2 つの回に分けたのは 0161 §2.4 の手順と違う。承認済みの手順を変える判断なので、`enable`（承認点 3）の根拠に使う前に記録して承認を得る
  （PR #371 の Codex のレビューの P1 の指摘）

## 2. Decision

### 2.1 R3 を 2 つの回の組で満たしたとする

2026-10-22 の R3 は、次の 2 つの回の組で 0161 §2.4 の条件を満たしたとする。

| 回 | 期間 | 負荷 | 満たしたもの |
|---|---|---|---|
| 本回 | 12:31:22〜14:31:27（2.00 h・7205 tick） | GPU 600 W 10 分（開始から 60 分） | 2 時間の期間・GPU の負荷・0121 §2.3 の表・trace v16 |
| 補う回 | 15:02:03〜15:27:07（0.42 h・1504 tick） | CPU の全スレッド 10 分（開始から 5 分） | CPU の負荷・0121 §2.3 の表・trace v16 |

根拠は次のとおり。

- **R3 の目的は満たしている。** 0161 §2.4 の R3 は「loop の毎 tick の処理と trace が変わったので、tick の時間と周期を負荷の下で見直す。
  回帰が無いことだけを見る」ためのもの。2 つの負荷のどちらの下でも、tick の時間と周期を同じ条件で測れていて、どの値も条件の内にある
- **2 つの負荷はもともと別々にかける。** 0121 §2.1 の決まりで、CPU と GPU を同時にかけない。1 つの回の中で続けてかけても、
  2 つの回に分けても、それぞれの負荷の下の tick を見ることは変わらない
- **2 つの回の間に何も変えていない。** 同じ `/opt`（`5ff6f96`）・同じ unit・同じ Control Config（v17・`stage: off`）で、
  間は fand を止めて BIOS の制御に戻しただけ。補う回の起動ログと最初の trace も本回と同じ値だった
- **長い時間の影響は T1 で見ている。** 2 時間の中で CPU の負荷が来ることだけを見る理由は R3 には無い。24 時間の連続運転は
  T1（`d3c5404`）で合格している。0161 §1.3 で、Critical Safety・Reactive Guard・Fallback・hardware backend・引き継ぎ実行部は
  T1 の後に変わっていないと確かめている（変わったのは起動の形・Workload Hint（`stage: off` では読み手も照合も動かない）・
  loop の trace の欄・migration・設定の版）

失うもの（§3）は記録に残す。

### 2.2 範囲

- 本記録は **2026-10-22 の R3 の一回だけ**に当てる。0161 §2.4 の手順（1 つの回の中で 2 つの負荷）は変えない。後で R3 をやり直すときは、0161 §2.4 のとおりに行う
- 判定に使うのは、2 つの回それぞれの 0121 §2.3 の表と trace の版・欠け。補う回の判定のスクリプトが出す「期間がおよそ 2 時間」と
  「GPU の負荷 10 分」の不合格・NG は 2 時間の本回のための行なので、補う回の判定には使わない（2 つとも本回で満たしている）
- 本記録の承認の前に、この組を `enable`（0161 §2.5 の手順 7・8）の根拠に使わない

### 2.3 試験のスクリプトへの教訓

root の一時 unit から負荷を起動するスクリプトは、作業ディレクトリを書ける場所にする（stress-ng は `--temp-path` を渡す）。
また、予定より早く負荷が終わったら印を残して止める（黙って先へ進まない）。導入先の作業用のスクリプト（リポジトリの外）だけの話で、
リポジトリのコードと手順書は変えない。

## 3. Consequences

### 良くなること

- 2 時間の soak をやり直さずに（約 2.5 時間）、R3 の目的（負荷の下の tick の時間と周期の回帰）を確かめた結果で承認点 3 へ進める
- 手順からの逸脱と、その理由・範囲が記録に残る

### 悪くなること・その緩和

| 悪くなること | 緩和 |
|---|---|
| CPU の負荷は、2 時間動き続けたプロセスではなく、起動から 5 分のプロセスにかかった。長く動いた後の CPU の負荷の下の tick は見ていない | T1 の 24 時間（`d3c5404`）で長く動いた後の負荷を見ている。`enable` の後も 0148 の通知と trace の `deadline_exceeded` を数日見る（0161 §2.5 の手順 10） |
| fand の起動と停止が 1 回ずつ増え、試験の条件が 0161 の想定と違う | 増えた起動は R2 の記録にも足した（7 回・最長 331 ms）。停止の後は BIOS の値に戻った |
| 補う回の CPU の最高は 84 °C で、中止の基準 88 °C の 4 °C 下（T1 の 24 時間の最高は 81 °C） | 吸気が 24〜25 °C と暖かかった。値は合否に使わず記録に残す。CPU の cooling floor（0123）が Top を決めていた（458 tick） |

## 4. 却下した代替案

| 案 | 却下した理由 |
|---|---|
| R3 を 2 時間やり直す | 約 2.5 時間かかる。R3 の目的に対して、分けた回で失うものは §3 の 1 行目だけで、それは T1 と `enable` の後の見守りで補える。所有者の判断（2026-10-22）で補う回を選んだ |
| 記録を作らずに、補う回の結果をそのまま合格に数える | 承認済みの手順を変える判断を記録なしに行うことになる（AGENTS.md「仕様に無い判断をした場合、実装より先にここへ記録して人間の承認を得る」。PR #371 の Codex の P1） |
| 0161 §2.4 を書き換えて、R3 を分けてよいことにする | 既存の記録は書き換えない。この一回の逸脱を、一般の手順の変更にしない（§2.2） |
