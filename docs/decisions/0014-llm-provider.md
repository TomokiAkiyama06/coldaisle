## 1. Context

Ollama（Mac、開発）と vLLM（Ubuntu、本番）はどちらも OpenAI 互換の
`/v1/chat/completions` を話す。要件 FR-501 は「`base_url` 差し替えで切替」を求める。

同時に FR-507 が「**LLM 不達時もダッシュボードとルールエンジンは正常動作する**」と
定めている。AI は監視の**外側**にあり、落ちていても本体は動き続けなければならない。

---

## 2. Decision

### 2.1 接続先とモデル名は**環境変数だけ**。設定ファイルに書かない

`OPENAI_BASE_URL` / `MODEL_NAME` / `OPENAI_API_KEY` から読む。
`config/ai.yaml` には待ち時間・再試行・生成の既定値だけを置く。

書く場所が2つあると、「どちらが効いているのか」を毎回確かめることになる。
**受入基準（環境変数の変更のみで切り替わる）を構造として守る。**

鍵は秘匿情報なので環境変数に限る（リポジトリは public。#41）。

### 2.1.1 `.env` は自動では読まない

`uv run --env-file .env`（または `UV_ENV_FILE`）で渡す。読み込みをコードへ
入れると、**どのファイルが効いているかがプロセスごとに変わる。**

渡し忘れは「未設定」として静かに通る（LLM なら「利用不可」）。
手順は `docs/llm-setup.md` と `.env.example` に書いた。

### 2.2 不達は**例外ではなく結果**として返す（FR-507）

`chat()` は接続の失敗・タイムアウト・HTTP エラーで例外を投げない。
`ChatResult(available=False, reason=...)` を返す。

**呼び出し側が `try` を書き忘れても、ダッシュボードとルールエンジンは動き続ける。**
例外にすると、書き忘れが「AI が落ちたら監視も落ちる」経路になる。

未設定のときも `None` を返さない。常に「利用不可」と答える
`UnavailableProvider` を返す（通知の宛先と同じ考え方。決定記録 0013 §2.1）。

### 2.3 思考モードは呼び出し側が決める。既定は**非思考**

日常の Q&A は非思考で低レイテンシ、診断時は思考モード（Issue #21）。
待ち時間も別に持つ（既定 30秒 / 120秒）。

指示は `chat_template_kwargs.enable_thinking` として送る。
**Qwen3 系 + vLLM の作法であり、対応しないバックエンドでは 400 になりうる。**
`send_thinking_flag: false` で外せるようにし、導入時に確かめる
（`docs/llm-setup.md`）。

### 2.4 `<think>` は**利用者へ見せる本文から外す**

応答から `<think>...</think>` を切り離し、`text` には含めない。
**閉じていない `<think>` も同じ扱いにする。** `max_tokens` に達すると
閉じタグが出ないまま切れるため、閉じたものだけを外す実装では
**長い診断のときだけ内部の推論が利用者へ出る。**

思考の途中経過が根拠のように読まれると、FR-508 の Evidence 形式
（何が測定値で何が推測かを明示する）が崩れる。必要なときは
`ChatResult.thinking` から取る。

### 2.5 落ちている相手に粘らない

再試行は既定2回、待ちは短い。**5xx と接続失敗だけ再試行し、4xx はしない**
（要求そのものが悪いなら粘っても直らない）。

待たせるより早く「利用不可」と答えるほうがよい。監視は AI を待たない。

## 3. Consequences

### 良くなること

- 環境変数2つでバックエンドが替わる。開発（Ollama）と本番（vLLM）で
  コードが分岐しない
- AI が落ちても監視が落ちない。**構造として**そうなっている（2.2）
- ツール呼び出し（#22）の受け口が既にある

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 呼び出し側が `available` を見落とすと空文字が表示される | `text` の既定は空文字で、`reason` に理由が入る。UI は `available` で分岐する |
| 思考モードの指示がバックエンド依存（2.3） | 外せるフラグと、導入時の確認手順を用意した |
| 実バックエンドとの疎通は試験できない | 輸送を差し替えて挙動を固定。実物での確認は `docs/llm-setup.md` の手順で行う |

---

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 接続先を `config/ai.yaml` に書く | 切り替えが2箇所になり、受入基準を壊す（2.1） |
| 不達を例外にする | 書き忘れが「AI が落ちたら監視も落ちる」経路になる（2.2） |
| 未設定のとき `None` を返す | 呼び出し側に分岐を書かせると、書き忘れが落ちる経路になる（2.2） |
| `<think>` をそのまま本文に含める | 思考の途中経過が根拠のように読まれる（2.4、FR-508） |
| 閉じた `<think>` だけを外す | `max_tokens` で切れた長い診断のときに内部の推論が出る（2.4） |
| 応答の形が違ったら例外にする | 「不達は結果として返す」約束が破れる。互換をうたう実装の差で呼び出し側が落ちる（2.2） |
| `.env` をコードで読み込む | どのファイルが効いているかがプロセスごとに変わる（2.1.1） |
| 4xx も再試行する | 要求が悪いなら直らない。待たせるだけ（2.5） |
| プロバイダごとにクラスを分ける（Ollama 用 / vLLM 用） | どちらも OpenAI 互換。分けると差し替えの意味が薄れる |
