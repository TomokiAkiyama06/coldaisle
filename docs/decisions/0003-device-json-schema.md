**ファームウェア（#11）とホスト（#12 SerialSource）は、この契約だけを参照する。**
実体は [`schemas/device_v1.schema.json`](../../schemas/device_v1.schema.json)。
本記録は、スキーマに書けない意図と、スキーマの外側の規則を定める。

---

## 1. Context

元仕様 §10 の JSON は測定値だけを持ち、次が判別できない（spec-review W-04）。

| 不足 | 起きること |
|---|---|
| スキーマバージョン | ファーム更新時にホストが黙って誤解釈する |
| シーケンス番号 | 取りこぼしに気づけない |
| 稼働時間 | ESP32 が勝手に再起動しても分からない |
| エラー理由 | `null` の原因が配線かセンサー故障か切り分けられない |
| メッセージ種別 | 起動バナーやログを同じストリームに流せない |

---

## 2. Decision

### 2.1 1行1件の JSON Lines

デバイスは USB CDC へ1行1件の JSON を出力する。行の区切りは `\n`。

### 2.2 メッセージ種別は3つ。`log` は v1 では中身を定義しない

| `type` | 内容 | v1 での扱い |
|---|---|---|
| `s` | サンプル | 取り込む |
| `hello` | 起動バナー。電源投入時に1回 | `devices` / `device_sensors` を更新（0002 §2.10） |
| `log` | デバイス側のログ | **ホストは無視する。中身は定義しない** |

`log` の構造を今決めない。使い道が固まっていない段階で形を決めると、
実際に必要になったときに `v` を上げることになる。
ホストは `type` が未知の値でも**そのサンプルだけを捨て、デーモンは動き続ける**。

### 2.3 サンプル

```json
{"v":1,"type":"s","seq":1042,"up":2605250,"room_temp":26.42,"room_humidity":48.20,
 "front_intake":27.87,"gpu_intake":28.25,"gpu_exhaust":28.87,"top_exhaust":27.06,
 "rear_exhaust":null,"err":["rear_exhaust:-127"]}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `v` | `1` | ✅ | スキーマバージョン |
| `type` | `"s"` | ✅ | |
| `seq` | 整数 ≧0 | ✅ | 単調増加。飛びで取りこぼしを検出（FR-105） |
| `up` | 整数 ≧0 | ✅ | 稼働ミリ秒。巻き戻り＝再起動（FR-106） |
| 各チャネル | 数値 または `null` | | 測定値。取得できなければ `null` |
| `err` | 文字列の配列 | | `<channel>:<reason>` 形式 |

**測定値のフィールドは必須にしない。** センサーが1本増減したファームウェアでも
サンプル全体が捨てられないようにするため（2.7）。

### 2.4 起動バナー

```json
{"v":1,"type":"hello","fw":"1.0.0","dev":"xiao-esp32s3","interval_ms":2500,
 "sensors":{"front_intake":{"kind":"ds18b20","gpio":1,"rom":"28FFFFFFFFFFFF01","res":11},
            "room":{"kind":"am2320"}}}
```

- `kind` が `ds18b20` のときだけ `gpio` / `rom` / `res` を必須とする
- `rom` は大文字16進16桁。プローブ入れ替えの検出に使う（FR-403、spec-review W-03）
- `res` は 9〜12。**11 を推奨**（spec-review C-01。12bit だと変換 750ms×5 で周期が破綻する）
- `interval_ms` はホストが期待サンプル数の算出に使う（0002 の `expected_count`）

**AM2320 には `gpio` を持たせない。** I²C は SDA / SCL の2本で、
単一の `gpio` では表せないため。ピン割り当ては spec-review W-01 の表が持つ。

### 2.5 デバイスのチャネル名とメトリクス名の対応

デバイスは短いチャネル名を送り、**ホストが正規のメトリクス名へ写像する。**
この対応表が契約の中心であり、どちらか一方だけを変えてはならない。

| デバイスのフィールド | メトリクス名（0002 §2.1） | 由来 |
|---|---|---|
| `room_temp` | `air.room` | AM2320 |
| `room_humidity` | `air.room_humidity` | AM2320 |
| `front_intake` | `air.front_intake` | DS18B20 #1 |
| `gpu_intake` | `air.gpu_intake` | DS18B20 #2 |
| `gpu_exhaust` | `air.gpu_exhaust` | DS18B20 #3 |
| `top_exhaust` | `air.top_exhaust` | DS18B20 #4 |
| `rear_exhaust` | `air.rear_exhaust` | DS18B20 #5 |

デバイス側を短い名前のままにするのは、**ESP32 の送信バイト数を抑える**ためと、
**デバイスがドメイン名前空間を知る必要がない**ため。
`air.` を付けるかどうかはホスト側の関心事であり、ファームウェアの関心事ではない。

写像はコードに直書きせず設定として持つ（AGENTS.md ルール6）。置き場所は #5 で決める。

### 2.6 スキーマは「形」だけを見る。値の妥当性は quality が持つ

**測定値に物理的な上下限を書かない。** `-127.00` も `85.00` も `100.00`%RH も
スキーマとしては通す。

理由: スキーマで弾くと**サンプル全体が捨てられ、同時に測れていた他の6メトリクスも失われる。**
異常値は「捨てる」のではなく「`suspect` として記録する」のが正しい（0002 §2.5）。

| 判定 | 担当 |
|---|---|
| 形（型・必須・桁） | 本スキーマ |
| 値の妥当性（`-127.00` / ちょうど `85.00` / 湿度の 0% 100% 張り付き） | quality（0002 §2.5、spec-review C-02 / C-04） |

### 2.7 追加に寛容にする。`v` は破壊的変更でのみ増やす ★承認が必要

サンプルの未知フィールドを**許可する**（`additionalProperties` を制限しない）。

| 変更 | `v` |
|---|---|
| メトリクスの追加、`err` の理由語彙の追加 | **据え置き** |
| フィールドの削除・改名、意味の変更、単位の変更 | **`v` を上げる** |

厳密に閉じた場合の失敗の仕方が悪い。ファームウェアが VRM 温度を1つ足しただけで
**全サンプルが検証に落ち、取り込みが完全に停止する。**
気づくのは30秒後の `SENSOR_FAULT` で、原因は「スキーマ違反」としか出ない。
寛容にしておけば、古いホストは新しいフィールドを無視して動き続ける。

副作用として、フィールド名のタイプミス（`front_intak`）は無視される。
ただしこれは FR-402 `SENSOR_MISSING` として検出される
（期待するチャネルが来ていない、という形で現れる）ので、見逃しにはならない。

### 2.8 非有限値は取り込み側で拒否する ★実装必須

**`NaN` / `Infinity` / `-Infinity` は JSON 仕様では不正だが、
Python の `json.loads` は既定で受け入れる。**
さらに `jsonschema` からは `number` に見えるため、本スキーマでも止まらない。

```python
json.loads('{"room_temp": NaN}')  # -> {'room_temp': nan}  例外は出ない
```

これが `readings.value`（REAL）に入ると、**そのメトリクスの min / max / mean が
恒久的に壊れる。** 生データを30日で消した後はロールアップからも取り除けない。

取り込み側は必ず `parse_constant` で拒否する。

```python
def _reject(token: str) -> float:
    raise ValueError(f"JSON として不正な定数: {token}")


json.loads(line, parse_constant=_reject)
```

この行は FR-103 の「JSON として解釈できない行」として破棄する。
`tests/test_device_schema.py` が、スキーマでは止まらないことと
`parse_constant` で止まることの両方を固定している。

### 2.9 `err` の書式と、LLM へ渡すときの扱い

- 書式は `<channel>:<reason>`。`reason` の語彙は v1 では固定しない
- `err` は**デバイス由来の文字列**である。要件 §7.4 に従い、
  LLM へ渡す際は必ずデータとしてタグで囲み、ダッシュボードでは HTML エスケープする
- `err` に理由があっても、`quality` の決定は値そのものから行う（2.6）。
  `err` は人間と診断のための補助情報

### 2.10 非 JSON 行は黙って破棄する（FR-103）

ESP32 は起動時に ROM のブートログを出す。行頭が `{` でない行と、
JSON として解釈できない行は**例外を投げずに破棄し、デーモンは動き続ける**
（AGENTS.md のコード規約、spec-review W-04）。

`tests/fixtures/serial_with_boot_log.txt` が実際のブートログ混じりの捕捉例で、
テストは「9行が破棄され、残る3行がすべて契約に合う」ことを確認している。

## 3. Consequences

### 良くなること

- ファームウェアとホストが1つのファイルを参照する。齟齬が出たらテストが落ちる
- センサーの増減でホストが停止しない（2.7）
- 異常値がサンプル全体を巻き添えにしない（2.6）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 未知フィールドを許すため、名前のタイプミスを検証で拾えない | `SENSOR_MISSING`（FR-402）として検出される |
| スキーマが値の妥当性を見ないため、検証を通っても異常値は入る | quality の判定（0002 §2.5）が受け持つ。責任範囲を本記録で明示 |
| `log` の形が未定義 | ホストは無視する。必要になった時点で追加する（`v` は据え置きでよい） |
| 非有限値がスキーマをすり抜ける | 取り込み側の `parse_constant` で拒否（2.8）。テストで固定 |

### フィクスチャ

| ファイル | 内容 |
|---|---|
| `device_v1_valid.jsonl` | 起動バナー、正常サンプル、`log` |
| `device_v1_missing.jsonl` | `null` + `err`、生の `-127.00` / `85.00`、湿度 100% 張り付き |
| `device_v1_schema_violations.jsonl` | スキーマが**弾かねばならない**13件 |
| `device_v1_nonfinite.jsonl` | `NaN` / `Infinity`。スキーマをすり抜けることの記録 |
| `serial_with_boot_log.txt` | ブートログ混じりの実際の捕捉例 |
| `serial_invalid_json.txt` | JSON として壊れている行 |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| `additionalProperties: false` で厳密に閉じる | フィールドが1つ増えただけで全サンプルが落ち、取り込みが完全停止する（2.7） |
| 測定値に物理的な上下限を書く | 異常値がサンプル全体を巻き添えにする。異常は捨てるのではなく記録する（2.6） |
| デバイス側で `air.front_intake` のような正規名を送る | 送信バイト数が増え、デバイスがホストの名前空間規約を知ることになる（2.5） |
| `log` の構造を先に決める | 使い道が固まっていない。決めると変更時に `v` を上げることになる（2.2） |
| CSV や独自バイナリ | ブートログとの混在を判別できない。JSON なら「`{` で始まりパースできる行」で切り分けられる |
| 非有限値をスキーマで弾く | JSON Schema に有限性の語彙が無い。取り込み側で塞ぐしかない（2.8） |
