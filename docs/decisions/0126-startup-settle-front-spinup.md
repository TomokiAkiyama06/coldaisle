## 1. Context

2026-10-14 に 0121 の T4 を行った（08:06〜08:19 の 1 回目と、08:31〜08:51 の測り直し）。

### 1.1 起動の落ち着き

`STARTUP` の間、Critical Safety は全 zone を Max にする。`startup_settle_ms` が過ぎ、CPU の温度が fresh で、全 zone の
tach の応答を確かめたら `NORMAL` に移り、Demand は `ramp_down` で下がり始める（0028 §2.6）。

1 回目は、BIOS から takeover したときの tach の記録（T3・T6・T4）を使った。Top と Rear は全開の ±5% に 3.6〜4.3 s で入った。
Front は BIOS の約 680 RPM から上がるのが遅く、5.6 s でも 1498 RPM（全開の 83%）だった。そのすぐ後に Demand が
下がり始めるので、Front が落ち着くまでの時間はこの記録からは測れなかった。

そこで測り直した。アイドルで全 zone を manual 0.35（約 630〜980 RPM。BIOS のときと近い）に落ち着かせてから
`ctl max` にし、fand の trace の回転数が全開の ±5% に入り、そのまま留まった最初の tick までを測った（3 回）。
試験の側からは基板を読んでいない（0125）。

| zone | 3 回 |
|---|---|
| Top | 5840 / 4841 / 5844 ms |
| Rear | 5840 / 4841 / 5844 ms |
| Front | 11841 / 12841 / 11844 ms |

trace の回転数は約 1.5 s ごとにしか変わらない（nct6775 の更新の閾値。0125）。そのため、実際に入った時刻は
この値より最大で 1.5 s 早い。逆に、ほかの読み手との位相によっては、fand から見えるのが最大でほぼ 1.5 s 遅れうる。

Front は 3 回とも 5000 ms の条件を満たさない。Top と Rear も、閾値を足すと 5000 ms を超える。

### 1.2 T4 の温度

下がる速さは、2 つの試行とも合格した（`elapsed_ms` で割った最大 0.0501/s、届く直前までの `bound_by` は `ramp_down`）。

温度は「下げる前の定常より 3 °C 以上上がらない」で判定する。下げる前の定常は `ctl max` の直前 60 s の中央値とする。
これを、Max から 0.35 で 60 s 見終えるまでの値と比べた。

- **GPU 300 W（測り直し）**: 最大の上がりは Rear の排気 +1.13 °C、CPU +2 °C（1 点）。合格。1 回目の GPU 300 W は、
  GPU の排気が落ち着く前に始めていたので、判定に使わない
- **アイドル（1 回目）**: 空気・GPU・12V-2x6 は上がらなかった（+0.12 °C 以内）。`cpu.package` だけが跳ねた。
  - `ctl max` の 1.1 s 後に 49 °C（Fan は全開へ上がる途中）。その後 10 s ほどで 40 °C に戻った
  - manual 0.35 の 3.4 s 後に 46 °C（Fan はまだ 0.85 以上）。その後 10 s ほどで 40 °C に戻った
  - その後、0.35 に届いてから 60 s の間は 39〜41 °C

Fan が全開へ上がる途中の `ctl max` の直後にも同じ跳ねが出ている。そのため、この跳ねは Fan を下げたことによるものではない。
試験のスクリプトが送る `coldaisle-control` のコマンドの起動（Python の起動と import）による、一瞬の CPU の負荷と見ている。
3 点の中央値を取っても、2 点続く跳ね（49 → 47、46 → 44）は消えない。

## 2. Decision

### 2.1 `startup_settle_ms` = 15000

測った最長（Front 12841 ms）に、tach の更新の閾値（1500 ms）を足すと 14341 ms になる。これより長い 15000 にする。

0125 は T6 の合格の条件に fand の 1 tick（1000 ms）も足した。同じように足すと 15341 ms で 15000 を超えるが、値は変えない
（2026-10-14 の所有者の判断）。理由は次のとおり。

- 上の時間は、fand 自身の tick の trace で回転数が全開の ±5% に入った時刻である。fand が読む位相（tick）の遅れはすでに含まれ、
  実際に入った時刻はこれより最大で更新の閾値の分だけ早い。足した 1500 ms は、ほかの読み手との位相で fand から見えるのが遅れる分である
- `startup_settle_ms` は tach を判定しない時間で、過ぎた後に Demand が `ramp_down`（0.05/s）で下がり始めるだけである。
  Front の全開の確認が 1 tick 遅れても、その間の Demand は 1.0 から 0.05 しか下がらない。0125 の stall の判定のように、
  遅れて見えることが誤った `tach_stall`（`EMERGENCY`）につながる値ではない
- T1 の 24 h の soak の起動の記録で、Demand が下がり始めるまでに 3 zone が全開の ±5% に入っていることと、起動の直後に
  誤った `tach_stall` が出ないことを確かめる（2.3）。足りなければ値を変える案を所有者に出す
status を `confirmed`・basis を本記録と `docs/fan-header-mapping.md` の T4 の結果にするのは、0121 §2.10 のとおり、
すべての試験がそろってから所有者の承認を得て行う。それまでは `provisional` のまま 15000 にする。

起動の後の Max を延ばすだけの変更で、安全側に倒れる。導入先の `/etc/coldaisle/control-config/safety.yaml` の値は、
本記録の承認の後に所有者が書き換える。

基板・Fan・driver を変えたとき、または `fanN_input` を読むプロセスを増やしたときは測り直す。

### 2.2 T4 の CPU の温度は、操作の直後 15 s を除いて判定する

0121 §2.6 T4 の温度の判定のうち、`cpu.package` だけは、試験のスクリプトが `coldaisle-control` を送った時刻から 15 s の間の
値を除いて判定する。除いてよいのは、同じ試行の `ctl max` の直後にも同じ大きさの跳ねが出ている場合に限る。
`ctl max` の直後は Fan が全開へ上がる途中で、Fan を下げたことによる上がりはありえないためである。
空気・GPU・12V-2x6 の温度は、除かずに全区間で判定する。

この扱いで、アイドルの試行は合格とする。除いた後の `cpu.package` の最高は 41 °C（+1 °C）である。

### 2.3 T4 の結果

2.1 と 2.2 により、T4 は合格とする。`ramp_down_per_s` 0.05 と `startup_settle_ms` 15000 は、0121 §2.10 の時点で `confirmed` にする。
ただし `startup_settle_ms` は 15000 にした設定で、T1 の起動の記録から Demand が下がり始めるまでに 3 zone が全開の ±5% に
入っていることと、起動の直後に誤った `tach_stall` が出ないことを確かめる。

## 3. Consequences

### 良くなること

- 起動の後、3 zone とも全開に落ち着いてから Demand を下げ始める。Front が全開に届く前に下げ始めることがなくなる
- T4 の判定が、試験の操作による CPU の跳ねで不合格にならない

### 悪くなること・その緩和

- 起動・再起動のたびに、全開の時間が 5 s から 15 s に延びる（騒音だけ。熱の面では安全側）。watchdog や書き込みの失敗で
  再起動した後も同じ
- 余裕は 659 ms と小さい。Front の Fan の劣化で立ち上がりが遅くなると足りなくなる。値は保守の測り直しで見直す
- CPU の温度の除外は、15 s より短い CPU の上がりを見逃しうる。この区間の Fan は 0.35 よりずっと高いので、Fan を下げたことによる
  上がりはこの区間には出にくい。空気の温度は除外しない

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| `startup_settle_ms` を 5000 のままにし、tach の応答を確かめた時点で十分とする | Front が全開の 83% のまま Demand が下がり始める。起動の落ち着きを確かめる意味が無くなる |
| 13000（測った最長の約 1 s 上） | tach の更新の閾値の分の遅れを吸収できない |
| CPU の温度を 3 点の中央値で判定する | 跳ねが 2 点続くので消えない（49 → 47、46 → 44） |
| アイドルの試行をやり直す | 試験のスクリプトはコマンドを送らずには操作できないので、同じ跳ねが出る |
| 0119 / 0121 を書き直す | 決定記録は書き換えない（追記のみ）。一部を置き換える新しい記録にする |
