## 1. Context

アラートは「いま異常か」しか答えない。**じわじわ悪くなっていることは、
その日のうちには分からない。** 前日比と欠測率を毎朝1枚にまとめる（FR-506）。

問題は、この種のレポートが**読まれなくなる**ことである。
毎朝届くが中身が薄いと、そのうち誰も開かない。

---

## 2. Decision

### 2.1 集計元は**1分ロールアップ**。生データは読まない

理由は3つ。

1. 生データは30日で消える（`config/retention.yaml`）。ロールアップは無期限
   （FR-204）なので、**過去のどの日でもあとから作り直せる**
2. **欠測率が本物になる。** `SqliteStore.stats()` の欠測率は「届いた行のうち
   `ok` でない割合」で**下限値**である。届かなかったサンプルは行が無いので
   数えられない。ロールアップは `expected_count` を持つ（0002 §2.8）
3. 1メトリクスあたり 1440 行で済む（生データは 34,560 行）

平均は**件数で重み付ける**（0004 §2.9）。単純平均だと、値の少ないバケットが
値の多いバケットと同じ重さになる。

### 2.2 統計はコードが出す。**モデルは所見の文だけ**

0016 §2.1 と同じ。表の数値をモデルに書かせない。

さらに、**表に無い数値が所見に現れたら、その所見を捨てる。**
表はロールアップから機械的に組み立てたものなので、そこに無い数値は
モデルが作った数値である。プロンプトでは「数値を書かない」と指示し、
検査で裏を取る。

所見が無くてもレポートは成立する（表だけが届く）。

### 2.3 `unit: count` のメトリクスは**合計**にする

`sys.queue_drops` に最低/平均/最高を出しても意味がない。
**メトリクス名で分岐しない**（AGENTS.md ルール6）。単位が決める。

**カウンタに欠測率を出さない。** 事象が起きたときだけ書かれる値なので、
期待サンプル数と比べると常に「ほぼ100%欠測」になる。

### 2.4 出力先は `var/reports/`（**Issue の記述からの変更**）

#25 は `docs/reports/` と書いているが、そこには置かない。

- レポートは**生成物であって文書ではない**。`docs/` は人が書いたものの場所
- **リポジトリは public**（#41）。室温と在室の傾向は生活パターンそのもので、
  公開リポジトリへ自動でコミットされうる場所に毎日書き出すのは避ける

`var/` は `.gitignore` に入れた。読みたいだけなら `--print` で標準出力へ出せる。

### 2.5 通知は `Router` を通さない

連投の抑制・夜間の方針・重大度の振り分けは、どれも**アラートの都合**である。
決まった時刻に1通出すレポートには当たらない。`Router` に分岐を足すと、
アラートを鳴らすかどうかの判定が読みにくくなる（0013 §2.3 の解除の分岐で既に
一段深い）。

`config/report.yaml` の `to` に書いた宛先へ直接送る。
**1つ落ちても残りへ送る**（1日1回しか出ない）。

全文はファイルに残し、通知は長ければ切る（LINE は5000文字で切られる）。

### 2.6 欠けを**黙って埋めない**

| 状況 | 出し方 |
|---|---|
| その日のデータが1つも無い | 「**この日のデータがありません**」と本文に書く。レポート自体が異常の知らせ |
| 前日のデータが無い | 前日比は `—`。**カウンタの前日を 0 と書かない**（不明であって「事象ゼロ」ではない） |
| 期待サンプル数を知らない | 欠測率は `—`。推測しない |
| 期待サンプル数を知るバケットと知らないバケットが混ざる | **知らないほうを母数から外す。** 0 として足すと、そのぶんの成功サンプルだけが分子に残り、欠測率が実際より低く出る（0% に張り付く）。外した場合は母数の分数を表に書く |
| バケットが 1440 分に満たない | `収録` 列に `1380/1440` と出す |

**欠測率と収録は別の列にする。** 欠測率は「届くはずのサンプルのうち届かなかった
割合」、収録は「そのメトリクスが記録されていた分数」である。装置ごと沈黙して
いた時間は欠測率には出ない（行が1つも無いため）。1列にまとめると、
どちらの欠けなのかが読めなくなる。

### 2.7 数えるのは**発火したアラートだけ**。日の境界は `fired_ms` に当てる

`pending` のまま消えたものは誰にも届いていない。
届いていないものを件数に入れると、前日比が読めなくなる。

**条件の成立時刻ではなく、発火時刻で日を切る。** 23:55 に条件が成立して 00:03 に
発火したアラートは、受け取った人にとって翌日の出来事である。成立時刻で切ると
前日の件数に入り、「昨日は静かだったのに件数が1件ある」という食い違いになる。

一覧（FR-304）は「いつ始まったか」を見たいので `started_ms` のままにし、
読み出しを `SqliteStore.fired_alerts()` として分けた。引数で切り替えると
呼び分けを間違える。

## 3. Consequences

### 良くなること

- 保持期間を過ぎた日でも、あとからレポートを作り直せる（2.1）
- 所見に架空の数値が入らないことが**検査で保証される**（2.2）
- レポートの生成が失敗しても、アラートの通知経路には影響しない（2.5）
- 取り込みが止まっていた日は、レポートが空になるのではなく**そう書かれる**（2.6）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| p95 が出せない（1分バケットから合成できない） | 最低/平均/最高で足りる。p95 が要るなら API で見る（0004 §2.9） |
| `coldaisle-rollup` の実行順に依存する | 収録の分数を出し、足りなければレポートに書く（2.6） |
| 設定ファイルが1つ増える | 通知・保持期間と同じ粒度。1つの関心事に1ファイル |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 生データから集計する | 30日で消える。欠測率が下限値にしかならない（2.1） |
| 表もモデルに書かせる | 数値を幻覚できる（0016 §2.1） |
| 所見の数値が違っていても文だけ直す | 表と食い違う所見は、直しようがない。捨てる（2.2） |
| `Router` に `kind == "report"` の分岐を足す | アラートの判定にレポートの都合が混ざる（2.5） |
| `docs/reports/` に書く | 生成物であり、public リポジトリに生活パターンを毎日書き出す（2.4） |
| 期待サンプル数が不明なバケットがあれば欠測率ごと `—` にする | 1440分のうち1分が不明なだけでその日の欠測率が消える。母数を書けば済む（2.6） |
| データが無い日はレポートを出さない | **止まっていたことが誰にも伝わらない。** 沈黙が最悪 |
| 取り込みデーモンの中で毎朝生成する | ロールアップと同じ理由。取り込みを遅らせる要素を増やさない（0008） |
| 派生値（`d.intake_rise` 等）も表に載せる | 1分平均どうしの差の最小/最大は、生の最小/最大と一致しない。誤解を生む（§5） |
