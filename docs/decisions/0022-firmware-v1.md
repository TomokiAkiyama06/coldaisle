## 1. Context

`sketch_aug21a` が手元で動いているが、監視に使える形ではない。

| 問題 | 何が起きるか |
|---|---|
| 12bit 逐次変換（750ms × 5） | **実周期が約6.5秒。** 2.5秒周期の前提が崩れる |
| ちょうど `85.00` を通す | DS18B20 のパワーオンリセット値。**排気温度としてありえない値ではない**ので誤警報になる |
| `seq` / `up` が無い | 取りこぼしと再起動をホストが検出できない（FR-105 / FR-106） |
| 起動バナーが無い | ROM ID を記録できず、プローブの入れ替わりに気づけない（FR-403） |
| ウォッチドッグが無い | ループが止まると**無言で停止する** |

## 2. Decision

### 2.1 試作を**土台にする**

ピン割り当て、ライブラリの選定（OneWire / DallasTemperature / Adafruit AM2320）、
`D0〜D8` の別名の使い方は `sketch_aug21a` のままにする。

**動いているものを捨てない。** このマシンには既にそのライブラリが入っており、
配線も検証済み（spec-review W-01）。作り直すと、直すべき点以外も未検証になる。

### 2.2 変換は **11bit + 非ブロッキングで5本同時**

```cpp
ds[i].setResolution(address, 11);        // 0.125C / 375ms
ds[i].setWaitForConversion(false);       // 既定は完了まで待つ
for (...) ds[i].requestTemperatures();   // 5本同時に開始
delay(400);                              // 375ms + マージン
```

spec-review C-01 のとおり。**5本が独立 GPIO である利点を使う。**
11bit にするのは、センサーの絶対確度が ±0.5℃ で 12bit（0.0625℃）が過剰だから。

AM2320 の読み取りは**変換待ちの間に**行う。時間を二重に使わない。

### 2.3 ちょうど `85.00` を `null` + `err` に落とす

spec-review C-02。**本物の 85.00 も落ちる**が、この系は空気温度を測るもので、
実測で 85.00 が出る状況は既に異常である。**取り違えるより落とすほうを採る。**

`-127.00`（無応答）も同じ扱い。どちらも理由を `err` に入れる
（`<channel>:-127` / `<channel>:85`）。

ホスト側の quality も同じ値を見張る（0002 §2.5）。**二重にする。**
ファームウェアを更新できない状況でもホストが気づけるようにするため。

### 2.4 JSON は**手で組む。ライブラリを入れない**

出力は固定の小さなスキーマで、文字列はこちらが作る値だけ（`fw` / `dev` / `rom` /
`err` の理由）。ArduinoJson を入れると、版を固定する対象と割り当て失敗という
経路が増える。

代わりに**安全に足す関数を1つ置く**。

```cpp
static void append(const char *fmt, ...);  // 溢れたら印を立てて、以降書かない
```

`snprintf` の戻り値をそのまま足し込んではいけない。**「収まっていれば書かれた
はずの長さ」を返す**ので、切り詰めが起きた時点で合計が配列長を超え、
`sizeof(line) - n` が size_t で巨大な値になって**バッファを越えて書く。**
（最初の実装がこれを踏んでいた。）

**切り詰められたら行を送らない。** 代わりに `type:"log"` を出す。
壊れた JSON はホストが捨てるのでデーモンは落ちないが、
「送ったのに届かない」原因の切り分けが難しくなる。

### 2.5 `up` は **64bit のタイマ**から作る

`millis()` は約49.7日で巻き戻る。ホストは `up` の巻き戻りを**再起動として扱う**
（FR-106）。稼働し続けているのに再起動したことにされるのを避けるため、
`esp_timer_get_time() / 1000` を使う。

### 2.6 周期は**締切で刻む**

`delay(INTERVAL_MS)` を処理の後に置くと、**実周期が処理時間ぶん伸びる**
（試作がそうなっていた）。固定の刻みで次の締切を進める。

大きく遅れたときは追いつかずに再同期する。**溜まった分を一気に送っても意味が無い。**

### 2.7 センサーが1本も無いときは **`hello` を出さない**

スキーマは `sensors` に1つ以上を要求する（`minProperties: 1`）。
空の `hello` は**契約違反の行**になる。代わりに `type:"log"` を出す。

サンプルは出し続けるので、ホスト側では SENSOR_FAULT / SENSOR_MISSING が鳴る。
**黙るのではなく、鳴る側に倒す。**

### 2.8 `hello` は**読み手が繋がった瞬間にも出し直す**

`delay(2000)` で待つだけでは足りない。**デバイスのほうが先に起動していると、
誰も読んでいない間に `hello` が流れて消える。** ホストはサンプルだけを受け取り、
ROM の一覧も `interval_ms` も知らないまま動き続ける（FR-403 が比べる相手を持てない）。

USB CDC の接続状態を見て、**立ち上がりでだけ**出し直す。

周期的に出さないのは、「電源投入時に `hello` が1回だけ」（#11 の受入基準）が
崩れ、ホストの記録が何度も書き換わるからである。
**読み手が付いたときに、その読み手のために出す。**

### 2.9 繋がっていないプローブを `hello` に載せない。**ただし記録は消させない**

`hello` は「そのとき繋がっている構成」を申告する。見つからないプローブを
載せると、その申告が嘘になる。

**一方で、ホストが記録を消してはいけない。** 起動時に1本繋がっていなかっただけで
その ROM を忘れると、あとで別のプローブを挿したときに**比べる相手が無く、
黙って受け入れる。** 較正のオフセットが間違ったプローブに対応したまま運用が続く。

実装は `rules.probe_mismatch()` に置いた。**記録側を基準に数える。**

| 状況 | 食い違いか | 理由 |
|---|---|---|
| ROM が変わった | ✅ | 差し替え |
| 記録にあるのに `hello` に無い | ✅ | 忘れさせない。消えたことを人に知らせる |
| `hello` にあって記録に無い | ❌ | 新設。較正された値がまだ無いので間違った対応にはならない |

これは決定記録 0012 §2.6 の「起動バナーの ROM **セット** ≠ 記録された ROM
**セット**」という定義どおりの挙動である。**コードが定義に追いついていなかった**
（`observed` 側だけを回していた）。決定の変更ではなく、その修正。

### 2.10 ピン番号は**スケッチに書く。代わりに表との一致を試験で縛る**

AGENTS.md ルール6 は定数をコードに埋めないことを求めるが、**ファームウェアは
`config/*.yaml` を読めない。** 生成したヘッダを使う方式は、Arduino IDE が
生成を自動で走らせないため**生成物が古くなる**経路を作る。埋め込みより悪い。

代わりに、ルール6 の意図（唯一の情報源を持ち、ずれたら気づく）を試験で満たす。

- スケッチのピン割り当て == `docs/spec-review.md` W-01 の表
- `firmware/README.md` の配線表 == W-01 の表
- `hello` の `gpio` == W-01 の表

D9/D10 へ退避するときは、**スケッチと表の両方を直さないと CI が落ちる。**
配線の文書と実装が一緒に動くことを強制しているので、これは欠点ではない。

### 2.11 AM2320 は連続失敗で**間引く**

spec-review C-04。読み取り失敗が5回続いたら約30秒読まない。
元仕様にコネクタの挿し間違いによる**発熱事象**が記録されている。
**異常状態のセンサーを叩き続けない。**

起動時にアドレス応答のセルフチェックもする（AM2320 は最初の1回が必ず失敗する
ので2回試す）。

### 2.12 **コンパイルと実測は人が行う。形の検査は自動化する**

このマシンに Arduino のツールチェーンが無い（`arduino-cli` / PlatformIO とも未導入）。
**スケッチはコンパイルしていない。** 実周期・抜線・リセットの確認も実機が要る。

できることはしてある。`tests/test_firmware_contract.py` が CI で見張る。

| 見張るもの | 理由 |
|---|---|
| 出力の例が `schemas/device_v1.schema.json` を通る | 契約の相手はこのスキーマ |
| スケッチのチャネル名 == ホストの写像表 | 片方だけ変えると黙って取り込まれなくなる |
| ピン割り当て == spec-review W-01 の表 | 検証済みの割り当てから勝手に動かさない |
| C-01 / C-02 / WDT / I²C の対策が消えていない | あとから「速くしたい」で外されるのを防ぐ |

**緑でも「動く」証明にはならない。「形が合っている」証明である。**
残りは `firmware/README.md` のチェックリストで人が確かめる。

## 3. Consequences

### 良くなること

- 2.5秒周期が守れる見込みが立つ（2.2 / 2.6）
- `85.00` の取り違えが起きない（2.3）
- 取りこぼしと再起動をホストが検出できる（`seq` / `up`）
- プローブの入れ替わりに気づける（`hello` の ROM ID）
- **プローブが消えたことにも気づける。** 記録された ROM は人が直すまで残る（2.9）
- デーモンを後から起動しても `hello` を受け取れる（2.8）
- ファームウェアとホストの食い違いが CI で止まる（2.12）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 本物の 85.00 も落ちる | この系では 85.00 自体が異常。ホストの quality も同じ判断をする（2.3） |
| 起動後に挿したセンサーを認識しない | `hello` は起動時の1回という契約。**配線を変えたら再起動する**（README に明記） |
| コンパイル未検証 | ライブラリ API の差異は人の手で確認する（2.12 / §5-1） |
| 分解能 0.125℃ | 空気温度にはセンサー確度（±0.5℃）のほうが支配的 |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 試作を捨てて書き直す | 配線とライブラリは検証済み。直すべき点以外を未検証に戻す（2.1） |
| 12bit のまま周期を 5 秒に延ばす | 要件の 2.5 秒を変えることになる。分解能は足りている（2.2） |
| `85.00` を通してホストだけで判定する | ファームウェアでも落とす。**二重にする**（2.3） |
| ArduinoJson を入れる | 固定の小さなスキーマに対して、版と割り当て失敗の経路が増える（2.4） |
| `snprintf` の戻り値を足し込む | 切り詰め時にバッファを越えて書く（2.4） |
| AM2320 を自前の I²C で読む | 既に入っているライブラリで足りる。自前実装は検証できる環境が無い |
| 空の `hello` を出す | 契約違反の行になる（2.7） |
| `hello` を周期的に出し直す | 「電源投入時に1回だけ」が崩れ、記録が何度も書き換わる（2.8） |
| 繋がっていないプローブも `hello` に載せる | 申告が嘘になる。直すべきはホスト側（2.9） |
| ピン番号を `config/*.yaml` から生成する | Arduino IDE が生成を走らせない。**生成物が古くなる**（2.10） |
| センサーを毎周期スキャンし直す | `hello` が起動時1回という契約と合わない。**再起動が正しい手順**（2.7） |
| 実機が無いので何も検査しない | 形の食い違いは実機なしで止められる（2.12） |
