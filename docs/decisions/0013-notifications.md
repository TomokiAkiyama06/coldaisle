## 1. Context

ルールエンジン（#18）が発火と解除を検出するようになった。これを人へ届ける。

決定記録 0001 が経路（D-03: 重大度で分岐）と夜間の方針（D-04: 夜間も通知。
ただし閾値確定までは critical のみ）を定めている。本記録は**どう届けるか**を確定する。

**通知は監視の外側にある。** 取り込み・保存・判定が本体であり、
通知が失敗しても本体は動き続けなければならない（FR-507 と同じ考え方）。

---

## 2. Decision

### 2.1 秘匿情報は環境変数から読む。設定ファイルにもコードにも置かない

Webhook URL とトークンは `COLDAISLE_SLACK_WEBHOOK` / `COLDAISLE_LINE_TOKEN` /
`COLDAISLE_LINE_TO` から読む。`config/notify.yaml` には**変数名だけ**を書く。

リポジトリは public（決定 Q-06 / #41）。`.env.example` に空の雛形を置き、
実物は `.env`（git 管理外）に置く。

**未設定の宛先は作らない。** 作って毎回失敗させると、ログが失敗で埋まって
本物の障害が見えなくなる。足りないことは**起動時に1度だけ警告する。**
黙って無効にはしない。

### 2.2 送るのは**状態ではなく遷移**

`firing` になった瞬間と `resolved` になった瞬間だけを送る。
発生中のあいだ送り続けると、受け取る側が「新しく起きたこと」を見分けられなくなる。

**`pending` は送らない。** 継続時間に届く前の揺らぎまで通知すると、
本物の発火が埋もれる（決定記録 0012 §2.4 と同じ理由）。

### 2.3 連投を抑える。**発火を届けたなら解除も必ず届ける**

同じ `(ルール, メトリクス)` は初回に送り、以降は `repeat_after_s`（既定30分）
まで送らない。

**解除は連投の抑制も夜間の方針も通さない。** 送らないと、受け取った側は
鳴りっぱなしだと思い続ける。昼に発火して夜に解除した warning が典型で、
夜間の抑制を解除にも当てると届かない。

**ただし、発火を送っていないなら解除も送らない。** 夜間に抑制した warning の
「解除」を夜中に鳴らすのは、夜間の方針（決定記録 0001 D-04）が避けようとして
いることそのものである。

> デーモンを再起動すると抑制の記録は消える。前のプロセスが送った発火の解除は
> 送られない。ダッシュボードと `/api/v1/alerts` には現在の状態が出るため、
> 取り違えは残らない。

### 2.3.1 重大度は**解除する前に**控える

解除したあとに保存済みの行から引くと、その行は既に `resolved` で
未解決の検索に掛からず、既定値（warning）に落ちる。
**critical の解除が warning の経路（Slack）へ流れる。**

ルールの状態として持ち、遷移に載せる。

### 2.4 送信は別スレッド。宛先が応答しなくても取り込みは止めない

宛先への POST を取り込みループの中で待つと、Slack が遅いだけで
サンプルを取りこぼす。待ち行列（128件）に積んで別スレッドが送る。

- 待ち行列は**有界**（常駐メモリ。NFR-05）。溢れたら数えて記録する
- 停止時は**送り切ってから**止める。宛先1つあたり最大10秒かかり順に処理するため、
  待ちは十分長く取る（既定30秒）。送り切れなければスレッドを手放さず、
  **停止に失敗したこととして記録する。** 短い待ちで諦めて参照を捨てると、
  最後の critical を積んだままプロセスが終わる
- 1つの宛先が落ちても、残りの宛先へは届ける。失敗は記録して続ける

### 2.5 夜間は critical のみ。**#19 が終わるまでフラグを true にしない**

夜間（既定 22時〜7時）の warning は送らない。critical は常に送る。

**夜間も通知する以上、誤警報が睡眠を削る。** 「通知が信用されなくなる」より
深刻な実害である（決定記録 0001 D-04 補足）。閾値を実測で確定してから
`night.warning_enabled` を true にする。

この既定値（false）は**テストで固定している。** 実測前に有効化されないように。

### 2.5.1 設定は読み込み時に検証する

タイムゾーンの綴り違いを、最初の warning の遷移まで持ち越さない。
持ち越すと、その例外は取り込み側で「1サンプルの破棄」として記録され、
**そのアラートは二度と通知されない**（発火の遷移はもう出ないため）。

### 2.6 本文は宛先によらず同じ。現在値とダッシュボードへの導線を載せる

- ルール名・重大度・状態・値
- **関連メトリクスの現在値**（本文だけで何が起きているか判断できるように）
- ダッシュボードの URL

発火と解除は記号でも区別する（🔴 / ✅）。文字だけだと通知の一覧で見分けにくい。

### 2.7 LINE は Messaging API の push を使う

**LINE Notify は2025年に終了している。** チャネルアクセストークンと送信先 ID の
両方が要るため、片方だけでは宛先を作らない。

> **要確認**: 実際の送信は実物のトークンでしか確かめられない。
> テストは差し替えた宛先で行っており、**本番の到達確認は運用開始時に行う。**

## 3. Consequences

### 良くなること

- 検出が人へ届くようになり、ルールエンジンが実運用の価値を持つ
- 連投の抑制と夜間の方針が設定に集まり、#19 の結果を反映する場所が1つになった
- 宛先が落ちても、`stdout`（構造化ログ）には必ず残る

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 実サービスへの到達はテストで確かめられない | 宛先の実装は差し替えて検証。到達確認は運用開始時（2.7） |
| 抑制の間隔中に状況が悪化しても送らない | 重大度が上がれば別のルールとして鳴る。解除は必ず届く（2.3） |
| 送信スレッドが増える | 有界の待ち行列。落ちても取り込みは続く（2.4） |
| 夜間の warning が届かない | #19 の完了までの暫定。フラグ1つで切り替わる（2.5） |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 秘匿情報を設定ファイルに置く | リポジトリは public。`.env` と環境変数に限る（2.1、#41） |
| 未設定の宛先も作って失敗させる | ログが失敗で埋まり、本物の障害が見えなくなる（2.1） |
| 発生中のあいだ定期的に送り続ける | 「新しく起きたこと」を見分けられなくなる（2.2） |
| 解除も抑制の対象にする | 鳴りっぱなしと区別できない（2.3） |
| 解除にも夜間の抑制を当てる | 昼に発火して夜に解除した warning が届かず、鳴りっぱなしだと思われる（2.3） |
| 発火を送っていなくても解除は送る | 知らせていないものの解除を夜中に鳴らすことになる（2.3） |
| 重大度を解除後に DB から引く | 未解決の検索に掛からず既定値に落ち、critical の解除が Slack へ流れる（2.3.1） |
| タイムゾーンを使うときに検証する | 最初の warning で例外になり、そのアラートが二度と通知されない（2.5.1） |
| 取り込みループの中で同期送信する | 宛先が遅いだけでサンプルを取りこぼす（2.4） |
| 夜間の warning を最初から有効にする | 実測前の閾値による誤警報が睡眠を削る（2.5、0001 D-04） |
| LINE Notify を使う | 2025年に終了している（2.7） |
