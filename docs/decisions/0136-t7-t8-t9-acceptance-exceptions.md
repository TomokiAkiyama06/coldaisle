## 1. Context

2026-10-14〜15 に、0121 の T7 と 0123 の T8・T9 (b) を実機で行った。結果は `docs/fan-header-mapping.md` にある。
次の 3 点が、FINAL の記録の合格の条件と合わなかった。所有者は 2026-10-15 に、3 点とも受け入れる判断をした。
本記録は、その判断と、受け入れる範囲を残す（AGENTS.md「決定記録」。FINAL の記録と違う判断は新しい記録で承認を得る）。

1. **T7 の GPU 600 W の試行 4 の吸気**
   - 試行 3（fand）の負荷の間に部屋が暖まり、吸気が 20.4 → 23.1 °C に上がった
   - そのため試行 4（BIOS）は、アイドルの記録（19.6 °C）より 3.5 °C 高い吸気で始まった
   - 0121 §2.9 は、負荷の前の吸気の差が ±1 °C を超えたらやり直すと決めている
2. **T8 の中間の負荷**
   - 151〜166 W を 3 分保持した。その間 CPU が 74〜75 °C になり、温度の曲線（0.80〜0.84）が power の曲線（0.70〜0.76）を上回った
   - 181 tick すべてで温度の曲線が Top の floor を決めた。power の曲線が決めた tick は 0
   - 0123 §2.1 は、10 tick に届かなければ合格にしないと決めている
3. **T9 (b) の健全度と Guard の閾値**
   - `telemetry_health` は decision trace にもログにも出ない
   - `threshold_profile` は Guard の発火と解除のログにしか出ず、一時停止の間に Guard は発火しなかった
   - そのため、`DEGRADED`・`conservative` になったことを直接見られなかった

## 2. Decision

### 2.1 T7 の GPU 600 W は、この 1 回に限って合格とする

2026-10-15 09:10〜10:28 の T7 の GPU 600 W（`t7gpu-0910-*`）を、やり直さずに合格とする。根拠は次の 2 つ。

- 吸気がそろっている試行 1（BIOS）とだけ比べても、fand は 6 項目すべてで、最高と最後の 2 分の平均の両方が 0.8〜2.6 °C 低い
  （合格の条件は「BIOS より 3 °C を超えて高くない」）
- 4 回の平均でも、fand は 6 項目すべてで BIOS 以下。温度の throttle の flag はどの試行でも立っていない

この例外は、この 1 回の結果にだけ当てる。0121 §2.9 の吸気の決まりそのものは変えない。以後の T7（曲線や設定を変えてやり直すときを含む）は、
0121 §2.9 のとおり吸気が外れたらやり直す。

### 2.2 `cpu_power_cooling_floor` は両端の 2 点を確定し、途中は実機では確かめない

- 100 W → 0.35 と 200 W → 1.0 の 2 点は、全スレッドの 3 回で確定する。0123 §2.1 の 1 行目と 2 行目は満たしている
  （power の曲線は 2.1〜3.8 s で効き、範囲の外の tick は 0、195 W 以上の tick を含む）
- 2 点の間は、コードが線形に補間する。実機ではこの補間を確かめていない。補間は、CI の
  `tests/test_critical_safety.py::test_cpu_power_jump_raises_the_top_floor_even_when_the_cpu_is_cool`（CPU 40 °C・157.5 W で中間の値）で担保する
- 2 点の間を実機で確かめないのは、この機械では、130〜170 W を保つと温度の曲線が先に floor を決め、power の曲線の途中が
  floor を決める場面が定常では現れないため。power の曲線の途中が効くのは、負荷の立ち上がりで温度が追いつくまでの数秒に限られる
- `safety.yaml` の `cpu_power_cooling_floor` の 2 点は、T1 の後にほかの値と一緒に `confirmed` にしてよい。`basis` には本記録を書く

機械・冷却・曲線のどれかが変わって、130〜170 W で power の曲線が floor を決めるようになったら、0123 §2.1 の中間の負荷の試行をやり直す。

### 2.3 T9 (b) の健全度と Guard の閾値は、CI のテストで確かめる

0123 §2.2 (b) の 2 行目（その間の telemetry の健全度と Guard の閾値）と、3 行目（戻した後）のうち健全度が `NORMAL` に戻る部分は、実機の観測の代わりに、次のテストが CI で通ったことで満たす。3 行目のうち power の項が戻る部分は、実機で `SIGCONT` から 1.8 s の tick で `cpu_power_unavailable` が消えたことで満たしている。
**テストが入るまで、これらは未完了とする。** 実機で見えた次の 2 点は、このテストの前提（収集の側が CPU Power を使えないと判定したこと）を裏付ける。

- 実機で `cpu_power_unavailable` が出たこと（最後の書き込みから 7311 ms）
- fault が上がらず、Top が 0.35 のままだったこと

テスト（#308 で足す）:

- `power.cpu.package` の時刻だけを `stale_after` より古くし、ほかの入力をそろえた frame を、`ControlStateEstimator`（本番と同じ
  `loop.py` の signal の組み立て）から Reactive Guard まで通す
- 確かめること:
  - 健全度が `DEGRADED` になる
  - Guard の `threshold_profile` が `conservative` になる
  - 新しい sample を渡した tick で `NORMAL`・`normal` に戻る
- 既存の `test_one_air_probe_loss_is_degraded_but_not_the_critical_group`（空気のセンサー）と
  `test_degraded_snapshot_uses_the_configured_conservative_threshold_set`（Guard 単体）は、規則を別々に確かめるだけなので、この代わりにしない

戻した後の T8 の全スレッドで Guard の発火 4 回がすべて `normal` の閾値だったことは、約 1 分後の値で、新しい sample を観測した tick の健全度を示さないので、合否の材料にしない。

#308 で健全度と閾値を trace に載せたら、T1 の間に実機でも確かめる（0123 §2.3）。

## 3. Consequences

### 良くなること

- 所有者の判断が、FINAL の記録と食い違ったまま残らない。どの値をどの根拠で確定したかを、本記録から辿れる
- T9 (b) の健全度は、推論ではなく、本番の signal の組み立てを通したテストで確かめることになる

### 悪くなること・その緩和

- T7 の GPU の比較は、試行 4 の初めの状態がそろっていない。緩和: 試行 1 だけとの比較でも 3 °C の余裕がどの項目にも残ることを確かめた。
  例外はこの 1 回に限り、以後は 0121 §2.9 のとおりやり直す
- `cpu_power_cooling_floor` の途中の傾きは、実機の経路では確かめていない。緩和: 途中は温度の曲線が先に決めるので、傾きが
  定常の Fan を決めることはない。補間は CI のテストで担保する。機械が変われば中間の負荷をやり直す（§2.2）
- T9 (b) は、#308 のテストが入るまで閉じない。緩和: そのテストは小さく、T1 の前に入れられる

## 4. 却下した代替案

- **T7 の GPU の試行 4 を、吸気が戻ってからやり直す**: 20〜50 分で済むが、所有者は試行 1 との比較で十分と判断した
- **`cpu_power_cooling_floor` を `provisional` のまま残し、測り方を変える**: 途中の傾きを実機で効かせるには、温度の曲線を一時的に
  緩める試験専用の設定が要る。0121 §2.1 は試験専用の設定を T6 にしか認めず、得られるものに比べて重い
- **T9 (b) の 2 行目を、コードの規則の推論だけで合格にする**: Codex のレビュー（PR #309）の指摘のとおり、既存のテストは規則を
  別々に確かめるだけで、CPU Power の古さから健全度と閾値までをつないでいない
- **trace に載せてから T9 (b) を実機でやり直す**: T1 を #308 の実装と /opt の更新まで待たせる。テストで足りるので選ばない
