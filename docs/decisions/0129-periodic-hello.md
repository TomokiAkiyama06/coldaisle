## 1. Context

`hello` は、基板が起動したときに自分の構成（DS18B20 の ROM・GPIO・分解能、`interval_ms`、ファームウェアの版）を取り込みへ知らせる。
取り込みはこれを `devices` / `device_sensors` に記録し、記録した ROM と比べてプローブの差し替え（`PROBE_CHANGED`。較正のオフセットが
別のプローブに当たり続けるのを防ぐ。FR-403）を見つける。ファームウェアはセンサーを起動時にしか数えないので、差し替えには必ず
基板の再起動が伴い、その直後の `hello` が差し替えを知らせる。

0022 §2.8 は、デバイスが先に起動して `hello` が誰にも読まれずに消える場合に備え、「USB CDC の接続状態の立ち上がり」で `hello` を
出し直すとした。2026-10-14 に導入先（XIAO ESP32-S3、Hardware CDC）で確かめたところ、これが働いていなかった（#43）。

| 観測 | 内容 |
|---|---|
| 届いてほしいときに届かない | USB を挿し直して基板が再起動した 2 回（17:01・17:05）とも、その後の `hello` が 1 回も届かなかった。取り込みはポートが見つからない間 1 → 2 → 4 → 8 s の間隔で探し直すので、ポートを開くのは基板の起動より数秒遅い。`setup()` の `hello` も、`(bool)Serial` の立ち上がりも、ポートを開く前に過ぎていた |
| 要らないときに届く | 再起動していないのに、10-14 だけで 234 回届いた（4 時間 29 分の 1 回の実行で `hello` 67 回・再起動の検出 0 回）。Hardware CDC の `(bool)Serial` は、ホストがポートを開いたこと（DTR）ではなく USB の状態と送信の詰まりで決まり、ときどき false になってから true に戻る |

いま再起動の後に構成が数分以内に届いているのは、2 行目の不具合のおかげで、偶然うまく回っているだけである。取り込みだけを
再起動したとき（`systemctl restart coldaisle-daemon`）も、立ち上がりが起きないので同じく届かない。

## 2. Decision

### 2.1 ファームウェア: `hello` を起動時と 60 s ごとに出す

- `setup()` で 1 回出す（今と同じ）。その後、前回の `hello` から 60 s（`HELLO_INTERVAL_MS = 60000`。スケッチの定数。0022 §2.10 と
  同じく Arduino IDE が生成を走らせないのでスケッチに置く）経つごとに、サンプルの行の間に 1 行出す
- `(bool)Serial` の立ち上がりで出し直す処理（0022 §2.8）はやめる。Hardware CDC では読み手を表さない
- 中身は今と同じ（起動時に数えた構成）。周期の `hello` で構成が変わることはない（センサーは起動時にしか数えない。0022 §3「起動後に挿したセンサーを認識しない」）
- 時刻は `seq` と同じ 64 bit の単調な時計（`esp_timer_get_time()`）で数える

基板の再起動の後も、取り込みの再起動の後も、ポートを開いてから**最長 60 s**（+ 1 周期 2.5 s）で構成が届く。

### 2.2 取り込み: 同じ内容の `hello` は記録し直さない

- 取り込みのプロセスは、直前に処理した `hello` の中身（`dev`・`fw`・`v`・`interval_ms`・センサーの一覧）を覚える
- 同じ中身の `hello` が来たら、`devices` / `device_sensors` / `sys.observed_probes` に書かず、規則のエンジンの `on_hello` も呼ばず、
  info のログも出さない。数（`hellos_repeated`）だけを取り込みの終わりの集計に足す
- 次のときは必ず処理する（今と同じ扱い）: プロセスの起動の後の最初の `hello`・中身が変わった `hello`。シリアルの再接続や
  デバイスの再起動の検出で、覚えた中身は消さない（中身が同じなら記録も規則も同じ結果になる）
- `devices.last_hello_ms`（0002 §2.10）の意味は「直近に**処理した**起動バナーの受信時刻」になる。60 s ごとには進まない
- 0022 §2.8 が周期の `hello` を却下した理由（記録が何度も書き換わる）は、この 2.2 で取り除く

### 2.3 取り込み: サンプルの `err` の中身を、変わったときだけログに残す

- サンプルの `err`（例 `top_exhaust:-127`・`room:absent`。0003 §2.3）の集合が直前のサンプルと変わったとき、warning で 1 行残す
  （増えたもの・消えたもの）。同じ `err` が続く間は出さない。DB には残さない（今と同じ）
- 欠測の原因（配線・センサーの故障・未接続）を後から追えるようにし、#43 の受け入れ基準「`err` に `<channel>:-127` が入る」・
  「`room:absent` が入る」を、シリアルポートを開かずに（AGENTS.md ルール 6）確かめられるようにする

### 2.4 #43 の受け入れ基準の読み替え

「電源投入時に `hello` が 1 回だけ出る」を「起動時に 1 回、その後 60 s ごとに出る。取り込みは同じ中身を記録し直さない」に読み替える。
確かめること:

1. USB を挿し直して基板を再起動した後、ポートを開いてから 62.5 s 以内に `hello` を処理する（「起動バナーを受け取った」のログ）
2. `systemctl restart coldaisle-daemon` の後も、62.5 s 以内に処理する
3. 再起動していない間は、「起動バナーを受け取った」のログが増えない（`hellos_repeated` だけが増える）
4. プローブを 1 本抜いて起動すると、`err` の変化のログに `<channel>:-127` が出る。AM2320 を抜いて起動すると `room:absent` が出る

## 3. Consequences

### 良くなること

- 再起動の後・取り込みの再起動の後に、プローブの差し替えに最長約 60 s で気づける（今は偶然に頼っていた）
- 意味の無い記録の書き換えとログ（1 日に数百回）がなくなる
- 欠測の原因がログに残る

### 悪くなること・その緩和

- シリアルの帯域が増える。`hello` は 1 行 約 500 byte（`firmware/sample_output.jsonl` の例で 494 byte）で 60 s に 1 回。サンプル（2.5 s ごと）の約 1/24 の行数で、無視できる
- 取り込みのプロセスが起動してから最初の `hello` までの最長 60 s は、`PROBE_CHANGED` を判定できない。差し替えは人が基板を
  止めて行う作業で、60 s の遅れは較正の誤りの期間（人が直すまで続く）に比べて短い
- 書き込みが要る（ファームウェアの更新。コンパイルと書き込みは人の手。0022 §2.12）

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| USB の方式を USB-OTG（TinyUSB）に変え、DTR でポートを開いた瞬間を検出する | 「1 回だけ」を保てるが、ボードの設定・書き込みの手順・リセットの挙動が変わり、実機で確かめることが増える。取り込みの再起動の扱いも DTR の実装に依存する |
| 起動から 30 s の間だけ、サンプルごとに `hello` を出す | 基板の再起動には効くが、取り込みだけを再起動したときに届かない |
| サンプルに構成の指紋（ROM の一覧のハッシュ）を載せる | 差し替えにすぐ気づけるが、どの ROM に変わったかは `hello` が要る。サンプルの形（0003）も変わり、作業が大きい |
| 取り込みが再接続の後に何かを送って `hello` を求める | デバイスへの書き込みの経路を作ることになる。v1 の契約は一方向 |
| 直さない | 今は余計な `hello` のおかげで数分以内に届いているが、その不具合が直ると（または環境が変わると）届かなくなる |
