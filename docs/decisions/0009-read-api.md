## 1. Context

決定記録 0004 が保存側の読み出し契約を、`docs/api-contract.md` が
Workspace との境界を定めている。本記録はその間、**HTTP として何をどう返すか**を
確定する。表現の選択（時刻の形、粒度の選び方、派生値の扱い）は
クライアントの実装を縛るため、コードのコメントではなく記録に残す。

---

## 2. Decision

### 2.1 メトリクスの単位・表示名は `config/metrics.yaml`（0004 §5 未決1 の決定）

決定記録 0004 §5 は「置き場所は #9 で決める」としていた。**ここに確定する。**

- 保存されるメトリクスの `unit` / `label`
- **派生値の定義**（`unit` / `label` / 被減数 / 減数）

派生値を式ではなく「引き算1つ」で書くのは、要件 §5.1 の5つがすべて差だからである。
任意の式を書けるようにすると、設定ファイルが小さな言語になり、
「この値が何を意味するか」がコードからも設定からも読めなくなる。

**メトリクス名は変えない**（0002 §2.1）。表示名は変えてよい。

### 2.2 派生値は**両方の測定値が `ok` のときだけ**計算する

`suspect` や `stale` を引き算すると、もっともらしい数値が出る。
`-127.00` から室温を引いた `-153.4` は「再循環が無い」ように見え、**故障を隠す。**

計算できない場合はキーを残して `null` を返す。キーごと省くと、
クライアントは「定義が無い」のか「今は出せない」のかを区別できない。

### 2.3 時刻は `ts_ms` と ISO8601（UTC）の両方で返す

| 形 | 用途 |
|---|---|
| `ts_ms` | 計算用。保存と同じ Unix ミリ秒（決定 D-05） |
| `ts` / `last_sample_at` | 人間とログ用。ISO8601、オフセットは `+00:00` |

**サーバはタイムゾーンを持たない。** 表示のためのローカル変換はクライアントが行う。
`api-contract.md` の例は JST 表記だが、同じ瞬間を指す表現であり解釈は変わらない
（日次CSV だけは人間が直接読むファイルなのでローカル時刻。決定記録 0008 §2.8）。

### 2.4 `series` は点数が上限を超えると自動で粗くする

上限は `COLDAISLE_MAX_POINTS`（既定 2000）。

- **要求より粗くはするが、細かくはしない。** 細かくすると、呼び出し側が
  想定した点数を超えて返すことになる
- 実際に使った粒度を `agg`、落としたかどうかを `downsampled` で返す。
  **黙って粒度を変えない**

粒度の候補は `raw / 1m / 5m / 1h`（0004 §2.9）。生の点数の見積りには
`devices.interval_ms` を使い、起動バナーが無ければ 2.5 秒とみなす。

### 2.5 `stats` は常に生データから計算する

分位数はロールアップから合成できない（0004 §2.9）。したがって `stats` に
`agg` は無い。**生データの保持期間（30日）を超える窓では p95 を返せない。**

### 2.6 `WS /api/v1/stream` は DB を見に行く

取り込みは別プロセスであり、プロセスをまたぐ通知の仕組みは持たない
（決定記録 0007 §2.11 と同じ理由）。**1秒ごとに最新値を問い合わせ、
変化していたら押し出す。**

最新値の取得はメトリクス数に比例する（0004 §2.11）ので、この頻度で問題にならない。
通知の仕組みを足すより、止まりにくいほうを採る。

### 2.7 `health` はデータが古ければ `ok: false`

**無音で古い値を返さない**（api-contract §3 が名指しで禁じている失敗）。
`stale` の判定は保存側と同じしきい値（`config/quality.yaml` の `stale_after_ms`）を使う。

欠測率は直近1時間の1分ロールアップから出す（0002 §2.8）。

### 2.8 取り込みソース種別は `system_state` に置く

FR-305 が求める「ソース種別」は API 側からは分からない。デーモンが起動時に
`sys.ingest_source` として書き、API はそれを読む。**変化時だけ書く**という
`system_state` の規則（0002 §2.6）に合う。

### 2.9 API の設定は環境変数から読む

`uvicorn coldaisle.api:app` には引数を渡せないため、CLI ではなく環境変数にする
（AGENTS.md ルール6 は環境変数を認めている）。

| 環境変数 | 既定 |
|---|---|
| `COLDAISLE_DB` | `var/coldaisle.db` |
| `COLDAISLE_QUALITY_RULES` | `config/quality.yaml` |
| `COLDAISLE_METRICS` | `config/metrics.yaml` |
| `COLDAISLE_MAX_POINTS` | `2000` |
| `COLDAISLE_STREAM_POLL_S` | `1.0` |

### 2.10 接続はスレッドごとに1本

`SqliteStore` はスレッド間で共有しない（0004 §2.8）。FastAPI の同期
エンドポイントはスレッドプールで動くため、スレッドローカルに持つ。

**停止時に閉じられない接続がある。** `sqlite3` の接続は作ったスレッドから
しか閉じられず、停止処理は別スレッドで走る。閉じ損ねた接続はプロセス終了時に
解放される。WAL はコミット済みなのでデータは失われない。

## 3. Consequences

### 良くなること

- 書き込み系が構造として存在しない。OpenAPI に `get` 以外が現れないことを
  テストで固定した（FR-307）
- クライアントは点数の上限を気にせず期間を投げられる。返ってきた `agg` を見れば
  何が起きたか分かる
- 派生値の定義が1ファイルに集まる。較正の変更で過去と食い違う問題も起きない（0002 §2.2）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| WebSocket が最大1秒遅れる（2.6） | 2.5秒周期の観測に対して十分。間隔は環境変数で変えられる |
| `stats` が保持期間を超える窓に答えられない（2.5） | 長期の傾向は `series` の `1h` を使う。p95 が要るなら生データを消す前に取る |
| 停止時に接続が残りうる（2.10） | WAL のためデータは失われない。プロセス終了で解放される |
| 派生値が `null` になる場面が増える（2.2） | それが正しい。値を出すと故障が隠れる |

---

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 派生値も保存する | 較正を変えたとき過去と食い違う（0002 §2.2） |
| 入力が `suspect` でも派生値を計算する | もっともらしい数値が故障を隠す（2.2） |
| 時刻をローカル時刻（JST）で返す | サーバがタイムゾーンを持つことになる。表示はクライアントの関心事（2.3） |
| 点数超過をエラーにする | クライアントが粒度を選び直す実装を全員が書くことになる（2.4） |
| 黙ってダウンサンプルする | グラフの解像度が変わったことに気づけない（2.4） |
| `stats` に `agg` を持たせる | p95 が合成できない。粒度で意味が変わる統計を返すことになる（2.5、0004 §2.9） |
| 取り込みから API へ通知を送る（ソケット等） | プロセス間の依存を増やす。止まったときの原因が層をまたぐ（2.6） |
| ソース種別を `devices.device_id` から推測する | `-mock` のような名前の慣習に依存する。状態は状態として持つ（2.8） |
