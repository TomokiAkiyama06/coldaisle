## 2. Decision

### 2.1 較正は品質判定の**後**に当てる

`classify()` で品質を決めてから、`ok` の値にだけ較正オフセット（FR-107）を足す。

**順序が逆だと番兵値をすり抜ける。** `-127.00 + 0.3` は `-126.7`、
ちょうど `85.00` も `85.3` になり、どちらも判定に掛からなくなる
（要件 §5.3 / spec-review C-02）。

較正は「正常な測定値のずれ」を直すものであって、**故障を示す値に足すものではない。**

### 2.2 較正は温度チャネルにのみ当てる

`config/calibration.json` の単位は℃。`air.room_humidity`（%RH）には当てない。
#13 で測るのも温度だけである。単位の違う値に同じオフセットを足す事故を、
実装の側で起こらないようにする。

### 2.3 非有限値は行ごと捨てず、値だけ落とす

`NaN` / `±Infinity` が正規化まで届いた場合、**そのチャネルの値を NULL にし、
品質（`missing` / `suspect`）は残す。** サンプル全体は捨てない。

決定記録 0003 §2.8 の「行として破棄する」は**パーサ（FR-103 / #12）の役目**である。
そこを通り抜けた1チャネルのために他の6チャネルの観測まで失うのは割に合わない。
`sensor_fail` シナリオで確かめているのと同じ原則で、
**1本の故障が全体の欠測に見えてはいけない。**

### 2.4 `seq` の飛びと再起動は「発生したときだけ」メトリクスに書く

| メトリクス | いつ書くか | 値 |
|---|---|---|
| `sys.dropped_samples` | `seq` が飛んだサンプルの時刻に1行（FR-105） | 飛んだ件数 |
| `sys.device_restarts` | `up` の巻き戻りを検出した時刻に1行（FR-106） | `1` |

**毎サンプル書かない。** 0 を書き続けると行数が14%増える一方、
読み出し側は「期間の合計」しか使わない。

**したがって `latest()` に出る値は「直近の欠損の大きさ」であって現在の状態ではない。**
ダッシュボードは `series` で期間集計する。

イベント表（#36）ができたらそちらへ移す。ログだけに残さないのは、
24時間連続運転の記録を後から集計できなくなるため。

### 2.5 未知のチャネルは捨て、初出だけログに残す

決定記録 0003 §2.7 の寛容さを取り込み側でも守る。ファームがフィールドを1つ
足しただけで全サンプルが落ちるのが最悪の壊れ方である。

毎サンプル記録するとログが埋まるため、**そのプロセスで初めて見たときだけ**出す。

### 2.6 「破棄」の定義

`Stats.discarded` が数えるのは**保存に失敗したサンプル**である。
主キー衝突（決定記録 0004 §2.7 で上書きを拒否した）や DB エラーが該当する。

1件破棄しても**プロセスは動き続ける**（AGENTS.md コード規約の唯一の例外）。
ただし握りつぶさず、件数とスタックを構造化ログへ残し、終了時に合計を出す。

### 2.7 合成の起点は `daemon.build()` ただ1箇所

時計・しきい値・較正値をここで作り、**同じインスタンス**を取り込みと保存へ配る。
`Clock` は型しか縛らないため（#42）、同一性はこの1箇所と、
それを検査するテストで担保する。

### 2.8 SIGTERM は次のメッセージの手前で効く

**処理中のサンプルは書き切る。** 途中で落とすと、1サンプルの一部だけが
保存された時刻ができる（決定記録 0002 §2.3 の「全行が同一の `ts_ms`」が崩れる）。

ソースが待機中の場合、実際に止まるのは次のサンプルが届いたときになる。
実機の周期は2.5秒なので、停止までの遅れはその範囲に収まる。

### 2.9 `devices.last_seen_ms` は起動バナー受信時のみ更新する

サンプルごとに `UPDATE` を撃たない。最終受信時刻が要る場合は
`readings` の最新行（`latest()`）から取る。決定記録 0002 §2.10 も
`devices` は起動バナーで更新するテーブルとしている。

### 2.10 起動バナーはセンサー構成を**丸ごと置き換える**

起動バナーはその時点の全構成を申告するため、差分更新にすると
外したセンサーの行が残り続ける。置き換える前の ROM は
`sensors_for()` で読めるので、`PROBE_CHANGED`（FR-403 / #14）の判定はできる。

#8 では ROM の変化を**警告ログに出すところまで**とし、アラート化は #14 で行う。

### 2.11 圧縮再生はデーモン単体の機能とする

`--speed` による時間圧縮は、**取り込みデーモン1プロセスの中でだけ意味を持つ。**
別プロセスの API から圧縮中のデータを正しく解釈することは**求めない。**

`SimulatedClock` はメモリ上のオブジェクトなので、プロセスを分けると共有できない
（#42）。API 側に実時計を渡せば圧縮再生のサンプルは実時刻より未来になり
（`data_age_seconds` が負になる）、別の `SimulatedClock` を渡せば誰も進めないので
止まったままになる。**どちらも壊れる。**

仮想時刻を DB 経由で共有する案は採らない。**圧縮再生の目的はルールと閾値の
検証であり、その検証に API は要らない。** 共有する案を採ると、心拍を書くための表・
毎周期の書き込み・その保持期間を v1 のスコープへ足すことになる
（`system_state` は「変化したときだけ書く」表なので流用できない。決定記録 0002 §2.6）。
得られるのは「圧縮再生中もダッシュボードが見える」ことだけで、割に合わない。

したがって次のとおりとする。

- **`--speed` が 1 以外のとき、デーモンは起動時に警告を1回出す**
- 圧縮再生中は API / ダッシュボードを同時に使わない。使っても表示は保証しない
- 継続時間ベースのルール（FR-401〜409）の検証は、**ルールエンジンを
  デーモンと同じプロセスに置いて**行う（#18 の配置制約）
- 実運用（`serial` ソース）は常に `WallClock` なので、この制約は開発時だけに効く

## 3. Consequences

### 良くなること

- 番兵値（`-127.00` / `85.00`）が較正でずれて見逃されることがなくなる
- 1チャネルの異常でサンプル全体を失わない。欠測率の母数が正しく残る
- 取りこぼしと再起動が**あとから集計できる**形で残る（ログだけではない）
- 時計・しきい値・較正値の出どころが1箇所になり、テストで同一性を確かめられる

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| `sys.dropped_samples` の `latest()` が現在の状態を表さない（2.4） | 読み出し側は `series` を使う。API（#9）の応答にこのメトリクスを最新値として載せない |
| 再起動が `readings` に入り、イベント表と二重管理になりうる | #36 で表を作る際にこちらを廃止する。移行するまでは1箇所だけに置く |
| 停止まで最大1周期（2.5秒）待つ（2.8） | 実運用の停止要件（NFR）に対して十分短い |
| `devices.last_seen_ms` が起動バナーの時刻を指す（2.9） | 列の意味を本記録で明示した。健全性判定は `latest()` の `age_ms` を使う |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 較正を先に当ててから品質を判定する | 番兵値がずれて判定をすり抜ける（2.1） |
| 非有限値が1つでもあればサンプルごと捨てる | 他の6チャネルの観測まで失う（2.3） |
| `sys.dropped_samples` を毎サンプル 0 で書く | 行数が14%増えるのに読み出し側が使わない（2.4） |
| 再起動をログにだけ残す | 24時間連続運転の記録を後から集計できない（2.4） |
| 未知チャネルで例外を投げる | ファームの1フィールド追加で取り込みが全停止する（2.5） |
| サンプルごとに `devices.last_seen_ms` を更新する | 毎周期の `UPDATE` に見合う用途が無い（2.9） |
| 各レイヤが自分で時計・設定を読む | 同じ設定の別インスタンスが混在する。#42 が防ごうとしている状態そのもの |
| 仮想時刻を DB へ書いて API と共有する | 心拍のための表・毎周期の書き込み・保持期間を v1 へ足すことになる。得られるのは圧縮再生中の表示だけ（2.11） |
