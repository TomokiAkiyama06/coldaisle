## 1. Context

Slack に届く通知の先頭の行は `🔴 [critical] RAPID_RISE [air.gpu_intake] — firing` の形で
（0135 §2.2）、重大度・ルール・メトリクス・状態がすべて英語の ID になっている。
所有者は「英語で読めない」とし、日本語にすることを選んだ（2026-10-15）。

所有者の選択（2026-10-15。最初の案を Slack で確かめたうえで、次の形を了承した）:

```text
🔴 [重大] GPU の吸気温度が急上昇しています
GPU吸気 37.2 °C（1 分で +5.2 °C）・室温 26.1 °C
GPU の前が塞がれていないか、排気が回り込んでいないかを確認してください。
RAPID_RISE / air.gpu_intake
```

- 見出しはルールごとの文。名前の重なり（「GPU吸気が高い（GPU吸気）」）を出さない
- 値と detail を重ねず、1 行に「対象の値（変化量や閾値の超過）・関係する値・室温」。数は小数 1 桁
- ルールごとの「確かめること」の一文
- 解除は「✅ [重大 解除] GPU の吸気温度の急上昇が収まりました」のような文と現在値の 1 行
- ダッシュボードの URL は、スマホから開けない既定（127.0.0.1）なら出さない
- 最後の行に ID を残す。重大度は critical=重大・warning=警告・info=情報
- 文はすべて設定に置き、翻訳に LLM を使わない

0135 §2.2 は見出しの形を決めているため、置き換える記録が要る。

## 2. Decision

### 2.1 先頭の行

| 種別 | 形 | 例 |
|---|---|---|
| 発火 | `<記号> [<重大度>] <title>` | `🔴 [重大] GPU の吸気温度が急上昇しています` |
| 解除 | `✅ [<重大度> 解除] <resolved_title>` | `✅ [重大 解除] GPU の吸気温度の急上昇が収まりました` |
| 発火の説明（#38） | `🔎 [<重大度>] 説明: <title>` | `🔎 [重大] 説明: GPU の吸気温度が急上昇しています` |

- `title` / `resolved_title` は `config/rules.yaml` の各ルールの文（2.3）
- 記号（🔴 critical / 🟠 warning / 🔵 info / 解除は ✅）は 0135 §2.2 のまま。重大度の語は critical=`重大`・warning=`警告`・info=`情報`
- **メトリクスの括弧は、ルールの定義がメトリクスを決めていないときだけ付ける。** 定義が決めているルール
  （`RAPID_RISE` なら `air.gpu_intake`）の文はその対象を言っているので重ねない。`SENSOR_MISSING` はアラートごとに
  メトリクスが違うので `センサーの値が欠けています（トップ排気）` とする。判定はアラートのメトリクスがルールの定義の
  メトリクス（`metric` / `core_metric` / `fan_metric`）に含まれるかで行い、文字列の一致は見ない
- 日次レポート（`📄`）と故障疑いの案件（`📄 エスカレーション候補 …`）の先頭の行は変えない（アラートではない）

### 2.2 本文

発火:

1. 先頭の行（2.1）
2. **値の行**（2.2a）。`・` で区切った 1 行
3. **確かめること**（`config/rules.yaml` の `hint`）
4. ダッシュボードの URL（**ループバックのアドレスなら出さない**）
5. **最後の行に ID**: `<RULE_ID> / <metric>`。メトリクスを持たないアラートは `<RULE_ID>` だけ

解除: 先頭の行・値の行（現在値だけ。注記なし）・URL（同じ規則）・ID。確かめることは載せない。

説明（`🔎`）: 先頭の行・説明の全文・URL（同じ規則）・ID。説明の全文（検証済みの文と LLM の文）は変えない。

- `値:` の行と `detail` の行は無くす（同じことを 2 回書いていた）。`detail` は DB に保存されたまま（2.5）
- URL: ホストが `127.*`・`localhost`・`::1` なら出さない。既定の `dashboard_url` はサーバー自身から見たアドレスで
  スマホの Slack から開けないため（#307）。`COLDAISLE_DASHBOARD_URL` で別の端末から開けるアドレスを与えると出る。
  日次レポート・案件の通知にも同じ規則を当てる
- 最後の行の ID は、ログ（構造化ログの `rule` / `metric`）・DB・`config/rules.yaml` と突き合わせるために残す。
  Slack の書式（小さい文字）は使わない。宛先によらず同じ本文にするため（0013 §2.6）

### 2.2a 値の行

**発火**は、先頭に対象の値とその意味（2.4）、続けて関係する値、最後に室温。**解除**は関係する値と室温だけ。

関係する値は次の順で選ぶ（所有者の追加の選択。空気のセンサー 7 本すべてが並んで長すぎたため）。

1. アラートのメトリクス（`SENSOR_MISSING` はアラートごとのメトリクス）
2. ルールの定義が参照する残りのメトリクス（`metric` / `core_metric` / `fan_metric`）
3. 1・2 が派生値なら、その材料（`config/metrics.yaml` の `derived` の `minuend`・`subtrahend`）
4. 最後に `config/notify.yaml` の `context_always`（既定 `[air.room]`。**必須**。`config/metrics.yaml` に無い名前なら起動時に落とす）

- 重複は先に出たほうだけを残す（室温そのもののアラートでは室温を重ねない。発火の先頭に出した対象も重ねない）
- 選び方は**ルールの定義と派生値の定義から機械的に決める。** ルールごとの手書きの一覧を持たない
- デーモンが持っている現在値（取り込みの最新のサンプルの `air.*` と、それから計算した派生値）に
  無いメトリクスは出さない。値が ok でないものは `—`
- 各項は `<メトリクス名> <値> <単位>`（例 `室温 26.1 °C`）

| アラート | 解除の値の行（発火では先頭が 2.4 の形になる） |
|---|---|
| `AIRFLOW_DEGRADED`（`d.gpu_delta`） | GPUが与えた熱・GPU排気・GPU吸気・室温 |
| `RECIRCULATION`（`d.intake_rise`） | 吸気上昇（再循環の指標）・前面吸気・室温 |
| `INTAKE_HIGH` / `RAPID_RISE`（`air.gpu_intake`） | GPU吸気・室温 |
| `ROOM_HIGH`（`air.room`） | 室温 |
| `HUMIDITY_OUT_OF_RANGE`（`air.room_humidity`） | 室内湿度・室温 |
| `SENSOR_MISSING`（例 `air.top_exhaust`） | トップ排気・室温 |
| `SENSOR_FAULT` | 室温 |

### 2.3 文と名前の置き場

`config/rules.yaml` の各ルールに次の 4 つを置く。**4 つとも必須**（欠けている・空なら設定の読み込みで `ValueError` にして起動しない）。

| 項目 | 使う場所 |
|---|---|
| `label` | 短い名前。日次レポートの表（2.6） |
| `title` | 発火の見出しの文（「〜しています」） |
| `resolved_title` | 解除の見出しの文（「〜が収まりました」「〜が戻りました」） |
| `hint` | 発火の本文の「確かめること」の一文 |

`hint` を必須にするのは推奨による（所有者の判断を待つ）: 任意にすると、新しいルールを足したときに手掛かりの無い通知が
静かに通る。通知を受けた人が次に何をするかを本文だけで分かるようにする（0013 §2.6 と同じ考え方）。

メトリクスの名前と単位は `config/metrics.yaml` の `label` と `unit`（既に必須）。無いメトリクス（DB にだけある
`gpu.1.core` など）は **ID のまま**表示し、単位を付けない。

初版の文（Claude の案。所有者が `config/rules.yaml` で直してよい。コードの変更は要らない）:

| ID | `title` | `resolved_title` | `hint`（要約） |
|---|---|---|---|
| `SENSOR_FAULT` | センサー基板からのデータが途絶えています | センサー基板からのデータが戻りました | USB ケーブルと電源・`journalctl -u coldaisle-daemon` |
| `SENSOR_MISSING` | センサーの値が欠けています | センサーの値が戻りました | 配線とコネクタ |
| `PROBE_CHANGED` | 温度プローブの入れ替わりを検出しました | 温度プローブの対応が較正と一致しました | 差し替えたなら較正をやり直す |
| `RECIRCULATION` | 排気が吸気側へ回り込んでいます | 排気の回り込みが収まりました | 前後の空き・排気が前へ戻る経路 |
| `INTAKE_HIGH` | GPU の吸気温度が高くなっています | GPU の吸気温度が下がりました | 室温・前面の Fan・吸気口 |
| `AIRFLOW_DEGRADED` | GPU を通る風量が落ちています | GPU を通る風量が戻りました | Fan の回転・フィルター・ケーブル |
| `RAPID_RISE` | GPU の吸気温度が急上昇しています | GPU の吸気温度の急上昇が収まりました | GPU の前が塞がれていないか・排気の回り込み |
| `ROOM_HIGH` | 室温が高くなっています | 室温が下がりました | エアコン・窓と扉 |
| `HUMIDITY_OUT_OF_RANGE` | 室内の湿度が範囲を外れています | 室内の湿度が範囲に戻りました | 加湿器・除湿器・エアコン |
| `GPU_FAN_NOT_MANUAL` | GPU の Fan を曲線のサービスが制御していません | GPU の Fan を曲線のサービスが再び制御しています | `systemctl status` / `journalctl -u coldaisle-gpu-fan` |
| `GPU_FAN_BELOW_CURVE` | GPU が熱いのに Fan が曲線より遅く回っています | GPU の Fan が曲線どおりに戻りました | 同上 |

### 2.4 値の書き方と単位（表示の側だけで整える）

`config/metrics.yaml` の `unit` の値（API の `unit` が返す値）は**変えない**。人が読む本文でだけ写す。

| `unit` | 表示 |
|---|---|
| `C` | `°C` |
| `flag` / `count` | 単位を付けない |
| それ以外（`%RH`・`%`・`W`・`GB`・`rpm`） | そのまま |

数は**小数 1 桁**、数と単位の間は半角の空白 1 つ（`26.1 °C`）。

発火の値の行の先頭は**ルールの型**で決める（ルールの ID で分岐しない。値の意味がルールの型ごとに違うため）。

| ルールの型 | 先頭の項 | 例 |
|---|---|---|
| 変化率（`SlopeRule`） | 対象の現在値と 1 分あたりの変化 | `GPU吸気 37.2 °C（1 分で +5.2 °C）` |
| しきい値（`ThresholdRule`） | 値と閾値 | `GPU吸気 41.8 °C（閾値 40.0 °C を超過）` |
| 範囲（`RangeRule`） | 値と外れた側 | `室内湿度 71.0 %RH（上限 70.0 %RH を超過）` / `（下限 20.0 %RH を下回る）` |
| 高温と低回転（`HotAndSlowRule`） | Fan の値と下限。続けて温度 | `GPU Fan速度（NVMLの目標値） 47.0 %（70.0 % 未満）・GPUコア温度 81.0 °C` |
| flag（`FlagOffRule`） | 出さない（0 / 1 は見出しの文が言っている） | — |
| 無音（`SilenceRule`） | 届いていない秒数 | `31 秒データが届いていない` |
| 連続（`ConsecutiveRule`） | 欠けた回数 | `トップ排気の値が 5 回続けて欠けた` |
| 出来事（`EventRule`） | `detail` をそのまま | `較正が対応していないプローブ: gpu_intake` |

### 2.5 `detail` の文は変えない

`detail` はルールエンジンが作り、DB（`alerts.detail`）に保存され、説明（#38）の材料になる。本記録では変えない。
通知の本文には出来事のルール（`PROBE_CHANGED`）でだけ載せる（それ以外は値の行と重なるため）。

### 2.6 日次レポートの表もルールの名前と日本語の重大度にする

`## アラート` と `## 日の終わりに続いているアラート` の表のルールの列を `<label>（<RULE_ID>）`、
重大度の列を 2.1 の語にする。測定値の表が既に `<表示名>（<メトリクス>）` の形なので揃える。
`coldaisle-report` に `--rules`（既定 `config/rules.yaml`）を足す。

LLM へ渡す版（`facts_markdown()`、0131 §2.4a）も同じ形で作る。除外の一覧のルールはその版に元から無いので、
その名前は LLM へ届かない。ルールの名前は設定の文字列で、時系列ではない（ルール 8 に当たらない）。
レポートの見出し（`# 日次レポート …`）と通知の先頭の行（`📄 日次レポート …`）は変えない。

### 2.7 変えないもの

- **故障疑いの案件資料**（`coldaisle-escalate`）とその通知の本文（URL の規則だけは 2.2 を当てる）
- **構造化ログの `rule` / `severity` / `metric`**: ID のまま（`text` だけが日本語になる）
- **連投の抑制・夜間の方針・宛先**（0013・0135 §2.1 / §2.3）: ID で判定するので変わらない
- **AI ツールの閾値（`describe_system` の `thresholds`）と運用メモリの事実**: 2.3 の 4 つの文を含めない
  （閾値ではないため。LLM へ渡すものと `memory/` を変えない）
- API・ダッシュボードの表示

### 2.8 翻訳に LLM を使わない

文と名前は設定の辞書を引くだけで決まる（決定論的）。LLM が止まっていても、同じ入力からは同じ本文になる。

## 3. Consequences

### 良くなること

- 所有者が Slack の通知をそのまま読め、次に何を確かめるかが本文で分かる
- 最後の行の ID でログ・DB・設定と突き合わせられる
- 文を変えるのに設定の変更だけで済む

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| 先頭の行に ID が無くなり、Slack の検索で ID を探しにくい | 最後の行に ID がある（本文の検索で掛かる） |
| 新しいルールを足すとき 4 つの文を書かないと起動しない | 起動時の検査で落ちる（2.3）。試験で全ルールに文があることを確かめる |
| 既定の設定ではダッシュボードの URL が通知から消える | `COLDAISLE_DASHBOARD_URL` を設定すれば出る（docs/notifications.md） |
| 値の行から `detail` の文が消える | `detail` は DB に残り、ダッシュボード・説明で読める。出来事のルールでは本文に出す |

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| `<名前>（<メトリクス>）— 発生` の形（この記録の最初の案） | 所有者が Slack で確かめ、名前の重なりと読みにくさで差し戻した |
| ID を先頭の行に残す | 所有者は最後の行を選んだ |
| 文をコードの辞書に置く | ルール 9（定数を設定へ）。所有者が文を直すたびにコードの変更が要る |
| 文・hint を任意にし、無ければ ID | 書き漏らしが英語の通知・手掛かりの無い通知として静かに通る |
| メトリクスの括弧を、名前が文に含まれるかの文字列の一致で決める | 表記の揺れ（「GPU吸気」と「GPU の吸気」）で誤る。定義で決める（2.1） |
| 値の行に空気のセンサーをすべて並べる | 長くて読めない（所有者が実際の Slack で確認） |
| 値の行に出すメトリクスをルールごとに設定へ書く | 手書きの一覧が増え、ルールの定義と食い違いうる |
| `config/metrics.yaml` の `unit` を `°C` に変える | API の `unit` が変わる。表示の側で写せば足りる |
| URL を出すかを別の設定の項目で決める | 既定のループバックは誰にも開けないので、項目を足すより出さないほうが単純 |
| LLM に文を作らせる | 所有者が否定。通知は LLM が止まっても届く必要がある |

## 5. 未決事項・仕様に無かった判断

1. **`hint` を必須にした**（2.3）。推奨であり、所有者の判断を待つ
2. **値の行の先頭の書き方をルールの型で決めた**（2.4）。flag は値を出さず、出来事は `detail` を出す
3. **URL の判定をループバックのホストで行った**（2.2）。環境変数を設定していても値がループバックなら出ない
4. **`detail` の文は変えていない**（2.5）。中のメトリクスの ID を日本語へ写すかは別に決める
5. **ダッシュボード・API のアラート一覧の表示**は変えていない。日本語にするなら別の Issue
6. 2.3 の文と hint の文言は Claude の案。所有者が直してよい
7. **`GPU_FAN_*` の値の行に GPU コアの温度が出ないことがある**。デーモンの現在値は取り込みのサンプルだけで、
   GPU の値は DB の最新値にある（Fan の値は発火の先頭に出る）。載せるなら現在値の出どころを足す別の判断になる
8. **値の行の派生値は通知のために計算する**（保存しない。0002 §2.2 のまま）。材料のどちらかが ok でなければ `—`
9. **変化率の値は丸めた後で表示する**（`1 分で +5.2 °C`）。発火の判定はルールエンジンの丸める前の値で行う
