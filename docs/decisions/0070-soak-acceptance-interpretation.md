## 1. Context

`coldaisle-soak-report`（#47）は24時間連続運転の DB を集計し、受入基準の合否を出す。
受入基準は「欠測率 1%未満（NFR-02）」「意図しない再起動が0回」とだけ書いており、
次の3点は**仕様に無い**。集計の実装はこれらを決めないと書けないため、ここで決める。

1. 欠測率を**何の単位で**判定するか（チャネルごとか、全体の合算か）
2. 欠測率の**母数**を何にするか
3. 「意図しない再起動」を DB からどう数えるか

既存の欠測率は別の定義で出している。`/api/v1/health` の `missing_ratio_1h` は、
直近1時間の1分ロールアップについて全メトリクスの `SUM(ok_value_count)` /
`SUM(COALESCE(expected_count, row_count))` を取った**合算値**である。

## 2. Decision

### 2.1 欠測率は「最も悪いチャネル」で判定する

周期的に届くデバイスのチャネル（決定記録 0008 §2.1.2）ごとに欠測率を出し、
**そのうち最大のもの**が閾値（`config/soak.yaml` の `missing_ratio_below`）未満なら合格とする。

- 合算すると、1本だけ死んだプローブが他のチャネルに薄まって見えなくなる。
  NFR-02 の最も厳しい読み方を採る
- **health API の `missing_ratio_1h`（合算値）とは別物である。** 同じ期間でも値は食い違う。
  レポートにはチャネル別の表を必ず載せ、どのチャネルで判定したかを備考に書く

### 2.2 母数は「期間の長さ ÷ 送信周期」。周期が分からなければ判定不能

- 分子は 0002 §2.8 と同じ（`ok` かつ値を持つ行の数。`suspect` も欠測に入る）
- 母数は `(end_ms - start_ms) // interval_ms`。`interval_ms` は起動バナー（`devices`）の値
- **0002 §2.8 との違い**: ロールアップはバケットごとに当時の期待値を積み、周期が不明なときは
  `row_count` を母数とする**下限値**を出す。soak は合否を出すための集計なので、
  下限値で合格を出さない。**周期が不明なら判定不能**にする
  - 行の数を母数にすると、装置ごと沈黙していた時間が欠測に数えられない
- `devices` は起動バナーのたびに上書きされ、過去の周期が残らない。
  そのため周期を申告したバナーの受信時刻をレポート（Markdown / JSON）に出し、
  **バナーが期間の終わり以降なら判定不能**にする（期間中の周期とは限らないため）
- 24時間 soak の間は送信周期を変えない前提とする。期間中に周期が変わった場合は正しく扱えない

### 2.3 デバイス再起動はすべて「意図しない」ものとみなす

DB（`sys.device_restarts`）には意図した再起動かどうかの記録が無い。
期間内の件数を全部数え、閾値（`max_device_restarts`、既定0回）以下なら合格とする。
意図した再起動があった場合は、人がレポートを読んで判断する（備考にその旨を出す）。

- 閾値を超えた件数は、周期データが無い期間でも**不合格**とする（再起動したまま送信が
  戻らなかった場合など。超過は件数だけで確定する）
- 閾値以下（既定では0件）で合格とするには、期間内に周期データがあることを要する。
  周期データが無ければ期間を観測できていたか分からないため**判定不能**とする
- 期間が終わっていなければ、件数によらず判定不能とする

### 2.4 集計は DB を書き換えない

集計は `SqliteStore` ではなく `mode=ro` の読み取り専用接続で開き、
マイグレーションも WAL への切り替えもしない。スキーマの版がコードと合わなければ開かずに落とす。

## 3. Consequences

- 良い: 1チャネルの故障を見逃さない。周期不明や期間外の周期で誤って「合格」と書かない
- 悪い: health API の欠測率とレポートの欠測率が食い違う。
  緩和: レポートに判定の単位と母数を明記し、チャネル別の表を出す
- 悪い: soak の後にファームウェアを更新して起動バナーが届くと、過去の期間は判定不能になる。
  緩和: soak の直後に集計する。`issues/15` の手順に従い期間の終わりに走らせる

## 4. 却下した代替案

- **全チャネルの合算で判定する**（health API と同じ）: 1本のプローブの故障が薄まる
- **ロールアップの `expected_count` を母数にする**: `suspect` の件数がロールアップに残らず、
  期間の端が分の途中だと切り揃えられない。バケットが無い（装置ごと沈黙した）時間は期待値も無い
- **周期不明なら `row_count` を母数にする**（0002 §2.8 の下限値）: 合否に下限値を使うと
  沈黙した時間が欠測に入らず、甘い側に倒れる

## 5. 未決事項

- seq 欠損・queue drops・`suspect` 件数は件数を出すだけで、閾値を持たない。閾値を設けるかは人が決める
- 意図した再起動を区別する記録経路（手動の注記など）を作るかは #47 の対象外
