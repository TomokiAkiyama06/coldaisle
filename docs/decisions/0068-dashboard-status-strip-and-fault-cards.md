## 1. Context

所有者がレビューしたデザインキャンバス「coldaisle UI案 (#48 #60 #106)」の
`Main`（通常）と `Dashboard-Fault`（`sensor_fail` ＋デーモン停止）のうち、
#134 は表示名・派生値の式・アラート表を反映した（決定記録 0039）。
キャンバスの注記が「確認したい点」として挙げている次の3つは、まだ反映していない。

1. 先頭に**状態の帯**を足す
2. 異常時、古い値は**取り消し線**（「古い」バッジは出さない）
3. 欠測は**斜線＋赤枠**

Issue #48 の受入基準の残りは、異常表示を人間が目視で確認すること。
確認できる見た目が、レビューしたキャンバスと違っていると、確認そのものが成り立たない。

0039 §2.3 は `stale` を「赤い左辺と値を薄くする」と書いており、2. は**その記述を変える**。
`missing` の左辺の色は 0011 §2.4 の記述（灰）を変える。どちらも FINAL の記録が
対象なので、書き換えずにここで置き換える。

## 2. Decision

### 2.1 状態の帯は `GET /api/v1/server-health` の `signal` / `summary` / `active_alerts` から描く

画面の先頭（赤帯の下、現在値の上）に、次の3つを1行で出す。

| 部分 | 出どころ |
|---|---|
| 信号（`GREEN` / `YELLOW` / `RED`。色と文字の両方） | `signal` |
| 一文の説明 | `summary`（`textContent` で。HTML として解釈しない） |
| 発生中のアラートの数（と、そのうち重大の数） | `active_alerts` の件数と `severity` |

**信号の規則を JS に持たない。** 規則は API 契約 §3 と決定記録 0040 / 0042 にあり、
ここで作り直すと2か所が食い違う。帯は、サーバが決めた `signal` をそのまま描く。

**取れていないときに `GREEN` を出さない。**

- まだ一度も取れていない → 帯を出さない（何も言わないのではなく、赤帯・カードが先に状態を言う）
- 直近の取得が失敗している → 前回の値は使わず、「状態不明」と出す（灰色）
- `signal` が未知の値 → 同じく「状態不明」

表示専用。読むのは GET だけで、書き込みの経路は増やさない（0011 §2.2）。

### 2.2 `stale` のカードは取り消し線を足す

0039 §2.3 の見た目（赤い左辺・薄い値）に、**値に取り消し線**を足す。単位には引かない。
文言のバッジは引き続き出さない（文言は画面全体の赤帯が担う。0039 §2.3）。

### 2.3 `missing` のカードは赤枠＋斜線にする

値の無いカードを、赤い枠（2px）と斜線の背景にする。バッジ「欠測」は残す。
灰色の左辺は、`stale` の赤との違いが小さく、欠測が目立たなかった。
**斜線は色に頼らない手がかり**である（色覚特性・印刷。0011 §2.4 と同じ考え方）。

## 3. Consequences

- **帯の色は `signal` のまま。** 周期メトリクスが `stale` になったとき、`signal` は
  `YELLOW` になる（`quality != ok`。0042）。取り込み元が止まっていれば `RED`。
  キャンバスは `stale` を `RED` で描いているが、JS で上書きしない。
  古さを大きく言うのは、引き続き赤帯（0011 §2.5）
- 定期更新のエンドポイントが4つから5つになる。`/api/v1/server-health` が失敗すると、
  ほかと同じく赤帯に「API に接続できません: /api/v1/server-health: …」が出る
- 帯の文言はサーバの `summary`（AI 要約か、決定論のテンプレート）。
  キャンバスの「室温 26.4℃、GPU吸気 28.3℃。異常なし」のように、
  値から文を JS で組み立てることはしない

## 4. 却下した代替案

| 案 | 却下の理由 |
|---|---|
| `/health` と `/alerts` から JS で信号を組み立てる | 信号の規則が API とダッシュボードの2か所になる。片方だけ直って食い違う |
| 現在の値から「異常なし」のような文を JS で作る | 何が異常かの判断を持ち込む。`summary` が同じ役目を決定論で果たしている |
| 帯に `gpu_mode` を出す（キャンバスにある） | 現在のモードを返す読み取りが無い。`/events` は期間内の切り替えの記録で、期間内に切り替えが無いと分からない |
| `stale` を取り消し線にせず 0039 のままにする | 却下ではなく、所有者がキャンバスで示した見た目。目視確認の対象と合わせる |

## 5. 未決事項

- **含めていないキャンバスの要素**（0011 の「作り込まない」に従い、所有者の判断を待つ）:
  2本目の帯（`SENSOR_FAULT` の一文）、履歴グラフの「受信なし」「欠測」の帯、
  現在値の見出しの「最後に受け取った値（時刻）」
- 帯に `gpu_mode` を出すかどうか。出すなら、現在のモードを返す読み取りの形が要る（Issue で相談）
- `active_alerts` はサーバ側の上限（`active_alerts_limit`、現在 100）まで。超えたときの数は
  下回る。実運用で届く数ではないため、表示では扱っていない
