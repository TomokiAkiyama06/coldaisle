## 1. Context

ダッシュボードの赤帯（API の失敗・データなし・未来の時刻・古い）と定期更新の
部分的な失敗は、条件の組み合わせで壊れた。文字列の検査ではそれを確かめられないため、
`app.js` を Node 上で実際に動かして描画結果を確かめるテストを足した
（赤帯の全16通り、「/alerts が失敗しても /health を使う」、構文検査）。

ところが CI には Node が無く、これらは**CI では飛ばされていた。**
飛ばされたテストは、壊れても誰も気づかない。

---

## 2. Decision

### 2.1 CI の `check` ジョブに Node（LTS のメジャー版で固定）を入れる

`actions/setup-node@v7` で `node-version: "24"`（2026-09 時点の Active LTS）を
pytest の前に入れる。LTS の更新はこの記録と `ci.yml` を同時に変える。

### 2.2 **Node はテストで JS を実行するためだけに使う**

- `package.json`・npm の依存・ビルド・バンドラ・トランスパイルは入れない
- テストは標準モジュール（`vm` / `fs`）だけで `app.js` を読み、最小のスタブ DOM で動かす
- ダッシュボードは引き続き依存の無い静的アセット（0011 §2.1）

0011 の「作り込まない」は**画面と配信の側**の制約であり、実行時の依存は増えない。
0011 §4 が却下した「ブラウザ自動テスト」（ヘッドレスブラウザ等）も入れない。

### 2.3 CI では Node が無ければ**失敗**させる

`tests/test_dashboard.py` の `_require_node()` は、`CI` 環境変数があるとき
Node が見つからなければ失敗させる（GitHub Actions は `CI=true` を設定する）。
手元では従来どおり飛ばす。**CI で黙って飛ばすのが、防ぎたい壊れ方そのもの**だから。

---

## 3. Consequences

### 良くなること

- 画面の振る舞い（条件の組み合わせ・部分的な失敗）が CI で毎回検査される
- 設定の漏れ（setup-node を外す等）が「飛ばされた」ではなく「失敗」として見える

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| CI の手順と所要時間が少し増える | setup-node は数秒。npm の依存は入れない |
| Node の LTS 更新の手間 | メジャー版だけ固定。更新時はこの記録と `ci.yml` を同時に変える |
| 手元に Node が無いと振る舞いのテストが飛ぶ | CI が必ず走らせる（2.3） |

---

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| 飛ばしたままにする | 壊れても気づけない。今回の PR で実際に組み合わせの不具合が続いた |
| Python で同じ判定を書き直して検査する | 検査しているのが JS ではなく写しになる |
| ヘッドレスブラウザ（Playwright 等）を入れる | 0011 §4 で却下済み。依存と CI の重さが釣り合わない |
| `nodejs-wheel` などを Python の開発依存に入れる | 全員の `uv sync` に数十 MB の Node が入る。必要なのは CI と、望む人の手元だけ |
