## 1. Context

配線位置だけでセンサーを同定していると、**ケース内で差し替えたときに
較正のオフセットもラベルも静かに間違ったまま運用が続く**（spec-review W-03）。

ROM の保存と `PROBE_CHANGED` は既に動いている（#8 / #18）。
残っていたのは「**人がどう気づき、どう確かめるか**」の側である。

---

## 2. Decision

### 2.1 記録された構成を **API で出す**

`GET /api/v1/devices` が、チャネル・メトリクス・種別・GPIO・ROM を返す。

**「どの物理プローブがどのメトリクスか」が分からなければ、ROM に意味が無い。**
`28FFFFFFFFFFFF05` という文字列だけを見せられても、現物のどれか分からない。

返すのは**記録された構成**であって、いま繋がっている構成ではない。
この2つが食い違っている状態が `PROBE_CHANGED` であり、
**記録の側は人が較正をやり直すまで動かない**（0012 §2.6）。

起動バナーを受け取る前は空で返す。**推測で埋めない。**

### 2.2 ダッシュボードに並べ、**食い違う行に印を付ける**

アラート欄に `PROBE_CHANGED` が出るだけでは、**どのプローブか分からない。**

ROM は等幅で並べる。**目で現物と突き合わせるための表示**だからである。

### 2.3 印は**文面にチャネル名が含まれるか**で決める

`PROBE_CHANGED` の `detail` は人が読む文である
（`較正が対応していないプローブ: rear_exhaust`）。

**文を単語に割って解釈しない。** 区切り文字や語順を変えられると、
黙って印が付かなくなる。チャネル名（`rear_exhaust`）は十分に特徴的なので、
**含まれるかどうかだけを見る。**

代わりに、**`detail` にチャネル名がそのまま入ることを試験で固定した**
（ルールエンジン側）。言い回しを変えるのは構わないが、名前を加工したら落ちる。

### 2.4 **ラベルと ROM の二重の同定**

`docs/calibration.md` の手順0（較正より前）にした。

- ラベルは**剥がれる**
- ROM は**読めるが、現物のどれか分からない**

どちらか一方では足りない。ラベルには番号ではなく**役割**を書く
（`front_intake` など）。番号だと、対応表を別に持つことになる。

---

## 3. Consequences

### 良くなること

- 差し替えたときに、**どのプローブかが画面で分かる**（2.2）
- ROM と現物の突き合わせができる（2.4）
- Workspace 側も同じ情報を取れる（2.1）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| API が1つ増える（契約の変更） | 追加のみ。`docs/api-contract.md` に記載した。**Workspace 側の Issue は人が起票する** |
| UI が `detail` の文面に依存する | チャネル名がそのまま入ることを試験で固定（2.3） |
| 記録された構成といまの構成が違いうる | **それが `PROBE_CHANGED` の意味**。画面にもそう書いた（2.1） |

---

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| ROM だけを一覧に出す | 現物のどれか分からない。メトリクスとの対応が要る（2.1） |
| いま繋がっている構成を返す | 記録の側が「較正が対応している構成」である（0012 §2.6） |
| `detail` を単語に割って解釈する | 区切りや語順を変えると黙って壊れる（2.3） |
| `PROBE_CHANGED` の対象チャネルを構造化して返す | アラートの型が1ルールのために広がる。文面の試験で足りる |
| ラベルに番号（#1〜#5）を書く | 対応表を別に持つことになる。役割を直接書く（2.4） |
