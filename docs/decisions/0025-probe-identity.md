## 1. Context

配線位置だけでセンサーを同定していると、**ケース内で差し替えたときに
較正のオフセットもラベルも静かに間違ったまま運用が続く**（spec-review W-03）。

ROM の保存と `PROBE_CHANGED` は既に動いている（#8 / #18）。
残っていたのは「**人がどう気づき、どう確かめるか**」の側である。

---

## 2. Decision

### 2.1 記録された構成を **API で出す**

`GET /api/v1/devices` が、チャネル・メトリクス・種別・GPIO・ROM を返す。

**「どの物理プローブがどのメトリクスか」が分からなければ、ROM に意味が無い。**
`28FFFFFFFFFFFF05` という文字列だけを見せられても、現物のどれか分からない。

返すのは**記録された構成**であって、いま繋がっている構成ではない。
この2つが食い違っている状態が `PROBE_CHANGED` であり、
**記録の側は人が較正をやり直すまで動かない**（0012 §2.6）。

起動バナーを受け取る前は空で返す。**推測で埋めない。**

### 2.2 ダッシュボードに並べ、**食い違う行に印を付ける**

アラート欄に `PROBE_CHANGED` が出るだけでは、**どのプローブか分からない。**

ROM は等幅で並べる。**目で現物と突き合わせるための表示**だからである。

### 2.3 **いま繋がっている ROM を残す**

食い違っているあいだ、観測した ROM を `sys.observed_probes`
（`system_state`）に置く。

記録の側は人が直すまで動かない（0012 §2.6）。**これが無いと、人は
「何に差し替わったのか」を知る手段が無い。** 画面に「記録された ROM」と
「いまの ROM」を並べて出せる。

### 2.4 印は**アラートの文面から読み取らない**

`sensor.changed`（API がその場のデータから出す）で決める。

文面から読み取ると2つ壊れる。

1. `Engine.on_hello` は**発火中なら何も返さない**ので、`detail` は最初の
   不一致のまま。あとから別のチャネルがずれても**印が動かない**
2. アラート一覧には上限がある。長く発火し続けた `PROBE_CHANGED` は、
   新しいアラートに押し出されて**一覧から落ちる**

どちらも「印が黙って消える」形の壊れ方で、**気づけない。**

### 2.5 差し替えの受け入れは**較正と一緒にしか行わない**

記録された ROM が意味するのは「**いまのオフセットが対応している個体**」である。

較正し直さずに ROM だけ受け入れると、古いオフセットが新しいプローブに
対応していることになり、**`PROBE_CHANGED` が黙るだけで実害は残る。**

`coldaisle-calibrate --apply` が、較正値の書き込みと一緒に受け入れる。
**受け入れる手段が無いと、`PROBE_CHANGED` は永久に解けない**（記録の側は
人が直すまで動かない設計なので、「人が直す」経路が要る）。

### 2.6 **ラベルと ROM の二重の同定**

`docs/calibration.md` の手順0（較正より前）にした。

- ラベルは**剥がれる**
- ROM は**読めるが、現物のどれか分からない**

どちらか一方では足りない。ラベルには番号ではなく**役割**を書く
（`front_intake` など）。番号だと、対応表を別に持つことになる。

---

## 3. Consequences

### 良くなること

- 差し替えたときに、**どのプローブかが画面で分かる**（2.2）
- ROM と現物の突き合わせができる（2.6）
- Workspace 側も同じ情報を取れる（2.1）
- **差し替えたあと、`PROBE_CHANGED` が解ける道がある**（2.5）
- 何に差し替わったのかが分かる（2.3）

### 悪くなること・その緩和

| トレードオフ | 緩和策 |
|---|---|
| API が1つ増える（契約の変更） | 追加のみ。`docs/api-contract.md` に記載した。**Workspace 側の Issue は人が起票する** |
| `system_state` にキーが1つ増える | 変化時だけ書く（0002 §2.6）。食い違いが解けたら空にする |
| 記録された構成といまの構成が違いうる | **それが `PROBE_CHANGED` の意味**。画面にもそう書いた（2.1） |

---

## 4. 却下した代替案

| 案 | 却下理由 |
|---|---|
| ROM だけを一覧に出す | 現物のどれか分からない。メトリクスとの対応が要る（2.1） |
| いま繋がっている構成を返す | 記録の側が「較正が対応している構成」である（0012 §2.6） |
| アラートの文面から印を決める | 文面が更新されない・一覧から落ちる。**黙って印が消える**（2.4） |
| ROM だけを受け入れる手段を作る | 古いオフセットが新しいプローブに対応する。アラートが黙るだけ（2.5） |
| 差し替えを自動で受け入れる | **静かに間違ったまま運用が続く**のを防ぐ仕組みが、静かに消える |
| 観測した ROM を残さない | 何に差し替わったのかを知る手段が無い（2.3） |
| `PROBE_CHANGED` の対象チャネルを構造化して返す | アラートの型が1ルールのために広がる。文面の試験で足りる |
| ラベルに番号（#1〜#5）を書く | 対応表を別に持つことになる。役割を直接書く（2.6） |
