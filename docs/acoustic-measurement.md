# 騒音の概算測定の手順

#94 の Acoustic Cost Model の曲線に、仮置きより少しましな根拠を与えるための手順（#95）。
方針の正本は [決定記録 0067](decisions/0067-acoustic-measurement-study.md)（**Proposed**）。

> **精度は概算でよい。** 目的は Zone 間・Demand 間の相対的な大小と、曲線の形をつかむこと。
> ここで作った曲線は `source.kind: approximate` のままにする（0067 §2.2）。
> 数値の目安はすべて暫定値。

## 1. 用意するもの

- 手持ちの騒音計、またはスマートフォンの騒音計アプリ（A 特性の dBA 表示があるもの）
- 毎回同じ位置に置くための目印（テープなど）
- 記録用の表（§4）

録音はしない（0067 §2.5）。

## 2. 条件

- **位置**: 普段座る位置の耳の高さ。毎回同じ場所・同じ向きに置く
- **負荷**: CPU / GPU は idle。GPU 本体の Fan とコイル鳴きが混ざらないようにする
- **背景**: 最初にサーバーの電源を切った状態の読みを取る。Fan の読みが背景より
  あまり大きくない（目安 5 dB 未満）ときは「背景に埋もれた」と印を付ける
- 空調など止められる音は止める。止められないものはメモに残す
- AIO Pump と GPU の Fan は coldaisle の制御外。変わったと気づいたらメモする

## 3. 手順

Fan は `coldaisle-fand` の `CALIBRATION` モードで動かす。PWM を直接書かない（0067 §2.4）。
Critical Safety と Reactive Guard の floor は外れないので、Top は CPU cooling floor 未満にならない。

1. 背景を読む（電源 OFF）
2. **Zone ごとの sweep**: 他の 2 Zone を低めの基準 Demand に固定し、1 Zone だけを
   0.0 / 0.25 / 0.5 / 0.75 / 1.0 で動かす
3. 各点で、回転数が落ち着くまで待ってから（目安 20 秒）、10 秒ほど見て**だいたいの dBA** を読む
4. 同時に耳で聞き、次が気になるかを印で付ける
   - 純音（キーンという鳴き）
   - うなり（ワンワンという周期的な揺れ）
   - 低いこもり
5. 最後に 3 Zone を一緒に 0.5 / 1.0 にした点も読み、Zone ごとの曲線から大きく外れていないか見る
6. **別の日（または時間帯）にもう一度**同じ手順を回す

Guard / Safety の介入で Demand が持ち上がった点は、その Demand の値として使わない。
decision trace の effective の値を見て確認する。

## 4. 記録の形

1 点 1 行。コミットするのは、この表と曲線だけ（機材の個体識別子・部屋の情報は書かない）。

| 列 | 例 | 内容 |
|---|---|---|
| `date` | 2026-10-01 | 測定日 |
| `instrument` | phone-app | 機材の種類（`phone-app` / `meter`）。型番やシリアルは書かない |
| `zone` | front | sweep した Zone（3 Zone 同時は `all`） |
| `effective_demand` | 0.5 | trace の effective |
| `rpm` | 1200 | その Zone の実測 RPM（目安） |
| `dba` | 38 | 読んだ値（整数でよい） |
| `background_dba` | 30 | その日の背景 |
| `tonal` / `beat` / `rumble` | true / false / false | 耳の印 |
| `note` | 空調 ON | 気づいたこと |

## 5. 曲線への写し方

- Zone ごとに、Demand に対する dBA の並びから**曲線の形**（どこから急に上がるか）を取る
- 印（純音・うなり・こもり）が付いた点は、同じくらいの dBA の点より `acoustic_cost` を少し上げる
- `acoustic_cost` は無単位のまま。dBA の読みをそのまま値にしない
- 写し方の具体（最小の読みを 0、最大を 1 にするなど）は、最初の結果を見て `acoustic.yaml` の PR で決める（0067 §5）
- `source.basis` には「概算 study（機材の種類・日付）」を書く

## 6. 確認

- **繰り返し**: 2 回の読みの差が大きい（目安 3 dB 以上）点は、位置か背景を確認して測り直す
- **dBA と耳の食い違い**: dBA では静かな側なのに印が付いた設定を列挙する。
  #95 の「SPL だけの案と周波数情報を使う案の比較」はこの一覧で代える（0067 §2.6）

## 7. もう1つのやり方: 普段の運転中に「うるさいか」を答える（0067 §2.8）

騒音計の代わりに（または併せて）、普段の運転中に感じたことを記録して、不快に感じ始める下限を探す。

1. UI（エアフロー画面など。表示専用）で、いまの各 Zone の Demand と RPM を見る
2. 気になったら / 気にならなかったら、書き込み専用の入口へ答える
   （予定の形: `coldaisle-event noise-feedback loud` / `ok`。実装は別 Issue）
3. 集計では、回答時刻の decision trace から各 Zone の effective Demand と RPM を取り、
   Zone ごとに `loud` が繰り返し付き始める Demand を下限の目安にする
4. CPU / GPU が高負荷のときや GPU 本体の Fan が回っているときの回答は、
   coldaisle が変えられない音の可能性があるので分けて見る

- **答えても Fan は変わらない。** 回答は記録だけで、制御ループは読まない
- 下限は `acoustic.yaml` の曲線の形（下限より上でコストを急に上げる）に使い、
  人が確認する PR で反映する。Fan Demand の上限にはしない（温度が上がればうるさくても回す）

## 8. 測り直す契機

- Fan の交換・追加、ケースの向きや設置場所の変更
- 決定記録 0056 §2.5 の宣言された変更（`DeclaredChange`）と同じ契機で検討する
