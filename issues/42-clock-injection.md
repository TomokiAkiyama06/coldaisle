## 背景

決定 D-05 で「デバイス時刻は信用せず、**ホスト受信時にタイムスタンプを付与する**」と
決めた。この方針自体は変えない。

一方 #6 の時間圧縮（`--speed 60`）は、**待ち時間だけ**を縮める。
値・`up`・`seq` は実時間で流した場合と同一になる。ここまでは意図どおりだが、
副作用としてホスト側の時刻だけが圧縮される。

```text
デバイス:  up が 60秒ぶん進む
ホスト:    ts_ms は 1秒しか進まない
```

## 何が壊れるか

継続時間ベースのルール（FR-401〜409）と `stale` 判定が、**圧縮再生では発火しない。**

| ルール | 条件 | `--speed 60` での挙動 |
|---|---|---|
| `SENSOR_FAULT`（FR-401） | 30秒以上サンプルなし | 実時間0.5秒 → **発火しない** |
| `RECIRCULATION`（FR-404） | 5分継続 | 実時間5秒 → **発火しない** |
| `stale`（要件 §5.3） | 10秒以上更新なし | 同上 |

#6 の `recirculation` シナリオは「閾値超過後5分以上そのまま」になるよう作ってあるが、
圧縮再生するとルールエンジンからは5秒間にしか見えない。
**#18 のテストが、意図した検証にならない。**

## やること

- [ ] `Clock` プロトコル（`now_ms() -> int`）を定義する
- [ ] `WallClock`（本番）と `SimulatedClock`（mock / replay。シナリオ時間から算出）
- [ ] `serial` は `WallClock`、`mock` / `replay` で `--speed` 指定時は `SimulatedClock`
- [ ] ルールエンジンと `stale` 判定も**同じ `Clock` インスタンスを参照する**
- [ ] **合成の起点（composition root）を1箇所にし、そこから同一インスタンスを配る**
- [ ] `clock.py` 以外で現在時刻を作らない（下の一覧を参照）
- [x] **プロセスをまたぐ場合の仮想時刻の共有方法を決める**（下記）
      → **決定済み。圧縮再生はデーモン単体の機能とする**（決定記録 0007 §2.11）

### プロトコルだけでは足りない

`Clock` は**インタフェースしか縛らない。** 取り込みへ `SimulatedClock`、
ルールエンジンへ `WallClock` を渡しても型は通り、`mypy` も通る。
**独立に作った2つの `SimulatedClock` も同様に食い違う**（片方だけが進む）。

型で防げない以上、次の2つで担保する。

1. 合成の起点を1箇所にする。ソース・保存・ルールエンジンへ配るのは
   `source.clock` から取った**同じオブジェクト**にする
2. **同一インスタンスであることをテストで確かめる**（`is` 比較）。
   「同じ値を返すこと」ではなく「同じものであること」を見る

### 現在時刻を作る API の一覧

`clock.py` を**唯一の例外**とし、以下を他所で呼ばない。綴りを2つだけ挙げると、
`time.time_ns()` のような別の綴りで素通りする。

```text
time.time / time.time_ns / time.gmtime / time.localtime / time.clock_gettime
datetime.now / datetime.utcnow / date.today
```

`time.monotonic()` / `time.perf_counter()` は**経過時間の計測**であり、
タイムスタンプを作らないので対象にしない（WAL 切り替えの再試行が使っている）。
別名 import（`import time as t`）と `from time import time` も検出すること。

### プロセスをまたぐ場合（決定済み）

`SimulatedClock` はメモリ上のオブジェクトなので、**プロセスを分けると共有できない。**
運用では取り込みデーモンと API を別プロセスで起動する（AGENTS.md のコマンド）。

| API 側に渡すもの | 起きること |
|---|---|
| `WallClock` | `--speed 60` のサンプルは実時刻より**未来**になる。`data_age_seconds` が負、`stale` が出ない、実時刻の `from` / `to` 範囲に入らない |
| もう1つの `SimulatedClock` | 誰も進めないので**止まったまま** |

**決定（2026-08-25、決定記録 0007 §2.11）: 圧縮再生はデーモン単体の機能とする。**
API から見えなくてよい。仮想時刻を DB 経由で共有する案は、心拍のための表・
毎周期の書き込み・保持期間を v1 へ足すことになるため採らない。

継続時間ベースのルールの検証は、**ルールエンジンをデーモンと同じプロセスに置いて**行う
（#18 の配置制約）。

### 既にある接ぎ目

ゼロからではない。#5 で入れた注入点を `Clock` へ寄せる形になる。

| 場所 | 現状 |
|---|---|
| `SqliteStore(clock=...)` | `Callable[[], int]` を受け取る。既定は `store.db.now_ms` |
| `SqliteStore.latest(at_ms=...)` | `stale` 判定の基準時刻を呼び出し側から渡せる |
| `MockSource` | ホスト時刻を持たない。付与するのは #8 の正規化 |

`Callable[[], int]` のままでも動くが、**時計という概念に名前が付かない。**
ただし名前を付けても、同一インスタンスが配られていることまでは保証されない
（上の「プロトコルだけでは足りない」）。抽象は読みやすさのため、
同一性は合成の起点とテストで担保する。

## 受入基準

> **完了（2026-08-25）**: 抽象と配線は #8 で、発火の検証は #18 で入った。
> 圧縮再生（速度30〜60）で `RECIRCULATION` と `SENSOR_FAULT` が発火することを
> テストで固定している（`tests/test_rules.py`）。実時計で判定していたら
> 一度も鳴らない。プロセスをまたぐ仮想時刻の共有は決定記録 0007 §2.11 で
> 「圧縮再生はデーモン単体の機能」と決めた。

- `--speed 60` で `recirculation` シナリオを流すと `RECIRCULATION` が発火する
- `--speed 60` で `dropout` シナリオを流すと `SENSOR_FAULT` が発火する
- 実時間（`--speed 1`）で流したときと、発火するアラートの集合が一致する
- **取り込み・保存・ルールエンジンが同一の `Clock` インスタンスを持つことを
  テストで確かめる**（型ではなく `is` で）
- 上記「現在時刻を作る API の一覧」の呼び出しが `clock.py` 以外に無いこと
  （テストで機械的に確かめる。別名 import と `from` 形式も含む）
