## 背景
既存の個人自動化基盤（Slack / LINE）へ接続する。

## やること
- [ ] Notifier抽象（`slack` / `line` / `stdout`）
- [ ] 重大度でのルーティング（要件 Q-02 を先に決定すること）
- [ ] 連続通知の抑制（同一アラートは初回とN分ごと、解除時のみ）
- [ ] 夜間の通知ポリシー（criticalのみ、など）
- [ ] 通知本文にダッシュボードへのリンクと該当メトリクスの現在値を含める

## 受入基準
- MockSourceで発火させた通知が実際に届く
- 1つのアラートで通知が連投されない

## 依存
#18

## ★2026-08-23 の決定を反映

- **ルーティング確定**: critical → LINE / warning → Slack（決定記録 D-1）
- **夜間も常時通知**（決定記録 D-2）

### ⚠️ 段階的な有効化が必要

夜間も通知する以上、**誤警報が睡眠を削ります。**
「通知が信用されなくなる」より深刻な実害です。

- [ ] **ベースライン測定（#19）が完了するまでは、夜間通知を critical のみに絞る**
- [ ] 閾値確定後に warning の夜間通知を有効化する
- [ ] この段階的有効化をフラグで切り替えられるようにする

これに伴い、以下の優先度を上げます。

- **#36（GPU Mode 別の閾値）** — 学習中の高温を異常と誤認しないため
- **#19（ベースライン測定）** — 実測に基づく閾値でないと誤警報が出る

### 通知先（確定）

- **Slack**: 監視専用チャンネルを新規作成して使用（既存の朝ブリーフィングとは分ける）
- **LINE**: 専用の宛先を使用

Webhook URL とトークンは `.env` で管理し、**リポジトリには絶対に含めない**。
リポジトリを public にする決定（Q-06）のため、これは必須です。
