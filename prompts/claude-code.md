# Claude Code 向けプロンプト集

クローンして本リポジトリのドキュメントを配置した直後から使えるプロンプトです。
コードブロックをそのままコピーして貼り付けてください。

**使い方の原則**

- **1回のセッションで複数のIssueを進めさせない。** 1 Issue = 1 ブランチ = 1 PR
- 最初に必ず「計画を出させてから」実装させる。いきなり書かせない
- 判断に迷ったら実装させず、質問させる（プロンプトにそう書いてあります）

---

## 0. キックオフ（最初の1回だけ）

リポジトリの状態を把握させ、実装計画を立てさせます。**このセッションではコードを書かせません。**

```text
このリポジトリは GPUサーバーの温湿度監視システム（coldaisle）です。
現時点ではドキュメントと Issue 定義だけがあり、コードは1行もありません。

まず以下を順に読んで、プロジェクトの全体像を把握してください。

1. README.md
2. AGENTS.md            ← あなたへの指示の正本。ここのルールは必ず守ること
3. docs/requirements.md ← 要件定義。特に §4.2 の設計判断 D-01〜D-07
4. docs/spec-review.md  ← ハードウェア仕様のレビュー。C-01〜C-04 は実装に直結する
5. ISSUES.md            ← Issue 一覧と着手順
6. issues/01〜issues/06 ← 最初に着手する範囲

読み終えたら、以下を出力してください。**この段階ではコードを書かないでください。**

A. プロジェクトの理解を10行以内で要約
B. AGENTS.md の「絶対に守るルール」を自分の言葉で列挙
C. issues/01（リポジトリ雛形）の実装計画
   - 作成するファイルとディレクトリの一覧
   - pyproject.toml に入れる依存と設定の方針
   - 判断に迷った点があれば質問として列挙
D. #1 から #6 までの実装順序と、各Issueの想定作業量

要件やIssueに書かれていない仕様を勝手に決めないでください。
不明点は C の質問として挙げ、私の回答を待ってください。
```

## 1. Issue 実装（毎回使うテンプレート）

`{N}` を Issue 番号に置き換えて使います。

```text
issues/{N}-*.md を実装してください。

手順:
1. issues/{N}-*.md を読む
2. その Issue が参照している docs/ の該当箇所を読む
3. 依存する Issue が完了しているか確認する（未完了なら指摘して止まる）
4. 実装計画を出す（ファイル単位で、何を作るか）
5. 私の承認を得てから実装に入る

ブランチ:
  git checkout -b feat/{N}-<短い説明>

完了条件:
  uv run ruff check . && uv run ruff format --check .
  uv run mypy src
  uv run pytest -k "not hardware"
  これらが全て通ること。通らない状態で「完了しました」と言わないこと。

守ること:
- AGENTS.md の「絶対に守るルール」に違反しないこと
- Issue の受入基準を1つずつ満たし、最後に自己チェックの結果を報告すること
- Issue に書かれていない機能を追加しないこと
- 仕様が曖昧なら、推測で決めずに質問すること
```

キックオフの後、この順で進めるのを推奨します。

### セッション1: 足場作り（#1 → #2 → #41）

```text
issues/01-repo-scaffold.md、issues/02-ci-pipeline.md、
issues/41-public-repo-hygiene.md を実装してください。

この3つはコードのロジックを含まない「足場」なのでまとめて構いません。
ただし以下の順で、それぞれコミットを分けてください。

1. #41 を先に — .gitignore と .env.example を最初に置く
   このリポジトリは public にする予定です。
   秘匿情報が一度でも入ると履歴から完全には消せません
2. #1 — uv によるプロジェクト作成、src/coldaisle/ レイアウト、
   ruff / mypy(strict) / pytest の設定
3. #2 — GitHub Actions

重要:
- pytest の markers に "hardware" を登録し、CI では -k "not hardware" で走らせること
- この時点ではまだ実装が無いので、ダミーのテストを1つ置いて CI が緑になることを確認する
- LICENSE は Apache-2.0 で配置（要件 Q-16 で推奨。異論があれば指摘して）

完了したら、実際に uv sync から pytest までを実行して結果を見せてください。
```

### セッション2: スキーマ確定（#3 → #4）

```text
issues/03-adr-metric-naming.md と issues/04-adr-device-json-schema.md を実装してください。

この2つは ADR（設計判断の記録）とスキーマ定義です。
ここで決めたものが以降すべての実装の前提になるので、慎重にやってください。

参照すべき箇所:
- docs/requirements.md §5.1（メトリクス命名規約）
- docs/requirements.md §5.2（デバイス出力 JSON スキーマ v1）
- docs/requirements.md §5.3（品質フラグの判定規則）
- docs/requirements.md D-04（ロング形式を選ぶ理由）
- docs/spec-review.md C-02（85.00°C の扱い）

特に注意:
- readings テーブルはワイド形式ではなくロング形式にすること。
  理由は将来 GPU/CPU/VRM を追加したときにスキーマ変更を避けるため
- 品質フラグに「ちょうど 85.00」を suspect として含めること。
  これは DS18B20 のパワーオンリセット値で、-127.00 と違って
  「ありえそうな値」なので見逃すと危険です
- tests/fixtures/ に正常系・欠測・ブートログ混入・不正JSON のサンプル行を置くこと

出力:
- docs/adr/0001-metric-naming.md
- docs/adr/0002-device-json-schema.md
- schemas/device_v1.schema.json
- tests/fixtures/*.jsonl
```

### セッション3: ★最重要（#5 → #6）

```text
issues/05-core-models-storage.md と issues/06-mock-source.md を実装してください。

このプロジェクトで最も重要な2つです。
理由: MockSource が完成した瞬間に、実機（ESP32もGPUサーバーも）が無い状態で
#8〜#25 のすべてが開発・テストできるようになります。ここがクリティカルパスです。

#5 で作るもの:

- WAL モード有効化
- v_latest ビュー
- 単純なマイグレーション機構
- 品質フラグ判定（-127.00 / ちょうど85.00 / null / stale）

#6 で作るもの:
- Source プロトコル: stream() -> Iterator[RawSample]
- MockSource。シナリオを YAML で定義し、切り替え可能にする

テストの要求:
- 「ちょうど 85.00 が suspect になる」テストを必ず書くこと
```

## 3. レビュー用（Codex に投げる）

実装が一段落したブランチに対して使います。**レビュー役にファイルを編集させないこと。**

```text
このブランチの変更をレビューしてください。ファイルは編集しないでください。
指摘のみを出力してください。

コンテキスト:
- AGENTS.md にプロジェクトのルールがあります
- 対応する Issue は issues/{N}-*.md です

重点的に見てほしい点:
1. AGENTS.md の「絶対に守るルール」に違反していないか
   特に: シリアルポートを開くのが ingest daemon だけになっているか、
   LLM に書き込み・実行権限を与えていないか、
   閾値やピン番号がコードにハードコードされていないか
2. Issue の受入基準を実際に満たしているか（「満たしたと書いてある」ではなく）
3. エラーハンドリング: 取り込みループが1サンプルの失敗で落ちないか
4. テストが「実装をなぞっただけ」になっていないか。
   実際にバグを検出できるテストか
5. 型注釈の抜け、mypy --strict を通すための ignore の乱用

出力形式:
- 重大度（must-fix / should-fix / nit）ごとに分類
- 該当ファイルと行番号
- なぜ問題か、どう直すべきか
```

## 4. 困ったときのプロンプト

### 実装が Issue から逸れてきたとき

```text
一度手を止めてください。

現在の変更内容を要約し、issues/{N}-*.md の受入基準と1項目ずつ突き合わせて、
「満たしている / 満たしていない / Issue に無いのに実装した」の3分類で報告してください。

Issue に無いものを実装していた場合、それが必要な理由を説明してください。
必要なら別 Issue に切り出します。不要なら削除してください。
```

### バグを直すとき（テストが通っただけで満足させない）

```text
このバグを修正してください。ただし以下の順序を守ってください。

1. まず**バグを再現するテスト**を書く。この時点でテストは失敗するはず
2. 失敗することを実際に実行して確認し、出力を見せる
3. 根本原因を特定して説明する（「たぶんここ」ではなく、根拠を示す）
4. 修正する
5. 同じテストが通ることを確認する
6. 既存のテストが全て通ることを確認する

「テストが通ったので直りました」だけでは受け付けません。
2 で本当に失敗したこと、3 の根本原因、5 で同じ条件で通ったことを示してください。

エラーを握りつぶす、テストの期待値を変える、といった修正はしないでください。
```

### 設計判断を求められたとき

```text
その判断は私がします。実装を進める前に、以下を出してください。

- 選択肢を2〜3案
- 各案のトレードオフ（何が良くなり、何が悪くなるか）
- あなたの推奨と、その理由
- この判断が後から変更しやすいか、しにくいか

判断が確定したら docs/decisions/ に決定記録として残します。
```

## 補足: このプロンプト集の使い方

- **キックオフ（0番）は最初の1回だけ。** 以降は 1番のテンプレートを使い回します
- Issue の粒度が大きすぎると感じたら、実装前に分割を相談してください
- **CI が最終的な裁定者です。** 「動きました」を信用せず、必ず ruff / mypy / pytest を通してください
- 並列作業は git worktree で分離します（AGENTS.md 参照）。同一ディレクトリで2つのエージェントを走らせないこと
